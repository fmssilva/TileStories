## 1. The Design Decision About 3 Tables (Why Markers-Only Now)

**Decision for this task: build one concrete factory for the markers table only (`DefaultCategoryStyles.Create()`). Do NOT build a generic 3-table abstraction.**

### Why

The three editor tables use **three different C# classes** with different fields:

| Table | Class | Key fields unique to it |
|---|---|---|
| Category Symbols | `CategoryStyleEntry` | `category` |
| Badge Categories | `BadgeCategoryEntry` | `key`, `label` |
| Outline Levels | `OutlineLevelEntry` | `key`, `label`, `pct`, `line_style`, `ring_width` |

A generic abstraction would need to handle three different data shapes — that means either an interface with `T`, or delegate-based construction. That machinery is only needed by one table today (category), which is the exact definition of **speculative code** (`20-code-quality.md`: "No speculative code. Implement only what the current task actually needs.").

** The three tables also don't seed the same way today: category **auto-seeds on LoadConfig + OnGUI** when empty; badge **auto-seeds on LoadConfig + OnGUI** when empty; outline **only has a manual button** — different behavior, not just different data.

### The Right Pattern: Sibling Factories by Convention

- **Now** (this task): `Assets/Framework/Editor/POIAuthoring/Shared/DefaultCategoryStyles.cs`
- **Future** (badge defaults): `.../shared/DefaultBadgeCategories.cs`
- **Future** (outline defaults): `.../shared/DefaultOutlineLevels.cs`

These follow the same static-factory pattern (`List<T> Create()`) but share nothing by inheritance — they are siblings by folder convention, not by type hierarchy. This is the "simple duplication over fragile generic abstraction* rule appliedcorrectly: the pattern is shared by naming convention; the data is per-table concrete. Adding badge/outline defaults later is trivially adding two sibling files, no existing code changes, no interface to design, no preesure to fit a wrong abstraction.
