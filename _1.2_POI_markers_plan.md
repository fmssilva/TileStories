## 2) Unity concepts primer (read this once, refer back as needed)

Six kinds of things exist in this project. Knowing which is which removes most of the
confusion about "where does this piece of data or code live."

- **C# script (`.cs`)** - a plain text file containing code. Two flavors matter here:
  a `MonoBehaviour` script can be attached to something in a scene and gets Unity's
  lifecycle calls (`Awake`, `Update`, etc.); a plain C# class cannot be attached to
  anything, it's just logic you call directly from code, and it's what the guidelines
  push business logic toward, since it can be tested without a scene.
- **Prefab (`.prefab`)** - a reusable, saved "template" of a GameObject (or a small tree
  of GameObjects) with its components and settings baked in. Think of it as a class you
  instantiate at runtime, but built visually in the Editor instead of in code. The POI
  marker visual (small icon + label) will be a prefab; spawning a POI at runtime means
  instantiating a copy of this prefab at a specific position.
- **ScriptableObject (`.asset`)** - a data container that lives as a file in the
  project, editable in the Inspector like a GameObject's component, but with no scene
  presence and no per-frame behaviour of its own. It's Unity's native way to store
  structured config data as an asset instead of as a runtime-parsed file. This project
  uses it as the *final*, baked form of wall config (Stage 4) - not written by hand,
  generated from JSON by an Editor tool.
- **JSON config file** - plain external text, edited by hand or by a small tool, human-
  readable, easy to diff in git, easy to hand-edit without opening Unity at all. This
  project's *authoring source of truth* for wall/POI data lives here, for exactly that
  reason - it's the format content gets written and reviewed in before Unity ever
  touches it.
- **Assembly Definition file (`.asmdef`)** - not a data or content file at all; it draws
  a hard compiler boundary around a folder of C# scripts, so that (for example) code
  under `Framework/Runtime` physically cannot reference code under `Framework/Editor`.
  Already set up correctly in this project (see the base-AR work summary).
- **Media assets** (`.png`, `.mp3`, `.glb`, `.mp4`, etc.) - the raw content files
  (images, audio, 3D models, video) referenced *by* the data above. A ScriptableObject
  or JSON entry for a POI points at a media asset by reference; it doesn't contain the
  media itself.

The practical takeaway for Stage 1.2: **JSON is what you and any agent read and edit by
hand for now. Prefabs are what gets visually placed and instantiated. ScriptableObjects
don't enter the picture until Stage 4.** Nothing in Stage 1.2 needs a ScriptableObject yet.

## 4) Research findings: how POI placement actually works

### 4.1 What x_norm/y_norm actually is (source: §13)

It is **not** a screen-space or camera-relative coordinate. It's a normalized (0-1)
position on a flat 2D reference of the wall - conceptually the same as clicking a point
on a photograph of the wall and recording "this POI is 40% across, 60% down the
photo." It exists specifically so POIs can be authored *before* any 3D capture data
exists: someone can look at a reference photo of a wall and rough in every POI's
approximate location in minutes, with no Unity, no device, and no site visit required.

This is a real, established technique, not something specific to this project. The
general method - annotate points of interest on an ordinary 2D photograph, then
reproject those annotations onto a 3D reconstruction of the same surface - is used in
cultural-heritage documentation and photogrammetry work, where a ray aligned with the camera's viewpoint and the 2D image coordinates of the annotated feature is cast toward the 3D model, and the point where that ray first meets the model becomes the 3D position of the annotation (PeerJ, "The best of two worlds: reprojecting 2D image annotations onto 3D models", 2024 - see §13). The base-AR-work implementation's existing "fallback to x_norm/y_norm mapping on a synthetic wall plane" was a simplified version of exactly this idea, reasonable for a roughly flat surface like LivingRoom but not one that would have generalized to a curved wall like Chafariz Velho. §4.5 replaces this synthetic-plane approach with something that does generalize - not a future upgrade to plan around, but this plan's own actual design.

**Where x_norm/y_norm fits in the pipeline:** it's the *fast, remote, rough-draft*
layer. It should never be the final source of a shipped POI's position once a wall has
been properly captured - it exists to unblock content writing and layout testing before
that capture happens, and remains as a fallback only for POIs nobody has gotten around
to precisely placing yet.

**How this reconciles with not yet knowing the map's coordinate frame or origin:** it
doesn't need to, and that's the point. x_norm/y_norm are defined purely relative to a
flat 2D reference (a photo of the wall) - they carry no relationship whatsoever to
Immersal's map coordinate system, and can be authored before that map even exists. The
two only get connected once real 3D reference points - calibration anchors (§4.5) -
are captured against the map/mesh once it's available. A calibration anchor is nothing
more than a POI-like entry with a known x_norm/y_norm and a real captured_position,
captured the exact same way (§7's Authoring Tool reads its position the same way it
reads any other POI's). Once a handful of these exist, any other POI's x_norm/y_norm
resolves by interpolating between the nearest two anchors - no separate calibration
step, no new tooling, no plane or cylinder parameters to define by hand. Workflow A
placement (§4.2) doesn't need any of this at all, since it skips x_norm/y_norm
entirely and places directly in map coordinates by eye - it's only the x_norm/y_norm
fallback math that
ever needs to know how "photo space" maps onto "map space."

### 4.2 The two supported Immersal placement workflows

Immersal's own documentation and sample projects define two officially supported ways
to get a precise 3D position for a piece of content anchored to a captured space.
Neither one is "guess and export later" - both were designed for exactly this task.
Sources for every claim in this subsection are listed in §13.

**Before either workflow: the one clarification that matters most.** There are two
completely separate things happening in this project that both involve a "POI marker
prefab," and conflating them is what made the original plan read as contradictory:

```
MECHANISM 1 - Authoring (Edit Mode, done once per POI, by a human, no code involved)
  You manually drag a marker prefab into the Hierarchy while NOT in Play Mode.
  It becomes a normal, persistent GameObject sitting in the scene file.
  You drag it around with the Move tool until it visually sits on the right
  spot on the reference mesh. This object's only job is to let you find a
  number. It is never shown to a visitor and is not what ships.
        |
        v  (a small Editor tool reads this object's position)
  [ captured_position gets written into the wall's JSON config file ]
        |
        v
MECHANISM 2 - Runtime spawn (Play Mode or the built app, every single time it runs)
  WallSession reads the JSON, and for every POI entry, calls Unity's
  Instantiate() *in code* to create a fresh copy of the marker prefab,
  parented under XR Space, positioned at the captured_position read from
  JSON. This is what a visitor actually sees. It does not exist in the
  Hierarchy at all until the app is running.
```

These two mechanisms share the same prefab asset, but the actual GameObjects involved
are never the same object - Mechanism 1's placed objects are a disposable measuring
aid; Mechanism 2 creates the real ones fresh every time, from data. The JSON file is
the only thing connecting them. This is also the direct answer to "can you place
dynamically generated prefabs in the scene" - no, and you don't need to: you're not
placing the dynamic ones at all, you're placing throwaway stand-ins purely to read a
number off them once, in Edit Mode, with nothing running. §8's Parts 2-4 are entirely
Mechanism 1 (Part 1 is a related but distinct rendering-only sanity check - also a
manually placed object, but checking whether it renders, not where it belongs).
`WallSession`/`POIPositionResolver` (§7 Phase A) is entirely Mechanism 2.

**Workflow A - Editor-time placement against the downloaded map mesh (primary method,
no device or site visit needed).** Immersal's own documentation is explicit about this:
to add a mesh for a captured map, you download the .glb file from the dashboard and add it into the scene, specifically so content can be placed more easily and accurately. This project already has exactly that file
(`146267-LivingRoom2-tex.glb`) sitting in `Assets/Apps/LivingRoom/` from the original
capture. One prerequisite worth flagging up front, since it's easy to miss:
Unity does not import .glb files natively - it needs the com.unity.cloud.gltfast package added through the Package Manager first (some Immersal tutorials instead convert the .glb to .fbx via Blender, but installing
glTFast is simpler and keeps the whole workflow inside Unity). This mesh only exists if
a wall's map was captured in Immersal's offline/manual mapping mode -
real-time capture mode never generates a mesh, so it never produces a .glb file at all - worth remembering as a requirement for any future wall's capture session, not just a LivingRoom detail.

Once imported, Immersal's own convention is that AR content is placed under the XR Space GameObject the SDK creates, or under a specific XR Map child if a scene has more than one map - "XR Space" and "XR Map" are Immersal's actual component names, worth using precisely rather than the
generic "AR Space" phrasing used loosely elsewhere in this document. Immersal's own
getting-started guidance confirms the point-cloud/mesh visualization it generates has
its own visibility control: after downloading a map, you select that XR Map's point-cloud visualization object and set its Render Mode, letting it show in the Editor while being excluded (or not) from
the built app. That setting is specific to Immersal's own auto-generated point cloud
object, though - for the custom `.glb` mesh brought in manually for this workflow,
Unity's own built-in `EditorOnly` tag (§8) is the reliable way to get the same effect.
This entire placement pass is genuinely regular Unity scene editing - no Play Mode, no
device, no localization needed for it. §8 gives the exact click-by-click procedure,
including the glTFast import step.

**Workflow B - Live on-device placement (secondary, for calibration/hard cases only).**
Immersal ships an official sample built around exactly this idea, the Content
Placement Sample: a self-contained prefab, built around a ContentStorageManager component, that handles placing and storing AR objects directly in the scene while the app is running - though the stock sample only supports placing repeated copies of a single object type. That's useful as a proof of the underlying mechanism (walk to
the real wall, drop a marker exactly where you're standing/pointing, the pose gets
resolved and stored in the live-tracked coordinate frame), but it isn't something to
adopt unmodified here, since this project's POI schema carries far more per-POI data
than one repeated object type. The Workflow B step described in Phase C below is a
small custom version
of the same underlying idea, built for this project's own JSON schema rather than
reusing Immersal's sample verbatim.

**Which to use when:** Workflow A is faster (no travel, no build-deploy cycle, work
from a desk) and precise enough whenever the downloaded mesh is detailed enough to
visually identify each POI's location. Use it for the bulk of placement work. Reserve
Workflow B for the small number of POIs where the mesh texture is too low-resolution or
ambiguous to place confidently by eye, or as a final on-site sanity check comparing
what Workflow A produced against the real wall. This directly answers the original
ambiguity in v1 of this plan ("capture real positions in-scene while localized" was
conflating the two workflows into one sentence).

### 4.3 Why captured_position should be a simple local transform, not computed math

A consequence of Workflow A that simplifies the runtime code: since a POI marker
authored in Workflow A is placed as a **child object under the same XR Space (or XR
Map) object** the point cloud and camera tracking use, its `localPosition` *is* the
captured_position - and once that same XR Space object gets correctly positioned at
runtime by Immersal's localization, Unity's transform hierarchy moves every child
(every spawned POI) with it automatically, for free. No wall-pose math is needed for
the captured_position branch at all. This narrows what `POIPositionResolver` actually
needs to decide: it only needs real logic for the x_norm/y_norm fallback branch
(projecting a normalized 2D point onto some representation of the wall's surface) - the
captured_position branch is just "instantiate under this parent, set localPosition."
This is a cleaner API than the original plan's "wall pose + POI data + optional
calibration context" description, and it's worth updating the resolver signature to
reflect it directly.

**One real bug in that original design, worth catching now rather than later:** v1
checked "is captured_position present and *non-zero*" as its signal for "has this been
captured yet." That's wrong on its own terms - a POI genuinely captured exactly at the
XR Space's local origin (0,0,0) is a real, legal position, not an edge case someone
would deliberately avoid, and this check would silently treat it as "not yet captured"
and fall through to the x_norm/y_norm approximation instead, with no error and no log
line to notice by. This is the same category of bug as the original captured_position
overlap issue (base-AR-work §7.4) - using a plausible real value as a stand-in for
"unset" instead of representing "unset" explicitly. The fix: make `captured_position`
an **optional/nullable field in the JSON schema** - omitted entirely when not yet
captured, rather than defaulted to `[0,0,0]` - and have the resolver check *presence*,
not magnitude. In C# this is a nullable struct or a small wrapper with a `HasValue`
flag; in the JSON itself it's just: the key doesn't exist yet for that POI. §7 Phase B
carries this into the schema; §7 Phase E's tests lock in the corrected behavior
explicitly, including a test for a POI captured exactly at the origin.

### 4.4 JSON -> ScriptableObject roadmap, confirmed correct (sources: §13)

Current practice for Unity data-driven projects backs the pipeline this project already
committed to: the highest-leverage pattern for a growing Unity project is combining ScriptableObjects with an external, human-editable format like JSON as part of a single end-to-end content pipeline, rather than picking one exclusively, and JSON is the better fit specifically for external interfaces, config authoring, and content that benefits from human readability and easy diffing, while ScriptableObjects are the better fit for the runtime-facing, performance-sensitive form of that same data. That is exactly the split already planned for Stage 1.2 (author in JSON) versus Stage 4 (bake to ScriptableObject, runtime reads only the baked
asset) - confirmed as the right call, not something to reconsider.

### 4.5 Non-flat and ring-shaped walls: the project's own established answer (sources: §13)

**Correction from the previous version of this plan.** A closer re-read of the global
work plan turned up that this exact problem is already solved there, and solved more
simply than the strategy-pattern (`IFallbackProjector`/geometry-per-shape-type)
approach this document previously proposed. What follows replaces that approach
entirely, not just extends it.

**The important thing to separate first: this is only a problem for the x_norm/y_norm
remote-authoring fallback, not for final placement.** Workflow A (§4.2) already handles
any wall shape correctly with zero extra work, because a person dragging a marker onto
the real captured mesh in the Editor is just looking at the actual geometry, whatever
shape it is - flat, U-shaped, circular, doesn't matter, the human eye and the Move tool
don't care.

**The established design: piecewise linear interpolation between calibration
anchors, not a shape-classified formula.** The global work plan's own
`POIPositionResolver.cs` specification converts x_norm/y_norm into a 3D position "using
piecewise linear interpolation between calibration anchors" - not by classifying a wall
as flat-vs-cylindrical and applying different trigonometry per type. Concretely:
place a small number of calibration anchors - captured exactly like any other POI,
using the same Workflow A/B tooling this plan already builds, nothing new to
construct - at meaningful reference points along the wall (at minimum one at each end
for a simple flat wall; **one at each panel join** for the Panorama's U-shape; several
points around the arc for Chafariz's circle, not just two at the far ends). A POI's
x_norm/y_norm is then resolved by interpolating *within the straight segment between
the two nearest calibration anchors*, never across a bend - which is exactly why panel
joins and arc points matter as anchor locations: a naive two-point interpolation across
a curved or multi-panel wall would place interpolated POIs inside the wall or floating
in front of it wherever the surface actually bends, since it would be treating a curved
path as a straight line between its endpoints.

**Why this is better than the shape-strategy approach, not just simpler:** one
algorithm handles every wall shape uniformly - flat, U-shaped, circular, or an
irregular shape that isn't a clean mathematical primitive at all - because what varies
between walls is purely *how many calibration anchors and where*, which is data, not
code. Framework code never needs a new class when a new wall's geometry doesn't match
an existing category, because there are no categories - this is a stronger instance of
"config as data, not code" than a `surface_type` field with per-type strategy classes
would have been. It also degrades gracefully for a wall shape nobody anticipated,
where a strategy pattern would need a developer to notice the mismatch and write a new
class first.

**Scope for Stage 1.2/LivingRoom specifically: probably minimal or none.** The
interpolation fallback's entire purpose, per the global plan's own reasoning, is
letting content get authored *before* a site visit happens - "content drafting can
happen away from the physical wall... without blocking on a site visit for every
placeholder POI." LivingRoom is the developer's own home; there is no site-visit
barrier to work around. Direct field capture (Workflow A) is realistic for all of
LivingRoom's Stage 1.2 POIs, so the interpolation math is worth implementing at minimal
effort now - a handful of calibration anchors, straightforward linear interpolation, no
panel-join or arc complexity needed for a small flat test room - mainly so the
resolver's fallback branch is a real, tested code path (§7 Phase E already commits to
testing it) rather than because LivingRoom's own content genuinely depends on it. The
panel-join/arc-anchor density decisions described above are a Panorama/Chafariz
concern, not a Stage 1.2/LivingRoom one - noted here so it isn't forgotten, not because
it needs building now.

**What this removes from the previous version of this plan:** `IFallbackProjector`,
`FlatWallGeometry`, `CylindricalWallGeometry`, and the `surface_type` config field are
all gone - superseded, not deferred. The cylindrical-projection research in §13 is kept
for the record (a real technique, genuinely well-established, and part of how this
answer was actually reasoned through) but is not what gets built; piecewise
interpolation between anchors is.

### 4.6 Visibility: three different problems, and it turns out none of them need building right now (sources: §13)

**Correction from the previous version of this plan, on top of the correction in §4.5.**
"Should a marker be visible" was covering three genuinely different problems, blurred
together under one "occlusion" label - and once separated, two of the three turn out to
already be resolved by decisions made elsewhere in the project, and the third is
explicitly out of scope this early. Stage 1.2 does not need to build anything from this
section. It's kept here as the reasoning trail for why, not as a spec for new code.

**Problem 1 - is the marker within the camera's field of view at all.** No code needed,
confirmed. A genuine 3D world-space object (a sprite/mesh actually sitting at its 3D
anchor position) gets standard GPU frustum culling for free, the same as every other 3D
object in any Unity scene - anything behind or outside the camera's view cone simply
isn't drawn.

**Problem 2 - the WorldToScreenPoint-behind-camera bug.** This only exists at all for
markers that manually project a 3D anchor onto a 2D screen position
(`Camera.WorldToScreenPoint`) - and the global work plan already settles that question
for this project: POI markers are uGUI on a **World Space Canvas**, not screen-space
projected UI - this is stated as the one deliberate, project-wide exception to "UI
Toolkit for all screen-space UI," specifically because World Space Canvas content is
genuinely 3D and needs to exist physically in the AR scene the way UI Toolkit cannot do
well. A World Space Canvas is rendered directly in 3D space by the camera, the same as
any other geometry - it never calls `WorldToScreenPoint`, so there is no projection
math for the behind-camera bug to corrupt. Problem 2 does not apply to this project's
architecture at all. (Content detail cards, by contrast, are UI Toolkit screen-space
overlays with no 3D position of their own - occlusion and frustum questions don't apply
to them either, for the more basic reason that they aren't anchored to a 3D point in
the first place.)

**Problem 3 - real wall/pillar occlusion.** This is the one genuinely not automatic -
Unity's normal depth-based occlusion can't help, since the "wall" a visitor sees is the
live camera passthrough feed, not Unity-rendered geometry with a depth-buffer entry to
test against (the reason ARKit/ARCore ship dedicated occlusion APIs rather than this
being solved by ordinary rendering). It's real, and it will matter on Chafariz - but the
global work plan already scopes it explicitly: an occlusion mesh reference (`mesh.glb`)
is reserved in the per-wall asset/schema structure now, precisely so adding it later is
not a breaking schema change, but building the actual occlusion *behavior* is
**Stage 7 stretch scope at the earliest, not a Stage 1-3 commitment** - and Stage 1.2
(this document) sits inside that same Stage 1-3 range the global plan already excludes.
Given that, Stage 1.2 does not add an `occlusion_mode` field, a
visibility-gate class, or any dot-product/raycast logic at all - not even as a
harmless-seeming stub. Every marker in front of the camera renders, full stop, matching
exactly what was asked for and what the established plan already calls for at this
stage. Revisit this section only once the project's own stage plan actually reaches
Stage 7.

### 4.7 A cheap safety net for small systematic misalignment (sources: §13)

Worth being honest about what is and isn't confirmed here. A claim worth checking
before acting on: that Immersal's exported mesh and its live-tracked map coordinate
frame can drift apart by a small amount (a scale or rotation offset), meaning every
`captured_position` placed against the mesh would be systematically off once tracked
live. Research turned up no specific, confirmed report of this for Immersal's native
`.glb` export workflow specifically - what Immersal's own documentation does say,
in a related content-placement context, is that an exported model and the map's point
cloud "should share the same coordinate system and should be aligned with each other"
- phrasing that reads as an expectation to verify, not an ironclad guarantee, which is
a weak but real signal that alignment is worth checking rather than assumed. Given
that, the honest position is: **not confirmed as a known problem, but cheap enough to
guard against regardless of whether this specific cause ever manifests.**

The guard, done simply: insert one empty GameObject - call it `PlacementCorrectionAnchor`
- as a child of XR Space, and parent every POI (both the Workflow A authoring rig and
the runtime-spawned markers) under *that* instead of directly under XR Space. Every
reference in this plan to "parented under XR Space" should be read from here on as
"parented under `PlacementCorrectionAnchor`, itself a child of XR Space" - functionally
identical in every normal case, since its own local transform stays at the identity by
default. The entire value is that if any systematic misalignment does show up in the
field - on Chafariz, or anywhere - nudging this one object's position/rotation in the
Inspector (or via a small runtime debug control) shifts every POI together, instantly,
without re-authoring or re-exporting a single JSON entry. This is simpler than adding
offset fields inside `POIPositionResolver` itself (the note's original suggestion) -
it costs one extra object in the hierarchy and reuses Unity's own transform-hierarchy
math, the same mechanism §4.3 already relies on for captured_position.

The already-planned Workflow A/B coordinate-frame spot check (§11) is what actually
determines whether this lever ever needs touching - it exists so there's an
immediate, no-rework fix available if that check finds drift, not because drift is
assumed to be happening.

## 5) Final decision: the authoring pipeline

1. Note how many calibration anchors the wall will eventually need (§4.5) - just one
   or two for LivingRoom's simple flat room; more, at panel joins or around an arc, for
   Panorama/Chafariz later. This is a data decision, not a code decision, and doesn't
   block anything else below.
2. Before building any placement tooling, hand-place a single marker prefab instance
   directly in the scene and confirm it's actually visible on-device (§7 Phase A1, §8
   Part 1). This isolates "does the marker prefab render correctly" from "is the
   position math correct" - cheap to do first, and it tells you immediately which
   category a later problem belongs to.
3. Author every POI in JSON first: `id`, `label`, category, and a rough `x_norm`/
   `y_norm` guess against the wall's reference. Fast, remote, no Unity needed - can be
   done from a reference photo at a desk. Gets content and layout testing moving
   immediately. No knowledge of the map's coordinate frame is needed for this step
   (§4.1's "how this reconciles with not yet knowing the origin" note).
4. Once the map/mesh is available, capture a small number of calibration anchors
   (§4.5) using the exact same field-capture method as any other POI - at minimum one
   at each end for a simple flat wall like LivingRoom - so the fallback interpolation
   has real reference points to work between.
5. Run the app (Editor, mock localization) and confirm markers appear, labels are
   correct, nothing overlaps in an obviously broken way, using the x_norm/y_norm
   fallback projection. This is a rough-draft visual check, not final placement.
6. Precisely place each POI using **Workflow A** (§4.2, §8): drag the downloaded map
   mesh into the scene as an Editor-only reference, then use the **Populate Rig from
   JSON** Editor tool (§7 Phase C, §8 Part 4) to auto-generate one correctly-named,
   roughly-positioned marker per POI in one click - computed from the same
   `x_norm`/`y_norm` fallback math already built in step 5, so you're nudging each
   marker the rest of the way against the real mesh, not placing every POI from
   scratch (Mechanism 1, §4.2 - these are not the same objects that get spawned at
   runtime).
7. Run **Capture Positions to JSON** (the other half of the same Editor tool) to write
   every adjusted marker's local position into the JSON as that POI's
   `captured_position` - present only when actually set (§4.3), never defaulted to
   `[0,0,0]`, and written via a full read-modify-write of the file so only the POIs you
   actually placed this session are touched (§7 Phase C, §9).
8. Re-run and verify markers align once captured_position takes over from the fallback.
9. For any POI where the mesh was too ambiguous to place confidently, do a targeted
   **Workflow B** on-site pass (§4.2) just for those POIs.
10. Add deterministic tests locking in resolver precedence and fallback behavior (§7,
    Phase E), including the origin-point edge case (§4.3).
11. Stage 4 (not now): compile the finished JSON into a `WallConfigAsset`
    ScriptableObject via an Editor validator/baker; runtime switches to reading the
    baked asset only.

## 7) Implementation sequence (good, not fast)

Steps are numbered per phase from here on (A1, A2, ... B1, B2, ...) rather than
continuously through the whole sequence - this plan has already gone through several
revisions where a small addition to one phase forced renumbering every phase after it;
per-phase numbering means a future change to Phase C, for instance, never touches the
numbers used in Phase D or E.

### Phase A - Foundation cleanup inside Stage 1.2 (start here)

A1. Create a minimal marker prefab; hand-place one test instance to confirm rendering
    before building anything else.
    - Build the visual (small icon + label stub) as a **uGUI prefab on a World Space
      Canvas** - this is already the established project-wide decision (the global
      work plan's one deliberate exception to "UI Toolkit for all screen-space UI"),
      not an open choice to make here. Confirmed by §4.6: this also means the
      WorldToScreenPoint-behind-camera question doesn't apply to this project at all,
      since World Space Canvas content is genuine 3D geometry, never
      screen-projected.
    - Before wiring any dynamic spawn code, hand-drag **one** instance of this prefab
      directly into the LivingRoom scene Hierarchy - a permanent object, positioned
      anywhere reasonable by eye, not spawned via code. Build and run on device,
      confirm it's actually visible. This is a rendering-only sanity check, fully
      decoupled from JSON, the resolver, or any spawn logic - if it fails, the problem
      is the prefab's materials/shaders/scale, not position math, and you want to know
      that before debugging position code that was never the issue. Delete this
      one-off test instance once confirmed (A2-A4 wire up the real dynamic path).
    - Assign the prefab to `WallSession.poiAnchorPrefab` for that dynamic path.
A2. Add a `PlacementCorrectionAnchor` empty GameObject as a child of XR Space (§4.7) -
    a one-time, cheap safety net. Every subsequent reference to parenting POIs "under
    XR Space" in this plan means under this object specifically from here on.
A3. Extract position logic out of `WallSession`.
    - Add `POIPositionResolver` in `Framework/Runtime/POI/`.
    - Move all position decision logic from session to resolver.
    - `WallSession` should only call the resolver and spawn the result.
A4. Define a clean resolver API, matching §4.3's finding and §4.5's established design.
    - If `captured_position` is present (field exists in the parsed data, regardless of
      its value - see §4.3's origin-point fix): no math needed - spawn the marker as a
      child of `PlacementCorrectionAnchor` and set `localPosition` directly.
    - Else: resolve from `x_norm`/`y_norm` by piecewise linear interpolation between
      the wall's calibration anchors (§4.5) - find the two nearest anchors, interpolate
      within that segment. No shape-classification, no per-wall strategy class - one
      algorithm, driven entirely by anchor data.
    - Signature: `bool TryResolvePosition(POIData poi, Transform correctionAnchor, out Vector3 localPosition)`.
    - No Unity scene dependencies inside the fallback math itself (plain class where
      possible - only the `Transform` parameter ties it to a scene at all, and that's
      unavoidable since it's the actual output target).
A5. Keep `WallSession` thin and assertive.
    - Assert config loaded before spawn.
    - Assert POI ids are non-empty before spawn.
    - Log one concise summary line for spawn totals, extended to include elapsed spawn
      time in milliseconds (§11 - this is what tells you, later, if the runtime spawn
      loop ever needs to become a staggered coroutine instead of a flat loop; no need
      to guess ahead of measuring).

### Phase B - Data contracts and schema increment (still Stage 1.2)

B1. Formalize POI position fields used now.
    - Keep existing fields, document them clearly in the config contract: `x_norm`,
      `y_norm`, `captured_position`.
    - `captured_position` is **optional** - omitted from a POI's JSON entry entirely
      until it's actually been captured, never defaulted to `[0,0,0]` (§4.3). In C#,
      represent this as a nullable type (`Vector3?` or an equivalent wrapper), not a
      sentinel value.
    - Add optional metadata to track capture provenance: `captured_position_source`
      (`workflow_a_editor` / `workflow_b_device` / `manual`),
      `captured_position_timestamp`.
    - Optional fields, ignored by runtime if absent.
B2. Add a wall-level (not per-POI) `calibration_anchors` list to config.
    - Each entry: an id, an x_norm/y_norm, and a captured_position - structurally
      identical to a POI entry, since a calibration anchor *is* one, just not rendered
      as a visitor-facing marker (§4.5). No `surface_type` or geometry-classification
      field is needed - the same interpolation logic handles any wall shape once
      enough anchors exist.
    - No occlusion-related field is added here. The global work plan already reserves
      an occlusion mesh slot (`mesh.glb`) in the per-wall asset structure for Stage 7;
      Stage 1.2 doesn't touch it and doesn't need its own placeholder field (§4.6).
B3. Create config quality checks (lightweight, pre-Stage-4).
    - Temporary runtime/editor validation helper: unique POI ids, valid norm ranges, no
      NaN/Infinity in captured coordinates.
    - Keep it simple and local; the full schema validator belongs to Stage 4.

### Phase C - Position acquisition workflow (critical - this is what was underspecified)

C1. Set up the map mesh as an Editor-only placement reference (Workflow A).
    - Drag `146267-LivingRoom2-tex.glb` into the Hierarchy as a child of the same XR
      Space/XR Map object the Immersal tracking components use.
    - **Immediately reset its Transform** (right-click the Transform component in the
      Inspector, choose Reset) so Position is exactly `(0,0,0)`, Rotation `(0,0,0)`,
      Scale `(1,1,1)`. Unity can assign an arbitrary local position to a dragged-in
      asset depending on exactly how it was dropped in, and Immersal's exported mesh
      is meant to already sit correctly in the map's coordinate frame once parented at
      identity - an un-reset offset here would silently shift every single
      `captured_position` placed against it by that exact amount. Cross-check by also
      enabling Immersal's own point-cloud visualization for this map (its Render Mode
      setting, §4.2) and confirming the mesh and point cloud visually coincide - if
      they don't even after the reset, the mesh itself was exported with an offset, a
      different and rarer problem the reset alone can't fix.
    - Tag that mesh object `EditorOnly` (Unity's built-in tag) so it's automatically
      stripped from builds - visible while editing, invisible to visitors.
    - See §8 for the exact click-by-click steps.
C2. Add a dedicated `POIAuthoringRig` empty GameObject as a child of
    `PlacementCorrectionAnchor` (A2), separate from the mesh reference added in C1.
    Everything the Authoring Tool creates or reads goes under this one object
    specifically - not "every child of XR Space" - so the tool can never mistake the
    mesh reference (or Immersal's own point-cloud visualization object, also a child
    of XR Space) for a POI marker.
C3. Build the POI Authoring Tool (`Framework/Editor`), covering two operations in one
    small Editor window rather than two separate tools:
    - **Populate Rig from JSON** - for every POI in the wall's JSON, computes a rough
      starting position using the same piecewise interpolation between calibration
      anchors (§4.5) the runtime resolver uses, then creates a persistent Hierarchy object at that
      position via `PrefabUtility.InstantiatePrefab()` - the Editor-correct call for
      this, since it keeps the prefab link intact, unlike `GameObject.Instantiate()`
      (a runtime-spawn API that would leave disconnected copies) - parented under
      `POIAuthoringRig` and named automatically after the POI's id. Every created
      object is registered with `Undo.RegisterCreatedObjectUndo(...)`, so a single
      `Ctrl+Z` cleanly removes the entire rig if needed, rather than leaving orphaned
      objects behind. Before creating anything, check whether `POIAuthoringRig`
      already has children - if it does, show a confirmation dialog
      (`EditorUtility.DisplayDialog`) asking whether to clear the existing rig first,
      and only proceed with `Undo.DestroyObjectImmediate(...)` on confirmation. This
      is what makes accidentally clicking the button twice harmless instead of leaving
      a duplicated, overlapping mess to untangle by hand.
    - **Capture Positions to JSON** - reads the *entire* wall JSON into memory first
      (a full deserialize, never string-patching specific keys), then for every
      currently-present child of `POIAuthoringRig` (matched by name = POI id)
      overwrites only that POI's `captured_position` and provenance fields in the
      in-memory structure. Any POI with no matching object currently in the scene is
      left completely untouched - not cleared, not guessed at. The whole structure is
      then serialized back out, overwriting the file. This full read-modify-write
      cycle is what makes repeated runs safe: because everything was read fresh and
      written back whole, nothing you didn't touch this session can be lost, and two
      separate placement sessions (e.g. today's hero POIs, next week's remaining
      ones) never conflict with each other's data.
    - This is this project's own equivalent of Immersal's `ContentStorageManager`
      pattern (§4.2), adapted to this project's own POI schema instead of Immersal's
      generic `content.json` format.
    - Both operations treat `calibration_anchors` (§4.5, §7 B2) exactly like regular
      POIs - they populate into the rig and capture back to JSON the same way, no
      separate tooling needed for them.
C4. Run **Populate Rig from JSON**. The Hierarchy now has one correctly-named, roughly-
    positioned marker per POI under `POIAuthoringRig`, computed straight from each
    POI's `x_norm`/`y_norm`.
C5. Manually nudge each marker with the Move tool while looking at the visible mesh
    (§8) - the real adjustment work, now starting from a rough position instead of an
    empty Hierarchy.
C6. Run **Capture Positions to JSON** to write every adjusted marker's position back.
C7. Delete the authoring-rig objects from the scene once captured (§8 Part 4, final
    step) - they've done their job and aren't part of what ships.
C8. Keep the x_norm/y_norm fallback path working for anything not yet captured.
    - Do not remove it. It's what lets remote content authoring continue in parallel
      with on-site/mesh-based placement work, and it's also what `Populate Rig from
      JSON` (C3) relies on for its rough starting positions.
C9. (Secondary, targeted only) Run Workflow B for ambiguous POIs.
    - Build with a temporary placement-mode toggle.
    - At the real wall, localized and tracking: tap to drop a marker at
      `camera position + camera forward * adjustable distance`, nudge distance until it
      visually sits correctly on the wall, confirm.
    - Log/save that position (device log or a temp on-device file, pulled via
      `adb pull`), merge into the JSON by hand or via the same Authoring Tool.

### Phase D - Marker rendering baseline (simple and robust)

D1. Implement minimal marker view behavior only, as a uGUI prefab on a World Space

    - Show fixed-size visual marker + short label, truncated to ~15 characters per the

D2. Separate responsibilities.

D3. Add the near-overlap visibility rule the global work plan already specifies: when

### Phase E - Testing and acceptance

E1. Add deterministic tests first (EditMode).

## 8) Concrete step-by-step Unity walkthrough (Workflow A - editor mesh placement)

**Parts 2-4 of this section are Mechanism 1 from §4.2** - regular Editor scene editing,
never Play Mode, on throwaway objects whose only job is to let you read off a position.
The real POIs a visitor sees are spawned separately, by `WallSession`, from the JSON
this section's last step writes into.

This assumes zero prior Unity experience. Basic Scene view navigation first, since
everything below depends on being able to look around the scene and the imported mesh:

- **Orbit the view:** hold the right mouse button and drag, or hold Alt and drag with
  the left mouse button.
- **Pan the view:** hold the middle mouse button and drag.
- **Zoom:** scroll the mouse wheel.
- **Frame an object:** select it in the Hierarchy panel, then press `F` with the mouse
  over the Scene view - snaps the camera to focus on it.

### Part 1 - Prove the marker renders, before building any placement tooling (§7 A1)

1. In the **Project** window, find the marker prefab (built in Phase A1).
2. In the **Hierarchy** window, find the **XR Space** object the Immersal SDK
   components are already attached to.
3. Drag the marker prefab from the Project window onto that XR Space object in the
   Hierarchy - this creates one persistent instance, a normal permanent scene object,
   not something spawned by code.
4. With that instance selected, type any reasonable-looking numbers into the
   **Position** X/Y/Z fields in the Inspector (it doesn't need to be correct yet - this
   step is only checking that the marker renders at all, not that it's in the right
   place).
5. Build and run on device. Confirm you can actually see the marker. If you can't, the
   problem is the prefab's material/shader/scale/rendering setup - fix that here, in
   isolation, before writing any position or spawn code, since debugging rendering and
   debugging position math at the same time makes it much harder to tell which one is
   actually broken.
6. Once confirmed, delete this test instance from the Hierarchy - Phase A2-A4 wires up
   the real dynamic spawn path that replaces it properly.

### Part 2 - One-time prerequisite before the `.glb` mesh can be used at all

0. Unity cannot open `.glb` files by itself. Open **Window > Package Manager**, click
   the `+` icon, choose **Add package by name**, and enter `com.unity.cloud.gltfast`.
   Install it. This only needs to be done once for the whole project, not per wall.
   (Also worth knowing for future walls: this mesh only exists because LivingRoom's
   map was captured in Immersal's offline/manual mapping mode - real-time capture mode
   never produces a `.glb`, so any future wall capture session needs to use manual mode
   if this workflow is going to be used for it too.)

### Part 3 - Bring the map mesh into the scene as a placement reference (§7 C1)

1. In the **Project** window, locate `146267-LivingRoom2-tex.glb` under
   `Assets/Apps/LivingRoom/`.
2. Drag the `.glb` file from the Project window directly onto the XR Space object in
   the Hierarchy - this makes it a child, inheriting the correct coordinate frame.
3. **Immediately reset its Transform**: right-click the Transform component's header in
   the Inspector and choose **Reset**, confirming Position reads `(0,0,0)`, Rotation
   `(0,0,0)`, and Scale `(1,1,1)`. Skipping this is the single easiest way to silently
   offset every POI you place later by whatever arbitrary amount Unity assigned the
   mesh when it was dragged in - worth treating as mandatory, not optional.
4. With the new mesh object selected, look at the **Tag** dropdown at the top of the
   **Inspector** window. Change it to `EditorOnly`. This one setting is what makes
   Unity automatically exclude it from any build, while leaving it fully visible while
   editing. (This is separate from - and works alongside - the Render Mode setting
   Immersal's own point-cloud visualization object has for the same purpose - worth
   enabling that too, briefly, just to visually confirm the mesh and the point cloud
   coincide before trusting either for placement.)
5. Press `F` with the Scene view focused to frame the mesh, then orbit/pan/zoom (above)
   until you can see the wall clearly.

### Part 4 - Populate, adjust, and capture every POI (§7 C3-C7)

1. With the POI Authoring Tool built (§7 C3), open it and click **Populate Rig from
   JSON**. The Hierarchy fills with one marker instance per POI in the wall's JSON,
   each already named after its POI id and roughly positioned from its `x_norm`/
   `y_norm` value - no manual dragging-in or renaming needed for this part. (If a rig
   already exists from an earlier session, the tool will ask before clearing it - see
   §7 C3.)
2. Select the first one in the Hierarchy and press `F` to frame it, so you can see
   where its rough starting position landed relative to the mesh.
3. With it selected, press `W` (or click the four-way-arrow icon in the top-left
   toolbar of the Scene view) to activate the **Move tool**. Three colored arrows and a
   small handle appear on the object.
4. Drag the colored arrows to move along a single axis (red=X, green=Y, blue=Z); drag
   one of the small colored squares between two arrows to move freely along that plane;
   drag the white center cube to move freely in the view plane. Use these while looking
   at the textured mesh to nudge the marker from its rough starting spot onto the exact
   point where the POI is depicted.
5. For fine adjustment, you can also type exact numbers directly into the **Position**
   X/Y/Z fields in the Inspector instead of dragging.
6. Repeat steps 2-5 for every POI - this is materially less work than placing each one
   from scratch, since every marker already starts approximately in the right place.
7. Save the scene (`Ctrl+S`) once done - the adjusted positions live in the scene file
   until the next step reads and writes them into JSON.
8. In the Authoring Tool, click **Capture Positions to JSON**. This writes every
   adjusted marker's position into the wall's JSON as `captured_position`, touching
   only the POIs currently present in the scene and leaving everything else in the file
   exactly as it was.
9. Delete the authoring-rig objects from the scene now (recommended, not just
   optional) - they've served their one purpose. Leaving them in risks exactly the
   confusion this section opened with: a second set of POI-shaped objects sitting in
   the Hierarchy that look like, but are not, what actually spawns at runtime. The
   JSON is now the source of truth; `WallSession` will spawn fresh marker instances
   from it at runtime, positioned from `captured_position`, every time the app runs.

## 11) Risks and mitigations for Stage 1.2

Risk: marker prefab not assigned in scene -> no visible markers.
- Mitigation: treat prefab assignment as an explicit Stage 1.2 entry checklist item.

Risk: resolver logic drifts back into `WallSession`.
- Mitigation: enforce the thin-orchestrator rule from the guidelines in code review and
  tests; `WallSession` should contain no `if`/`switch` that decides a position.

Risk: the x_norm/y_norm fallback doesn't generalize to curved walls.
- Mitigation: resolved architecturally, and more simply than previously planned here -
  `POIPositionResolver` interpolates between calibration anchors (§4.5) rather than
  applying a flat-plane formula, so Chafariz's curved geometry is handled by placing
  more anchors around its arc, not by writing new geometry-specific code.

Risk: a POI's `captured_position` is misclassified as "not yet captured" because it was
checked by magnitude (non-zero) instead of presence, and the POI happens to sit exactly
at the map origin.
- Mitigation: resolved in the schema design (§4.3, §7 Phase B) - `captured_position` is
  an optional/nullable field, checked for presence, never for magnitude. Locked in by
  an explicit test for the origin-point case (§7 Phase E).

Risk: the imported `.glb` mesh carries an arbitrary local position offset from however
it happened to be dragged into the Hierarchy, silently shifting every single
`captured_position` placed against it by that same amount.
- Mitigation: Reset Transform is an explicit, non-optional step immediately after
  import (§7 C1, §8 Part 3), with a visual cross-check against Immersal's own
  point-cloud visualization to catch the rarer case of an offset baked into the mesh
  data itself, which a Transform reset alone can't fix.

Risk: running "Populate Rig from JSON" a second time by accident (double-click, or
re-running mid-session) creates a duplicated, overlapping set of authoring objects.
- Mitigation: the tool checks whether `POIAuthoringRig` already has children before
  creating anything, and asks for confirmation before clearing it (§7 C3) - prevention,
  not just recovery. `Undo.RegisterCreatedObjectUndo` (§7 C3) is the recovery layer for
  whatever this doesn't catch - a single Ctrl+Z removes a whole accidental rig.

Risk: the Editor-time authoring-rig objects (Mechanism 1, §4.2) get confused with the
real runtime-spawned POIs (Mechanism 2), or accidentally ship in a build.
- Mitigation: the authoring objects live only under the dedicated `POIAuthoringRig`
  container (§7 C2), never mixed with the mesh reference or anything else under XR
  Space, and are explicitly deleted once their positions are captured (§8 Part 4, final
  step) rather than left in the scene indefinitely. Worth a quick Play Mode sanity
  check after a placement pass confirming the spawned count matches the JSON's POI
  count exactly, not double-counting any leftover authoring objects that happened to
  still be active.

Risk: instantiating every POI in a single flat loop the moment the wall localizes
causes a noticeable frame hitch as POI counts grow toward the thesis's largest case
(~150 on the Panorama).
- Mitigation: not solved speculatively - A5 (§7 Phase A) logs spawn duration on every
  run, giving a real number to watch as POI counts grow through later stages. If and when
  that number crosses a threshold worth caring about, converting the flat loop into a
  staggered coroutine (`yield return null` between spawns) is a small, contained
  change - but building it now, before any measurement shows a problem, would be
  solving a problem that may not exist at Stage 1.2's actual scale (10-60 POIs).

Risk: without any occlusion handling, POI markers on the far side of a wraparound wall
(Chafariz, a hypothetical full ring) render as if floating in space in front of a
visitor who can't actually see that part of the wall from where they're standing.
- Mitigation: not addressed in Stage 1.2 at all, and confirmed as correct rather than a
  gap - the global work plan explicitly scopes real occlusion behavior as Stage 7
  stretch work (§4.6), well past this project's near-term stages. The per-wall occlusion mesh slot
  (`mesh.glb`) the global plan already reserves in the asset schema is what prevents
  this from being a breaking change whenever Stage 7 actually arrives - nothing further
  needs reserving here.

Risk: mesh-based (Workflow A) and live (Workflow B) placements end up in slightly
different coordinate frames if the downloaded mesh isn't perfectly aligned to the live
map.
- Mitigation: after the first placement pass, do one quick on-site spot check comparing
  a couple of Workflow-A-placed POIs against the real wall in a live run, before trusting
  the method for the rest. If there's drift, it points at a mesh/map alignment issue
  worth fixing before placing everything else - and `PlacementCorrectionAnchor` (§4.7)
  is the immediate, no-rework lever to apply a fix with if this ever comes up.

Risk: over-focus on UI polish before data correctness.
- Mitigation: lock placement accuracy and tests first; visual polish after baseline
  stability.
