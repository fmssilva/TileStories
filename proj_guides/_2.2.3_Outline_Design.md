# Outline Design (2.2.3)

The status contour ring: how a POI's condition (destruction/damage level) is shown, the colour
ramp, and how the ring is sized and spun. Split out of `_2.2_Marker_Design.md` on 2026-09-22
alongside `_2.2.1_Marker_Design.md` and `_2.2.2_Badge_Design.md`. Sibling docs: `_2.2.1_Marker_Design.md`
(the symbol), `_2.2.2_Badge_Design.md` (the badge, which interacts with unknown status),
`_2.2.4_Markers_Effects.md` (the `rotate_contour` per-level flag this domain's spin speed drives),
`_5.1_Editor_Tab.md`, `_2.2_Marker_Design_Archive.md`.

**Audience:** an agent or developer with full Unity Editor + project access and no chat history.
Everything in this file was re-derived from the code on disk and from real test runs on 2026-09-22.

## 2. Concepts

### 2.1 The single condition palette

`StatusRamp` is the ONE table every outline-mode-affected element reads from: the gold ring, the
same-hue ring + symbol fill, and the (status-fallback) badge fill (`_2.2.2` §2.2 rule 4) all
resolve the same POI's status through the same `StatusRamp.Resolve(pct)` — the three
representations never disagree about what colour a given damage level means.

### 2.2 The three Outline Color modes — three genuinely different design decisions, not one colour picker with options

- **`uniform`** ("Uniform color"): every level shares the SAME ring colour, one shared,
  developer-adjustable field (`outline_uniform_color_hex`, default the framework's original gold).
  The ring is the *only* place status shows — the symbol fill stays the category's plain colour
  regardless of damage. Only the dash pattern (line style) differs between levels; the colour never
  does.
- **`same_hue`** ("Same hue as marker"): the ring *and* the symbol fill both take the marker's own
  category colour and darken toward black as `status_pct` rises (`StatusRamp.ShadeTowardBlack`);
  the icon's opacity also fades toward 0.28 at 100%. A marker's category identity (its hue) is
  legible at every damage level; only lightness communicates condition.
- **`per_type`** ("Per outline type"): each row of the level table carries its OWN colour
  (`OutlineLevelEntry.color_hex`) — the only mode where the developer picks a genuinely different
  colour per damage level, rather than one shared rule.

Each needs a structurally different amount of colour data: Uniform needs exactly one colour field;
Same hue needs no colour field at all (derived from the category); Per outline type needs a full
*table* of colours (one per level). This is why the level table's Color column, and the
Uniform-mode colour row above the table, are each shown in exactly one of the three modes and never
more than one at once — showing a per-row colour in Uniform mode was Pass 1's actual bug (§1).

### 2.3 Unknown is a third state, not a blend

Three structurally separate cases, never conflated:

1. `has_status = false` — this wall/POI has no condition axis at all (e.g. a mural with no
   "destroyed" concept). No ring, no ring-related badge.
2. `has_status = true`, known `status_pct` — a real point on the damage scale.
3. `has_status = true`, `status_unknown = true` — the wall tracks condition, but this specific
   POI's fate is a genuine historical unknown. Rendered identically regardless of outline mode: the
   universal grey "?" badge, plus a dotted grey ring if the wall has outline levels.

## 4. Editor

`GlobalScene/POIEditorToolWindow.MarkerDesign.cs`, `DrawGlobalOutlineSection`. Fields, in order:
Enable outline (toggle) -> Outline Color (3-option popup: Uniform color / Same hue as marker / Per
outline type) -> **Outline color** (colour swatch+hex row, shown ONLY in Uniform color mode) ->
Ring size (slider) -> Contour spin (scalar field, clamped 0-360) -> the Outline Types table (key +
details + style sprite + colour override, the last shown ONLY in Per outline type mode + search
keywords + delete) -> the Test sub-foldout. Turning the outline back on from "none," or loading a
config with an unrecognised saved mode, now normalises to `uniform` (never silently to a mode with
no runtime meaning).

Per-POI: **Outline** foldout (`DrawPoiOutlineFields`, shown only when outline is enabled) — Has
status toggle, Status level dropdown (or a raw percentage slider if no levels are authored yet),
Status unknown toggle (which auto-assigns the `"unknown"` level key and `unknown_damage` badge
category if present — `ApplyUnknownStatusDefaults`).

**Test sub-foldout:** shared `DrawDomainTestSubSection` helper (`_2.2.1` §4), with one addition only
Outline has: the **"Add outline demo grid"** switch (+ a "Base marker" popup when ticked) is drawn
before the three guides via an optional `drawBeforeGuides` callback on `DrawDomainTestSubSection`
(`DrawOutlinePreviewSwitch`). The three guides walk through Enable outline, Outline Color
(contrasting `lamp`/`lamp_military` under Uniform color vs Same hue as marker), the Uniform-mode
colour row, the new Ring size / Contour spin fields (naming that every LivingRoom hierarchy level
ticks `rotate_contour`), the level table (Per outline type only), the demo grid, and the per-POI Has
status / Status unknown toggles (naming `dev_marker_nostatus`, `_2.2.1` §6, for the "no axis" case).

**The demo grid** (`OutlinePreviewSpawner`, off by default, registered in
`DevFeatureBuildGuard.Registry`): one "No outline" control cell, then one cell per configured
outline level (its real colour, dash pattern and — if the level's hierarchy style rotates its
contour — spin) plus an "Unknown" cell. It rebuilds live whenever a Play Mode edit changes the
outline mode/colour/levels (`WallSession.ApplyMarkerSettings`), the same way the effects grid
rebuilds on an effects edit. It lives `OutlinePreviewSpawner.FarOffsetMetres` (6500 m) above the
scene — a different height than the effects grid's 5000 m — so the two never coincide if both
switches are ever left on together.

## 5. Explicitly deferred

Shape-matched dashed rings for non-circle marker shapes (`_2.2.1` §2.1) · a status/category filter
UI that would exploit `same_hue`'s hue/lightness toggle potential — noted in the archive as a
future idea, no filter UI exists yet to drive it · a per-level ring size or spin override (both
stay wall-wide fields, matching every other geometry setting in this domain's own precedent) ·
named colour PRESETS (e.g. quick-pick swatches for red/orange/blue/purple next to the Uniform color
picker) — considered in P5 and deliberately left out: a free colour picker already reaches any
colour, and a preset list is another small taxonomy to keep in sync for limited benefit.
