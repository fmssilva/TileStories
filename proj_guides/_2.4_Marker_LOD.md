# LOD, Selection, Clustering &amp; Zoom (2.4)

Scene-wide, continuously-evaluated system that decides **how many** markers
render and **how prominently**, as the visitor moves and looks around a
wall — plus the AR camera zoom feature that lets a visitor "get closer"
digitally. Distinct from `_2.3_Marker_Hierarchy.md` (which decides how big
*one* marker is, authored, static per level) — this domain decides which
markers exist on screen *this frame*, driven by live camera position.

## 1. Scope

**In scope:** distance-based selection (LOD), screen-space density
evaluation, clustering (aggregation), continuous shrink/fade density
response, hysteresis, soft transitions, frustum culling, AR camera zoom
(global FOV-based) and its effect on the above.

**Explicitly out of scope, separate future domains:**
- **Displacement** (moving individual overlapping markers/labels apart,
  leader lines) — `MarkerOverlapResolver.cs` above is that domain's
  starting point, not this one's.
- **Marker/tap selection UI** (highlighting or opening a specific tapped
  POI) — separate future file, alongside a local-magnifier zoom variant if
  ever wanted (this doc implements **global** zoom only, see §9).
- **Search & filtering** — separate future file. This domain's visibility
  logic should be designed so a future filter predicate can intersect with
  it (§4), not fight it, but building the filter UI itself is out of scope
  here.

## 2. Core invariant — true per-marker 3D distance

**Every distance value used anywhere in this domain is the real 3D
Euclidean distance from the camera to that specific marker's world
position** (`Vector3.Distance(camera.transform.position,
marker.transform.position)`), never a single shared "distance to the wall
plane" value reused across every marker. This is what makes the "standing
close to the wall, looking sideways" scenario resolve correctly for free —
a marker 15m to the side has a genuinely large distance value despite the
visitor standing flush against the wall at their own position, and
therefore correctly gets thinned/shrunk like any other far marker. This is
a hard requirement, not an optimization detail — a shortcut that computes
distance once per frame and reuses it for every marker would only visibly
break in this one scenario, making it an easy, dangerous thing to get
wrong. State it as an explicit invariant in code comments on `LODController`
itself, not just here.

**`WallSession.cs` change**, needed for `LODController` to iterate markers:
```csharp
// was: local variable inside SpawnPOIs()
public IReadOnlyList<MarkerView> SpawnedMarkers { get; private set; }
// set at the end of SpawnPOIs(), same place the overlap resolver call is
```

## 3. Data model — `WallConfigData.cs`

```csharp
public class LodBandEntry
{
    public float max_distance_m;   // band applies up to this distance
    public int max_visible_count;  // -1 = unlimited ("show all" band)
}

[System.Serializable]

    public int cluster_min_count = 5;                 // select_hide/cluster/hybrid: escalate to hide-or-cluster here
    public bool density_safety_escalation_enabled = true; // see §6.2
    public float density_safety_escalation_multiplier = 2f; // see §6.2

    public float fov_culling_margin_deg = 10f;

    public float zoom_tap_step = 1.5f;
    public int zoom_tap_levels = 2;      // 3rd tap/click returns to 1x

    public bool zoom_show_ui_buttons = true;

```

Wall-level: `public LodSettings lod_settings = new();`

**Default `bands`** (resolves the 5m/7m disagreement — picks the number
already committed to code in the `LODController.cs` stub). **All three
tiers are explicit rows — there is no implicit "beyond the last row"
behaviour.** Rows must be sorted ascending by `max_distance_m`; the last
row's `max_distance_m` is a real, large sentinel value (not a special
case a low-context agent has to infer), and lookup is a plain ordered
scan — first row whose `max_distance_m` the marker's effective distance
is under, wins:

| max_distance_m | max_visible_count |
|---|---|
| 2.0 | -1 (all) |
| 7.0 | 15 |
| 9999.0 | 5 |

`LodAutoSuggest` (§6.2) must generate all three rows explicitly, not two
— an earlier draft of that function generated only two rows and relied on
an undocumented "implicit" fallback for the third, which is exactly the
kind of gap this note exists to close.

**Why `cluster_min_count = 5`, not 2 or 3:** this is the deliberate
boundary against Displacement's territory. Two or three markers that are
merely close together are `MarkerOverlapResolver`'s problem (nudge apart).
Only once a region is genuinely dense does collapsing markers into one
cluster read better than nudging — 5 is a starting point to tune, not a
hard rule, but it should stay meaningfully higher than Displacement's
implicit 2-marker threshold so the two systems don't compete over the
same small groups.

**Why `density_radius_px` reuses 40f:** `MarkerOverlapResolver` already
established 40px as "close enough to be a problem" for this exact
codebase's marker sizes — reusing the constant keeps the two domains'
sense of "close" consistent rather than picking an arbitrary second
number that means something subtly different.

## 4. `LODController.cs` — architecture

New MonoBehaviour, `Runtime/POI/LODController.cs`, added to the same
GameObject as `WallSession`. Runs a periodic evaluation, **not every
frame** — density/LOD state doesn't change fast enough to need 60Hz, and
recomputation over up to ~150 markers is cheap but not free-cheap.
Cadence is developer-tunable (`lod_settings.evaluation_interval_s`, §3)
rather than hardcoded — a lower-end device or an unusually dense wall may
want a coarser interval than the 0.2s default:

```csharp
private float _timer;

void Update()
{
    _timer += Time.deltaTime;
    if (_timer < _settings.evaluation_interval_s) return;
    _timer = 0f;
    Evaluate();
}
```

`Evaluate()` per cycle, in order (each step's output narrows what the next
step considers, cheapest filters first). **Ordering correction from an
earlier draft**: density response must run *before* the count cap, not
after — capping by raw POI count first and evaluating density only on the
survivors is blind to spatial clustering (it could keep several markers
that happen to be crammed into one dense screen region while discarding a
lone, easy-to-render marker elsewhere, entirely by priority-sort luck):
1. **Frustum cull** (§8) — skip markers outside the camera's FOV + margin
   entirely; they don't enter distance/density evaluation this cycle.
2. **Effective distance** per surviving marker (§10: real distance ÷ zoom
   factor).
3. **LOD band lookup** — which band the marker's effective distance falls
   into (§3's explicit three-row lookup), apply hysteresis (§7) before
   accepting a band change. This determines the band's `max_visible
   _count` ceiling but does **not** truncate yet.
4. **Density response** (§5, §6) on every marker in the band, in priority
   order — produces a set of **visual units**: some markers survive
   individually, some are absorbed into a `MarkerClusterView` (§6.1),
   where one cluster counts as exactly one visual unit no matter how many
   POIs it represents.
5. **Count-cap truncation** — `max_visible_count` (from step 3) is a cap
   on the number of resulting **visual units** from step 4, not raw POI
   count. If still over the cap, drop lowest-`hierarchy_level`-priority
   units first (an entire low-priority cluster can be dropped as one
   unit, same rule as an individual marker).
6. **Apply** — visibility/size/cluster state written to each `MarkerView`
   (or hidden in favour of a cluster representative), all changes routed
   through the soft-transition fade (§7), never an instant hard cut.

## 5. Density evaluation

Per-marker radius check in **screen space**, run on every marker that
survived frustum culling and band lookup (§4 steps 1-3) — i.e. before the
count cap, in priority order (highest `hierarchy_level` priority first),
so density response can make an informed decision before any unit gets
dropped for being over the cap:

```csharp
// For each surviving marker, count how many OTHER surviving markers
// project within density_radius_px of it in screen space.
// O(n^2) over a small n (post-LOD, expect tens, not hundreds) — fine at
// this project's scale (thesis ceiling ~150 POIs total, fewer per band).
// Do not reach for a spatial grid/hex-bin structure here — that solves a
// scale problem this project doesn't have, and grid binning introduces a
// real artifact (two markers straddling a cell boundary read as "far"
// even when visually adjacent). A plain radius check gives every marker
// its own continuous density score instead of a per-cell average,
// avoiding visible banding between adjacent cells.
```

**Why screen space, not a separate world-space clustering pass:** for a
flat wall, all POIs are coplanar — there is no marker literally hidden
behind another the way a 3D city model has occlusion. What looks like
"markers piling up" when a visitor stands close and looks along the wall
at a shallow angle is **foreshortening** (perspective compression at a
grazing angle), and a screen-space projection of each marker's true world
position already captures that compression correctly, automatically, with
no separate 3D-space system needed. This caveat is deliberate: if this
project ever extends to a non-flat/sculptural wall, true depth occlusion
would need separate handling — not needed now.

**Real risk, now resolved rather than just flagged:** density/clustering
decisions made purely from screen-space projections will change as
viewing **angle** changes even at constant distance (walking sideways) —
an earlier draft of this doc flagged this without solving it. Concrete
fix, reusing machinery this domain already has rather than inventing a
new threshold: a marker's cluster membership (joining or leaving a
cluster, or crossing the `shrink_and_fade` ramp's thresholds) only commits
after **two consecutive `Evaluate()` cycles** agree — one cycle crossing a
threshold is provisional, not applied; the same result on the next cycle
(`evaluation_interval_s` later, §3) makes it real. This is the same
asymmetric-stability idea as §7's distance hysteresis, applied to the
density axis instead, and it costs nothing new to configure — it rides on
the existing evaluation cadence rather than adding another margin value
the developer has to tune.

## 6. `density_response_mode` — four strategies, developer-selected

"Automatic vs. manual" turned out to be two genuinely different ideas that
had been collapsed into one vague, unimplemented placeholder in an earlier
draft of this doc. Splitting them: one has no open design questions and is
fully specified below (§6.1); the other is deliberately, specifically
deferred, for a stated reason, not a hand-wave (§6.2's closing note).

Named per the cartographic *generalization operators* taxonomy (McMaster &
Shea, 1992 — §18 bibliography), so each mode maps to an established,
distinct technique rather than an arbitrary in-house invention:

- **`none`** — density is still evaluated (cheap) but nothing acts on it;
  only distance-band selection (§4) applies.
- **`select_hide`** ("Selection") — markers over the local density
  threshold beyond `cluster_min_count` are hidden outright, lowest
  `hierarchy_level` priority first.
- **`cluster`** ("Aggregation/Typification") — markers over threshold
  collapse into one `MarkerClusterView` representative (§6.1) at their
  group's centroid; expand on tap (future Zoom/selection domain owns the
  expand interaction, this domain owns creating the cluster and its
  static representative).
- **`shrink_and_fade`** (continuous, closest to Bell/Feiner/Höllerer's
  "modify size and transparency" — §18) — no marker disappears or merges.
  **Formula, one linear ramp driving both size and opacity together** (a
  single rule, not separate "some markers only shrink, others only fade"
  special-casing — simpler to implement and to reason about):
  ```csharp
  float t = Mathf.InverseLerp(shrink_start_neighbor_count, cluster_min_count, neighborCount);
  float densityFactor = Mathf.Lerp(1f, 0.4f, t); // 0.4 = floor, never fully vanishes
  // apply densityFactor as an additional multiplier on top of _2.3's
  // hierarchy-level size, and as the CanvasGroup.alpha multiplier (§7)
  ```
  Every marker whose neighbor count is between the two thresholds shrinks
  and fades together, proportionally — at `shrink_start_neighbor_count`
  it's unaffected (`densityFactor = 1`), at `cluster_min_count` it's at
  its floor (`densityFactor = 0.4`, never fully invisible — a partially
  faded, small marker still reads as "something is here," unlike a hard
  hide). The 0.4 floor is a starting point to tune, not a hard rule.
- **`hybrid` (default)** — `shrink_and_fade`'s ramp above applies once a
  marker's neighbor count passes `shrink_start_neighbor_count`; if density
  is still at or above `cluster_min_count` after shrinking (i.e. `t`
  reaches 1 and the marker is still over-threshold), escalate to
  `cluster` instead of leaving it pinned at the 0.4 floor. **Default because the "close + sideways" scenario (§5) is
  realistic, expected visitor behaviour for a large physical mural, not an
  edge case** — a soft, continuous response feels better than markers
  abruptly collapsing into cluster badges as someone turns their head, and
  `hybrid` is the only mode that behaves gracefully across the full range
  from "slightly crowded" (shrink only) to "genuinely too dense to render
  individually" (cluster). `shrink_start_neighbor_count < cluster_min
  _count` always — validate this at Stage-4-equivalent config validation,
  don't let a developer configure them backwards silently.

### 6.1 Cluster representative — `MarkerClusterView.cs`

New small prefab + component, **not** a repurposed `MarkerView`/`POIData`
— a cluster has no single POI identity, it's an aggregate (member POI
list, centroid world position, per-category counts). Keeping it a
separate type avoids overloading `MarkerView` with a dual real-POI/
cluster-aggregate responsibility.

**Default `cluster_icon_mode = "pie_and_count"`**: a ring of stacked
`Image` components, each `Image.type = Image.Type.Filled`,
`fillMethod = Image.FillMethod.Radial360`, one slice per category present
in the cluster sized by proportion (`fillAmount = categoryCount /
totalCount`, each slice's `fillOrigin`/rotation offset by the previous
slice's cumulative angle) — standard Unity UI technique, no custom shader
needed. A centered count label (`"+N"`) on top, matching the label-text
styling already established for markers. `dominant_category` and
`count_only` are simpler fallback modes (single category icon + count;
plain count only) for developers who find the pie busy on a small marker.

### 6.2 "Automatic" — two concrete features, fully specified, both buildable now

**Editor-time auto-suggest (`LodAutoSuggest.cs`, new, `Editor/POIAuthoring/
Shared/`, pure static, no MonoBehaviour, no runtime dependency)** — given
the wall's total POI count (already known once `config.json` is loaded in
the Editor), compute a starting-point set of `LodSettings` values, and
expose a **"Suggest Values"** button next to the LOD table that fills the
fields with the result — same interaction pattern as the existing Outline
table's `RecomputeLevelPercentSpacing` auto-spacing button, not a new UI
idiom. The developer can then hand-edit any field afterward exactly as
if they'd typed it themselves; this button doesn't create a persistent
"auto mode," it's a one-shot convenience that writes ordinary `manual`
values. No runtime schema field needed for this at all — it's Editor-only
code, which is why the earlier `density_response_selection` field was the
wrong shape for it.

```csharp
public static LodSettings Suggest(int totalPoiCount)
{
    // Deliberately simple, explainable heuristic — a starting point to
    // hand-tune, not a claim of optimality. Documented here so a future
    // reader can see exactly why these numbers, not treat them as magic.
    int outer = Mathf.Min(5, totalPoiCount);
    int middle = Mathf.Min(15, totalPoiCount);
    int clusterMin = Mathf.Max(3, Mathf.RoundToInt(totalPoiCount / 10f));
    int shrinkStart = Mathf.Max(2, clusterMin / 2);
    return new LodSettings {
        bands = new() {
            new LodBandEntry { max_distance_m = 2f, max_visible_count = -1 },
            new LodBandEntry { max_distance_m = 7f, max_visible_count = middle },
            new LodBandEntry { max_distance_m = 9999f, max_visible_count = outer },
        }, // all three tiers explicit — no implicit "beyond the last row" case
        cluster_min_count = clusterMin,
        shrink_start_neighbor_count = shrinkStart,
        // all other fields left at their LodSettings defaults
    };
}
```

**Runtime safety-net escalation** — `density_safety_escalation_enabled`
(default on) + `density_safety_escalation_multiplier` (default 2.0): if
the developer's chosen `density_response_mode` is anything **other than**
`hybrid`, and a region's measured neighbor count exceeds `cluster_min
_count × density_safety_escalation_multiplier`, `LODController` overrides
the configured mode for that region only, this cycle only, and applies
`cluster` behaviour regardless — a deterministic threshold crossing, not
a judgment call, and therefore fully Tier-0-testable (§14). This exists so
a developer who deliberately chose `select_hide` or `shrink_and_fade` (not
`hybrid`) doesn't end up with an unreadable pile of overlapping markers in
a region denser than they anticipated when they picked that mode — a
correctness safety net, not a competing "smart" system. Set the multiplier
high enough that it essentially never fires under the configured mode's
intended operating range, and only catches genuine misconfiguration or an
unexpectedly dense POI placement.

**What's still genuinely deferred, and why — not a hand-wave**: a system
that continuously re-tunes the *numeric thresholds themselves* at runtime
based on live-observed visual quality (the direction Tatzgern et al.'s
2016 adaptive-density work points toward, §18) is **not** included above,
for a specific reason: "does this look less cluttered" is not a
computable ground truth — it's inherently a Tier 1 (vision) or Tier 2
(human) judgment, per this project's own verification tiers (`40-testing
.md` §4.5). A system that self-tunes against an untested heuristic
couldn't be verified with a deterministic `Assert` the way everything
else in this framework is, and the project doesn't yet have real usage
data to calibrate such a heuristic against even if one were written. This
is the one piece worth revisiting once real user-testing data exists, not
before — everything else originally bundled under "automatic" is now
fully specified above.

## 7. Hysteresis + soft transitions

**Hysteresis — two distinct mechanisms, not one shared rule, because the
two axes need different kinds of stability:**
- **Distance-band transitions** (§4 step 3): margin-based. Demoting
  (fewer markers / smaller / more clustered) happens exactly at the
  configured threshold; **promoting back happens only after crossing back
  by `hysteresis_margin_m`** beyond it. This prevents the flicker that a
  visitor's natural body sway would otherwise cause right at a boundary —
  without needing to round/quantize distance (already rejected in `_2.3`'s
  size-compensation discussion for the same flicker reason, same fix
  applies here: buffer the *transition*, don't quantize the *input*).
- **Density/cluster-membership transitions** (§5, §6): consecutive-cycle-
  based, not margin-based — a distance margin doesn't make sense for a
  screen-space angle-drift problem. See §5's resolution: a threshold
  crossing only commits after two consecutive `Evaluate()` cycles agree.

**Soft transitions** — every visibility/size/opacity change this domain
makes routes through a fade, never an instant cut, using `transition_fade
_duration_s`. Reuses the same `CanvasGroup` mechanism `_2.3`'s
`MarkerRevealEffect` introduced (check the prefab first, per the
Implementation Status note above, before adding a second `CanvasGroup`).
A hide-via-LOD fade and a `_2.3` reveal-on-spawn fade are the same
mechanism serving two different triggers — don't build two fade systems.

## 8. Frustum culling

Cheap pre-filter, step 1 of `Evaluate()` (§4), gated by
`frustum_culling_enabled` (default on — a developer with unusual wall
geometry or debugging a visibility issue may want to disable it rather
than fight it). Use `GeometryUtility.CalculateFrustumPlanes(camera)` +
`GeometryUtility.TestPlanesAABB` against each marker's bounds, **or**, for
this project's UI-canvas markers, a simpler viewport-space check
(`camera.WorldToViewportPoint`, test x/y within `[0,1]` inflated by the
margin). `fov_culling_margin_deg` widens the effective FOV used for this
test only (not the render camera's real FOV) so markers just outside the
visible edge don't pop in abruptly the instant they cross into view —
they're already "known" and mid-transition by the time they're visually
on screen.

## 9. AR camera zoom — global, FOV-based

Confirmed design: **global zoom** (the whole view scales, not a local
magnifier — a local-magnifier variant is a materially different feature,
deferred to the future Zoom/selection domain if ever wanted). The visitor
re-aims the phone themselves after zooming, same as a real camera lens —
**no auto-pan/recenter toward a tapped cluster.** This is a deliberate
simplicity choice: implementing auto-pan would require tracking a virtual
look-direction independent of the phone's real orientation, complexity a
physical zoom lens has never needed either.

**`ARZoomState.cs`** — new static class, `Runtime/Tracking/`, mirrors the
resolver pattern used everywhere else in this codebase (one system
writes, others read, no tight coupling):
```csharp
public static class ARZoomState
{
    public static float ZoomFactor { get; private set; } = 1f;
    public static void SetZoom(float value, float min, float max)
        => ZoomFactor = Mathf.Clamp(value, min, max);
}
```

**`ARZoomController.cs`** — new MonoBehaviour, drives `Camera.fieldOfView`
from `ARZoomState.ZoomFactor`, reads `lod_settings.zoom_*` for its clamp
range and step sizes. **Capture the camera's native FOV once, before any
zoom is ever applied** — an AR passthrough camera's FOV is device/lens-
determined, not a value to hardcode:
```csharp
private float _baseFov;
void Start() => _baseFov = _camera.fieldOfView; // capture before first SetZoom call
void LateUpdate() => _camera.fieldOfView = _baseFov / ARZoomState.ZoomFactor;
// narrower FOV = zoomed in; ZoomFactor 1 => _baseFov unchanged
```
**Both the AR passthrough background and the world-space markers zoom
together automatically** because both render through the same camera —
do **not** implement zoom by cropping/scaling the passthrough texture
separately, that desyncs the camera image from the 3D markers and looks
broken.

**Real risk, not yet resolved, verify early rather than discover late in
Phase B:** ARFoundation's `ARCameraManager`/`ARCameraBackground` commonly
manage `Camera.fieldOfView` and/or `Camera.projectionMatrix` itself, every
frame, to keep the passthrough image correctly aligned with the physical
device camera's real optical properties. If it does this **after** this
domain's `LateUpdate` (or via a different mechanism, e.g. writing
`projectionMatrix` directly rather than `fieldOfView`, which some
ARFoundation provider plugins do), this whole FOV-based zoom approach
could be silently overridden or fought every frame, on real hardware, in
a way a mock-provider Editor test would never reveal. **This needs a
short, real-device spike — build the minimal `ARZoomController` above
against the project's actual ARFoundation setup and confirm the FOV
change actually sticks and renders correctly, before investing further in
Phase A's zoom test suite.** If it doesn't work as designed, the fallback
is manipulating `Camera.projectionMatrix` directly (still zooms passthrough
+ markers together, same underlying idea, different API surface) — noting
the fallback exists now so it isn't a from-scratch redesign if the primary
approach turns out blocked.

**Input, three layered mechanisms, not alternatives:**
- Continuous pinch (legacy `Input.touchCount == 2`, delta of the distance
  between the two touch positions frame-to-frame — no new package
  dependency needed; the new Input System wasn't found in use anywhere
  else in this project, don't introduce it just for this one gesture).
  Follows the finger directly, no animation — `zoom_transition_speed_s`
  doesn't apply here, only to the two discrete-jump mechanisms below.
- Double-tap step-cycle: `zoom_tap_step` per tap, up to `zoom_tap_levels`
  steps, one more tap beyond the last level returns to 1x. Animates over
  `zoom_transition_speed_s` rather than snapping instantly — this is the
  "speed" the developer asked to be able to tune, distinct from the
  discrete *size* of each step (`zoom_tap_step`).
- On-screen UI buttons (`zoom_show_ui_buttons`) — zoom in / zoom out / fit
  back to 1x, same `zoom_transition_speed_s` animation as the double-tap
  cycle. **Corrected here from an earlier draft that specified a uGUI
  Screen Space Overlay canvas** — the work plan's own architecture
  decision (§2, "UI system") is explicit: *all* screen-space UI is UI
  Toolkit, uGUI is reserved for world-space content only (markers, in
  this project). These buttons are screen-space chrome, not attached to
  any marker, so UI Toolkit is what the project's own stated rule already
  requires — not a new decision, a corrected application of an existing
  one. See §10a for where this project's UI Toolkit foundation gets built
  — this is the first domain that needs it. Both an interaction
  convenience and, since not every developer will want on-screen chrome,
  independently toggleable.

**Reset, one canonical path regardless of how zoom was applied**: the
"fit back to 1x" UI button calls `ARZoomState.SetZoom(1f, ...)` directly
and is the single defined reset action. The double-tap cycle's own
"one more tap past the last level returns to 1x" is a second *entry point*
to that same reset call, not a separate reset implementation. Pinch has no
dedicated reset gesture of its own — pinching back down to 1x already
achieves it continuously, and the UI button (if enabled) covers the
"snap back instantly" case. Don't build a third reset mechanism.

**Hard clamp**: `zoom_min`/`zoom_max` are enforced in `SetZoom` above,
not just a soft UI limit — an unclamped zoom drives `effective_distance`
(§10) toward zero, which breaks every size/LOD formula downstream and
pushes FOV toward a degenerate near-zero value. This is a correctness
requirement, not a UX nicety.

## 10. Effective distance — the zoom → LOD hookup

**The one detail that makes zoom actually reveal more markers instead of
just magnifying the same small set.** Every distance value `LODController`
uses (§2's invariant) is computed as:

```csharp
float effectiveDistance = realDistance / ARZoomState.ZoomFactor;
```

Without this, zooming in would only make an already-selected cluster look
bigger — the LOD band/density logic would still be evaluating the
un-zoomed real distance and wouldn't "unlock" any additional markers,
which would feel broken (visitor zooms in, expects more detail, gets a
magnified version of the same reduced set). With it, "zoomed in" is
treated as equivalent to "physically closer" for every selection decision
in this domain — exactly the "real" zoom behaviour requested.

## 14. Phase A — isolated verification, before live wiring

Per `40-testing.md` §4.4. `MarkerGalleryHarness` today is a **single-row**
layout (proven pattern for comparing marker variants side by side) — this
domain needs markers **spatially distributed** (some close, some far,
some deliberately clustered, some spread along a wide "wall" at varying
angles) to exercise distance bands, density, and frustum culling
meaningfully. Build a **new** dev scene/harness for this domain
(`Assets/Dev/LODGallery/` or similar), following the same data-struct-
driven principle (`40-testing.md` §4.4) — one list of fabricated marker
positions + hierarchy levels drives both the harness placement and the
test asserts, so they can't drift apart.

- **Tier 0**: fabricate a marker layout (mixed distances, a deliberately
  dense cluster, a sparse region) and a virtual camera at a fixed pose;
  call `LODController.Evaluate()` directly (extract the evaluation logic
  into a method callable without a live `Update()` loop for testability);
  `Assert` the exact expected visible set, band assignment, and cluster
  membership per marker. Repeat at 2-3 camera poses (including one at a
  shallow angle along the fabricated wall, directly exercising §5's
  foreshortening case) and at 2-3 `ARZoomState.ZoomFactor` values
  (confirms §10's hookup: same real positions, different effective
  distance, different expected visible set).
- **Tier 0**: hysteresis — move the fabricated camera to sit exactly on a
  band boundary, evaluate repeatedly across several ticks without moving
  it further, assert the band does **not** flicker (same result every
  tick at a stationary boundary position).
- **Tier 0.5**: cluster tap-target size — the cluster representative's
  rendered size (§6.1) must clear the 44×44px minimum (WCAG 2.5.5) even
  when it represents markers whose own level would otherwise be tiny —
  a cluster badge existing specifically to be tappable, unlike an
  individual low-priority marker, means this check matters more here than
  it did as an edge-case note in `_2.3`.
- **Tier 1 (vision, one consolidated pass, itemized checklist)**: one
  screenshot each of (a) the dense-cluster scene at `cluster` mode, (b)
  the same scene at `shrink_and_fade`, (c) the same at default `hybrid`.
  > (a): is exactly one cluster marker visible in the dense region, with a
  > visible pie-slice breakdown and a "+N" count? [yes/no, describe if no]
  > (b): are individual markers in the dense region visibly smaller/more
  > transparent than an equivalent marker in the sparse region? [yes/no]
  > (c): at this density level, did hybrid choose shrink or cluster?
  > [state which — not a right/wrong check, a description for a human to
  > judge against the two configured thresholds]
  > All three: is the frustum-culling margin visible — are there markers
  > partially visible at the screen edge rather than popping in abruptly?
  > [yes/no]
- **Tier 1, zoom**: screenshot before/after a fabricated zoom-in on the
  dense cluster. > Are more individual markers visible after zooming in
  than before? [yes/no — this is the one check that most directly
  validates §10; "no" here means the effective-distance hookup is broken
  even if every other test passes]

Do not proceed to live wiring (§12 step 8) until every item above is
green.
