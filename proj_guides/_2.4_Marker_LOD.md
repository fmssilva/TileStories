# LOD, Crowding, Clusters and Zoom (2.4)

This domain decides, every fraction of a second while the visitor moves, **which markers are on screen and
how prominently**, from each marker's real distance to the camera and from how crowded the screen is around
it. It also owns the AR camera **zoom**, which lets a visitor "walk closer" digitally. It is distinct from
`_2.3_Marker_Hierarchy.md`, which decides how big ONE marker is (authored, static per level): this domain
decides which markers exist on screen this frame, driven by the live camera.

This file is the single reference for the domain: design, data, code, Editor, testing (automated, vision and
device), design history and bibliography. It replaces the former `_2.4.1_Vision_Tests.md`,
`_2.4.2_Human_Tests.md` and the `_2.4.3` plan tracker.

## 2. Scope and boundaries

**In scope:** distance bands (how many markers per distance), screen-space crowding and the five responses
to it (none, select and hide, cluster, shrink and fade, hybrid), cluster markers, band and crowding
hysteresis, soft transitions, frustum culling, global AR zoom and its effect on all of the above, the
Editor's LOD and Zoom sections, and the dev-only LOD demo field.

**Neighbouring domains:**
- **Displacement** (`_2.5_Marker_Displacement.md`) nudges overlapping markers and labels apart. It runs as
  step 8 of this domain's pipeline, on the markers LOD kept. The line between the two is deliberate: two or
  three close markers are displacement's problem; only a genuinely dense spot (Crowded At, default 5) is
  thinned or clustered here.
- **Hierarchy** (`_2.3`) provides each marker's priority. It decides who survives a band's cap and who stays
  in a crowd.
- **Selection / search / filter** (`_2.6`): the selection dim and filter fades compose with LOD's visibility
  (section 3.7). Expanding a cluster on tap belongs to a future selection/zoom domain, not here.

## 3. Design

### 3.1 Core invariant: true per-marker 3D distance

Every distance in this domain is the real Euclidean distance from the camera to THAT marker, measured at its
**undisplaced** position (`MarkerView.UndisplacedWorldPosition`), divided by the current zoom. Never one shared
"distance to the wall". This is what makes "standing close to the wall, looking along it" work for free: a
marker 15 m to the side is genuinely far and is thinned like any far marker. Measuring at the undisplaced
position matters too: measuring where displacement had moved a marker fed displacement back into itself and
made markers drift (correction C11).

### 3.2 The pipeline (`LODController.Evaluate`)

`LODController` sits on the WallSession object and evaluates every `evaluation_interval_s` (0.2 s by
default, not every frame: distance and crowding change slowly). Each cycle, cheapest filter first:

1. **Frustum cull** -- markers outside the view (plus a margin) skip the rest of the cycle.
2. **Effective distance** -- real distance / zoom factor.
3. **Band lookup** with hysteresis -- which Distance Band each marker is in. This sets the band's cap but
   does not cut yet.
4. **Crowding** -- for each marker, how many others are within `density_radius_px` on screen.
5. **Response** -- the chosen response turns markers into visual units: kept, shrunk, hidden, or merged into
   a cluster (5b: `ReconcileClusters` builds and reuses the cluster markers; one cluster = one unit).
6. **Count cap** -- each band's Max markers applied to visual units, least important first.
7. **Apply** -- size, opacity and visibility written to each marker, always through the soft fade.
8. **Displacement** (`_2.5`) on the units that survived.

**Order matters.** Crowding runs before the cap. Capping raw POIs first would keep several markers crammed
into one spot and discard a lone, readable marker elsewhere by sort luck. A test fabricates exactly that case
so the wrong order would fail.

**Live settings.** `LODController` compares `WallSession.LodSettings` by reference every frame. A new object
(a live Editor edit) restores every marker, forgets every remembered band, crowding and cluster decision,
and re-evaluates with the new rules. Enable LOD off restores everything once.

After each evaluation `LODController.LastStats` publishes a `LodStats` (shown, shrunk, hidden by crowding /
by Max markers / out of view, clusters and their members, per-band shown of total, zoom), built from the same
final units the markers were drawn from, so the Editor's Live LOD Readout cannot disagree with the screen.

### 3.3 Distance bands

Bands are an ordered table (`max_distance_m`, `max_visible_count`, -1 = all). A marker belongs to the first
row whose distance exceeds its effective distance. **Every tier is an explicit row**; the last row's large
value (9999 m) is a real catch-all, never an implicit "beyond the last row" rule. Framework default:
under 2 m all, under 7 m 15, beyond 5 (the 7 m cutoff came from the original stub and settled a 5 m / 7 m
disagreement). The Editor warns about a table the runtime cannot use (empty, unsorted, no catch-all).

**Band hysteresis** (`hysteresis_margin_m`, 0.5 m): moving to a farther band happens exactly at the edge;
coming back needs the extra margin. That stops markers blinking while a visitor sways at an edge, without
rounding the distance itself.

### 3.4 Crowding: screen space, and why

Crowding is a plain O(n^2) radius check in screen space over the markers that survived culling (tens, not
hundreds, at this project's scale; a grid would add cell-boundary artefacts for no gain). Screen space is
the right space for a flat wall: markers are coplanar, so what looks like "markers piling up" when standing
close at a grazing angle is foreshortening, and projecting each true position captures it automatically. A
sculptural, non-flat wall would need real occlusion handling; not needed now.

Because screen positions change with the viewing angle, a crowding decision (joining or leaving a cluster,
crossing a shrink threshold, being hidden) only **commits after two evaluations in a row agree**. This is
the angular counterpart of band hysteresis and needs no extra setting.

`density_radius_px` defaults to 40 px, the same "close enough to be a problem" value displacement uses, so
both domains mean the same thing by "close".

### 3.5 The five responses

Named after the cartographic generalisation operators (McMaster and Shea 1992), so each maps to an
established technique:

- **None** -- crowding is measured, nothing acts on it; only the bands apply.
- **Select & Hide** (Selection) -- in a crowd, markers are taken from most to least important (priority,
  then distance) and one is kept while **fewer than Crowded At already-kept markers** are within the radius;
  the rest are hidden (`LODController.SelectAndHide`). A crowd keeps its most important markers and none of
  them stays crowded. (It first hid every crowded marker, so a crowd vanished whole: C17.)
- **Cluster** (Aggregation) -- crowded markers merge into one cluster marker (section 3.6).
- **Shrink & Fade** (after Bell, Feiner and Hollerer 2001) -- no marker disappears. One linear ramp drives
  size AND opacity together: `t = InverseLerp(Shrink Starts At, Crowded At, neighbours)`,
  `factor = Lerp(1, Shrink Floor, t)`, applied to the marker's root scale and alpha. At Crowded At a marker
  sits at the floor (default 0.4, never below 0.1): faint and small, but still saying "something is here".
- **Hybrid** (default) -- shrink first, then cluster once a marker reaches Crowded At. Default because
  standing close and turning your head is normal behaviour at a large mural, and only hybrid behaves
  gracefully from "slightly crowded" to "far too dense".

**Safety Net** (Select & Hide and Shrink & Fade only, on by default): a marker with more than
Crowded At x Safety Multiplier (default 2) neighbours is clustered anyway, so a region far denser than the
developer expected never becomes an unreadable pile. A deterministic threshold, not a judgment call.

**Why Crowded At defaults to 5, not 2 or 3:** it is the boundary with displacement. Small groups are nudged
apart; only a genuinely dense spot is thinned or merged. Shrink Starts At must stay below Crowded At (the
Editor warns; otherwise nothing ever shrinks).

### 3.6 Cluster markers (`MarkerClusterView`, `POI_Cluster.prefab`)

A cluster is its own small prefab and component, never a repurposed `MarkerView`: it has no single POI
identity, only members, a centroid and category counts.

- **Look** (Cluster Icon): Pie & Count (one filled radial slice per member category, proportional, closed
  all the way round, a dark centre disc, "+N" on top), Dominant Category (the most frequent category's icon
  and "+N"), Count Only ("+N"). Standard UI Image fills, no custom shader.
- **Size**: clusters live on the wall like markers, so they are sized in metres, not pixels: largest
  member's symbol x Cluster Size (1-4, default 1.2), growing a little with the member count. They shrink with
  distance exactly like markers and stay a comfortable tap target (checked by real projection: at least
  44 px, never half the screen). (Pixel numbers on a world-space canvas once made them 48-112 metres: C5.)
- **Priority** = the best member's hierarchy priority. A fixed rule, not a setting: it is the only correct
  meaning of "least important first" for a unit that represents several POIs.
- **Band Source** (developer's choice): the cluster's band comes from its centroid (default, smoothest), its
  nearest member (near as soon as one member is) or its farthest member (near only when all are).
- **Stability**: clusters use the same band hysteresis (Cluster Band Hysteresis, on) and a **Dissolve
  Grace** (default 3 evaluations) before a cluster whose group disappeared fades out, so clusters do not pop
  at the edge of a crowded area. Cluster views are pooled and reused when a new group overlaps an old one's
  members.
- **Orientation**: clusters always face the camera; only their vertical alignment follows the Orientation
  section (`cluster_vertical_alignment_mode`, `_2.1`).

### 3.7 Visibility channels and transitions

A marker's opacity is three independent channels multiplied (`MarkerView.ComposeAlpha`): **visible**
(LOD, `SetVisible`), **selection** (dim by selection or filter, `SetSelectionAlpha` -- its only writer is
`SelectionHighlightController`, `_2.6` section 5) and **crowding**
(Shrink & Fade, `SetDensityFactor`, which also scales the root). One shared value once meant a marker hidden
by LOD could never come back (C2). Every change fades over `transition_fade_duration_s` (0.3 s), never a hard
cut. Tap raycasts take their final state at the START of a fade: a marker LOD is hiding or merging into a
cluster stops taking taps at once (a cluster tap used to land on its fading members). The spawn reveal (`_2.3`) heads for the marker's current resting look, so a reveal never overrides a
LOD decision made during it (C8).

### 3.8 Frustum culling

A viewport test inflated by `fov_culling_margin_deg` (10 deg): markers just outside the screen edge are
already decided, and fading in, when they come into view. It only saves work; turning it off changes
nothing visible, which is why it is a switch for debugging.

### 3.9 Zoom: global, FOV-based

**Design.** The whole view zooms, like a real lens (a local magnifier is a different feature, deferred). The
visitor re-aims the phone; no auto-pan. `ARZoomController` writes `Camera.fieldOfView = baseFov / zoom` in
`LateUpdate`, with the base captured once at start (an AR camera's FOV comes from the device, never
hardcoded). Because the passthrough image and the markers render through the same camera they zoom
together; cropping the camera texture instead would desync them. `ARZoomState` is the one global zoom value
(one writer, many readers), hard-clamped to Min/Max Zoom: an unclamped zoom drives effective distance and FOV
toward zero and breaks every formula downstream.

**The hookup that makes zoom useful (effective distance).** LOD divides every distance by the zoom, so
zooming in counts as walking closer and **unlocks more markers**, instead of magnifying the same reduced
set. The Tier 1 check "more markers after zooming in" is the one check that proves it (section 7.5).

**Input, three layered mechanisms:** pinch (follows the fingers, no animation; new Input System
EnhancedTouch, since the project runs the new Input System only), double-tap step cycle (Double-Tap Step
per tap, Double-Tap Levels steps, the next tap returns to 1x), and on-screen buttons (in, out, back to 1x).
Double-tap and buttons animate over exactly **Transition (s)**, eased and frame-rate independent
(`ARZoomMath.AnimatedZoom`), and a step starts from where a running animation is heading, so a quick second
click goes a level further (C19). Reset has one canonical path (`ResetToBase`); the tap cycle's "back to 1x"
is a second entry point to it. Enable Zoom off returns the view to 1x; new Min/Max apply at once.

**On-screen buttons** are screen-space UI, so UI Toolkit (`ZoomControlView` + UXML + USS, the shared
`PanelSettings.asset`, `SafeAreaHelper` for notch and home bar): three 48 px round buttons docked bottom
right, shown only while Enable Zoom and Show On-Screen Buttons are on. This was the project's first UI
Toolkit screen, so it also built the shared foundation other screens reuse.

**Real-device risk.** AR Foundation may manage the camera's FOV or projection matrix itself every frame on
real hardware, which an Editor test can never reveal. If the FOV write does not stick, the fallback is to
write `Camera.projectionMatrix` directly (still zooms passthrough and markers together). This is the one
open device check (section 7.6, task A).

### 3.10 "Automatic" values, and what stays deferred

**Suggest Values** (Editor only, `LodAutoSuggest`, pure): from the wall's POI count n, three explicit bands
(2 m all, 7 m min(15, n), 9999 m min(5, n)), Crowded At = max(3, round(n / 10)), Shrink Starts At =
max(2, Crowded At / 2). A one-shot, explainable starting point that writes ordinary values the developer can
edit; it changes nothing else.

**Deferred on purpose:** runtime self-tuning of the thresholds against observed clutter (the direction of
Tatzgern et al. 2016). "Looks less cluttered" has no computable ground truth yet; it is a vision or human
judgment, so a self-tuning loop could not be verified by an assert, and there is no usage data to calibrate
it. Worth revisiting once real visitor data exists.

## 4. Data model (`WallConfigData.cs`)

Three wall-level blocks, each `= new()` so a config without them gets working defaults:

```csharp
public class LodSettings                                  // "lod_settings"
{
    public bool enabled = true;
    public List<LodBandEntry> bands = DefaultBands();      // 2 m all / 7 m 15 / 9999 m 5
    public float hysteresis_margin_m = 0.5f;
    public float transition_fade_duration_s = 0.3f;
    public float evaluation_interval_s = 0.2f;
    public string density_response_mode = "hybrid";        // none|select_hide|cluster|shrink_and_fade|hybrid
    public float density_radius_px = 40f;                  // Crowding Radius
    public int shrink_start_neighbor_count = 2;            // Shrink Starts At
    public int cluster_min_count = 5;                      // Crowded At
    public float shrink_min_factor = 0.4f;                 // Shrink Floor (size AND opacity)
    public float cluster_size_ratio = 1.2f;                // Cluster Size (x largest member)
    public bool density_safety_escalation_enabled = true;  // Safety Net
    public float density_safety_escalation_multiplier = 2f;
    public string cluster_icon_mode = "pie_and_count";     // pie_and_count|dominant_category|count_only
    public string cluster_band_source = "centroid";        // centroid|nearest_member|farthest_member
    public bool cluster_band_hysteresis_enabled = true;
    public int cluster_dissolve_grace_cycles = 3;
    public bool frustum_culling_enabled = true;
    public float fov_culling_margin_deg = 10f;
}
public class LodBandEntry { float max_distance_m; int max_visible_count; string details; } // -1 = all

public class ZoomSettings                                 // "zoom_settings"
{
    public bool enabled = true;
    public float min_factor = 1f, max_factor = 4f;
    public float tap_step = 1.5f; public int tap_levels = 2;
    public float transition_duration_s = 0.25f;            // exact animation length
    public bool show_ui_buttons = true;
    public float double_tap_window_s = 0.3f, double_tap_move_tolerance_px = 50f;
}

public class DemoFieldSettings                            // "demo_field": dev-only, section 7.2
{
    public bool enabled = false, show_labels = true;
    public int seed = 1;
    public float distance_m = 1.5f, width_m = 6f, height_m = 2.5f, depth_m = 8f;
    public int dense_clump_count = 8; public float dense_clump_radius_m = 0.08f;
    public List<DemoFieldLevelCount> level_counts;         // markers per hierarchy level (max 60; clump max 30)
}
```

The JSON keys are kept stable even where the Editor label differs (`cluster_min_count` is "Crowded At");
renaming saved keys would break configs for no gain. Zoom has its own block since 2026-09-25 (it lived
inside `LodSettings`: C14). Both LivingRoom config copies list the three bands explicitly and ship the demo
field OFF.

## 6. Editor: Global Scene > LOD and Zoom

**LOD.** Enable LOD (off hides the rest but keeps the values, and restores every marker in Play Mode), then
sub-foldouts in the order a developer tunes them:
- **Distance Bands** -- table Up to (m) / Max markers (-1 = all) / note / remove; + Add band; Suggest Values;
  Band Hysteresis (m); inline warnings for a table the runtime cannot use (also in the save-time report).
- **Crowding** -- Response, then only the rows that Response uses: Crowding Radius (px), Shrink Starts At,
  Crowded At, Shrink Floor, Safety Net + Safety Multiplier. `LodEditorRules` decides which rows show, and a
  test pins those rules against `LODController`'s own, so the Editor never shows a row that does nothing.
- **Clusters** (only when the settings can build a cluster) -- Cluster Icon, Cluster Size, Band Source,
  Cluster Band Hysteresis, Dissolve Grace (cycles).
- **Transitions & Performance** -- Fade (s), Evaluation Interval (s), Frustum Culling + Culling Margin.
- **Test** (open by default) -- Add LOD demo field and its rows (Show labels, markers per hierarchy level,
  Dense Clump, Clump Radius, Field Distance / Depth / Width / Height, Reshuffle), the **Live LOD Readout**,
  and the three collapsed guides (Scene / Playmode / Device).

**Zoom.** Enable Zoom; Zoom Range (Min / Max Zoom); Gestures & Buttons (Double-Tap Step, Double-Tap Levels,
Transition (s), Double-Tap Window (s), Tap Tolerance (px), Show On-Screen Buttons); Test (guides).

Every row has an (i) help that names Editor controls only and is app-agnostic (tests enforce ASCII, no
wall names, no doc or code references, every option explained).

**Where each setting can be tested.** Scene view: nothing (LOD needs a moving camera; the guides say "Not
possible in Scene test"). Play Mode: every LOD, Zoom and demo field setting, **live** -- each edit reaches
the running wall through its applier; Save All to JSON keeps it, Copy to StreamingAssets makes the next Play
start with it. Device only: pinch, double-tap, the real camera FOV, real walking distances, heat.

## 7. Testing

### 7.1 Approach

Pure logic gets Tier-0 unit tests; every seam between components gets a test on real objects (real
`WallSession`, real prefabs, real `LODController`, real cluster prefab, the shipped LivingRoom config) and,
where it matters, the **real wall scene**. The domain's hardest lesson: every early demo-field test built its
own camera at the origin with no scene around it, so all were green while the field was invisible in the app
(C15). A preview that lives in the real scene needs a test that looks through the real scene's camera.

### 7.2 The LOD demo field (Tier A harness)

The LivingRoom wall (26 POIs: three families of six markers within ~30 cm -- lamp, painting, camera, levels
1-5 -- plus developer fixtures) cannot reach a band's Max markers or several bands at once, so most settings
could not be seen working. LOD > Test > **Add LOD demo field** spawns real `POI_Marker`s: a chosen number per
hierarchy level scattered through a box deep enough to span several bands, plus one dense clump, with a
seeded placement (Reshuffle). The real `LODController` evaluates them (displacement too), and the wall's own
POIs pause while it is on.

**Where it stands (`DemoFieldStage`).** In the Editor, on an empty stage 3500 m above the scene: the camera
moves to the stage's start when the field turns on and back to its exact pose when it turns off; edits
rebuild the field in the same place. Placed in front of the start camera it had been hidden inside the
scanned room mesh (C15). A device cannot move its AR camera, so a development build uses the start pose.

Dev-only rules (`_5.1_Editor_Tab.md`, "Dev-only features and build safety"): off by default and in the
shipped config, honoured only in the Editor and development builds, registered in `DevFeatureBuildGuard`.
Only one demo view can be on at a time (it has no camera of its own; the effects/outline grids would cover
it). Search does not index demo markers. The field also exercises Displacement and Zoom.

**Live LOD Readout.** Next to it, the readout prints what LOD decided in its last evaluation, so every
setting's effect is a number, not only a look. Example, Hybrid on the default field: "Shown: 16 of 28
markers / Clusters: 1 (holding 9 markers) / Hidden by crowding: 0 | by Max markers: 3 | out of view: 0 /
Zoom: 1.0x / Band 2 (up to 7 m, max 15): 12 of 12 shown ...".

## 8. Design history (decisions and corrections)

Kept because it explains the current design and is quotable in the thesis report.

### 8.1 Key decisions

- **Screen-space crowding over a world-space clustering pass** (section 3.4): correct for a flat wall by
  construction (foreshortening is a projection effect); a world-space pass would need its own notion of
  "close" and would miss the grazing-angle case.
- **Two hysteresis mechanisms, not one**: a distance margin for bands (body sway), a two-cycle agreement for
  crowding (angle drift). A distance margin makes no sense for an angular problem.
- **Crowding before the count cap** (section 3.2); the cap counts visual units, so a cluster is one unit.
- **"Automatic" split into two buildable features** (Suggest Values, Safety Net) and one honestly deferred
  one (self-tuning), instead of a vague placeholder.
- **Cluster priority is fixed to the best member**; only the band source is a developer choice.
- **Global FOV zoom** over a local magnifier or a cropped camera texture; one canonical reset path.
- **Zoom buttons in UI Toolkit** (screen space), markers in uGUI world space: the project's spatial UI rule.
- **Real-scene verification**: the demo field is proven through the wall scene's own camera, not a
  fabricated one.
- **Test seam**: `ReconcileClusters` is `internal`, reached through one `InternalsVisibleTo` at the runtime
  assembly root, so the cluster lifecycle is testable without widening the public API.

### 8.2 Corrections (every one has a real test named after it)

Early build (2026-08):
- Count-cap priority sorted by distance instead of hierarchy priority; `ComparePriority` now compares
  priority first, distance only as a tie-break.
- `displacement_tiebreak` was dead config in `LodSettings`; it now lives in `DisplacementSettings` (`_2.5`).
- The shallow-angle and zoom-unlock Tier-0 checks were missing although the harness existed; added.
- The cluster prefab's dominant icon reference was persisted as empty (a child created in code is not part
  of the prefab asset until added to it); fixed by a two-phase, idempotent wiring tool.
- Duplicate `AssemblyInfo` with a wrong friend-assembly name; one seam at the runtime root.

Domain review (2026-09-25):
- **C1** The wall scene held no `LODController`: nothing in this domain (nor displacement) ran in the app.
- **C2** One alpha value for "dim" and "hidden": a marker hidden by LOD never came back (now three channels).
- **C3** The shrink factor was computed and never applied: Shrink & Fade did nothing visible.
- **C4** The zoom rig was not connected to the wall and the buttons were in no scene.
- **C5** Clusters sized in "pixels" on a world-space canvas, i.e. 48-112 metres (now metres, from members).
- **C6** The band table's delete broke the IMGUI layout (rebuilt on `TableRowScope`).
- **C7** Suggest Values reset every LOD and Zoom field (now only bands and the two crowding counts).
- **C8** The reveal animation overrode LOD decisions made during it.
- **C9** The cluster prefab drew a white square over the pie and count.
- **C10** Pie slices rotated the wrong way, leaving a wedge-shaped gap.
- **C11** LOD measured displaced positions, feeding displacement back into itself (drift, flicker).
- **C12** Band Source was offered in the Editor and ignored at runtime.
- **C13** The config shipped an empty band table (three hidden runtime defaults).
- **C14** Zoom settings lived inside `LodSettings` (split into `zoom_settings`).

Round 2, "the demo field does nothing" (2026-09-25):
- **C15** The demo field spawned inside the scanned room mesh (moved to an empty Editor stage).
- **C16** Yaw-only facing applied a rotated parent's yaw twice (edge-on markers; affects devices).
- **C17** Select & Hide hid every crowded marker (now keeps the most important).
- **C18** The zoom buttons' stylesheet was never linked and used web-CSS properties UI Toolkit drops; the
  clone's container was 0 px tall, so the strip sat above the screen.
- **C19** A quick second zoom click was lost, and Transition (s) was an exponential approach, not a duration.
- **C20** The Editor mock camera threw every frame when no main camera existed.
