# POI Detail Card -- Blocks (3.1)

What a visitor sees after selecting a POI: a bottom sheet over the camera that holds an ordered stack
of content BLOCKS (text, facts, images, audio, quiz, 3D...). This domain builds the card container, the
block contract and registry, every block kind in incremental tiers, the config model, the Editor's new
"Detail Card" tab and the per-POI "Card Content" section, and a LivingRoom fixture (`lamp`, "The Lamp", authored as
Castelo de Sao Jorge) that exercises every block. Navigation between blocks is `_3.2`; styles, themes
and the sunlight (high-contrast) expansion are `_3.3`.

Design source: the Design canvas "POI Card Block Catalog" (artboards: Full POI card, New blocks,
Variants, Single-POI card flow, Editor Card tab). This file is the build plan; the canvas is the look.

## 2. The visitor's flow (single POI)

1. Tap a marker -> it is selected (`SelectionEventBus`, `_2.6`), its name label shows.
2. The card opens at **peek** (compact header only). Swipe up -> **half** (<= 40% of the screen,
   summary + actions). Drag up -> **full** (the whole block stack, scrollable). Nothing ever opens
   above half by itself.
3. A heavy block (3D, 360, video, gallery lightbox) can open as a **takeover**: full screen over the
   card, a breadcrumb back ("Castelo > 3D model"), sibling media chips.
4. Close: swipe down past peek, tap the X, or tap empty camera space. Selection clears; the marker
   keeps a visited state (`_3.1` only records it; drawing a visited tick is a marker-domain change,
   flagged in section 12).
5. Audio started in the card keeps playing in a small mini-player after the card closes, until it ends
   or another POI's audio starts (Tier 4).

## 3. Architecture

Folders follow `10-structure.md` section 1: pure logic in `Runtime/Blocks/`, UI Toolkit views in
`Runtime/UI/Cards/`, Editor drawing in `Editor/POIEditor/DetailCard/` and
`Editor/POIEditor/SpecificMarker/`.

**Pure (Runtime/Blocks/, plain C#, EditMode-testable):**
- `BlockKindDefinition` -- one kind: `key`, `family` (ontology, `_3.2`), display name, `variants`,
  `fields` (the field schema), allowed display modes, default variant. The ONE description of a kind:
  the runtime view, the Editor field drawer and the validator all read it. `ShowsFor(poi, block, wallPois)`: whether
  the kind has something to show (status: the POI has a status; compare_points: both POIs have one and the other is
  on the wall), else skipped as `NotForThisPoint` with the kind's `NotShownForPoiNote`.
- `BlockFieldDefinition` -- `key`, `type` (section 5.3), `label`, `required`, `help`. `required` on an Items row's
  sub-field makes that row incomplete when empty (`BlockFieldReader.ItemIsComplete`); the view leaves it out.
- `BlockRegistry` -- `Register(BlockKindDefinition, Func<IBlockView> factory)`, `TryGet(kind)`,
  `All`. Public API: an app registers its own kinds without touching Framework (step 11).
- `BuiltInBlocks` -- registers every framework kind; called once at startup and by the Editor.
- `BlockStackBuilder` -- config (+ the wall's POIs, `wallPois`) -> the list of instances that WILL render: unknown kind
  skipped (dev warning), kind disabled wall-wide skipped, nothing to show for this POI skipped, required field empty
  skipped, a required Items field with no complete row skipped (`NoCompleteRow`), unsupported variant -> kind
  default. Pure, so "why is block X missing?" is a unit test, not a debug session. `CardTitleOf(poi, lang)`: the
  title a POI's card shows (its header's, else its name) -- how compare_points names the other POI.
- `BlockFieldReader` -- typed, language-aware reads (`Text(key)`, `Items(key)`, `Asset(key)`, `ItemColor`...) with
  fallback to the wall's default language; `ItemIsComplete` (the row rule), `TryParseColor` (the one accepted colour
  form: `#RRGGBB` / `#RGB`, no names, no alpha).
- `SheetStopRule` -- stop heights from screen height + safe area, the 40% cap, snap target from drag
  position and velocity (a flick = faster than 1.2 screen heights per second goes one stop further).
- `CardTapRule` -- tap vs drag (short and still) and "a tap on nothing closes the card".
- `TapOutsideDismissal` -- tap outside vs double-tap zoom: a tap on nothing closes only after the zoom's double-tap
  window, a second tap inside it (judged by `ARZoomMath.IsDoubleTapOK`, the zoom's own rule) keeps the card open.
- `CardStrings` -- the card's own UI texts (close, "Did you know?", status and sources words): framework defaults in
  `CardStrings.asset` (`CardStringTable`), a wall's wording in `card_settings.strings`.
- `GlossaryMarkup` + `CardGlossary` -- long-text paragraphs and `[[term]]` / `[[shown words|term]]` glossary words;
  definitions in `card_settings.glossary`.
- `CardStatusRule` -- the status block's colour and line through the MARKERS' rule (`MarkerVisualResolver`), the card
  tokens only when the wall draws no ring.
- `Media/` -- `IMediaSource`, `ResourcesMediaSource` (ref-counted `Resources` loads), `ScopedMediaSource`
  (one view's loads, released together).
- `MediaPathRule` -- the one rule of an Asset field's value: a path RELATIVE to the wall's media folder with a file type of
  the field's `MediaKind` (png / jpg / jpeg for `Image`); the Editor warns with it, the builder skips a required picture it
  refuses (`InvalidMedia`) and an Items row with one is incomplete. `StoredPathFor`: what the Editor stores for a picked file.
- `HeaderCollapseRule` (6C), `ZoomPanRule` and `SpotlightCropRule` (7A) -- pure placement rules of the collapsing header, the
  zoom_image picture and the spotlight crop.
- `State/` (8A, 8B) -- `CardLocalState`: the ONE store of what a visitor did on the cards on this device (a knowledge answer per
  question row, a feedback vote, a poll vote per block -- the option's authored row, `poll` slot --, an item collected -- `collected`
  slot --, a block revealed). `IPollResults` (8B): the seam where OTHER visitors' poll votes would come from; `NoPollResults`
  returns nothing, so the poll view hides its results bars and never shows a percentage (see the poll row in section 6). A key names its place, `ts.card.<wall>.<poi>.<block key>.<slot>`, each part
  escaped so a "." in an id never merges two places; PlayerPrefs cannot list its keys, so every key it writes is also recorded
  in one index entry of the same store and `ResetAll` (the POI Editor's Card Container > Test > Reset Saved Card State) removes
  exactly those. It sits over `ICardStateStore` (`PlayerPrefsCardStateStore` in the app, `MemoryCardStateStore` in tests and the
  gallery). View-only state never goes in it. `ICardEvents` (+ `CardEvent`, `CardEventKinds`, default `LogCardEvents`): the seam
  where the plan's telemetry will plug in -- a block raises an event, whoever implements the interface decides what happens; no
  backend here. `PoiCardHost` owns both (`State` per wall id, `Events`) and hands them to every bind through `BlockBindContext`.
- `CardServices` (step 11) -- the card's ONE typed service lookup: `Add<T>` (a second T is refused), `Get<T>` (null when absent), `Has<T>`,
  `Remove<T>`, keyed by the exact type registered, no reflection, no container. `CardServices.Shared` is what the wall's `PoiCardHost` and
  the gallery harness hand to every bind by default (`Services` on both; a test hands its own); an app fills it at startup the way it fills
  `BlockRegistry.Shared`, so a kind it registers gets its own dependency with NO field added to a Framework class. A view asks through
  `BlockBindContext.Service<T>()` and treats null as "nothing to show" (`PollBlockView`: no `IPollResults` = no results bars, as before).
  `Strings`, `Media`, `Host`, `State` and `Events` stay plain fields of the context: what every kind may use.
- `ContentSeenRule` (8A) -- when the visitor has "seen the content" of the open card: the stack scrolled to its end, or all of it
  fits (needs a viewport: at the peek stop nothing is visible). `BlockKindDefinition.ShowAfterViewedField` names a kind's Toggle:
  while it is on, `BlockStackView` keeps that block's whole slot (heading and gap) hidden until `ContentSeenRule` says so, then
  shows it and remembers it (`CardLocalState.Seen`) so it shows at once the next time. The views know nothing of it.
- `KnowledgeCheckRule` (8A) -- which question rows a look can show: multiple_choice = the options that have words (two or more) and a
  Right Option that is one of them; image_choice = the options that have a picture `MediaPathRule` accepts; true_false_swipe = the
  statement, its explanation and the `is_true` Toggle. Rows cannot nest, so a question's options are flat slots `option_1..4` /
  `image_1..4` (`BlockRegistry` refuses nested Items). `Question.Row` is the authored row index the answer is stored under, so
  leaving a row out never moves another question's saved answer. `SwipeChoice` judges a swipe through `SwipePageRule` (right = True,
  left = False). `BlockKindDefinition.ShowsFor` now receives the resolved variant (the block's own, else the Block Library's
  default): a question is valid or not per look. `FeedbackRule` -- a vote is thumbs 0 / 1 or stars 1..5, reported as
  "down" / "up" / "1".."5"; a stored vote the look cannot have counts as no vote.
- `SwipeGrabRule` (8A-fix) -- when a finger on a swipeable card (the true / false statement) is TAKEN by the card: past a slop and
  clearly more sideways than vertical. Until then the view leaves the pointer alone and the stack's ScrollView keeps it, so a finger
  that lands on the big card and moves up or down scrolls the stack (`SwipePageRule` judges the finished swipe, this rule the drag).
- `PollRule` (8B) -- a poll's options are the rows with words (at most six, each keeping its authored row: the vote is stored under
  it), `CanShow` needs a question and two options, `Percentages` turns counts an `IPollResults` gave into whole percents adding up to
  100 (largest remainder) and is `null` with no counts or no votes: nothing here invents a number.
- `CollectRule` (8B) -- the wall's collectable items are COUNTED FROM THE CONFIG (every collect block of every POI, `Block Library`
  aware), `Progress` is the visitor's count of them (the block being shown always counts as one: never "0 of 0"), the item's name
  defaults to the point's card title and its series to the point's category name.
- `DialogueRule` (8B) -- a dialogue's lines in order with their replies in flat slots `choice_1..3` / `reply_1..3` (a row cannot nest);
  rows with no words are left out, a choice with no label is never offered, `Problems` names both by row number for the Editor.

**Views (Runtime/UI/Cards/, UI Toolkit, plain C# like `_2.6`'s views):**
- `IBlockView` -- `VisualElement Root`, `Bind(BlockInstanceData, BlockBindContext)`, `Unbind()` (the stack then
  releases the view's media scope). `BlockBindContext`: POI, taxonomy, variant, language + fallback, `IMediaSource`,
  `CardStrings`, `CardGlossary`, the wall's `MarkerVisualSettings` (`MarkerLook`), `IBlockHost` (`ShowOnWall`, `OpenTakeover`,
  `SelectPoi`, `OpenUrl`, `TryGetViewer`; play audio joins with Tier 4), and (8A) `State` (`CardLocalState`) and `Events`
  (`ICardEvents`), null where a caller has none (a block then keeps its state in the view only), and (step 11) `Services` with
  `Service<T>()` (`CardServices`: what a kind needs beyond those, an app kind's own dependency included).
- `PoiCardSheetView` -- the sheet: grabber, X, stops, drag (pointer capture), close request.
- `CardIcons` -- the card's ONE icon set, drawn by USS from four generic parts (frame, two bars, a dot) in an 18 px glyph
  box: `show_on_wall` (the actions), `time`, `access`, `location`, `info`, `ticket`, `light` (practical_info). Since 8A-fix it also
  holds `VectorGlyph`, for shapes USS borders cannot draw: a `VisualElement` painted with `generateVisualContent` + `Painter2D`
  (`CardIcons.Shape`: Tick, Cross, Star, ThumbUp, ThumbDown; each shape's paths are `OutlinesOf(shape)` in 0..1 units of the glyph's
  square, pure and unit-tested; the colour is the element's resolved USS `color`, so a `--ts-*` token; the stroke is a share of the
  glyph's side, `StrokeUnits`; `Filled` fills the closed outlines, so a star / thumb is an outline while off and solid when on). The
  knowledge_check marks, feedback's stars and thumbs, the poll tick and the collect stamp's star are all one.
- `BlockStackView` -- the header in its own slot PINNED at the top of the sheet (the title never scrolls
  away; peek shows exactly its top part), every other block in a `ScrollView` (no scroll bar: a phone card is
  dragged), a FOOTER pinned under it for the variants a kind declares `FooterVariants` (the sticky call to action);
  views pooled per kind (work plan rule 2: never instantiate-and-destroy per tap); each bound view gets its own
  `ScopedMediaSource`.
- `CardTextView` -- one long text: a Label per paragraph, glossary words as `<link>` (a tap opens the definition under
  the paragraph), lede / drop-cap first paragraph; shared by rich_text, fun_fact and pull_quote.
- `TakeoverView` -- the full-screen view over the card (the sheet's sibling in the card layer, carrying the token classes):
  Back + breadcrumb ("card title > name"), a chip per sibling page, the page drawn by whoever opened it
  (`IBlockHost.OpenTakeover(name, pages, start, TakeoverPageDrawer)`) through the view's OWN media scope (given back on a page
  change and on close); the sheet is never rebound, so closing returns to the same stop and scroll. First user: the gallery
  lightbox (7A). Block display modes `expandable` / `takeover` are not offered by any kind yet (TODOs).
- `CardImage` -- one picture of the card: a clipped frame, the picture as a background image, the "picture unavailable" words
  (CardStrings) instead of a file that cannot be shown; loads lazily through the block's scope, only a path `MediaPathRule`
  accepts. Every Tier 2 picture is one.
- One `<Kind>BlockView.cs` per kind, grouped by family: `Cards/Blocks/About/`, `Ar/` (8B), `Media/`, `Guides/`,
  `Stories/`, `Play/`, `Visit/`, `Community/`, `Meta/`; each family folder holds its own `<Family>.uss` (6C).

**The one MonoBehaviour:** `PoiCardHost` on a new scene object `PoiCard` (own `UIDocument`, the
shared `PanelSettings`, sort order 2 -- above `SearchUI`). Subscribes to `SelectionEventBus`, asks
`WallSession` for the POI + config, builds sheet + stack, owns nothing else (`20-code-quality.md`
session/orchestrator rule).

**Styles:** `Runtime/UI/Cards/PoiCard.uss` (the container only), `CardParts.uss` (parts several families share: text, chip,
icons, the `.card-pill` button) and one `Blocks/<Family>/<Family>.uss` per family, each written only with `var(--...)` for
colours, sizes, radii, fonts, + `Runtime/UI/Cards/CardTokens.uss` (the minimal default token set). The host adds them in that
order (`PoiCardHost.CardStyleSheets`, shared with the Phase A harness). `_3.3` turns the token
file into presets; nothing in this doc writes a literal colour or size in C# or UXML.

**Why plain view classes + one host:** same reason as `_2.6` section 2 -- testable without a scene,
each view owns only its container, no view hunts for a `UIDocument`.

### 3.1 Options weighed

**Where block content lives (the big one).** The config is read and written with `JsonUtility`
everywhere (`WallConfigLoader`, `ConfigFileIO`, undo history `ConfigHistory`), and JsonUtility cannot
store a list of different C# types.

| Option | For | Against |
|---|---|---|
| A. One flat `BlockInstanceData` with every field of every kind | typed, trivial JSON | grows with every kind; apps cannot add a kind's fields without editing Framework |
| B. Per-kind typed lists on the POI (`texts[]`, `images[]`...) + an order list | typed | same Framework-edit problem; order kept in two places |
| **C. Generic instance + schema:** `BlockInstanceData { kind, variant, display, fields: List<BlockFieldValue> }`, the kind's `BlockKindDefinition` says which fields exist and their types | one data class for every kind (JsonUtility OK), apps add kinds with zero Framework edits, the Editor draws any kind from its definition, the validator (Stage 4) checks against the same definition | string-keyed field access -> mitigated by `BlockFieldReader` + a test per kind that every defined field round-trips |

**Chosen: C.** It is the only option where the block registry is a real extension point (work plan
Stage 2: "a downstream project can add a new block type without forking the package").

**Serializer switch rejected:** moving the config to Newtonsoft (installed as a dependency, 3.0.2)
would allow polymorphic lists but touches every config reader, the undo history and ~40 round-trip
tests for no gain over C.

**Card host placement.** (1) Keep the card inside `SearchUIHost` (today's `DetailCardView`) -- ties
the card's lifecycle to the search UI; the card is its own domain. (2) Card views mounted into the
`SearchUI` document by a second host -- two hosts fighting over one document's layout. (3) **Own scene
object + own UIDocument (chosen)** -- the same pattern `ZoomRig` and `SearchUI` already use.

## 4. Card container

- **Stops:** `peek` (header block in its `compact` variant + grabber), `half` (<= 40% of the safe-area
  height: header + first content block + actions), `full` (safe-area top minus a gap). Heights come
  from `card_settings.container` (section 5.1) and `SheetStopRule`.
- **Opening stop:** `peek` by default, `half` allowed; `full` is never an auto-open stop
  (work plan Stage 0 item 1: "never auto-expanded").
- **Dismiss:** swipe below peek, X button, or tap on empty camera space (verify first whether a tap on
  nothing already clears the selection in `_2.6`'s input path; reuse it if so).
- **Motion:** the sheet's HEIGHT is its stop (so the ScrollView viewport is exactly the visible part; a
  `translate` would leave the stack's bottom off screen at half), animated by a USS transition on `height`
  (`--ts-duration`), switched off while a finger drags; `reduce_motion` (visitor setting, `_3.3`) jumps.
- **Tap outside (built):** the host polls the Input System pointer; a press-release that `CardTapRule` calls
  a tap, where `EventSystem.RaycastAll` finds nothing (no marker, no UI Toolkit panel -- the panel raycaster
  reports the card and the search UI), clears the selection. Nothing did this before (`_2.6` only cleared on
  a re-tap or the X).
- **Tap outside vs double-tap zoom (step 5b):** a tap on nothing does not close at once while zoom is on: it waits
  `zoom_settings.double_tap_window_s`; a second tap inside the window and the move tolerance (the zoom's own
  `ARZoomMath.IsDoubleTapOK`) is the zoom's double tap -- the card stays, the zoom steps in. Any other tap (a marker,
  the card, a far tap) or a selection change cancels the pending close. Zoom off: nothing to wait for, it closes at
  once (`TapOutsideDismissal`, `PoiCardHost.ClosePending`).
- **Takeover (built 7A):** `TakeoverView` covers the whole card layer; Back returns to the same stop and scroll position; a
  tap on it is a tap on the UI (never "empty space"); another card, or closing the card, closes it.
- **Full stop and the search UI (6C):** the full stop reaches the top of the screen, where the search bar sits; while the card
  RESTS at full the search top (bar, filter tray, view switch) steps aside and comes back at any lower stop or on close, the
  query and filters kept (`SheetStopRule.CoversScreenTop`, `SearchUIHost.SetTopCoveredByCard`). Why this rule and not "full
  ends below the search bar": the half stop (<= 40%) never reaches the bar, and a full card that stopped below it would lose
  the bar's height on every phone for a bar the visitor is not using while reading.
- **Header collapse (6C):** once the stack scrolls, the pinned header shows only its top part (title + chip; the subtitle and
  the heading kicker step out) -- one class on the header slot, no second header; back at the scroll top it opens again
  (`HeaderCollapseRule`: hysteresis, and never a collapse that would leave nothing to scroll).
- **Headings and rhythm (6C):** every kind has the common `heading` field (its first field, `BlockKindDefinition.CommonFields`);
  the stack draws it above the block in one look, and the one gap `--ts-block-gap` under every block (no block adds its own
  margin). A kind may name a default heading (`DefaultHeadingKey`: compare's "Side by side", sources' "Sources").
- **Selection switch while open:** selecting another POI rebinds the stack in place (pooled views,
  no rebuild of the sheet), keeps the current stop.

### 5.1 Wall level: `card_settings`

| Field (Editor label) | Default | What it does |
|---|---|---|
| `enabled` (Enable Detail Card) | true | off: selection still works, no card |
| `languages` (Languages) | `["en","pt"]` | the languages every localized field shows rows for; first = fallback (and, until a visitor language setting exists, the language shown) |
| `media_resources_path` (Media Folder) | `""` | Resources-relative folder of the wall's card media; an `Asset` field stores a path inside it |
| `container.open_stop` (Open At) | `peek` | `peek` or `half` |
| `container.half_max_ratio` (Half Height Max) | 0.40 | cap of the half stop (0.25-0.40) |
| `container.dismiss_on_tap_outside` (Tap Outside Closes) | true | |
| `container.keep_audio_on_close` (Keep Audio Playing) | true | mini-player after close (Tier 4) |
| `kinds` (Block Library table) | every built-in kind enabled, default variants | per kind: `kind`, `enabled`, `default_variant`, `details` |
| `strings` (Card Texts) | empty = the framework's wording | per key: `text` in each language; a wall's wording of a card UI text (`CardStrings`) |
| `glossary` (Glossary) | empty | per word: `term`, `definition` in each language; a card long text links it as `[[term]]` |

### 5.2 POI level: `POIData.card`

```json
"card": {
  "blocks": [
    { "key": "block_1", "kind": "header", "variant": "image_parallax", "display": "inline",
      "fields": [
        { "key": "title",    "text": [ { "lang": "en", "value": "St George's Castle" },
                                      { "lang": "pt", "value": "Castelo de Sao Jorge" } ] },
        { "key": "subtitle", "text": [ { "lang": "en", "value": "Military - c. 1700 on the panel" } ] },
        { "key": "image",    "asset": "castelo/hero.png" }
      ] }
  ]
}
```

- `key`: generated `block_N`, never shown, never reused (same identity rule as taxonomy rows,
  `TaxonomyRowKeys`).
- A POI with no `card` or an empty `blocks` list shows the header only (name + summary from the
  existing `name` / `summary` fields), so every existing POI keeps working with zero authoring.
- `POIData.name` and `summary` stay untouched: search and markers keep reading them.

### 5.3 Field types (`BlockFieldType`)

| Type | Stored in `BlockFieldValue` as | Editor draws |
|---|---|---|
| `LocalizedText` | `text: [{lang, value}]` | one single-line row per wall language |
| `LocalizedLongText` | `text: [{lang, value}]` | one multi-line area per language |
| `Number` | `number` | float field |
| `Toggle` | `flag` | toggle |
| `Choice` | `value` (one of the field's options) | popup |
| `Asset` (image today; audio/video/model/captions with their tiers) | `asset` (a path RELATIVE to the wall's media folder; `MediaPathRule`) | object field filtered by the field's `MediaKind`; a file inside the Media Folder is stored as its path there, one outside is stored as picked and warned (the card leaves it out: `InvalidMedia`), a wrong type or a missing file warned (7A) |
| `Number` | `number` | slider over the definition's `NumberMin`..`NumberMax`; unset reads as `NumberDefault` (7A) |
| `Items` (repeater) | `items: [BlockItemData]` (each item has its own text/number/asset/value) | table rows, add/remove/reorder |
| `PoiRef` | `value` (a POI id) | POI popup by list title ("3. North tower"); a stale id stays selected as "(missing)", never shown as the id (`ReferencePopupOptions`, `missingLabel`) |
| `Color` | `value` (`#RRGGBB` or `#RGB`, `BlockFieldReader.TryParseColor`) | colour picker + hex (the tables' `DrawColorSwatchAndHex`); text that is not a colour is kept as typed with a warning under it, and the card leaves that row out |

`BlockItemData` holds its own keyed sub-fields, `fields: List<BlockItemFieldValue>`, each the shape of a
field value without nested items (a fact = label + value), so a quiz option, a fact, a gallery image, a
hotspot and a timeline event all reuse it. It cannot reuse `BlockFieldValue` itself: that type would contain
itself, which Unity's serializer cannot store. Languages are a list, not `en`/`pt`
fields, so ES/FR later is a data change (work plan: "add a translated string table, never find and
replace").

## 7. How each block is built (the micro-cycle)

For EVERY kind, in this order; the next kind starts only when the previous one is proven:

1. **Definition** in `BuiltInBlocks`: fields, variants, family, display modes.
2. **Round-trip test**: an instance with every field filled survives `JsonUtility` save/load and the
   window's undo/redo (walked by reflection, like `SearchFilterEditorTabTests`).
3. **View** (`<Kind>BlockView`), styled only through its family's `<Family>.uss` + tokens (after 6C).
4. **Phase A** (`40-testing.md` section 4.4, UI Toolkit recipe): (a) static check of the view in
   **UI Builder**; (b) add entries to `CardGalleryDefinitions` -- every variant x (short, long, missing
   optional field, missing media) -- and run the gallery scene. One data list drives the harness and
   the tests.
5. **Phase A tests** (`CardGalleryTests`, PlayMode): each entry builds, no text overflow at 390 px,
   text/background contrast >= 4.5:1 via `UIAccessibility`, tap targets >= 44 px, a render
   `TestEvidence/Card/Card_<kind>_<variant>.png` for the Tier 1 vision pass.
6. **Editor**: nothing to write -- the Card Content section draws the kind from its definition.
   Verify the rows by opening the window (drawing never writes: existing `DrawingNeverWritesTests`
   pattern).
7. **Fixture**: author the kind's content on `lamp` through the Editor window (section 8), save.
8. **Phase B test** (`PoiCardSceneTests`, real `LivingRoomScene`): select `lamp` through the bus,
   open full, the block is present in the authored order with the authored text.
9. **Docs**: `10-structure.md` tree entry for every new file; this file's status row.
