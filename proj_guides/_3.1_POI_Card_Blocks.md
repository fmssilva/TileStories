# POI Detail Card -- Blocks (3.1)

What a visitor sees after selecting a POI: a bottom sheet over the camera that holds an ordered stack
of content BLOCKS (text, facts, images, audio, quiz, 3D...). This domain builds the card container, the
block contract and registry, every block kind in incremental tiers, the config model, the Editor's new
"Detail Card" tab and the per-POI "Card Content" section, and a LivingRoom fixture (`lamp`, "The Lamp", authored as
Castelo de Sao Jorge) that exercises every block. Navigation between blocks is `_3.2`; styles, themes
and the sunlight (high-contrast) expansion are `_3.3`.

Design source: the Design canvas "POI Card Block Catalog" (artboards: Full POI card, New blocks,
Variants, Single-POI card flow, Editor Card tab). This file is the build plan; the canvas is the look.

## 1. Scope

**In:** the card container and its states for ONE selected POI (marker -> label -> peek -> half ->
full -> dismiss -> back to the wall); every block kind listed in section 6 except the deferred ones;
block display modes `inline`, `expandable`, `takeover`; per-POI content authoring; English + Portuguese
text from the first field onwards.

**Out (other docs or later stages):**
- Navigation between blocks and card layout modes (tabs, pages, accordion, bento) -> `_3.2`.
- Theme presets, sunlight high-contrast mode, per-block style overrides -> `_3.3`. This doc only
  requires that every visual value is a USS variable from day one (`30-ui-content.md`).
- Lenses: era / lapse (`lapse_states`), visitor profile (`content_by_profile`) -> a later `_3.4`.
  Work plan Stage 2 items 6 and 9; they change what blocks show but are not blocks.
- Scene-level features: circuits, badges/toasts, guide character overlay, sharing, wall hunt -> Stage 3.
- Search indexing of card text: card text is NOT indexed in this domain (see section 9, "Why").

## 2. The visitor's flow (single POI)

1. Tap a marker -> it is selected (`SelectionEventBus`, `_2.6`), its name label shows.
2. The card opens at **peek** (compact header only). Swipe up -> **half** (<= 40% of the screen,
   summary + actions). Drag up -> **full** (the whole block stack, scrollable). Nothing ever opens
   above half by itself.
3. A heavy block (3D, 360, video, gallery lightbox) can open as a **takeover**: full screen over the
   card, a breadcrumb back ("Castelo > 3D model"), sibling media chips.
4. Close: swipe down past peek, tap the X, or tap empty camera space. Selection clears; the marker
   keeps a visited state (`_3.1` only records it; drawing a visited tick is a marker-domain change,
   flagged in section 12).
5. Audio started in the card keeps playing in a small mini-player after the card closes, until it ends
   or another POI's audio starts (Tier 4).

## 3. Architecture

Folders follow `10-structure.md` section 1: pure logic in `Runtime/Blocks/`, UI Toolkit views in
`Runtime/UI/Cards/`, Editor drawing in `Editor/POIEditor/DetailCard/` and
`Editor/POIEditor/SpecificMarker/`.

**Pure (Runtime/Blocks/, plain C#, EditMode-testable):**
- `BlockKindDefinition` -- one kind: `key`, `family` (ontology, `_3.2`), display name, `variants`,
  `fields` (the field schema), allowed display modes, default variant. The ONE description of a kind:
  the runtime view, the Editor field drawer and the validator all read it.
- `BlockFieldDefinition` -- `key`, `type` (section 5.3), `label`, `required`, `help`.
- `BlockRegistry` -- `Register(BlockKindDefinition, Func<IBlockView> factory)`, `TryGet(kind)`,
  `All`. Public API: an app registers its own kinds without touching Framework (step 11).
- `BuiltInBlocks` -- registers every framework kind; called once at startup and by the Editor.
- `BlockStackBuilder` -- config -> the list of instances that WILL render: unknown kind skipped (dev
  warning), kind disabled wall-wide skipped, required field empty skipped, unsupported variant ->
  kind default. Pure, so "why is block X missing?" is a unit test, not a debug session.
- `BlockFieldReader` -- typed, language-aware reads (`Text(key)`, `Items(key)`, `Asset(key)`...) with
  fallback to the wall's default language.
- `SheetStopRule` -- stop heights from screen height + safe area, the 40% cap, snap target from drag
  position and velocity (a flick = faster than 1.2 screen heights per second goes one stop further).
- `CardTapRule` -- tap vs drag (short and still) and "a tap on nothing closes the card".
- `Media/` -- `IMediaSource`, `ResourcesMediaSource` (ref-counted `Resources` loads), `ScopedMediaSource`
  (one view's loads, released together).

**Views (Runtime/UI/Cards/, UI Toolkit, plain C# like `_2.6`'s views):**
- `IBlockView` -- `VisualElement Root`, `Bind(BlockInstanceData, BlockBindContext)`, `Unbind()`
  (releases media), `Dispose()`. `BlockBindContext`: POI, taxonomy, language, `IMediaSource`,
  `IBlockHost` (open takeover, play audio, request "show on wall").
- `PoiCardSheetView` -- the sheet: grabber, X, stops, drag (pointer capture), close request.
- `BlockStackView` -- the header in its own slot PINNED at the top of the sheet (the title never scrolls
  away; peek shows exactly its top part), every other block in a `ScrollView`; views pooled per kind (work
  plan rule 2: never instantiate-and-destroy per tap); each bound view gets its own `ScopedMediaSource`.
- `TakeoverView` -- full-screen host for a block in `takeover` mode, breadcrumb + sibling chips. Built with
  its first user, Tier 2 (step 7), not before (no untested code).
- One `<Kind>BlockView.cs` per kind, grouped by family: `Cards/Blocks/About/`, `Media/`, `Guides/`,
  `Stories/`, `Play/`, `Visit/`, `Community/`.

**The one MonoBehaviour:** `PoiCardHost` on a new scene object `PoiCard` (own `UIDocument`, the
shared `PanelSettings`, sort order 2 -- above `SearchUI`). Subscribes to `SelectionEventBus`, asks
`WallSession` for the POI + config, builds sheet + stack, owns nothing else (`20-code-quality.md`
session/orchestrator rule).

**Styles:** `Runtime/UI/Cards/PoiCard.uss` (layout, only `var(--...)` for colours, sizes, radii,
fonts) + `Runtime/UI/Cards/CardTokens.uss` (the minimal default token set). `_3.3` turns the token
file into presets; nothing in this doc writes a literal colour or size in C# or UXML.

**Why plain view classes + one host:** same reason as `_2.6` section 2 -- testable without a scene,
each view owns only its container, no view hunts for a `UIDocument`.

### 3.1 Options weighed

**Where block content lives (the big one).** The config is read and written with `JsonUtility`
everywhere (`WallConfigLoader`, `ConfigFileIO`, undo history `ConfigHistory`), and JsonUtility cannot
store a list of different C# types.

| Option | For | Against |
|---|---|---|
| A. One flat `BlockInstanceData` with every field of every kind | typed, trivial JSON | grows with every kind; apps cannot add a kind's fields without editing Framework |
| B. Per-kind typed lists on the POI (`texts[]`, `images[]`...) + an order list | typed | same Framework-edit problem; order kept in two places |
| **C. Generic instance + schema:** `BlockInstanceData { kind, variant, display, fields: List<BlockFieldValue> }`, the kind's `BlockKindDefinition` says which fields exist and their types | one data class for every kind (JsonUtility OK), apps add kinds with zero Framework edits, the Editor draws any kind from its definition, the validator (Stage 4) checks against the same definition | string-keyed field access -> mitigated by `BlockFieldReader` + a test per kind that every defined field round-trips |

**Chosen: C.** It is the only option where the block registry is a real extension point (work plan
Stage 2: "a downstream project can add a new block type without forking the package").

**Serializer switch rejected:** moving the config to Newtonsoft (installed as a dependency, 3.0.2)
would allow polymorphic lists but touches every config reader, the undo history and ~40 round-trip
tests for no gain over C.

**Card host placement.** (1) Keep the card inside `SearchUIHost` (today's `DetailCardView`) -- ties
the card's lifecycle to the search UI; the card is its own domain. (2) Card views mounted into the
`SearchUI` document by a second host -- two hosts fighting over one document's layout. (3) **Own scene
object + own UIDocument (chosen)** -- the same pattern `ZoomRig` and `SearchUI` already use.

## 4. Card container

- **Stops:** `peek` (header block in its `compact` variant + grabber), `half` (<= 40% of the safe-area
  height: header + first content block + actions), `full` (safe-area top minus a gap). Heights come
  from `card_settings.container` (section 5.1) and `SheetStopRule`.
- **Opening stop:** `peek` by default, `half` allowed; `full` is never an auto-open stop
  (work plan Stage 0 item 1: "never auto-expanded").
- **Dismiss:** swipe below peek, X button, or tap on empty camera space (verify first whether a tap on
  nothing already clears the selection in `_2.6`'s input path; reuse it if so).
- **Motion:** the sheet's HEIGHT is its stop (so the ScrollView viewport is exactly the visible part; a
  `translate` would leave the stack's bottom off screen at half), animated by a USS transition on `height`
  (`--ts-duration`), switched off while a finger drags; `reduce_motion` (visitor setting, `_3.3`) jumps.
- **Tap outside (built):** the host polls the Input System pointer; a press-release that `CardTapRule` calls
  a tap, where `EventSystem.RaycastAll` finds nothing (no marker, no UI Toolkit panel -- the panel raycaster
  reports the card and the search UI), clears the selection. Nothing did this before (`_2.6` only cleared on
  a re-tap or the X).
- **Takeover:** `TakeoverView` covers the sheet; back returns to the same scroll position.
- **Selection switch while open:** selecting another POI rebinds the stack in place (pooled views,
  no rebuild of the sheet), keeps the current stop.

## 5. Config ontology

### 5.1 Wall level: `card_settings`

| Field (Editor label) | Default | What it does |
|---|---|---|
| `enabled` (Enable Detail Card) | true | off: selection still works, no card |
| `languages` (Languages) | `["en","pt"]` | the languages every localized field shows rows for; first = fallback (and, until a visitor language setting exists, the language shown) |
| `media_resources_path` (Media Folder) | `""` | Resources-relative folder of the wall's card media; an `Asset` field stores a path inside it |
| `container.open_stop` (Open At) | `peek` | `peek` or `half` |
| `container.half_max_ratio` (Half Height Max) | 0.40 | cap of the half stop (0.25-0.40) |
| `container.dismiss_on_tap_outside` (Tap Outside Closes) | true | |
| `container.keep_audio_on_close` (Keep Audio Playing) | true | mini-player after close (Tier 4) |
| `kinds` (Block Library table) | every built-in kind enabled, default variants | per kind: `kind`, `enabled`, `default_variant`, `details` |

### 5.2 POI level: `POIData.card`

```json
"card": {
  "blocks": [
    { "key": "block_1", "kind": "header", "variant": "image_parallax", "display": "inline",
      "fields": [
        { "key": "title",    "text": [ { "lang": "en", "value": "St George's Castle" },
                                      { "lang": "pt", "value": "Castelo de Sao Jorge" } ] },
        { "key": "subtitle", "text": [ { "lang": "en", "value": "Military - c. 1700 on the panel" } ] },
        { "key": "image",    "asset": "castelo/hero.png" }
      ] }
  ]
}
```

- `key`: generated `block_N`, never shown, never reused (same identity rule as taxonomy rows,
  `TaxonomyRowKeys`).
- A POI with no `card` or an empty `blocks` list shows the header only (name + summary from the
  existing `name` / `summary` fields), so every existing POI keeps working with zero authoring.
- `POIData.name` and `summary` stay untouched: search and markers keep reading them.

### 5.3 Field types (`BlockFieldType`)

| Type | Stored in `BlockFieldValue` as | Editor draws |
|---|---|---|
| `LocalizedText` | `text: [{lang, value}]` | one single-line row per wall language |
| `LocalizedLongText` | `text: [{lang, value}]` | one multi-line area per language |
| `Number` | `number` | float field |
| `Toggle` | `flag` | toggle |
| `Choice` | `value` (one of the field's options) | popup |
| `Asset` (image/audio/video/model/captions) | `asset` (path under the wall's media root) | object field filtered by media type |
| `Items` (repeater) | `items: [BlockItemData]` (each item has its own text/number/asset/value) | table rows, add/remove/reorder |
| `PoiRef` | `value` (a POI id) | POI popup (existing `DrawReferencePopupField` pattern) |

`BlockItemData` holds its own keyed sub-fields, `fields: List<BlockItemFieldValue>`, each the shape of a
field value without nested items (a fact = label + value), so a quiz option, a fact, a gallery image, a
hotspot and a timeline event all reuse it. It cannot reuse `BlockFieldValue` itself: that type would contain
itself, which Unity's serializer cannot store. Languages are a list, not `en`/`pt`
fields, so ES/FR later is a data change (work plan: "add a translated string table, never find and
replace").

| Mode | Built here | Meaning |
|---|---|---|
| `inline` | yes | full block in the stack |
| `expandable` | yes | teaser in the stack, full view in a sheet/takeover |
| `takeover` | yes | opens straight to full screen |

## 7. How each block is built (the micro-cycle)

For EVERY kind, in this order; the next kind starts only when the previous one is proven:

1. **Definition** in `BuiltInBlocks`: fields, variants, family, display modes.
2. **Round-trip test**: an instance with every field filled survives `JsonUtility` save/load and the
   window's undo/redo (walked by reflection, like `SearchFilterEditorTabTests`).
3. **View** (`<Kind>BlockView`), styled only through `PoiCard.uss` + tokens.
4. **Phase A** (`40-testing.md` section 4.4, UI Toolkit recipe): (a) static check of the view in
   **UI Builder**; (b) add entries to `CardGalleryDefinitions` -- every variant x (short, long, missing
   optional field, missing media) -- and run the gallery scene. One data list drives the harness and
   the tests.
5. **Phase A tests** (`CardGalleryTests`, PlayMode): each entry builds, no text overflow at 390 px,
   text/background contrast >= 4.5:1 via `UIAccessibility`, tap targets >= 44 px, a render
   `Assets/Screenshots/Card_<kind>_<variant>.png` for the Tier 1 vision pass.
6. **Editor**: nothing to write -- the Card Content section draws the kind from its definition.
   Verify the rows by opening the window (drawing never writes: existing `DrawingNeverWritesTests`
   pattern).
7. **Fixture**: author the kind's content on `lamp` through the Editor window (section 8), save.
8. **Phase B test** (`PoiCardSceneTests`, real `LivingRoomScene`): select `lamp` through the bus,
   open full, the block is present in the authored order with the authored text.
9. **Docs**: `10-structure.md` tree entry for every new file; this file's status row.

## Design history

- 2026-09-26: catalog of ~70 block variants designed on the canvas; the developer chose to build the
  whole catalog now (framework goal: switch designs fast) rather than the work plan's six core kinds,
  accepting the scope risk noted in the work plan's risk register.
- 2026-09-26: data model option C (generic instance + schema) chosen over typed lists because the
  config is JsonUtility-only and apps must add kinds without Framework edits (section 3.1).
- 2026-09-26: fixture on existing POIs (`lamp` full, `lamp_military` short) instead of a separate Panorama config, to
  keep every existing test untouched.
- 2026-09-26 (steps 0-5 build): `BlockItemFieldValue` added (items need several keyed sub-fields; a recursive
  type is not serializable); `card_settings.media_resources_path` added (no field said where a wall's media
  lives); the sheet animates `height`, not `translate` (scroll viewport = visible part); the header is pinned
  outside the ScrollView; `TakeoverView` deferred to its first user (Tier 2); `BlockFieldDrawer` draws only the
  field types a registered kind uses (localized text today) with a guard test that fails for a kind whose type
  has no drawer; `SearchPanels.Card` removed (no reader left); `SafeAreaHelper.ApplyAsOffsets` moved out of
  `SearchUIHost` so both hosts share it; layout tokens `--ts-touch-target`, `--ts-grabber-*`,
  `--ts-sheet-top-gap` and `--ts-size-caption` added to the token set (`_3.3` section 2).
