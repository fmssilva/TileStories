# Marker Design (2.2.1)

The base marker symbol: background shape, category colour, icon, and how a developer configures
and tests all three. Split out of `_2.2_Marker_Design.md` on 2026-09-22 alongside `_2.2.2_Badge_Design.md`
and `_2.2.3_Outline_Design.md`, once the domain's runtime consolidation and editor cleanup were
verified. Sibling docs: `_2.2.2_Badge_Design.md` (the second symbol), `_2.2.3_Outline_Design.md`
(the status ring), `_2.2.4_Markers_Effects.md` (animated effects), `_5.1_Editor_Tab.md` (the POI
Editor window), `_2.2_Marker_Design_Archive.md` (the full historical build record — original spec,
audit rounds, the gallery build-out, the sun-square bug, background-shape/ring-extensibility work).

**Audience:** an agent or developer with full Unity Editor + project access and no chat history.
Everything in this file was re-derived from the code on disk and from real test runs on 2026-09-22.

## 2. Concepts

### 2.1 Background shape

One wall-level setting, `marker_shape`: `"circle" | "rounded_square" | "hexagon" | "diamond" |
"star" | "none"`. `"none"` hides the coloured backdrop entirely — the icon floats on the wall and
only the outline ring and badge remain (used by markers that want to read as "just an icon", not a
filled shape). A per-POI shape override is deliberately not offered: a consistent shape across the
whole wall is what makes a marker read as "a point of interest" rather than a random icon.

The status ring is deliberately **not** shape-matched: a dashed ring only has pre-made art for a
circle (`Runtime/UI/Markers/Rings/`). Pairing a non-circle shape with an outline mode still works —
the ring is always drawn as a circle regardless of the fill shape — which avoids needing a full
dash-ring asset set multiplied by shape count.

### 2.2 Category colour and icon

`category` is free-form wall data, forever — never hardcode a category switch statement anywhere
in this domain. Confirmed against the real `LivingRoom/config.json`: its categories (`"Royal
Government"`, `"religious"`, `"military"`, `"residential"`, `"economic"`, `"infrastructure"`) share
nothing with any other wall's taxonomy. `CategoryPalette.ResolveColor`'s fallback is a deterministic
hash of the category string, not a fixed lookup table, so *every* category renders distinctly with
zero authoring.

A wall can still hand-pick specific colours: `WallConfigData.category_styles` is an *optional*,
*additive* list (§3) — any category not listed still falls through to the hash/icon-library
fallback untouched. This is "automatic default + optional explicit override," not one or the other.

### 2.3 Custom symbol override

`has_custom_symbol` / `custom_symbol_key` on a POI replaces just the resolved icon key; the
category's fill colour, the outline ring, and the badge are all unaffected. This is the only
per-POI visual override this domain offers — everything else (shape, colour) comes from the
category or the wall.

## 3. Runtime implementation

### 3.1 Files

| File | Role |
|---|---|
| `Runtime/Core/WallConfigData.cs` | `marker_shape`, `badge_shape`, `marker_outline_mode`, `marker_use_badge`, `badge_corner`, `badge_size_ratio`, `ring_size_ratio`, `contour_spin_deg_per_s`, `marker_icon_library_resources_path`, `category_styles`. |
| `Runtime/Core/MarkerShape.cs` | The six background-silhouette values. |
| `Runtime/Core/MarkerOutlineMode.cs` | `Uniform` / `SameHue` / `PerType` / `None` (see `_2.2.3`). |
| `Runtime/Core/MarkerVisualsParser.cs` | String <-> enum parsing for shape/outline mode, `TryParseBadgeCorner`, `NormalizeLineStyle`. Every parse method logs once and falls back to a safe default; no method throws. |
| `Runtime/POI/CategoryPalette.cs` | Hash-based fallback colour/icon + `Configure`/`ClearOverrides` for wall-authored `category_styles`. |
| `Runtime/POI/MarkerVisualSettings.cs` | **New in this pass.** The wall-level marker look, resolved ONCE from `WallConfigData` by `Resolve(config, wallIconLibrary)`. `ApplyPalettes(config)` points every static palette (`CategoryPalette`, `BadgeCategoryPalette`, `StatusRamp`, `MarkerHierarchyResolver`) at the config in one call, including resetting `StatusRamp` to its defaults when a config has no outline levels (a config-swap could previously leave a *previous* wall's ramp active). `WallSession`, the editor's Scene rig, and the live Play Mode applier all build this the same way, so "what does this config mean visually" has exactly one answer. |
| `Runtime/POI/MarkerVisualResolver.cs` | **New in this pass.** Pure, static: `Resolve(POIData, MarkerVisualSettings) -> MarkerVisualState` (background/fill/icon/ring/badge decisions, as plain data — no sprites, no scene). Shared with `_2.2.2`/`_2.2.3` since the three domains' decisions are tightly coupled (an outline mode affects the badge fallback, a shape affects the badge backdrop). `MarkerView` only draws the returned state. |
| `Runtime/UI/Markers/MarkerView.cs` | `Initialise(anchor, settings, effects, effectDefaults, styleOverride)` — the one entry point every spawn path calls. `ReapplyVisuals(settings)` — swap in new settings on a running marker with no reveal restart (mirrors the existing `ReapplyEffects`). `ApplyVisuals()` calls `MarkerVisualResolver.Resolve` then only draws. |
| `Runtime/UI/Markers/MarkerCircleGlyphView.cs` | One reusable "coloured shape + centred icon" element — used at two sizes/positions for both Symbol and Badge (`_2.2.2`). |
| `Runtime/UI/Markers/MarkerCircleSpriteFactory.cs` | Shared source of runtime-generated circle/ring sprites. |
| `Runtime/UI/Markers/SpriteKeyLibrary.cs` | Generic `{key -> Sprite}` lookup, reused for icons, shapes, and ring line styles. |
| `Runtime/Core/WallSession.cs` | `RefreshVisualSettings()` (load + spawn + live all call it), `ApplyMarkerSettings(config)` (the live Play Mode seam). |

### 3.2 How a marker is spawned (`WallSession.SpawnPOIs`)

1. `RefreshVisualSettings()` loads the wall icon library from `Resources`, calls
   `MarkerVisualSettings.ApplyPalettes(config)`, then `MarkerVisualSettings.Resolve(config,
   wallIconLibrary)`. Called once here — not only in `LoadConfigCoroutine` — so `SpawnPOIs` is
   self-sufficient even if a test or tool injects `_config` directly without running `Awake`.
2. Each POI's `MarkerView.Initialise(anchor, _visualSettings, effects, _effectDefaults)` is called
   once at spawn.
3. `ApplyVisuals()` resolves the hierarchy style (size, label, effects — `_2.3`), then calls
   `MarkerVisualResolver.Resolve(poi, settings)` and draws the result: background shape and fill,
   icon, ring (`_2.2.3`), badge (`_2.2.2`).

### 3.3 Live Play Mode (`_5.1_Editor_Tab.md` §0 "PlayMode Live Config")

`LivePlayModeMarkerApplier` (Editor assembly only, `Editor/POIEditor/LivePlayModeConfig/`):
fingerprints every wall-level marker field plus the three taxonomy tables plus each POI's own
`category` / `badge_category` / `has_status` / `status_pct` / `status_unknown` /
`status_level_key` / `has_custom_symbol` / `custom_symbol_key` — explicitly **not** position,
facing, or `hierarchy_level_key` (those belong to the Orientation domain's own applier). On a
matching change, `WallSession.ApplyMarkerSettings(configCopy)` copies the wall-level fields,
re-applies the palettes, then calls `ReapplyVisuals` on every spawned marker after re-pointing its
`POIAnchor` at the copy's matching POI (so a per-POI edit — e.g. switching a POI's category — shows
up live too). The running wall always gets its own private copy; it can never mutate the window's
authoring `WallConfigData`.

animation, tap legibility); the Playmode guide states which edits are LIVE and which still need

## 8. Design history: why one domain became four files

Through the 2026-08-06 restructure (see the archive's own header), a single file,
`_2.2_Marker_Design.md`, covered marker, badge, outline *and* effects together, plus a long
"design principles" section shared across all three. Effects were split out first, into
`_2.2.4_Markers_Effects.md`, on 2026-08-06. On 2026-09-22 a deep audit and cleanup pass
(triggered by a developer request to verify the whole marker design domain end to end) found:

- A real, silent-data-loss bug in the outline mode picker (the old `free_colors` editor value —
  see `_2.2.3_Outline_Design.md` §1).
- The wall-level marker settings resolved three separate times across the codebase, with real
  drift risk.
- Legacy code (the `MarkerStyle` enum, the `marker_style` config field) still fully wired despite
  the split-mode fields (`marker_outline_mode`/`marker_use_badge`) having superseded it long ago.
- No shared, reusable pure decision logic — `MarkerView` made every visual call inline, at 943
  lines.
- No live Play Mode support for this domain (Effects and Orientation already had it).
- Marker/Badge/Outline editor rows still hand-built, not on the shared field-drawer helpers other
  sections already use.

Fixing all of this touched marker, badge and outline code in the same commits (they share the new
`MarkerVisualSettings`/`MarkerVisualResolver` runtime classes and the same
`POIEditorToolWindow.MarkerDesign.cs` editor file), which is also why the resulting docs are three
separate files (this one, `_2.2.2_Badge_Design.md`, `_2.2.3_Outline_Design.md`) rather than one:
each is genuinely a distinct developer-facing concept (what the marker looks like vs. its second
symbol vs. its condition ring), even though the code underneath is now more shared than it used to
be, not less. `_2.2_Marker_Design.md`, the pre-split file, was deleted once this section captured
its one piece of content not already covered elsewhere (everything else in it was navigation,
superseded by each split file listing its own siblings in its header).
