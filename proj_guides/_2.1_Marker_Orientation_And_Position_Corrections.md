## 2) Root cause, with the actual arithmetic

Two changes were made to `POI_Marker.prefab` that combine to produce
multi-meter-tall label text:

1. **The root's `localScale` was changed from `(0.15, 0.15, 0.15)` to
   `(0.3, 0.3, 0.3)`.** The original `_2.1_Marker_Orientation.md` plan (§4,
   point 4) explicitly said: *"Leave the root's own sizeDelta, localScale,
   Canvas, and CanvasScaler settings exactly as they are."* This was not
   followed.
2. **The Label's TextMeshPro `Font Size` was left at `24`, unchanged, after
   its `RectTransform.localScale` was correctly flattened from `(0.1,0.1,0.1)`
   to `(1,1,1)` per the plan.** The plan explicitly warned about exactly this:
   *"do not assume the old font size (24) is still correct once the
   compensating child scale is removed; verify visually."* This warning was
   not acted on.

TextMeshPro's `Font Size` field is a local-space unit, subject to the same
parent-scale multiplication as any other `RectTransform` value (`sizeDelta`,
`anchoredPosition`). That means the *effective* on-screen glyph height is:

```
effective glyph height = fontSize × Label.localScale.y × Root.localScale.y
```

**Before this stage** (working correctly): `24 × 0.1 × 0.15 = 0.36` -
roughly 36cm total label height, reasonable for a wall marker.

**Current state** (broken): `24 × 1 × 0.3 = 7.2` - roughly **7.2 meters**
per glyph. A single character 7 meters tall, rendered at the marker's
correct, unmoved real-world position, is what you are seeing - not a
misplaced marker.

The Symbol is affected the same way: `sizeDelta (0.12, 0.12) × localScale
(1,1,1) × Root.localScale (0.3) = 0.036m` (3.6cm) - small enough to be
completely hidden behind a 7-meter letter, matching "I can't even see the
actual marker sphere."

**Correction to the previous diagnosis:** the Canvas Scaler's "Reference
Pixels Per Unit" field, which the earlier fix proposal targeted, does not
control geometric size for a World Space canvas - per Unity's own
documentation, that field (together with the rest of the UI Scale Mode
settings) only affects pixel density/crispness for World Space canvases; the
actual world size is controlled purely by `RectTransform.sizeDelta ×
localScale` through the hierarchy. **Do not change the Canvas Scaler's
`Reference Pixels Per Unit` or `UI Scale Mode` fields as part of this fix -
they are not the cause, and changing them will not fix the size problem.**

## 4) The fix, with concrete values (not "tune visually" this time)

This supersedes the original plan's "leave root scale unchanged" instruction
in §4, point 4 - that instruction, followed literally alongside the font-size
oversight, is part of how this bug happened. Root cause: **two independent
scale multipliers (root scale and per-child scale) doing overlapping jobs is
inherently error-prone** - exactly the kind of compounding-magic-number chain
Stage 2.1's original plan (§2.2) was trying to eliminate in the first place,
just not completely enough. The cleanest fix removes the redundancy
entirely: make the root's scale the *only* multiplier in the whole marker,
set to a clean `1`, so every `sizeDelta` and `anchoredPosition` value in the
prefab directly means meters, with no second hidden multiplier to account
for.

**Apply these exact values:**

| Object | Field | Current (broken) | Set to |
|---|---|---|---|
| `POI_Marker` (root) | `localScale` | `(0.3, 0.3, 0.3)` | `(1, 1, 1)` |
| `Symbol` | `sizeDelta` | `(0.12, 0.12)` | **no change** - already correct once root is fixed (yields a 12cm circle) |
| `Symbol` | `localScale` | `(1, 1, 1)` | **no change** |
| `Label` | `sizeDelta` | `(0.25, 0.06)` | **no change** - already correct once root is fixed (25cm × 6cm text box) |
| `Label` | `localScale` | `(1, 1, 1)` | **no change** |
| `Label` | `anchoredPosition` | `(0, -0.07)` | **no change** for now - leaves roughly a 1cm gap below the Symbol's edge; note as a candidate for a small later adjustment (e.g. `-0.09`) but not required to fix the current bug |
| `Label` (TextMeshPro) | `Font Size` | `24` | `0.05` (starting point - see note below) |
| Canvas / `CanvasScaler` | any field | - | **do not change anything here** |

With these values: effective glyph height becomes `0.05 × 1 × 1 = 0.05` (5cm)
- reasonable for a wall marker viewed from a normal AR distance. Symbol
becomes a 12cm circle. Both numbers are now driven by exactly one scale
value (the root's `1`), so a future uniform resize (e.g. for hero-vs-
secondary importance) only ever requires changing that one field again.

**Note on the font size value (`0.05`):** this is a starting point derived
from the arithmetic above, not a value confirmed by visual inspection - the
implementing agent cannot see the rendered result, so this number should be
treated as "should be approximately right, needs human visual confirmation"
per §6, not as a guaranteed-final value. If the human confirms it reads too
large or too small, the correction is a straightforward multiply (e.g. "text
looks roughly double size" → try `0.025`) rather than a re-diagnosis.

## 6) Checks the implementing agent can do without seeing anything

These are all text/log/number based - no screenshots, no "does it look
right."

1. **Re-run the §3 log comparison after the fix.** `dist=` values must be
   identical to before the fix (they should not change at all, since nothing
   touched in §4/§5 affects position) - this confirms the fix didn't
   accidentally touch anything position-related.
2. **Arithmetic self-check.** After editing the prefab, re-open it and read
   back the actual saved values for `POI_Marker.localScale`, `Symbol.sizeDelta`,
   `Label.sizeDelta`, and `Label` font size. Recompute effective glyph height
   and effective symbol diameter using the formulas in §2, and confirm they
   land in a sane range: glyph height roughly `0.03`-`0.08` (3-8cm), symbol
   diameter roughly `0.08`-`0.20` (8-20cm). If either is wildly outside these
   ranges, something wasn't applied correctly - re-check before moving on.
3. **Compile check**, per guidelines §6: run the project through Unity batch
   mode, check the resulting log file for any `error CS` line before trusting
   anything else. No code changed in this fix (only prefab data), but confirm
   the project still compiles cleanly regardless, since a prefab edit made
   through a text/YAML editing path can occasionally corrupt a `.meta` GUID
   reference.
4. **Run the existing PlayMode test suite**, including
   `MarkerBillboard_CameraMoved_MarkerRotationMatchesCamera` (already present
   in `MarkerOverlapResolverTests.cs`, confirmed correctly written) and the
   three existing `MarkerOverlapResolver` tests. None of them touch prefab
   sizing, so all four should already be passing and should remain passing -
   if any fail, that's new information, not expected, and worth reporting
   rather than working around.
5. **Overlap-resolver regression, log-based.** Run the app with the
   `painting_1`..`painting_4` LivingRoom test POIs. `MarkerOverlapResolver`
   already logs its grouping decisions to the Console (grouped-marker count
   and IDs). Confirm the same POIs are grouped the same way as they were
   before this stage's work - this is a text comparison, not a visual one,
   and confirms the offset math itself is unaffected by the sizing fix
   (expected, since `MarkerOverlapResolver.cs` is untouched, but worth
   confirming rather than assuming).
6. **(Recommended, optional) Add an Editor-only sanity-check test** that
   loads `POI_Marker.prefab` via `AssetDatabase.LoadAssetAtPath` and asserts,
   in code, that the computed effective glyph height and effective symbol
   diameter (per the formulas in §2) fall within the sane ranges from check 2
   above. This is the kind of regression this exact bug represents - a scale
   value changed on one object without a dependent value on another object
   being updated to match - and a numeric guardrail test catches that class
   of mistake automatically in the future without needing anyone to look at
   a screen. Place it alongside `POIPositionResolverTests.cs` in
   `Assets/Framework/Tests/Editor/`, since it needs `UnityEditor.AssetDatabase`
   and therefore belongs in an Editor-only test assembly, not the Runtime
   PlayMode one.
