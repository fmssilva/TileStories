## 2. Concepts

### 2.1 The six effects

| Effect | Look | Config block (`effect_defaults`) | Chosen in the level table |
|---|---|---|---|
| Pulse | the symbol grows and shrinks smoothly (breathing) | `pulse` | Pulse checkbox |
| Ripple Rings | three thin rings flow outward one after another | `ripple_rings` | Ripple = `ripple_rings` |
| Ripple Discs | three filled discs flow outward one after another | `ripple_discs` | Ripple = `ripple_discs` |
| Halo Ring | one thin ring behind the symbol, breathing at steady brightness | `halo_ring` | Halo = `halo_ring` |
| Halo Disc | one soft filled disc behind the symbol, breathing | `halo_disc` | Halo = `halo_disc` |
| Beacon | one ring that grows and fades out, then restarts (a single outward wave) | `beacon` | Halo = `beacon` |

Naming logic (this replaced the confusing Sun / Accent names): **Ripple** = three waves (a layered effect),
**Halo** = one layer, **Beacon** = one outward wave. A level has two slots plus a flag:
one Ripple option (none / rings / discs), one Halo option (none / ring / disc / beacon), and Pulse on or off.
They stack: one Ripple + one Halo + Pulse can all run on the same marker. Within a slot the options are
alternatives (there is one `MarkerRippleEffect` and one `MarkerHaloEffect` per marker).

### 2.2 Definition vs assignment (the one rule to remember)

1. **Global Scene > Effects** DEFINES how each effect looks and which effects this wall uses.
2. **Global Scene > Hierarchy Levels** CHOOSES, per level: Ripple, Halo, Pulse, Rotate, reveal delay / duration.
3. **Every POI takes the effects of its hierarchy level** (`hierarchy_level_key`). There is no per-POI effect.
   A POI with no level gets the framework fallback: 12 cm, no label, no effects, 0.35 s reveal.

Only enabled effects are offered in the level dropdowns. A level that still points at a disabled effect
shows "(disabled)" and does nothing until the effect is ticked again (nothing is silently lost).

### 2.3 Switches

- `effects_enabled` (master, default true): off = no pulse / ripple / halo / beacon anywhere, and the animation margin is removed from the displacement radius. Also a "reduce motion" option. The reveal fade-in is separate. In the editor, switching it off only HIDES the rows below it; every value is kept and still saved, so a slip of the mouse loses nothing (test `TurningEffectsOffAndOn_KeepsEverySetting_ThroughSaveAndLoad`).
- `<block>.enabled` (per effect, default true): the effect's own checkbox in its foldout header. Off = its rows are hidden, it disappears from the level dropdowns, and markers that still request it ignore the request.
- Both are applied by `EffectDefaults.FilterEnabled(requested)`: master first, then each effect's checkbox. Rendering (`MarkerView.ActiveEffectFlags`) and the displacement radius (`GetVisualRadiusWorld`) both use it, so they cannot disagree.

## 3. Runtime implementation

### 3.1 Files

| `Runtime/UI/Markers/MarkerRippleEffect.cs` | Three staggered waves; `RippleStyle` Rings or Discs. |

| `Runtime/POI/MarkerHierarchyResolver.cs` | `EffectFlagsOf(level, logWarnings)`: the ONE parser of a level's `ripple_effect` / `halo_effect` / `pulse`. Unknown strings are ignored with a warning. `HierarchyStyle` carries size, label, effect flags, rotate, reveal delay and duration. |
| `Runtime/Core/WallConfigData.cs` | `EffectDefaults` (blocks, `FilterEnabled`, `IsEffectEnabled`, `SelectableEffects`) and `HierarchyLevelEntry` effect fields. |
| `Runtime/Core/WallSession.cs` | Passes `_config.effect_defaults` to every marker; after spawning POIs, delegates to `EffectsPreviewSpawner.TrySpawn` (section 6). |

### 3.2 How an effect is applied (`MarkerView.ApplyEffects`)

1. `ActiveEffectFlags` = the level's flags (from the resolved `HierarchyStyle`, or the `effects` parameter when no level resolved, e.g. the galleries), then filtered by `EffectDefaults.FilterEnabled`.
2. Pulse: `ApplyDefaults(pulse)` then `SetActive`.
3. Ripple: `SetStyle(Rings|Discs)` + `ApplyDefaults(ripple_rings|ripple_discs)` then `SetActive`. If both were somehow requested, rings win.
4. Halo: `Configure(symbol, Ring|Disc|Beacon)` + `ApplyDefaults(halo_ring|halo_disc|beacon)` then `SetActive`. Priority HaloRing > HaloDisc > Beacon.
5. Defaults are applied BEFORE `SetActive`, so the first `Update` tick already animates with them.

Each `ApplyDefaults` is a safe no-op when the block is null (the compiled-in `[SerializeField]` values are used) and clamps to the same limits as the Inspector attributes.

### 3.3 The animation maths (what the tests compare against)

- **Breathe** (Pulse, Halo Ring, Halo Disc): `scale = base * (1 + amplitude * (sin(2*pi*t/period) * 0.5 + 0.5))`, constant alpha for halos.
- **Sawtooth** (Beacon, each Ripple wave): `u = repeat(t/period, 1)`, `s = u*u*(3-2u)` (smoothstep), scale = lerp(start, end, s), alpha = lerp(alpha, 0, s). Ripple waves use `u = repeat(cycle - delay, 1)` with delays 0 / stagger / 2*stagger for inner / middle / outer.
- Ripple layer scale envelopes: inner 1.03 to 1.16, middle 1.10 to 1.36, outer 1.20 to 1.62 (hardcoded, not authorable). Beacon uses `start_scale` to `end_scale` from config.
- `t` is `Time.time`, so the phase depends on the absolute play time.

### 3.4 Sizing: layers are relative to the symbol

Every layer is sized in multiples of the symbol diameter (`MarkerEffect.SymbolDiameter`, read at `SetActive` time, after `MarkerView` has sized the symbol from the level's `size_cm`):

- Ripple layers: 0.8 / 1.0 / 1.2 symbol diameters (inner / middle / outer).
- Halo / Beacon: `size` (default 1.2) is a MULTIPLE of the symbol diameter.

This fixed a real flaw: layers used to be absolute (0.16 to 0.24 m), so on a 30 cm marker the halo was hidden behind the symbol and on a 7 cm marker it was about 3x too big. A 20 cm marker looks unchanged (1.2 x 0.2 m = the old 0.24 m). Proven by `EffectsKeepTheirLookRelativeToTheMarker_WhateverTheMarkerSize`.

### 3.5 Robustness rules built into the effects

- **Clamping (attributes only guard the Inspector, not values assigned from config):** period >= `MinPeriodSeconds` (0.1 s; a period of 0 used to give NaN scale and Unity rejected the assignment); pulse amplitude 0 to 0.45; ripple stagger 0 to 0.25, alphas 0 to 1; halo base alpha 0 to 1, breathe amplitude 0 to 0.4.
- **Authored scale is captured once.** `Configure` runs on every `Initialise`; re-reading the target's scale mid-animation used to bake the animated value in as the new base (the marker never shrank back). Test `ReInitialiseMidAnimation_DoesNotDriftTheBaseScale`.
- **Sprites** come only from `MarkerCircleSpriteFactory`. If ripples ever render as hard-edged squares, it is the stale static sprite cache surviving Play Mode sessions (archive section 18.12); do not re-derive the circle maths.
- **Unknown option strings** in a level are ignored (a warning), never a crash.

### 3.6 Reveal and Rotate (per level, not "effects" but configured beside them)

- **Reveal**: `MarkerRevealEffect.Play(delay, duration)` is called from `MarkerView.Initialise` with the level's `reveal_delay_s` / `reveal_duration_s`: the marker starts hidden (alpha 0, scale 0), waits the delay, then fades and scales in with smoothstep. In Edit Mode it snaps to full (coroutines do not tick). Test `RevealDelayAndDuration_OfTheLevel_DriveTheRealFadeIn` (plus the older `MarkerRevealEffectTests`). LivingRoom staggers levels 0 / 0.2 / 0.5 / 0.8 / 1.0 s.
- **Rotate** (`rotate_contour` per level): `ring.SetRotating(showRing && level.RotateContour)` makes the status ring spin. Only meaningful when the wall's outline mode is not `none`; the editor hides the checkbox otherwise. Covered by the `MarkerGalleryTests` rotate-contour rows.

### 3.7 Live updates in Play Mode (edit in the window, see it now)

While Play Mode runs, every change made in the POI Editor's Effects page (or the Hierarchy Levels effect columns, undo and redo included) reaches the running wall at once; no restart. Nothing is saved by this: the window keeps the edits (its config and "unsaved" flag survive Play Mode), and Save / Copy to StreamingAssets stay the permanent step.

- The mechanism is shared with the Orientation domain (`_2.1` section 13.5); its architecture, file list and the recipe for adding a domain are in `_5.1_Editor_Tab.md` section 0 > PlayMode Live Config. Effects only contributes `LivePlayModeEffectsApplier` and the runtime seams below.
- Where it lives: all of it in the Editor assembly, `Editor/POIEditor/LivePlayModeConfig/`, so no live-update logic can ever be compiled into a build. Runtime only offers two ordinary methods: `MarkerView.ReapplyEffects(EffectDefaults)` and `WallSession.ApplyEffectSettings(defaults, levels)`.
- Flow: `DrawConfigMutationScope` (and undo/redo) -> `LivePlayModeConfigPush.PushToRunningWall` -> `LivePlayModeConfigDispatcher` (applies only domains whose fingerprint changed; the first push to a new wall applies all) -> `LivePlayModeEffectsApplier.Apply` -> `WallSession.ApplyEffectSettings`: swaps in a private copy of `effect_defaults`, reconfigures the level resolver, re-applies effects on every spawned marker, rebuilds the Focus grid.
- The Effects fingerprint is `effect_defaults` plus ONLY each level's ripple / halo / pulse columns (`key=ripple/halo/pulse`); a facing, size or reveal edit does not re-push effects (an EditMode test caught it hashing whole levels).
- Re-apply keeps each effect's base scale, does not restart Reveal, does not rebuild visuals.
- Limit: only the Effects domain is wired. Marker, Badge, Outline and level size/label edits still need a restart (level size edits reach the resolver but not already-spawned markers).
- To add a domain (orientation, LOD...): one class implementing `ILivePlayModeApplier` next to the others, one line in `LivePlayModeConfigPush`, plus its tests in `LivePlayModeConfigTests`.
- Proof: `LivePlayModeConfigTests` (EditMode, real WallSession and markers), `EffectsPreviewSpawnerTests` (PlayMode: grid on/off/rebuild, effects re-applied), and a real Play Mode run through the window's own mutation scope (master off -> every marker showed no effect, on -> restored).

## 4. Configuration

### 4.1 `effect_defaults` (wall level, `WallConfigData.effect_defaults`)

Missing keys load as the defaults below; a missing `effect_defaults` block means everything on with the compiled-in values. Snake_case keys.

| Block | Fields (default) |
|---|---|
| (top level) | `effects_enabled` (true) |
| `pulse` | `enabled` (true), `amplitude` (0.18), `period` (1.6) |
| `ripple_rings`, `ripple_discs` (same shape, stored separately) | `enabled` (true), `period` (1.8), `stagger` (0.12), `inner_alpha` (0.55), `middle_alpha` (0.36), `outer_alpha` (0.2), `tint_color_hex` ("#F2CA71") |
| `halo_ring` | `enabled`, `size` (1.2, x symbol), `base_alpha` (0.28), `tint_color_hex`, `period` (2.0), `breathe_amplitude` (0.15), `outer_scale` (0.90), `inner_scale` (0.80) |
| `halo_disc` | `enabled`, `size` (1.2), `base_alpha` (0.28), `tint_color_hex`, `period` (2.0), `breathe_amplitude` (0.15), `radius_scale` (0.85) |
| `beacon` | `enabled`, `size` (1.2), `base_alpha` (0.28), `tint_color_hex`, `period` (2.0), `start_scale` (1.0), `end_scale` (1.8), `outer_scale` (0.90), `inner_scale` (0.80) |
| `preview` | `enabled` (false), `base_poi_id` ("" = plain grey circle). Dev-only, section 6. |

Why one block per effect (including two ripple blocks): a wall can give filled discs lower alphas than thin rings, or Beacon a slower period than a breathing ring. Shared parameters would make an edit to one effect silently change another.

### 4.2 Level fields (`hierarchy_levels[]`, `HierarchyLevelEntry`)

`ripple_effect` (`none|ripple_rings|ripple_discs`), `halo_effect` (`none|halo_ring|halo_disc|beacon`), `pulse` (bool), `rotate_contour` (bool), `reveal_delay_s`, `reveal_duration_s`, plus size / label / priority / facing override (see `_2.3`). LivingRoom (5 levels): level_1 = ripple discs + halo ring + pulse, level_2 the same, level_3 = ripple rings + halo disc + pulse, level_4 = halo disc + pulse, level_5 = beacon + pulse; all with rotate on.

### 4.3 Renames (2026-09-21, no compatibility layer; LivingRoom regenerated)

`sun_effect` -> `ripple_effect`, `accent_effect` -> `halo_effect`; `sun_contours/sun_circles` -> `ripple_rings/ripple_discs`; `ring_pulse/simple_sun` -> `halo_ring/halo_disc`; `effect_defaults.sun/accent` -> one block per effect; classes `MarkerSunEffect` -> `MarkerRippleEffect`, `MarkerAccentEffect` -> `MarkerHaloEffect`. Removed earlier (`_2.3` section 12): per-POI `is_hero`, `hero_icon_key` (custom symbols replaced it), `effect_mode`, per-POI `rotate_contour`. Old walls' `sun`/`accent` blocks would simply be ignored (defaults apply); LivingRoom's values equalled the defaults, so nothing changed visually.

### 4.4 Config discipline

`config.json` is always regenerated through the editor's Save (or a `JsonUtility.ToJson` round trip), never hand-edited: `JsonUtility` writes every field in the class's order. Play reads `Assets/StreamingAssets/<Wall>/config.json`, so edits need Save All to JSON + Copy to StreamingAssets before Play.

## 6. Focus on Effects Grid (dev-only preview)

**What it is:** in Play Mode (and development builds) the screen shows a labelled grid of REAL markers on a neutral background: row block 1 = "No effect" + one cell per effect (effects switched off are labelled "(off)"), row block 2 = one cell per hierarchy level with its real size, effects and reveal timing. Toggle: Global Scene > Effects > Test > **Focus on Effects Grid** (`effect_defaults.preview.enabled`, default off). **Base marker** dropdown: "Plain grey circle" or any POI of the wall (its category colour, icon, status, badge, and its level's size). While on, the real markers are hidden; untick to see the wall again. Release builds ignore the switch (`EffectsPreviewSpawner.IsAllowed(isEditor, isDebugBuild)`), so a config left on does nothing there.

**Why it works the way it does (three failed designs first):** world-space UI is depth-tested, so a grid placed near the wall is hidden by the room mesh, and any other wall can do the same. A grid 3.76 m in front (first version) and 1 m in front (second) were both hidden by the mesh. Moving the real camera is not an option (on a device its pose is owned by AR tracking). Final design:

- `EffectsPreviewSpawner` builds the grid `FarOffsetMetres` (5000 m) above the scene, where nothing else exists.
- `EffectsPreviewFocus` (on the grid root) owns a dedicated grid camera: same field of view, render target and viewport as the main camera, depth +100, solid neutral-grey clear (`EffectsPreviewSpawner.BackgroundColor`), far plane just behind the grid. The main camera's far plane never reaches 5000 m, so it draws nothing of the grid; the grid camera draws nothing of the wall.
- Fit: `FitDistance` gives the camera distance at which the grid fills the view; `ChooseColumns` picks the column count that needs the least distance (portrait = few columns, landscape = many). The component refits when the aspect ratio or field of view changes (resized Game view, rotated phone, AR zoom).
- The grid root copies the main camera's ROTATION each frame, so cells (which face the camera) and the layout stay upright when a phone rolls. Cells use screen-up orientation and ignore the wall's facing mode (a `yaw_only` or wall-fixed cell would show its label back to front).
- `WallSession.SpawnPOIs` delegates after spawning the real POIs and passes a callback that runs the real `MarkerView.Initialise` with the wall's own visual settings plus the cell's `HierarchyStyle` override, so the spawner needs no wall knowledge. The grid is reached from the real bootstrap path (tested).

Limits: focus mode hides the wall; the far offset assumes no main camera with a far plane beyond 5 km; 7 to 10 cm level cells are only a few pixels on a phone-size view (8 to 14 px radius at 600x680).

### 7.2 The render-test method (reuse it for any visual domain)

Checking viewport COORDINATES is not proof that something is visible (that is how a grid hidden behind the room mesh passed its first tests). `EffectsPreviewRenderTests` instead renders the cameras to a texture (portrait, like a phone), reads the pixels back and judges each cell from pixels: (1) symbol coverage against the known backdrop colour; (2) the effect's visible extent = pixels in the ring around the symbol (upper half only, so the label below does not count) that differ from the SAME grid rendered with every effect off; (3) best-vs-worst frame over about 2 s to prove animation; (4) an opaque wall 50 cm in front of the main camera stands in for the room mesh. A frame is saved to `Assets/Screenshots/effects_preview_grid_render.png` as evidence. Measured (best frame): Ripple Rings 1.45 to 1.53 symbol radii, Discs 1.50 to 1.57, Halo Ring 1.25, Halo Disc 1.18 to 1.19, Beacon 1.74 to 1.83, Pulse 1.17, "No effect" 0.

## 8. Design decisions and why

| Decision | Reason |
|---|---|
| Effects per hierarchy level, defined once on the Effects page | One place decides "how it looks", one place decides "who gets it"; no per-POI overrides to drift. |
| One parameter block per effect, plus per-effect enabled | Independent tuning; no hidden coupling; the wall developer defines a palette of the effects it uses. |
| Master switch keeps values and only hides rows | A mistaken click must not lose work; also the reduce-motion / weak-device switch. |
| Sizes in symbol diameters | The same effect must look right on every marker size (proven by render test). |
| Clamp at the point of use | `[Range]`/`[Min]` only guard the Inspector, never values assigned from config. |
| Layers in `MarkerCircleSpriteFactory`, no per-effect textures | Runtime-generated sprites; one domain-reload-safe cache. |
| Two components (Ripple, Halo) instead of six | One instance per marker per slot; options within a slot are alternatives. |
| Far-away grid with its own camera | Immune to any scenery on any wall; does not touch the real camera. |
| Focus grid in config, ignored in release builds | Works in development builds (a real device stress test) without shipping a dev feature. |
| Removed Glow and Particle effects | Never active, no prefab used them; re-add only with a real art path. |

## 9. Known limits and deferred ideas

**Limits:** ripple ring sizes (0.8 / 1.0 / 1.2 symbols) and the scale envelopes (section 3.3) are hardcoded, not authorable (exposing them would be speculative until a wall needs it). Halo Ring and Halo Disc are subtle with the default settings (thin rim, 18 to 25 percent outside the symbol at the breathing peak): raise Size, Base alpha or Breathe amplitude. Effect tints (gold at low alpha) are hard to see on a light wall photo. The editor rig calls `MarkerView.Initialise` without `effect_defaults` (Edit Mode shows no animation; only the displacement radius reads `effects_enabled`). Labels of REAL POIs under `yaw_only` can read mirrored when seen from behind (observed in the Game view; an Orientation-domain matter, not changed here).

**Deferred (do not build unless separately requested):** shimmer / gleam sweep across the icon (polish, needs the discovery-toast moment first); discovery burst (one-shot particle pop, needs a "first seen" flag in `POIData`); bob / float vertical drift (fights `MarkerOverlapResolver`, which assumes a fixed base position; needs its own design pass); heat-haze shader (GPU cost on mobile); a wall-wide "effect speed" multiplier or shared tint (considered, left out to avoid new inheritance rules); a header row with (i) buttons on the level table's effect columns.

## 10. How to add a new effect

1. Create a class inheriting `MarkerEffect` (override `SizeReference` if it sizes itself from the symbol).
2. Add a flag to `MarkerEffectFlags`, a case in `MarkerEffectNames.DisplayName`, an entry in `EffectDefaults.SelectableEffects` and `EffectDefaults.IsEffectEnabled`.
3. Add its parameter block (with `enabled`) to `EffectDefaults`.
4. Parse its option string in `MarkerHierarchyResolver.ParseEffectString` (via `EffectFlagsOf`) and add a level option to the editor arrays in `EffectsHelp.cs`.
5. Wire it in `MarkerView.ApplyEffects` (give it ITS block).
6. Add its foldout in `POIEditorToolWindow.Effects.cs` with (i) texts and a help constant that mentions the hierarchy-level link; add it to the guides.
7. Add a gallery row in `MarkerGalleryDefinitions`, then extend the tests: the reflection-driven round trip / undo tests pick the new fields up automatically; add its own parameter test to `MarkerEffectConfigTests`, extend the expected-name lists in the guide tests, and add it to the render tests' effect list.
