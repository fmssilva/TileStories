# TileStories - Stage 2.1: Marker Orientation

Domain owner doc for how markers, labels, badges and cluster aggregates are
ORIENTED (rotated) at runtime and in the Editor rig. Position, sizing, visual
encoding, LOD and displacement are other domains - see section 0.

**Status: fully implemented and verified.** This document describes the
current system as built and re-verified on disk on 2026-09-21 (compile: zero
`error CS`; latest full run after adding live Play Mode updates (section 13.5): EditMode 838/838, PlayMode 115/116 - the one failure is `OrientationWallSessionIntegrationTests.SpawnPOIs_RealMarker_SymbolIsTopmostRaycastTarget` (0 raycast hits, cause not yet found; it failed before any live-update work and fails with a focused Editor too); a real Play Mode check in
`Assets/Dev/OrientationGallery/OrientationGalleryScene.unity` confirmed every
Vertical Alignment / Facing Options combination behaves correctly under an
actual 45-degree camera roll, read directly off `transform.up`, not
eyeballed). Device verification (section 13, Tier 2) is the one item still
open and requires a human with hardware.

**Domain review (2026-09-24), verified with the runs in `_2.2.1_Marker_Design.md` section 1a:**

- [x] **Bug: `yaw_only` showed every marker from BEHIND** (mirrored labels, seen in the Game view on the
      LivingRoom scene, which ships with `yaw_only`). `ResolveRootRotation` built its yaw from the
      marker-to-camera direction, while a world-space uGUI canvas is read from the side its forward points

      earlier test stayed green because none asserted WHICH side faces the viewer:
      `ResolveRootRotation_CameraFacingModes_ShowTheReadableSideToTheCamera` now does, for all three

      (was "Facing column") and no longer names a wall scene, a code class or the gallery scene.

This is the second full design of this domain. The first (built the same
project, same month) used one flat `marker_orientation_mode` enum
(`screen_aligned | world_up | yaw_only | wall_fixed | none`) that conflated
two independent questions - which way is "up", and what the marker faces -
plus an exposed roll-snap/pitch-clamp configuration domain. A direct developer
usability pass on the shipped UI found the flat enum genuinely confusing to
reason about and the roll/pitch domain more configuration surface than any
real wall needed. This document describes the redesign that came out of that
review, replacing the first design wholesale rather than layering a migration
on top of it (first version of the project - no backward-compatibility
constraint).

## 1. Scope

**In scope:** every rotation applied at runtime or in the Editor rig to the
marker root, its Label, its Badge and cluster aggregates; the config and
Editor UI selecting between strategies; the Phase A harness proving them.

**Out of scope:** position resolution, displacement *decisions* (this domain
only touches `MarkerView`'s label-offset write-back, never the displacement
algorithm), visual encoding, hierarchy sizing, LOD banding, and the Ring's
`rotate_contour` spin (a local Z spin on the Ring child that composes with
everything here and needs no change).

---

## 2. Architecture: two orthogonal domains, not one enum

Every marker element's orientation is decided by answering two independent
questions:

1. **Vertical Alignment** - which direction counts as "up" for this element:
   the real world's gravity-up, or the phone screen's own up.
2. **Facing Options** - what the marker root actually points at: a fixed,
   painted-on-the-wall angle; a wall-glued tilt that only turns to follow the
   visitor left-right; or a full look-at-the-camera billboard.

These are genuinely independent - a marker can be `world_up` aligned and
`wall_fixed` facing (stays flat on the wall, upright relative to gravity,
never turns), or `screen_up` aligned and `always_facing_camera` facing (always
looks at the visitor, tilts with the phone). Label, Badge and cluster
aggregates each get their OWN Vertical Alignment choice (independent of the
root's), which is what makes "marker faces the camera, but the label stays
upright in the world" achievable without a third axis - it is just "root:
`always_facing_camera` + `screen_up` (or `world_up`), label:
`world_up` (or `screen_up`)".

A third, smaller domain, **Update Cost**, controls how often orientation is
re-resolved (a pure performance knob, orthogonal to both of the above). A
fourth section, **Test**, is Editor-only tooling to verify the other three
without guessing.

Two hardcoded (non-developer-exposed) implementation details support this
without adding configuration surface: a safety pitch clamp inside
`always_facing_camera` (section 4.2) and always-on rotation smoothing (section
5.1). Both existed as exposed, developer-configurable fields in the first
design of this domain; both are now fixed, sensible defaults instead, because
neither ever needed a second value in practice.

## 3. `ScreenUpWorld` - the screen-up primitive everything else builds on

```csharp
// Screen "up" as a world-space direction, read from the camera's real projection
// so it stays correct whether AR Foundation compensates for device rotation in the
// camera transform or in the display matrix. Never assume cam.transform.up.
public static Vector3 ScreenUpWorld(Camera cam)
{
    if (cam == null) return Vector3.up;
    float z = cam.nearClipPlane + 1f;
    Vector3 a = cam.ViewportToWorldPoint(new Vector3(0.5f, 0.5f, z));
    Vector3 b = cam.ViewportToWorldPoint(new Vector3(0.5f, 0.6f, z));
    Vector3 d = b - a;
    return d.sqrMagnitude > 1e-12f ? d.normalized : cam.transform.up;
}
```

**Do not assume which mechanism the SDK uses** for device-rotation
compensation (camera transform vs. display matrix) - deriving screen-up from
the camera's own projection is correct either way. This is the one piece of
math every `screen_up` alignment (root, label, badge, cluster) reads through.

## 4. Design: the option matrix

Framework rule: do not pick one strategy, ship all the good ones and let the
wall developer choose in the Editor.

### 4.1 Vertical Alignment

| Field | Values | Purpose |
|---|---|---|
| `vertical_alignment_mode` | `world_up` (default) \| `screen_up` | The marker root's own vertical alignment. `world_up`: stays upright against real-world gravity, turning the phone does not spin it. `screen_up`: always aligned to the phone's screen edges instead |
| `label_vertical_alignment_mode`, `badge_vertical_alignment_mode`, `cluster_vertical_alignment_mode` | `inherit` (default) \| `world_up` \| `screen_up` | Per-element override, independent of the root. `inherit` follows the root rigidly |
| `up_reference` | `world_gravity` (default) \| `spawn_root` \| `custom` | Which real-world vector `world_up` alignment actually means. `world_gravity`: `Vector3.up`, **no gyroscope needed** - ARKit's default `worldAlignment` is `.gravity` and ARCore's world space has +Y opposite gravity (section 14), so Unity world +Y already IS gravity-up. `spawn_root`: `WallSession.MarkerSpawnRoot.up` - use only if this wall's Immersal map was scanned at a tilt and isn't gravity-aligned. `custom`: the authored `custom_up_x/y/z` vector |

`MarkerOrientationResolver.ResolveVerticalUp(mode, screenUp, upReference)` is
the one function every element (root, label, badge, cluster) resolves its
"up" through, so `world_up`/`screen_up` mean exactly the same thing
everywhere - there is no second implementation to drift out of sync.

**Why not add a device-gyroscope up source?** Evaluated and rejected. The AR
world frame is already gravity-aligned by the SDK (see above), so a raw gyro
read would be a second, noisier source of the same fact - `up_reference`'s
three options already cover every real need (true gravity, a tilted map's own
up, or an explicit authored override).

### 4.2 Facing Options

| Field | Values | Purpose |
|---|---|---|
| `facing_mode` | `wall_fixed` \| `yaw_only` \| `always_facing_camera` (default) | What the marker points at |
| `facing_basis` | `view_plane` (default) \| `camera_position` | Only meaningful for `always_facing_camera`. `view_plane`: every marker parallel to the camera's near plane, no perspective skew. `camera_position`: each marker's forward points away from the camera individually - reads more physical for large markers, slight skew off-centre |

- **`wall_fixed`**: `Rotation = parentRotation * authoredLocalRotation`, using
  the POI's authored `editor_rotation_x/y/z_deg` (Specific Marker tab's
  Facing row, section 7) unchanged. Never moves at runtime regardless of
  camera. Ignores `vertical_alignment_mode` entirely - the authored angles
  ARE the alignment.
- **`yaw_only`**: keeps the authored X/Z wall tilt exactly as painted, and
  replaces only Y (yaw) every frame with a live camera-facing value, computed
  by projecting the camera-to-marker direction (so the forward points AWAY from the camera, the side a
  world-space canvas is read from), expressed in the PARENT's frame (the yaw is composed as a local
  rotation, so a world yaw would count a rotated parent's yaw twice), onto the plane perpendicular to
  the resolved vertical-alignment up, then taking that look rotation's own Y
  Euler angle (the same "Y = yaw, composed outermost" convention the Specific
  Marker tab's yaw slider and `PoiRotationResolver.ToEulerQuaternion` already
  use). A marker painted on a tilted wall stays glued to that wall's plane in
  X/Z, but still turns left/right to face the visitor. Camera roll has zero
  effect (regression-tested: `MarkerOrientationResolverTests.
  ResolveRootRotation_YawOnly_KeepsAuthoredXZTilt_RegardlessOfCameraRoll`,
  `OrientationGalleryTests.Entry5_YawOnly_RollHasNoEffect`).
- **`always_facing_camera`**: full look-at billboard using
  `vertical_alignment_mode` for its up and `facing_basis` for its forward. A
  hardcoded, non-developer-exposed safety clamp
  (`MarkerOrientationResolver.AlwaysFacingCameraMaxPitchDeg = 80f`) stops a
  marker swinging to a near edge-on angle when a visitor stands very close to
  or almost directly below/above it - the one real failure mode a fuller,
  exposed pitch-clamp configuration domain would have existed for.

There is no `"none"` facing mode. It would be exactly equivalent to
`wall_fixed` with the POI's authored angles left at their seeded `(0,0,0)`
default, so it would add a redundant option rather than a distinct behaviour.

**Degenerate-input guard** (`always_facing_camera` and `yaw_only` only):
when the view direction is nearly parallel to the up reference (e.g. looking
straight down at a `world_up` marker), a raw `Quaternion.LookRotation` would
produce garbage. `ResolveRootRotation` detects this
(`Mathf.Abs(Vector3.Dot(fwd.normalized, up.normalized)) > 0.999f`, about 2.6
degrees from parallel) and returns `Resolved = false`; the caller
(`MarkerBillboard`) then keeps the previous frame's rotation rather than
snapping to identity. This is a genuinely different case from the pitch clamp
above - the clamp handles steep-but-valid angles (up to ~87 degrees before
this guard takes over); see `MarkerOrientationResolverTests.
ResolveRootRotation_AlwaysFacingCamera_NearCameraDoesNotFlipEdgeOn`'s own
comment for the exact boundary math.

### 4.3 Per-hierarchy-level override

`HierarchyLevelEntry.facing_mode_override` (empty string = inherit the wall
setting) lets any one hierarchy level's markers use a different Facing
Options mode than the wall default - a framework default suggestion (not a
fixed rule) is to keep a wall's most important tier `always_facing_camera`
for legibility while lower tiers use `wall_fixed` so they read as part of
the wall; which level counts as "most important" and how many tiers exist is
entirely up to each wall's own hierarchy design (`_2.3_Marker_Hierarchy.md`).
It fits the existing architecture exactly - `HierarchyLevelEntry` already carries
per-level `rotate_contour`, `size_cm`, `show_label` and effect flags - and it
is one string field plus one lookup (`MarkerHierarchyResolver.
ResolveFacingModeOverride`), not a new system. Vertical alignment has no
per-level override - only Facing Options genuinely needed one; per-POI
overrides remain out of scope (section 12: the hierarchy level is the right
granularity and already exists).

### 4.4 Update Cost

| Field | Purpose |
|---|---|
| `update_mode` = `every_frame` (default) \| `interval` \| `on_camera_delta` | Thermal budget. 150 markers times per-frame quaternion work is the one real cost here. **`every_frame` is the recommended default**: `interval`/`on_camera_delta` throttling can leave the root's rotation stale for a moment relative to the label/badge displacement system's own per-cycle roll compensation (`MarkerView.ApplyLabelOffset`, section 10), producing a visible position mismatch after a fast camera turn. The CPU cost of `every_frame` is negligible even at 150 markers; only switch away from it if a real profiling pass on a dense wall shows a need |
| `update_interval_s` (0.05), `camera_delta_deg` (0.5) | Parameters for the two non-default modes |

**`LateUpdate` is not an option and must not become one.** The camera's final
pose for the frame is only known after every `Update` has run; writing
rotation in `Update` uses last frame's camera pose and produces a one-frame
lag that reads as swimming markers. `LateUpdate` is the only rotation write in
`MarkerBillboard`. Do not add an `Update()` write-back.

### 4.5 What was deliberately cut, and why

The first design of this domain also exposed: `roll_snap_mode` (`none` /
`quarter_turns` / `screen_orientation`) with a hysteresis field, an exposed
`clamp_pitch_enabled` + `max_pitch_deg` pair, an exposed
`rotation_smoothing_time_s` (default 0 = instant), and a `badge_corner_mode`
(`inherit` / `screen_fixed`) that re-rotated the badge's anchored position to
hold a fixed screen corner as the root rolled. All four were built, tested and
working - they were cut for being configuration surface without matching
demand for a first version, not because they were broken:

- Roll snapping deleted entirely - "just rotate smoothly" was the explicit
  goal; no quarter-turn snapping, no screen-orientation-locked snapping.
- Pitch clamping kept, but hardcoded (section 4.2) instead of exposed - the
  one real protection it provided is still there, just not a developer
  decision.
- Rotation smoothing kept, but hardcoded (section 5.1) - always on, no
  instant-vs-smoothed toggle.
- Badge corner holding deleted - the badge's screen position simply goes
  wherever the root's own rotation naturally puts it, like every other child.
  "Keep it simple: the badge always stays in the same position relative to
  the marker" was the explicit design instruction this replaced it with.

## 5. `MarkerOrientationResolver` - the pure core

Stateless and static so every decision is Tier-0 testable with no scene
running. Everything it needs is passed in; it hands back a result struct and
remembers nothing between calls.

```csharp
public struct OrientationResult
{
    public Quaternion Rotation; // the world rotation to write
    public bool Resolved;       // false = degenerate input; caller keeps its previous rotation
}

public static class MarkerOrientationResolver
{
    public static Vector3 ScreenUpWorld(Camera cam);                                   // section 3
    public static Vector3 ResolveVerticalUp(string mode, Vector3 screenUp, Vector3 upReference); // section 4.1

    public static OrientationResult ResolveRootRotation(
        OrientationSettings settings, string facingModeOverride,
        Vector3 markerWorldPos, Vector3 camPos, Vector3 camForward,
        Vector3 screenUpWorld, Vector3 upReference,
        Quaternion parentRotation, Quaternion authoredLocalRotation);                    // section 4.2

    public static Quaternion ResolveChildLocalRotation(
        string childVerticalAlignmentMode, Quaternion rootWorldRotation,
        Vector3 screenUpWorld, Vector3 upReference);                                     // pure Z counter-rotation

    public static float RootRollDeg(Quaternion rootWorldRotation, Vector3 screenUpWorld); // used by children + section 10
    public static Vector2 Rotate2D(Vector2 v, float degrees);                            // used by section 10
    public static Quaternion ClampPitch(Quaternion target, Vector3 upReference, float maxPitchDeg);
    public static bool ShouldUpdate(OrientationSettings s, float secondsSinceLastUpdate, float cameraAngleDeltaDeg);
    public static Vector3 ResolveUpReference(OrientationSettings s, Transform spawnRoot);
}
```

`ResolveChildLocalRotation`: desired up is `ResolveVerticalUp(childMode,
screenUp, upReference)`; the angle is `Vector3.SignedAngle(rootWorldRotation *
Vector3.up, desiredUp, rootWorldRotation * Vector3.forward)`, returned as
`Quaternion.Euler(0, 0, angle)`. Pure Z, so it never disturbs
`anchoredPosition` - this is what lets a label counter-rotate for legibility
without ever touching displacement's own offset math (section 10).

## 6. Runtime components

### 6.1 `MarkerBillboard` (on `POI_Marker`'s root)

```
Fields: OrientationSettings _settings; string _facingModeOverride; Transform _spawnRoot;
        Quaternion _authoredLocalRotation; MarkerChildOrientation[] _children (cached);
        float _lastUpdateTime; Vector3 _lastCamForward; bool _hasLastCamForward;
        bool _hasResolvedOnce (section 6.2).

Configure(settings, facingModeOverride, spawnRoot): the ONE entry point. Called by
  WallSession.SpawnPOIs at runtime, the Editor rig path (section 8), and the gallery
  harness/tests. Never called per frame. Snapshots transform.localRotation as the
  "authored" rotation wall_fixed uses fully and yaw_only uses partially (X/Z).
  Resets _hasResolvedOnce to false (section 6.2).

Awake(): cache Camera.main; if null, log a warning and disable (a genuinely
  expected state for isolated gallery/pipeline tests spawning outside any
  camera-tagged scene, not an invariant violation - no Debug.Assert here).

LateUpdate() ONLY - no Update():
  1. ShouldUpdate gate; if false, return (children are not ticked either).
  2. screenUp = ScreenUpWorld(camera); upRef = ResolveUpReference(settings, spawnRoot).
  3. result = ResolveRootRotation(...).
  4. if resolved: write rotation (section 6.2 for the snap/smooth split); else keep previous.
  5. Tick each cached child with the FINAL root rotation for this frame.
```

### 6.2 Snap-on-first-resolve, smooth thereafter

Rotation smoothing (0.12 second exponential damping against AR pose jitter,
`Quaternion.Slerp(current, target, 1f - Mathf.Exp(-Time.deltaTime /
0.12f))`) is always on and not developer-exposed. But the VERY FIRST resolve
after a `Configure()` call snaps directly to the target instead of smoothing
from whatever rotation the object happened to have: a freshly spawned or
reused marker must show its correct orientation on its first visible frame,
never visibly rotate in from an arbitrary starting pose. This matters
specifically for pooled cluster views (section 6.4), which get `Configure()`
called again on reuse with a completely different aggregate - without the
reset, they would visibly swing from the previous cluster's rotation toward
the new one instead of appearing instantly correct.

```csharp
if (result.Resolved)
{
    transform.rotation = _hasResolvedOnce
        ? Quaternion.Slerp(transform.rotation, result.Rotation, 1f - Mathf.Exp(-Time.deltaTime / RotationSmoothingTimeS))
        : result.Rotation;
    _hasResolvedOnce = true;
}
```

### 6.3 `MarkerChildOrientation` (one on Label, one on Badge)

Holds a single `_verticalAlignmentMode` string (`inherit` by default), set by
`MarkerBillboard.Configure`. `Tick(rootWorldRotation, screenUpWorld,
upReference)` sets `transform.localRotation` from
`ResolveChildLocalRotation(...)` and does nothing else - no anchored-position
rewriting (section 4.5: badge corner holding was removed). Costs one string
comparison when the mode is `inherit`.

### 6.4 Clusters

`POI_Cluster.prefab` carries `MarkerBillboard` too. Clusters are dynamic LOD
aggregates with no authored per-POI rotation, so their facing is HARDCODED to
`always_facing_camera` - never configurable or inherited - and only their
vertical alignment is developer-choosable, via `cluster_vertical_alignment_mode`
(`inherit` = the wall's own `vertical_alignment_mode`). `LODController.
EnsureSettings` computes this effective `OrientationSettings` once per config
change (not per spawn - cluster views are pooled and reused):

```csharp
string clusterVerticalMode = _orientationSettings.cluster_vertical_alignment_mode == "inherit"
    ? _orientationSettings.vertical_alignment_mode
    : _orientationSettings.cluster_vertical_alignment_mode;
_effectiveClusterOrientation = new OrientationSettings(_orientationSettings)
{
    vertical_alignment_mode = clusterVerticalMode,
    facing_mode = "always_facing_camera"
};
```

Newly instantiated cluster views (the `isNew` branch of the spawn path) get
`Configure(effectiveClusterOrientation, modeOverride: "", spawnRoot)` called.

## 7. Config schema

In `WallConfigData.cs`, mirroring `DisplacementSettings`' own pattern (same
`[Serializable]` class, `= new()` field on `WallConfigData`, copy
constructor):

```csharp
[Serializable]
public class OrientationSettings
{
    // --- Vertical Alignment ---
    public string vertical_alignment_mode = "world_up";        // world_up | screen_up (marker root)
    public string label_vertical_alignment_mode = "inherit";   // inherit | world_up | screen_up
    public string badge_vertical_alignment_mode = "inherit";   // inherit | world_up | screen_up
    public string cluster_vertical_alignment_mode = "inherit"; // inherit | world_up | screen_up
    public string up_reference = "world_gravity";              // world_gravity | spawn_root | custom
    public float custom_up_x = 0f, custom_up_y = 1f, custom_up_z = 0f;

    // --- Facing Options ---
    public string facing_mode = "always_facing_camera";
        // wall_fixed | yaw_only | always_facing_camera
    public string facing_basis = "view_plane";                 // view_plane | camera_position (always_facing_camera only)

    // --- Update Cost ---
    public string update_mode = "every_frame";        // every_frame | interval | on_camera_delta
    public float update_interval_s = 0.05f;
    public float camera_delta_deg  = 0.5f;

    // --- Test ---
    public bool edit_mode_preview_enabled = true;   // Scene-Mode Preview, ON by default

    public OrientationSettings() { }
```

### 8.1 Specific Marker tab - the "Facing" row

Inside each POI's Position foldout (`PositionTabs.cs`), three "Facing X / Y / Z"
rows (named to match the global Orientation section's own Facing Options
domain, not "Rotation") carry 0-360 sliders wired to
`POIData.editor_rotation_x_deg / editor_rotation_deg (Y) / editor_rotation_z_deg`.
The sliders carry no per-mode logic: the developer picks which axes matter. They
sync live in both directions with Unity's Scene-view Rotate tool AND the
Inspector Transform (Scene mouse events plus a ~10 Hz `OnInspectorUpdate` poll,
both through `MarkerSceneEdit.cs`). Sync compares ORIENTATIONS
(`PoiRotationResolver.IsSameOrientation`), never raw euler triples, because
`eulerAngles` returns an equivalent but different triple for e.g. X=100.
The first row's `(i)` help button explains which `facing_mode` values consume
which angles at runtime (section 4.2).

**Verified locks facing too (changed 2026-09-18; earlier versions left facing
free).** While a POI is Verified the sliders are disabled, and any Scene-view or
Inspector rotation snaps back to the stored angles with a non-blocking Scene-view
notice (same revert-on-edit mechanism as the position lock). Defaults: the first
POI starts at (0,0,0); the row `+` copies all three angles from the source POI.
Moving or rotating a marker in the Scene view auto-reveals its section (Specific
Marker tab, POI expanded, Position foldout open, scrolled into view) once per
selected marker, and also when the edit was blocked by the lock or overridden by
the preview (a Move/Rotate handle drag counts as the gesture). Tests:
`PoiFacingLockAndSyncTests.cs`, `PoiFacingModesAndLifecycleTests.cs`.

**Scene-Mode preview warnings (`FacingEditAdvice.cs`).** With `edit_mode_preview_enabled`
ON, a Facing edit that the effective facing mode (the POI's hierarchy-level
override, else the wall's) overrides queues an `EditorNotice` (shown as a native OK dialog after a 0.5 s quiet period so it never opens mid-drag): every axis in
`always_facing_camera`, only Y in `yaw_only`, nothing in `wall_fixed`. Unknown
mode strings behave as `always_facing_camera`, matching the resolver. A test
checks the warning against the real preview pipeline on a real `POI_Marker`
prefab, so it can never claim an axis is inert when it is not. Under preview the
Rotate gizmo is a real edit only in `wall_fixed` (there the preview shows the
authored angles untouched); elsewhere its output is overwritten by the preview.

**Messages:** every short developer-facing message in the POI Editor (verified lock, preview warnings, "nothing to clear", invalid path, rejected rename, missing rig) goes through `EditorNotice` -> native `EditorUtility.DisplayDialog` (OK). Decisions that need a return value stay `EditorUtility.DisplayDialog`.

**Bug fixed 2026-09-18:** `POIEditorToolWindow.OnDisable` did not unsubscribe
`HandleSceneGui`, so a closed window's handler kept running with its stale config
snapshot (e.g. a POI still verified there), reverting rotations and showing the
verified warning while the live window said unverified.

## 9. Scene-Mode preview (`RigLifecycle.cs`)

(UI label "Scene-Mode Preview"; formerly "Edit-Mode Preview". The config key stays
`edit_mode_preview_enabled`.) **Scene view only:** no runtime code reads this flag,
so it has no effect in Play Mode or on a device, where `MarkerBillboard` always
runs for real.

An `edit_mode_preview_enabled` toggle. When on, `HandleOrientationPreviewSceneGui`
runs `ApplyOrientationPreview(sceneView.camera)` on every
`SceneView.duringSceneGui` repaint: one `MarkerOrientationResolver.
ResolveRootRotation` call per rig child, using the SAME resolver the Play-Mode
path (`MarkerBillboard.LateUpdate`) uses - never a parallel implementation. It
then ticks each child's `MarkerChildOrientation` (Label, Badge) against the
root's final rotation (`TickPreviewChildren`), so Label/Badge vertical
alignment is visible too. It deliberately does NOT call `MarkerBillboard.
Configure`, which would snapshot the preview rotation as the "authored" one.

**What the preview cannot show** (say so in the guide, do not treat as bugs):
cluster aggregates (LOD-only, runtime), Update Mode / Interval / Camera Delta
(need frames and time), the 0.12 s smoothing, and any roll-dependent behaviour
(the Scene camera cannot roll, so World Up and Screen Up look identical at zero
roll -- test in Play Mode with Z/C).
This lets a developer see what `world_up`/`yaw_only`/etc. will look like
without entering Play Mode. Nothing animates here (`MonoBehaviour.LateUpdate`
does not tick in Edit Mode) - this checks the static result at the Scene
camera's current angle only, which is expected, not a bug.

**The guard that prevents this from corrupting authored data:** the rig's
children are real, persistent scene GameObjects, and two other code paths
normally read a rig child's `localRotation` back into
`editor_rotation_x/y/z_deg` (`HandleSceneGui`'s `SyncPoiRotationFromScene`,
unconditional; and `CapturePositions`'s rotation-capture block, on save).
Both now early-return while preview is active, and
`RestoreRigRotationsFromConfig()` restores every rig child's `localRotation`
from the stored config angles the moment preview switches off - so a preview
session can never leave the rig showing a rotation the developer never
actually authored, and never gets silently captured as if they had.

`wall_fixed` mode is the one case where Edit Mode and Play Mode agree
exactly (the authored angles ARE the runtime angles either way) - tested
directly, not just documented.

## 10. The one coupled domain: `MarkerView.ApplyLabelOffset`

`_2.5_Displacement.md`'s label-offset write-back is the ONLY code outside this
domain that depends on the root's rotation. `screenOffsetPx` (a screen-space
pixel offset) is converted to a local-space `anchoredPosition` delta; that
conversion is only trivially correct (root-local X/Y == screen X/Y) when the
root has zero roll relative to the screen. In every other case:

```csharp
float rollDeg = MarkerOrientationResolver.RootRollDeg(transform.rotation, screenUpWorld);
Vector2 localOffset = MarkerOrientationResolver.Rotate2D(worldOffset, -rollDeg);
// write localOffset (not worldOffset) into anchoredPosition
```

`rollDeg` is 0 whenever the root is effectively screen-aligned (e.g.
`vertical_alignment_mode == "screen_up"` with `always_facing_camera`), so the
expression reduces to the simple case exactly then. Tested at both roll 0
(`ApplyLabelOffset_UnrolledCamera_ScreenOffsetMatchesRequest`) and a
45-degree-rolled `world_up` camera
(`ApplyLabelOffset_WorldUpWithRolledCamera_ScreenOffsetStillMatchesRequest`).

**Label and badge ROTATION need no displacement change at all.** Overlap is
point+radius, `anchoredPosition` is applied before the child's own rotation,
and leader lines are world-space. Only the root's roll, via the one call site
above, matters to displacement.

**This is exactly why `update_mode` defaults to `every_frame` (section 4.4).**
If the root's rotation write is throttled but `ApplyLabelOffset` reads
`transform.rotation` on its own LOD-cycle schedule, the two can briefly
disagree after a fast camera turn, producing a visibly wrong label offset
until the next orientation update lands. This was found and diagnosed by
direct developer observation before being traced to its root cause here.

### 13.5 Live updates in Play Mode (tune orientation while the wall runs)

While Play Mode runs, every change in Global Scene > Orientation (all four sub-sections) and every level's Facing override in the Hierarchy Levels table reaches the running markers and clusters at once, undo and redo included. No Save / Copy / restart. Nothing is saved by it: stop Play and the edits stay in the window; Save All to JSON + Copy to StreamingAssets keeps them (next Play reads that copy). The whole mechanism and how to add another domain: `_5.1_Editor_Tab.md` section 0 > PlayMode Live Config.

What happens on a push (`LivePlayModeOrientationApplier` -> runtime):
- `WallSession.ApplyOrientationSettings(settings, levels)` swaps the wall's `orientation_settings` for a private copy, reconfigures the level resolver, and calls `MarkerBillboard.ReapplySettings(settings, thatLevelsFacingOverride)` on every spawned marker. Label and Badge modes are re-handed to their `MarkerChildOrientation`.
- `LODController.ReapplyClusterOrientation()` recomputes the effective cluster settings (forced `always_facing_camera`, vertical alignment from `cluster_vertical_alignment_mode` or inherited) and re-points every cluster already on screen. New clusters pick them up on spawn.

Why `ReapplySettings` and not `Configure` again: `Configure` snapshots the marker's CURRENT rotation as its "authored" rotation (what `wall_fixed` and `yaw_only` use). After the first frame that rotation is the already-rotated one, so calling it again would silently lose the authored rotation. `ReapplySettings` keeps the authored rotation and the spawn root, keeps the smoothing state (the change glides in over the usual 0.12 s constant instead of snapping), and forces the next `LateUpdate` to re-resolve so `interval` / `on_camera_delta` update modes do not delay the change until the next tick or a camera move.

Also live: each POI's own Facing X/Y/Z (the authored rotation): the applier fingerprints it and calls `WallSession.ApplyPoiFacing`, which hands every running marker its new authored rotation through `MarkerBillboard.SetAuthoredLocalRotation` (Configure cannot be reused: it would snapshot the current, camera-resolved rotation). Nothing in this domain needs a restart.

Proof:
- PlayMode `OrientationLiveUpdateTests` (real markers, real frames): world_up <-> screen_up on a rolled camera (marker up vector vs `ScreenUpWorld`); Label alone follows screen_up while the root stays world_up; wall_fixed -> always_facing_camera -> wall_fixed returns exactly to the authored rotation; a level override affects only that level's markers; an `on_camera_delta` change is applied with a still camera (verified red with the force flag removed, 35 degrees off); the marker points at the caller's copy and a null push is ignored; a real cluster from `LODController` follows a live vertical-alignment change.
- EditMode `LivePlayModeConfigTests`: every `OrientationSettings` field (walked by reflection) and the levels' facing override change the fingerprint, effects / size / name edits do not; a push repoints real markers with their own level override and leaves effects untouched.
- Real run: in LivingRoomScene Play Mode, the window's own mutation scope set `facing_mode` yaw_only -> wall_fixed -> yaw_only and the running marker's settings followed both ways.

## 15. Build/verification history (for provenance only - not current design)

One environment issue is worth recording here rather than only in a session
