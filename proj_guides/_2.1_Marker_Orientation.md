## 3. The problem being solved

Reported symptom: turning the phone to landscape rotates markers AND labels on
screen, so the visitor must tilt their head to read them.

Cause: `cam.transform.rotation` aligns the marker to the **camera transform's**
up. AR Foundation may compensate for device screen rotation in the display or
projection matrix rather than in the camera transform, in which case camera-up
and screen-up diverge by 90 degrees and the marker tips over. `MarkerView.cs`
line ~550 asserts in a comment that root-local X/Y "ARE screen X/Y by
construction" - true only when the two coincide.

**Do not assume which mechanism the SDK uses.** Derive screen-up from the
camera's own projection, which is correct either way:

```csharp
// Screen "up" as a world-space direction, read from the camera's real projection
// so it stays correct whether AR Foundation compensates for device rotation in the
// camera transform or in the display matrix. Never assume cam.transform.up.
public static Vector3 ScreenUpWorld(Camera cam)
{
    if (cam == null) return Vector3.up;
    float z = cam.nearClipPlane + 1f;
    Vector3 a = cam.ViewportToWorldPoint(new Vector3(0.5f, 0.5f, z));
    Vector3 b = cam.ViewportToWorldPoint(new Vector3(0.5f, 0.6f, z));
    Vector3 d = b - a;
    return d.sqrMagnitude > 1e-12f ? d.normalized : cam.transform.up;
}
```

Making the default mode `LookRotation(cam.transform.forward, ScreenUpWorld(cam))`
reproduces today's look exactly when the screen is unrotated and MAKES
`_2.5_Displacement.md`'s stated invariant true rather than merely usually true.
It is a bug fix, not a redesign - which is why it is Block 1, before any feature.

## 4. Design: the option matrix

Framework rule: do not pick one strategy, ship all the good ones and let the wall
developer choose in the Editor. Two orthogonal axes rather than one fat enum,
which is what makes "markers up in screen, labels up in world" fall out for free.

### 4.1 Marker root modes

| `marker_orientation_mode` | Rotation | When a wall wants it |
|---|---|---|
| `screen_aligned` (default) | `LookRotation(fwd, screenUp)` | Maximum legibility; marker plane always parallel to the near plane, never foreshortens. Today's intent, fixed |
| `world_up` | `LookRotation(fwd, upRef)` | Faces the viewer but stays upright in the real world, so turning the phone does not spin it. Also never foreshortens |
| `yaw_only` | Rotate about `upRef` only; `fwd` = view direction projected onto the plane perpendicular to `upRef` | Classic cylindrical billboard, most "physical". Foreshortens when looking steeply up or down - only sensible on short walls |
| `wall_fixed` | `parentRotation * authoredLocalRotation` from the POI's `editor_rotation_x/y/z_deg` | Marker painted flat onto the wall surface. Makes the authored angles live at runtime instead of dead editor-preview data |
| `none` | `parentRotation` (identity in the parent frame) | Debug, or a wall orienting markers by some other system |

`facing_basis`, for `screen_aligned` and `world_up`:
- `view_plane` (default): `fwd = cam.transform.forward`. Every marker parallel to
  the near plane; no perspective skew anywhere on screen.
- `camera_position`: `fwd = markerWorldPos - camPos`. Each marker literally points
  at the camera. Slight skew off-centre; reads as more physical for large markers.

`up_reference`, for `world_up` and `yaw_only`:
- `world_gravity` (default): `Vector3.up`. **No gyroscope needed** - ARKit's
  default `worldAlignment` is `.gravity` and ARCore's world space has +Y opposite
  gravity (section 19), so Unity world +Y already IS gravity-up.
- `spawn_root`: `WallSession.MarkerSpawnRoot.up`. Use when the Immersal map frame
  is not gravity-aligned and "up" should mean "up the wall".
- `custom`: the authored `custom_up_x/y/z` vector.

### 4.2 Child element modes

`label_orientation_mode` and `badge_orientation_mode`: `inherit` (default) |
`screen_up` | `world_up`. Implemented as a pure Z `localRotation` on that child,
cancelling the difference between the root's current up and the desired up
measured about the root's forward axis. This is what gives always-readable labels
without moving the root, and it is the combination the wall developer most often
wants: `marker_orientation_mode = screen_aligned` with
`label_orientation_mode = world_up`, or the reverse.

`badge_corner_mode`: `inherit` (default) | `screen_fixed`. When the root is not
screen-aligned, the badge's fixed local offset `(0.042, 0.042)` drifts to a
different screen corner as the device rotates. `screen_fixed` re-rotates that base
offset by the same roll angle already computed for the child rotation, so the
badge holds its screen corner. Costs one extra 2D vector rotation; it reuses the
roll the child component has in hand, so there is no second computation.

### 4.3 Per-hierarchy-level override

`HierarchyLevelEntry` gains one optional field,
`orientation_mode_override` (empty string = inherit the wall setting). This lets
hero markers stay `screen_aligned` for legibility while scale-proving background
markers use `wall_fixed` so they read as part of the wall. It fits the existing
architecture exactly - `HierarchyLevelEntry` already carries per-level
`rotate_contour`, `size_cm`, `show_label` and effect flags - and it is one string
field plus one lookup, not a new system. Per-POI overrides are still out of scope
(section 18): the hierarchy level is the right granularity and already exists.

### 4.4 Conditioning and cost

| Field | Purpose |
|---|---|
| `roll_snap_mode` = `none` \| `quarter_turns` \| `screen_orientation` | `quarter_turns` snaps the MEASURED roll to the nearest 90 degrees, so a hand-held tilt never leaves a permanently skewed label. `screen_orientation` instead reads the OS's committed `Screen.orientation` and snaps to that, which is steadier once the device has settled but does nothing while the app is orientation-locked. Genuinely different answers; ship both |
| `roll_snap_hysteresis_deg` (default 15) | Deadband so the snap cannot flicker at a boundary |
| `clamp_pitch_enabled` / `max_pitch_deg` (default 75) | Stops a marker tipping fully edge-on when a visitor looks steeply up a 6 m wall |
| `rotation_smoothing_time_s` (default 0 = instant) | Exponential damping against AR pose jitter |
| `update_mode` = `every_frame` \| `interval` \| `on_camera_delta` | Thermal budget. 150 markers times per-frame quaternion work is the one real cost here (`_0_work_plan.md` performance rules) |
| `update_interval_s` (0.05), `camera_delta_deg` (0.5) | Parameters for the two non-per-frame modes |
| `cluster_orientation_mode` = `inherit` \| any marker mode | Clusters usually want the same behaviour, but not always |

**`LateUpdate` is not an option and must not become one.** The camera's final pose
for the frame is only known after every `Update` has run; writing rotation in
`Update` uses last frame's camera pose and produces a one-frame lag that reads as
swimming markers. Block 1 deletes the `Update` body for this reason. Do not
re-add it.

## 5. Library and package research

**Decision: hand-rolled, on Unity's own math and camera APIs. No new package.**

| Candidate | Exact integration path | Verdict |
|---|---|---|
| XRI `LazyFollow` | `com.unity.xr.interaction.toolkit` via Package Manager; component `XR/Lazy Follow`, type `UnityEngine.XR.Interaction.Toolkit.UI.LazyFollow` | **Rejected.** `RotationFollowMode.LookAtWithWorldUp` does cover `world_up` + `camera_position`, and `LookAt` part of `screen_aligned`. It covers none of: label/badge counter-rotation, badge corner hold, `yaw_only`, `wall_fixed`, roll snapping, pitch clamp, update throttling, per-level override, or cluster wiring. This project uses AR Foundation without XRI today; adding the toolkit for two of thirteen behaviours is the bloat `.clinerules/20-code-quality.md` warns about. Its `minAngleAllowed`/`maxAngleAllowed` smoothing is a lag model, not the damping wanted here |
| Unity `BillboardRenderer` | Built in | **Not applicable.** Renders SpeedTree `BillboardAsset`s only |
| TextMeshPro | Already installed | No orientation facility |
| Asset Store billboard packages | - | **Rejected.** All are short `LookAt` wrappers; a dependency with no upside |

**Use these built-ins instead of hand-rolling the maths:**
`Camera.ViewportToWorldPoint` (section 3), `Quaternion.LookRotation`,
`Quaternion.Slerp`, `Vector3.ProjectOnPlane`, `Vector3.SignedAngle`,
`Mathf.DeltaAngle`, `Screen.orientation`.
**Do not** reach for `Input.gyro` or `Input.acceleration`: the AR world frame is
already gravity-aligned (section 19) and the sensors are a second, noisier source
of truth.

## 8. `MarkerOrientationResolver` - the pure core

All decisions live here so they are Tier-0 testable with static calls and no scene
(`.clinerules/40-testing.md` 4.2). v2 claimed this domain had "no pure logic to
extract" - true of a one-line billboard, false of the option matrix.

The resolver is **stateless**. Everything it needs to remember between frames is
passed in and handed back through one result struct, so tests are deterministic
and the component owns all state.

```csharp
public struct OrientationResult
{
    public Quaternion Rotation;      // the world rotation to write
    public float SnappedRollDeg;     // feed back as previousSnappedRollDeg next frame
    public bool Resolved;            // false = degenerate input; caller keeps its previous rotation
}

public static class MarkerOrientationResolver
{
    // Block 1 creates the file with only this method.
    public static Vector3 ScreenUpWorld(Camera cam);          // section 3

    // Block 2 adds everything below.

    // Resolve the world rotation for a marker root. Applies, in this order:
    //   1. pick fwd from facingBasis (or the mode's own rule)
    //   2. pick up from the mode (screenUpWorld / upReference)
    //   3. degenerate guard -> Resolved = false
    //   4. roll snapping (rollSnapMode, hysteresis, previousSnappedRollDeg)
    //   5. pitch clamp
    // wall_fixed and none ignore steps 1-2 and return
    // parentRotation * authoredLocalRotation (wall_fixed) or parentRotation (none).
    public static OrientationResult ResolveRootRotation(
        OrientationSettings settings,
        string modeOverride,            // from the POI's hierarchy level; "" = use settings
        Vector3 markerWorldPos, Vector3 camPos, Vector3 camForward,
        Vector3 screenUpWorld, Vector3 upReference,
        Quaternion parentRotation, Quaternion authoredLocalRotation,
        float previousSnappedRollDeg,
        ScreenOrientation screenOrientation);

    // Child LOCAL rotation (pure Z) so the child's up matches the desired basis.
    // Returns identity for "inherit".
    public static Quaternion ResolveChildLocalRotation(
        string childMode, Quaternion rootWorldRotation,
        Vector3 screenUpWorld, Vector3 upReference);

    // The signed roll of the root about its own forward, relative to screen up.
    // Shared by ResolveChildLocalRotation, the badge corner hold and Block 5.
    public static float RootRollDeg(Quaternion rootWorldRotation, Vector3 screenUpWorld);

    // Rotate a 2D offset by degrees. Used for the badge corner hold and Block 5.
    public static Vector2 Rotate2D(Vector2 v, float degrees);

    // Snap to the nearest quarter turn with hysteresis around the boundary.
    public static float SnapRollDeg(
        float rollDeg, string snapMode, float hysteresisDeg,
        float previousSnappedDeg, ScreenOrientation screenOrientation);

    public static Quaternion ClampPitch(Quaternion target, Vector3 upReference, float maxPitchDeg);

    public static bool ShouldUpdate(
        OrientationSettings s, float secondsSinceLastUpdate, float cameraAngleDeltaDeg);

    public static Vector3 ResolveUpReference(OrientationSettings s, Transform spawnRoot);
}
```

Concrete rules that de-risk the work:

- **Degenerate `LookRotation`.** When the view direction is nearly parallel to the
  up reference (looking straight down at a `world_up` marker),
  `Quaternion.LookRotation` produces garbage. Guard:
  `if (Mathf.Abs(Vector3.Dot(fwd.normalized, up.normalized)) > 0.999f)` return
  `Resolved = false`. The component then keeps its previous rotation. Do NOT emit
  identity, which reads on screen as a marker snapping flat.
- **`RootRollDeg`:**
  `Vector3.SignedAngle(screenUpWorld, rootWorldRotation * Vector3.up, rootWorldRotation * Vector3.forward)`.
- **`ResolveChildLocalRotation`:** desiredUp is `screenUpWorld` for `screen_up` and
  `upReference` for `world_up`. The angle is
  `Vector3.SignedAngle(rootWorldRotation * Vector3.up, desiredUp, rootWorldRotation * Vector3.forward)`,
  returned as `Quaternion.Euler(0, 0, angle)`. Pure Z, so it never disturbs
  `anchoredPosition`.
- **Badge corner hold:** `newAnchoredPos = Rotate2D(baseAnchoredPos, -RootRollDeg(...))`,
  written by `MarkerChildOrientation` alongside the child rotation. The base value
  is captured once on first use, exactly as `MarkerView.EnsureLabelBaseCaptured`
  already does for the label, and is never accumulated.
- **`yaw_only` forward:** `Vector3.ProjectOnPlane(camPos - markerWorldPos, up)`,
  with the same degenerate guard.
- **`screen_orientation` snapping:** map `ScreenOrientation.Portrait` -> 0,
  `LandscapeLeft` -> 90, `PortraitUpsideDown` -> 180, `LandscapeRight` -> 270, and
  anything else (`AutoRotation`, unknown) falls back to `quarter_turns` behaviour
  on the measured roll. Passing `ScreenOrientation` in as a parameter rather than
  reading `Screen.orientation` inside the resolver is what keeps this Tier-0
  testable and is also why Block 0 adds an override source.
- **Smoothing lives in the component, not here**, so the resolver stays pure and
  frame-independent. The component applies
  `Quaternion.Slerp(current, result.Rotation, 1f - Mathf.Exp(-dt / tau))`.

## 9. Runtime components

### 9.1 `MarkerBillboard` (rewritten in place, same file and class name)

```
Fields: OrientationSettings _settings (framework defaults until Configure runs);
        string _modeOverride; Camera _camera; Transform _spawnRoot;
        MarkerChildOrientation[] _children (cached, never queried per frame);
        Quaternion _lastRotation; float _lastUpdateTime, _snappedRollDeg;
        Vector3 _lastCamForward.

Configure(OrientationSettings settings, string modeOverride, Transform spawnRoot):
  the ONE entry point, called by WallSession.SpawnPOIs at runtime AND by the
  editor rig path (section 14). Caches GetComponentsInChildren<MarkerChildOrientation>(true)
  and pushes the label/badge modes onto them. Never called per frame.

Awake(): cache Camera.main; assign canvas.worldCamera (keep today's behaviour);
  Debug.Assert(_camera != null, "[Marker] MarkerBillboard found no Main Camera");
  if null, log one line and disable.

LateUpdate() ONLY -- there is no Update():
  1. ShouldUpdate gate; if false, return (children are not ticked either, which is
     the intended cost trade-off: nothing moved, so nothing needs re-orienting).
  2. screenUp = ScreenUpWorld(_camera); upRef = ResolveUpReference(_settings, _spawnRoot).
  3. result = ResolveRootRotation(... _snappedRollDeg, ScreenOrientationSource.Current).
  4. if (!result.Resolved) keep _lastRotation; else _snappedRollDeg = result.SnappedRollDeg.
  5. optional Slerp toward the target; write transform.rotation; store _lastRotation.
  6. call Tick(rootRotation, screenUp, upRef) on each cached child component.
  Never writes position.
```

Step 6 calls the children explicitly rather than relying on script execution
order, which is not a contract worth depending on: the root's rotation for this
frame must be final before a child measures its roll against it.

### 9.2 `MarkerChildOrientation`

One instance on the Label and one on the Badge. Holds its mode strings (set by
`Configure`), its captured base `anchoredPosition`, and a `Tick(...)` method that
sets `transform.localRotation` from `ResolveChildLocalRotation` and, when
`badge_corner_mode == "screen_fixed"` on a badge, rewrites `anchoredPosition` from
the captured base. Does nothing at all when the mode is `inherit`, so the default
path costs one string comparison.

### 9.3 Clusters

Add `MarkerBillboard` to `POI_Cluster.prefab`. `LODController` computes the
effective cluster settings **once**, where it already caches `_dispSettings` from
`WallSession` - not per spawn, since cluster views are pooled and re-used. When

otherwise a single `new OrientationSettings(wallSettings)` copy with

### Block 5
The compensation, concretely. `ApplyLabelOffset` currently writes
`screenOffsetPx`-derived world units straight into `anchoredPosition`, which is
root-local. When the root is not screen-aligned those axes differ from screen axes
by the root's roll, so:

```csharp
float rollDeg = MarkerOrientationResolver.RootRollDeg(transform.rotation, screenUpWorld);
Vector2 localOffset = MarkerOrientationResolver.Rotate2D(worldOffset, -rollDeg);
// write localOffset (not worldOffset) into anchoredPosition
```

`rollDeg` is 0 in `screen_aligned`, so the expression reduces to today's behaviour
exactly and the default path is unchanged. The sign convention is settled
empirically by the first test below, which asserts the resulting **screen** offset -
if it comes out mirrored, flip the sign and re-run; do not reason about it on paper.

**Tier 0:** in `DisplacementLabelTests`, with `marker_orientation_mode = world_up`
and the camera rolled 45 degrees, assert the label's resulting screen-space offset
from the marker centre matches the requested `screenOffsetPx` within 2 px. Add the
same assertion at roll 0 to prove the default path did not move. Then re-run the
whole existing displacement suite unchanged: pass = zero failures across
`DisplacementComputeTests`, `DisplacementLabelTests`, `DisplacementAlgorithmTest`,
`DisplacementHysteresisTests`, `LeaderLineVisibilityTests`.

## 17. Cross-domain impact and notes for future agents

- **`_2.5_Displacement.md` is the only coupled domain, and only in one method.**
  `MarkerView.ApplyLabelOffset`'s comment states root-local X/Y are screen X/Y.
  After Block 1 that is reliably true for `screen_aligned`; it was only usually
  true before. For `world_up` / `yaw_only` / `wall_fixed` it is false, which is
  what Block 5 compensates. Patch that comment when Block 5 lands and patch
  `_2.5_Displacement.md` in the same session (`.clinerules/60-finishing.md` 6.2).
- **Label and badge rotation need no displacement change at all.** Overlap is
  point+radius, `anchoredPosition` is in the root's frame and is applied before
  the child's own rotation, and leader lines are world-space. Verified 2026-09-18.
  An agent later "fixing" displacement for label rotation is solving a problem
  that does not exist.
- **Do not rename `MarkerBillboard`** - section 6.
- **A gallery/test spawn helper that calls `reveal?.SetFullAlphaAndScale()` right after
  `MarkerView.Initialise(...)` is not enough to guarantee full scale on the next frame.**
  `Initialise` itself starts the reveal fade/scale-in coroutine (`reveal_duration_s` is
  0.35s even for the framework Fallback style, never 0), and that coroutine is still
  running after the explicit override - it overwrites root `localScale` back down on the
  very next `yield return null`, making any screen-space measurement (raycast hit test,
  projected pixel size) depend on frame timing instead of being deterministic. Found via a
  `OrientationGalleryTests` failure that only reproduced running the whole class, never a
  single test alone (different `Time.deltaTime` on the first frame masked it in isolation).
  Fix: call `reveal.StopAllCoroutines()` before `SetFullAlphaAndScale()`, exactly as
  `DisplacementGalleryTests.cs` already does - `OrientationGalleryHarness.SpawnEntry` now
  does the same. Any future gallery/test harness that spawns `POI_Marker` and needs an
  immediately-stable scale must do the same, in that order.
- **`editor_rotation_x/y/z_deg` stops being dead data** once `wall_fixed` ships.
  `WallConfigData.cs` and `PoiRotationResolver.cs`'s comments patched 2026-09-18
  (Block 4), along with `_5.1_Editor_Tab.md` section 4.4/11 which said the same.
  **Real bug caught in the same pass, cross-checking Block 4 against Block 7**:
  `WallSession.SpawnPOIs` hard-set a freshly spawned marker's `localRotation` to
  `Quaternion.identity` before `MarkerBillboard.Configure` ran, which meant
  `wall_fixed` mode's "authored" rotation (captured from `transform.localRotation`
  at `Configure` time) was ALWAYS identity, never the POI's real
  `editor_rotation_x/y/z_deg` - `wall_fixed` would have silently done nothing at
  runtime despite passing every test written against it in isolation, exactly the
  class of seam bug `40-testing.md` 4.2.1 warns about. Fixed by setting the
  spawned marker's initial `localRotation` from `Quaternion.Euler(poi.
  editor_rotation_x_deg, poi.editor_rotation_deg, poi.editor_rotation_z_deg)`
  instead, which is a no-op for every other mode (all ignore this field) and for
  any POI whose angles are still the seeded `(0,0,0)` default. Regression test:
  `OrientationWallSessionIntegrationTests.SpawnPOIs_WallFixed_UsesPoiAuthoredRotation`.
- **Effects that write rotation:** `MarkerRingView.SetRotating` spins the Ring
  child's own Z and composes correctly. Any FUTURE effect that writes the ROOT's
  rotation will fight the billboard - route it through a child object or
  `MarkerChildOrientation` instead.

## 18. Explicit non-goals

- Per-POI orientation overrides. The hierarchy level (section 4.3) is the right
  granularity, already exists, and already carries per-level visual properties. A
  per-POI field would multiply the Specific Marker tab for no requested use case.
- Distance-driven size compensation and marker-count management - `_2.4` LOD owns these.
- A centralized orientation manager iterating every marker. `update_mode` gives the
  cost control without the machinery; revisit only if a real profiling pass on a
  150-POI wall shows a need (`.clinerules/20-code-quality.md`: no speculative code).
- Writing rotation in `Update` as a selectable option - section 4.4 explains why
  `LateUpdate` is the only correct answer.
- Any Layout Group or Content Size Fitter in the marker prefab; the marker's
  content is fixed and bounded, so auto-layout machinery buys nothing.
