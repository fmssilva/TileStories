## Framework philosophy — read before building anything
This is a **framework** for building an app for *any* large heritage
wall of *any* shape and theme — not a single app. When a task below
involves a choice between implementation approaches, the goal is
**never** "pick the one best option and hardcode it." Implement **all**
genuinely good options, and expose the choice — plus each option's
key parameters — as a real, configurable control in the POI Authoring
window (dropdown/toggle/table, matching this codebase's existing
patterns — see `_2_4_Marker_LOD.md` §6's `density_response_mode` or
`_2_5_Marker_Displacement.md` §5's `displacement_algorithm` for the
established shape of "several good algorithms, developer picks per
wall, each with its own tunable fields"). Do not introduce a new
hardcoded constant, magic number, or single-fixed-behavior switch where
a genuinely different wall might reasonably want a different answer.
Where an entry below already made this call explicitly (e.g. 2.6-d's
"one clear winner, not a config toggle" reasoning), that reasoning is
recorded in the entry — read it, don't second-guess it reflexively, but
do apply this same two-level thinking (architecture-level: 3 structural
options, trade-offs, pick one; implementation-level: 3 concrete
approaches, pick the simplest robust one; *then*, separately, ask
whether the *feature choice itself* — not the code structure — should
be developer-configurable) to any new decision this file's entries
don't already resolve.

## 2.6-af — Select/Filter/Search: missing Tier 0.5 tap-target and contrast tests for 3 UI surfaces

**WHAT:** §17 explicitly requires, as concrete no-vision checks: (1)
minimap dot tap-target size, (2) filter-tray chip tap-target size (both
"44×44px minimum, same check as every prior domain"), and (3) WCAG
contrast on the filter tray and results list text against their
backgrounds. Confirmed via grep: zero references to `44`/
`MeetsMinTapTarget` in `MinimapViewTests.cs` or any Filter-folder test
file; zero references to `ContrastRatio`/`MeetsContrastAA` in any
Filter/Search/Results test file. The reusable utilities for both checks
already exist and are correctly used elsewhere in this same domain (see
2.5-q, 2.6-y for the tap-target pattern) — this is a coverage gap, not a
missing capability. Also note (no separate entry needed, subsumed by
2.6-i): §17's Tier 0 "combining two facets narrows correctly" and Tier 1
"camera-highlight dims non-matching markers"/"list view shows expected
filtered set" checks are currently un-passable given 2.6-i's gap — they

static (List<int> anchors, List<int> movers) PartitionByPriority(
    List<int> groupPriorities, List<int> memberIndices)

    bool allEqual = groupPriorities.All(p => p == minPriority);
    if (allEqual) return (new List<int>(), memberIndices); // symmetric fallback, no anchors

    var anchors = new List<int>();

    // chain to pick exactly one true anchor if the algorithm needs a single point
    // to repel from (force_directed can anchor multiple; candidate_position/fixed_axis

}

## 1.2 — Marker Positioning: Draft/Precise two-tier redesign

**IMPORTANT SIMPLIFICATION found during design, before you start:** an
earlier version of this plan considered also computing norm values FROM
a manually-dragged scene position (reverse interpolation). **This is not
needed.** Under the state machine below, dragging the scene object (or
editing a real field) always triggers the Draft→Precise switch — there
is no reachable state where the developer is still in Draft mode after
manually moving the object. So norm→3D (one direction only) is the only
interpolation math this feature needs. Do not build reverse
(3D→norm) interpolation — it would be unused complexity.

### WHAT — full state machine (the spec)

- **New POI, no position data at all:** starts in **Draft**. `x_norm`/
  `y_norm` default to `0.5`/`0.5`. Segmented control shows Draft
  selected. Real X/Y/Z fields visible but read-only/grayed, showing the
  live-interpolated preview value (see 1.2-c) rather than being empty.
- **Loading an existing POI from JSON:** mode is derived from
  `poi.has_captured_position` — **no new persisted field**. `true` →
  starts in Precise; `false` → starts in Draft. This is the same flag
  `POIPositionResolver`/`MarkerHierarchyResolver`-adjacent runtime code
  already reads — do not add a parallel `position_mode` field, it would
  be a second source of truth for the same fact.
- **Draft mode:** norm sliders/fields are the only editable position
  controls. Every change re-runs the live preview (1.2-c): the scene
  placement-aid object's `Transform.localPosition` updates to the
  interpolated result, and the (grayed, read-only) real X/Y/Z fields
  mirror that same computed value, so a developer can see the actual
  meters-value a given norm position resolves to without it being
  authoritative yet. **This rule holds unconditionally whenever mode =
  Draft, including immediately after a Precise → Draft revert (1.2-f)
  — the grayed real fields always show the live norm preview, never a
  dormant preserved `captured_position`, even though that preserved
  value still exists in the data and reappears (un-grayed, editable
  again) the moment mode switches back to Precise. This is the single
  rule that resolves what would otherwise be two competing claims about
  what the grayed fields display — see 1.2-f, which describes the same
  moment from the data-preservation angle; both describe the same
  behavior, not two different ones: the data is preserved (not erased),
  but its display is gated by mode, not by whether it happens to be the
  most recent capture.**
- **Switching Draft → Precise** happens on any of:
  1. Developer explicitly clicks "Precise" on the segmented control.
  2. Developer types into a real X/Y/Z field (any keystroke that changes
     the value).
  3. Developer manually drags/moves the placement-aid object in the
     Scene view.
  On first occurrence in a session (or ever, if not dismissed — see
  1.2-e), show a confirmation popup. Once switched: `has_captured_position
  = true`, real X/Y/Z fields become the writable authoritative source,
  norm fields freeze at their current values (grayed, read-only,
  preserved as a historical "how this was originally drafted" record —
  never auto-updated again).
- **Populate Rig's own programmatic repositioning must NOT trigger the
  switch** — it already uses norm-interpolation as a one-shot starting
  nudge (per `_1_2` §5 step 6) for POIs without a capture yet; that is
  expected, intentional, and must stay Draft-mode. Only genuine manual
  interaction (a real mouse drag in Scene view, or a keystroke in a real
  X/Y/Z field) should count — see 1.2-e for how to distinguish these.
- **Switching Precise → Draft** (developer clicks "Draft" on the
  segmented control): `has_captured_position = false`. **Do NOT clear
  `captured_position`'s stored values** — keep them, just gray them out
  and stop them driving anything. If the developer flips back to
  Precise, their prior placement reappears exactly as it was. This is a
  deliberate data-safety choice, not a shortcut — full data deletion
  must be a separate, explicit action (1.2-f).

### 1.2-c — Draft-mode live preview: HOW/WHERE/WHY

**HOW:** On every norm-field change (or every `OnGUI` repaint while the
foldout is open and in Draft mode — match whichever perf characteristic

### 1.2-e — Auto-switch + confirmation popup: HOW/WHERE/WHY

**HOW:** **A critical ordering bug was found and fixed here during this
entry's adversarial re-check — read this note before implementing.**
The original spec only suppressed the drift-check after
`PopulateRig()`/`RefreshRigVisuals()`, but 1.2-c's own live-preview
writes ALSO move the same placement-aid `Transform` this drift-check
watches — every single norm-slider drag would otherwise be immediately
misdetected as a "manual scene drag" and incorrectly fire the
Draft→Precise switch on the very first slider interaction, making Draft
mode's live preview effectively unusable (it would auto-complete to
Precise the instant a developer touched any norm control). Traced
through concretely: frame N, developer drags a norm slider → `OnGUI`
fires → 1.2-c computes a new `localPosition` and writes it to the
placement-aid `Transform` → without a fix, 1.2-e's drift-check (also
running that same `OnGUI`/`OnSceneGUI` pass) sees "position changed
since I last checked" and, having no way to tell that change was its own
sibling feature's doing, treats it as manual input.

**A first-draft fix (during this section's first adversarial re-check)
proposed a one-frame suppression flag, set by all three programmatic
writers and "cleared at the start of the next OnGUI/OnSceneGUI pass."
On a second, independent re-check, that timing assumption itself turned
out to be fragile** — Unity does not guarantee a single, well-defined
"next pass" ordering between `OnGUI` (the Editor window's own IMGUI) and
`OnSceneGUI` (Scene-view events); they're dispatched by different code
paths and can interleave in ways not safe to hard-code an assumption
about. **Corrected fix, avoiding the timing assumption entirely:**
reuse the same robust pattern already used for 1.2-d's "Field → scene" /
"Scene → field" pair (no suppression flag there either — see 1.2-d's own
note) — maintain a single private field,
`_lastKnownDraftPreviewPosition` (`Vector3?`, null until first set), and
update it *synchronously, in the same call*, every time any of the three
programmatic writers (`PopulateRig`, `RefreshRigVisuals`, 1.2-c's
live-preview update) writes to the placement-aid `Transform` — i.e. the
write and the bookkeeping update happen together, one line apart, not
across a frame boundary:
```csharp
localPosition = /* computed result */;
placementAidTransform.localPosition = localPosition;
_lastKnownDraftPreviewPosition = localPosition; // same call, no timing window
```
The drift-check then simply compares the Transform's **current**
position against `_lastKnownDraftPreviewPosition`: equal (within a
small epsilon) → nothing to flag, our own last write already accounted
for this position; different → something else moved it since our last
write, which can only be a genuine manual drag. This needs no flag,
no "which pass," no assumption about `OnGUI`/`OnSceneGUI` ordering at
all — it only requires that every programmatic writer updates the
bookkeeping value in the same call where it writes the Transform, which
is a much easier property to guarantee and verify by reading the code
than a cross-frame timing window is.

On a genuine manual trigger (drag or field edit) while still in Draft
mode: flip `has_captured_position =
true`, then show the popup **unless** the dismiss preference is set.
Popup text (confirmed wording from design discussion):
> *"You're now placing this POI's real position. The Draft (norm)
> controls are disabled for it — from here on, position it either by
> dragging it in the Scene view or by typing exact numbers below, and
> both will always stay in sync."*
> `[ ] Don't show this again`  `[ OK ]`

Persist the dismiss choice via `EditorPrefs`, same pattern as this
tool's existing `SkipPromptPrefKey`-style flags (confirmed present in
`POIAuthoringToolWindow.cs`, reuse that exact mechanism/key-naming
convention, add a new key rather than repurposing an existing one).

**WHERE:** Same file; `_lastKnownDraftPreviewPosition` as a new private
field on the same partial class 1.2-c/1.2-d/1.2-f all already touch —
not a per-method-local variable, it must be visible to `PopulateRig`,
`RefreshRigVisuals`, and 1.2-c's method, all three of which live in
different files/partial-class members already (`RigLifecycle.cs` for
the first two, `SpecificMarker.cs` for the third) — confirm it's
declared somewhere all three can reach (e.g. alongside this tool's other
cross-file private fields in `POIAuthoringToolWindow.cs` itself) rather
than accidentally scoped to only one file. New small popup — check
whether `Assets/Framework/Editor/POIAuthoring/Shared/` already has a
generic confirm-dialog helper (this session found `EntryDetailsPopup`,
`ExistingSymbolPickerPopup`, `HelpInfoPopup`, `EditorAlertPopup` there —
read each before writing a new one; `EditorAlertPopup` in particular may
already be the right generic shell for a dismissible OK-only message).

**WHY:** Directly matches the developer's own request for this UX
(confirmed in the design conversation) — an explicit, one-time,
dismissible heads-up rather than a silent mode flip, since flipping
`has_captured_position` has real runtime behavioral consequences
(§4.3's precedence rule) a developer should consciously understand
happened at least once.

**A second, related state bug — also found and fixed during this
section's second adversarial re-check, not the first:** if
`_lastKnownDraftPreviewPosition` is a single field (not keyed per-POI)
and the developer switches which POI's foldout is displayed (collapses
POI A, expands POI B — both in Draft mode), the field still holds POI
A's last value. The very next drift-check against POI B's placement-aid
`Transform` would then compare B's real position against A's stale
bookkeeping value — an almost-certain mismatch, incorrectly flagged as
"manual drift," incorrectly flipping POI B to Precise the instant its
foldout opens, with zero actual user interaction. **Fix:** the moment
the Position foldout starts displaying a different POI (foldout
expand/POI-selection change), immediately re-run 1.2-c's live-preview
computation once for the newly-selected POI *before* any drift-check
can run against it — this naturally re-seeds
`_lastKnownDraftPreviewPosition` to the correct, current value as a
side effect of the same write-and-bookkeep pattern already established
in 1.2-c, rather than needing a second, separate reset mechanism. Treat
"just started displaying this POI" as equivalent to "we just wrote its
preview position," which is already handled correctly by the existing
pattern once this one re-seed call is added at the right trigger point.

## 2.6-al — Select/Filter/Search: synonym feature is architecturally a dead end, never reaches the running app

**WHAT:** Found while investigating an unrelated question (menu-item
organization) — the `TileStories/Search/Create Synonym Asset` menu item
creates a `SearchSynonymGroups` `ScriptableObject` asset
(`Assets/Framework/Editor/POI/SearchSynonymGroups.cs`), intended to hold
developer-authored synonym groups for `_2.6`'s search-synonym feature.
This class is wrapped in `#if UNITY_EDITOR` and its own comment says so
explicitly: *"Entirely editor-only: the type is absent from player
builds."* `POISearchIndex.ConfigureWithSynonyms(IList<SynonymGroup>
groups)` (`Assets/Framework/Runtime/POI/POISearchIndex.cs` line 452) is
the only entry point that would ever apply synonym data to the live
search index — **confirmed via project-wide grep, its only callers
anywhere in the codebase are its own test file
(`SearchSynonymGroupsTests.cs`, 4 test methods)**. `WallSession.cs` never
calls it. There is no code path, anywhere, editor or runtime, that reads
a `SearchSynonymGroups` asset and feeds it into `ConfigureWithSynonyms`.
**Net effect: a developer can create the asset via the menu, fill in
synonym groups through its Inspector, and it will never affect search
results in the actual running app — the feature is correctly unit-tested
in complete isolation from anything that would make it real,** the same
failure pattern as 2.6-i (filter tray) found earlier in this same
domain, just smaller in scope.

**Root cause, not just a missing wire:** this isn't merely an
unconnected call site — the architecture itself is a dead end. Because
`SearchSynonymGroups` is `#if UNITY_EDITOR`-only, **no runtime
`MonoBehaviour`/class can ever hold a reference to it**, so there was
never a way to ship it to players even if someone wired it up.
`SynonymGroup` itself (the actual data class,
`Assets/Framework/Runtime/POI/SynonymGroup.cs`) is plain, serializable,
and NOT editor-only — it's already usable exactly like every other
taxonomy list in this codebase (`search_fields`, `hierarchy_levels`,
etc., all confirmed as `List<T>` fields directly on `WallConfigData`
during the `_2.3`/`_2.6` audits).

**HOW:** Don't patch the existing dead-end path — replace it with the
same pattern already used successfully everywhere else in this domain:
1. Add `public List<SynonymGroup> synonym_groups = new();` directly to
   `WallConfigData` (`Assets/Framework/Runtime/Core/WallConfigData.cs`),
   alongside the other top-level lists — confirm exact placement
   consistent with `search_fields`'s location, same section.
2. Delete (or keep only as a one-time import helper, see step 4)
   `SearchSynonymGroups.cs`'s `ScriptableObject`/menu-item approach —
   it's no longer the source of truth.
3. Wherever `WallSession` builds/configures `POISearchIndex` (confirmed
   call site exists, per the `_2.6` audit's `POISearchIndex.Build(config)`
   check), add
   `searchIndex.ConfigureWithSynonyms(config.synonym_groups);` right
   after `Build`.
4. Add a Synonym Groups editing UI to the existing "Search & Filter"
   foldout (`Assets/Framework/Editor/POIAuthoring/GlobalScene/POIAuthoringToolWindow.GlobalScene.cs`
   lines 479-663, or its own file if 5.1-b's file-split recommendation
   is done first — check that entry, this is a natural fit for the new
   file if it exists yet) — a simple add/remove list of (key, synonyms[])
   rows, same `DrawFramedFoldout`/table-row pattern already used
   throughout this file. This makes the old menu item fully redundant —
   remove it once the in-window UI lands, don't leave two authoring
   paths for the same data.

**WHERE:** `Assets/Framework/Runtime/Core/WallConfigData.cs` (new
field); `WallSession.cs` (wire the call); `GlobalScene.cs` or its
Search-Filter split (new UI); delete
`Assets/Framework/Editor/POI/SearchSynonymGroups.cs` once the above
lands (or repurpose it as a one-time "import from a legacy
