# Badge Design (2.2.2)

The badge: a second, smaller symbol on the marker for a second meaning axis (in LivingRoom: damage
state), independent of the marker's own category colour and icon. Split out of `_2.2_Marker_Design.md`
on 2026-09-22 alongside `_2.2.1_Marker_Design.md` and `_2.2.3_Outline_Design.md`. Sibling docs:
`_2.2.1_Marker_Design.md` (the symbol), `_2.2.3_Outline_Design.md` (the status ring, which the badge
interacts with for the "unknown status" case), `_5.1_Editor_Tab.md`, `_2.2_Marker_Design_Archive.md`.

**Audience:** an agent or developer with full Unity Editor + project access and no chat history.
Everything in this file was re-derived from the code on disk and from real test runs on 2026-09-22.

## 2. Concepts

### 2.1 Symbol and Badge are the same component

Both are "a coloured shape with a centred icon" — `MarkerCircleGlyphView` (`Runtime/UI/Markers/`)
is used for both, just at different size/position/content. `SpriteKeyLibrary` (a plain
`{key -> Sprite}` lookup) is used as both the icon library and the shape library — same data shape,
one class. This is why the Badge editor section reuses the exact same `DrawSymbolTable` renderer as
the Marker section (`_5.1_Editor_Tab.md` §4.5).

### 2.2 Badge precedence (the one rule to remember)

For a given marker, exactly one of four things happens, checked in this order:

1. **Hidden** — badges are off wall-wide, or this POI has no status at all (`has_status = false`).
2. **Universal unknown ("?")** — `status_unknown` is true. Wins over everything else below,
   regardless of `badge_category` or outline mode. Resolved by `ResolveUnknownBadge`: the POI's own
   `badge_category` if it resolves, else the wall's `unknown_damage` badge category if present,
   else a hardcoded neutral grey + the `"unknown"` icon key.
3. **Category badge** — `marker_use_badge` is on and the POI names a `badge_category` that
   resolves in the wall's `badge_categories` table. Uses that entry's own colour and icon.
4. **Status-fallback badge** — `marker_use_badge` is on, the status is known, but no
   `badge_category` resolves. Uses the resolved status colour (`_2.2.3`) with the *symbol's own
   icon* (not a badge-specific icon — there is no badge icon to use).

### 2.3 Corner and size are placement, not identity

`badge_corner`/`badge_size_ratio` control *where* and *how big* the badge sits relative to the
symbol — a purely geometric choice, orthogonal to *what* the badge shows (§2.2) and to the
category taxonomy (colour/icon per badge key). Changing the corner never changes which badge a POI
shows; it only moves it.

## 3. Runtime implementation

### 3.1 Files

| File | Role |
|---|---|
| `Runtime/Core/WallConfigData.cs` | `marker_use_badge`, `badge_shape`, `badge_corner`, `badge_size_ratio`, `badge_categories` (`List<BadgeCategoryEntry>` — key/label/icon_key/color_hex/details/search_keywords). |
| `Runtime/Core/MarkerVisualsParser.cs` | `TryParseBadgeCorner(raw, out Vector2 direction)`: `"top_right"` -> `(0.7, 0.7)`, etc. Unknown corner falls back to top-right and returns `false` (same "explicit failure, safe default" shape as every other parse method here). |
| `Runtime/POI/BadgeCategoryPalette.cs` | `TryResolve(key, out BadgeDefinition)` + `Configure`/reset for the wall's `badge_categories`. |
| `Runtime/POI/MarkerVisualSettings.cs` | `BadgeDirection` (resolved from `badge_corner`), `BadgeSizeRatio` — see `_2.2.1` §3.1. |
| `Runtime/POI/MarkerVisualResolver.cs` | `BadgeSource` enum (`Hidden`/`UnknownStatus`/`Category`/`StatusFallback`) + the precedence logic in §2.2 — see `_2.2.1` §3.1. |
| `Runtime/UI/Markers/MarkerLayout.cs` | `MarkerLayoutProportions.badgeDirection` / `badgeSizeRatio` — now set from `MarkerVisualSettings` at `Initialise`/`ReapplyVisuals` time (`MarkerView.UseSettings`) instead of only ever reading the prefab's compiled-in serialized values. |
| `Runtime/UI/Markers/MarkerView.cs` | `ApplyVisuals` draws `MarkerVisualState.Badge`/`BadgeColor`/`BadgeIconKey` (from `_2.2.1` §3.1's `MarkerVisualResolver.Resolve`): resolves the badge's own background shape sprite (`badge_shape`, independent of the symbol's `marker_shape`) and icon, or hides the Badge child entirely. |

### 3.2 Live Play Mode

Covered by the same `LivePlayModeMarkerApplier` as `_2.2.1` §3.3 — badge fields are part of the
same fingerprint and the same `WallSession.ApplyMarkerSettings` call, since badge and symbol share
one taxonomy-driven visual pipeline. There is no separate badge applier.

## 4. Editor

`GlobalScene/POIEditorToolWindow.MarkerDesign.cs`, `DrawGlobalBadgeSection`. Fields, in order:
Enable badge (toggle) -> Badge back shape (popup) -> Badge corner (popup, new) -> Badge size
(slider, new) -> the Badge Category table -> the Test sub-foldout. All on the shared field-drawer
helpers with (i) help text (`POIEditorToolWindow.MarkerDesignHelp.cs`). When "Enable badge" is off,
the whole rest of the section is replaced by a `HelpBox` and the Test sub-foldout still renders (so
its guides remain reachable even while the domain is off).

Per-POI: **Badge Style** foldout (`DrawPoiBadgeStyleFields`, only shown when `marker_use_badge` is
on) — a single Badge category dropdown, built the same way as the Marker section's Category
dropdown (`_2.2.1` §4).

**Test sub-foldout:** shared `DrawDomainTestSubSection` helper (`_2.2.1` §4). The three guides walk
through Enable badge, the new corner/size fields, the badge table, and the per-POI dropdown, naming
real LivingRoom badge keys (`intact`, `partial_damage`, `destroyed`, `unknown_damage`) and the new
`dev_marker_nobadge` fixture for the status-fallback case.

## 5. Explicitly deferred

A per-level badge size or corner override (badge geometry stays wall-wide, matching
`marker_shape`'s own "one setting for the whole wall" precedent, `_2.2.1` §2.1) · a badge that
shows two icons at once (stacking) — the current model is one badge per marker, matching the "the
badge is always circular anyway" reasoning already used to justify offering `Badge` as an
alternative to an outline mode historically (see the archive).
