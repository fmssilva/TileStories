# POI Detail Card -- Styles and Sunlight Contrast (3.3)

How the card LOOKS and how a developer changes it: one design-token set, three style presets (Stone &
Gold Luxury, Candlelit Antiquarian, Glassmorphic Aurora), each in dark and light, each with a
high-contrast "sunlight" expansion for outdoor walls; per-block style overrides; and the Editor rows
that edit all of it with a live contrast check. Applies to everything `_3.1` (blocks) and `_3.2`
(navigation) draw.

Design source: the Design canvas artboards "3 styles x standard / sunlight" and "POI Editor - Card
tab". Style origin: the developer's prototype files (`app_main_style_luxury_*`,
`app_backup_style_candlelit_*`, `app_backup_style_2_aurora_*`), improved for contrast.

### R1. Decided by the developer (2026-10-22)

- **ONE main theme, built to the end first.** Premium heritage look ("art, heritage, modern, AR, minimal, well organised, not
  overwhelming, clear navigation and affordances"). More themes only after it is finished (`__mixed_TODOs.md` "Themes after the
  main one", incl. a children's theme and a runtime visitor profile).
- **Two modes, light and dark, BOTH high contrast. No separate "sunlight" / high-contrast variants** (drops the old 3 presets x
  2 modes x sunlight matrix, the sun button and the `sunlight` wall policy). **Light is the default**, with a visitor toggle.
- **Contrast is proven twice at every step: by arithmetic tests AND by looking at the render** (design quality, not only
  "nothing broken"). Neither replaces the other.
- **Developer review gates:** every phase / block ends by showing what was done and asking the developer SPECIFIC questions
  ("this is the block preview design and flow -- does it read right?"), not a generic "OK?".
- Block previews over accordions on the main page: a block opens its whole self in a page of its own (full view) and Back
  returns; the developer may still choose other layouts (`_3.2`'s five).

### R2. Research findings so far (verify each again in P0 / P2 before it becomes a rule)

**UI Toolkit, by Unity version** (project: **6000.3.19f1 LTS, URP 17.3**):

| Feature | Version | Notes for this domain |
|---|---|---|
| USS `filter:` (blur, grayscale, tint, opacity, sepia, invert, hue-rotate, contrast, custom) on an element's OWN subtree | **6.3** (have it) | Blurs the element itself, NOT what is behind it. Useful for a blurred picture, a disabled look, a transition |
| UI Shader Graph (URP UI material, UI nodes) | **6.3** (have it, URP) | The animated gradient border, gradients, a glow, a shimmer: possible today as a material. Cost: per-element material breaks batching -- use for ONE focal element |
| Vector images (SVG import, Painter2D AA) | **6.3** | Icons as SVG instead of USS-drawn lines |
| `aspect-ratio` | **6.3** | Picture frames by proportion, not fixed heights |
| Per-glyph text animation (`PostProcessTextVertices`) | **6.3** | Title reveals; use sparingly |
| `backdrop-filter` (real "liquid glass" over the camera) + `drop-shadow()` | **6.6** (non-LTS) | URP only, screen-space panels only, no USS transitions on it; a 6.6 forum report of grey instead of blur with a translucent background (IN-153404) |
| `linear-gradient()` / `radial-gradient()` backgrounds, `gap`, `z-index`, keyframed animation (released), ATG text default at runtime | **6.7 LTS** (announced for Q4 2026) | Most of the "wow" polish lands here. **Still in beta on 2026-10-22** |

Consequence: **design effects as progressive enhancement.** Tokens name the effect (`--ts-sheet-glass`, `--ts-elevation-1`); on
6.3 they resolve to a fallback (tinted translucent fill, a border + a 9-slice or Shader Graph shadow); after an upgrade to 6.7 LTS
the same tokens switch to `backdrop-filter` / `drop-shadow()` / gradients. Steps that depend on engine effects go LAST in the
build order so an upgrade can land before them. The upgrade itself is a decision for when 6.7 LTS ships (recommended: 6.7 LTS,
not 6.6, which is a short-support release).

**Fonts:** UI Toolkit uses TextCore `FontAsset`; markers use `TMP_FontAsset` (`FontKeyLibrary`). Not confirmed that one asset
serves both in 6.3 (TMP 4.0 docs mark `TMP_FontAsset` obsolete in favour of `FontAsset`; forum threads disagree). Safe plan: one
`.ttf` per type ROLE, two generated assets per key (TMP + TextCore), one library and one key per role. The P0 spike tests
whether a single asset works in both.

**OS accessibility:** `UnityEngine.Accessibility.AccessibilitySettings` (Android / iOS) gives `fontScale` and
`isBoldTextEnabled` with change events -- no reduce-motion flag. The OS "reduce motion" needs a small native read (iOS
`UIAccessibility.isReduceMotionEnabled`, Android `Settings.Global.ANIMATOR_DURATION_SCALE`) -- P0 confirms.

**USS variables:** `var()` cannot nest in functions (`rgb(var(--x))`) and USS has no math. Whether `--a: var(--b)` resolves is
NOT documented -- P0 tests it; the token tiers (R4) depend on it.

**Today's code:** card USS has zero literals (all `var(--ts-*)`), but `CardTokens.uss` is one flat list of ~150 tokens mixing
global, card and block values on `.ts-card`; the card sets NO font (theme default; since P4.3, 2026-10-23, every panel speaks in the theme's
two faces, Build log); `SearchUI.uss` has its own palette
(`--surface`, `--accent` ...), `ZoomControlView.uss` its own `--ts-zoom-*`; markers write colours in C#
(`MarkerHaloEffect` / `MarkerRippleEffect` gold tint, `MarkerClusterView` disc colours).

### R3. Critique of the Stitch light "immersive" prototype (direction kept, spec not)

Keep: white block surface on a tinted ground (common region), icon + title + format line per block, one rhythm between blocks,
the peek carousel, the drag-to-rotate and before/after handles as affordances, a serif for titles. Its motion (`code.html`) is
modest and buildable: reveal on scroll (opacity + translate, 0.45 s, cubic-bezier(0.16, 1, 0.3, 1)), press (0.2 s), one
rotating contour (`contourRotate` 6 s) and the audio bars.
Change: drop the HUD noise (FPS, mesh, LOD, polygon counts, coordinates); one accent instead of five; no 10-11 px mono caps;
no pastel-on-pastel badges; Playfair only at large sizes or replaced by a sturdier serif; no text over glass; long blocks as
previews; a compact header (the "Half is mostly header" TODO); the bottom app tab bar is app chrome, not this domain. Its dark
version is an inverted light one -- dark needs its own elevation model (surface tone, not shadow).

### R4. Working proposals to settle in the phases (recommendation first)

- **Token tiers.** T1 primitives (palette ramps, spacing scale on 4/8 px, radius scale, type scale, durations, easings) and T2
  semantic roles (`surface`, `ink`, `accent`, `focus`, `elevation-n`, `motion-enter` ...) are APP-wide: one root class for every
  UI Toolkit panel (card, search, zoom, onboarding), and read by UGUI (markers, clusters, effects) from the same source. T3
  component tokens live in the component's OWN USS (`Media.uss` defines `--ts-hotspot-pin`), defaulting to T1/T2 values, so a
  global change reaches every component and one component can still diverge on purpose. Content colours (swatches, a wall's
  status rings) stay content. C# holds behaviour constants only.
- **Single source of truth for UGUI + UITK** (P4 decides): (a) a Theme asset (ScriptableObject) as the source, the Editor
  generating the theme USS from it, a test failing when the USS is stale; or (b) USS as the source, C# reading resolved values
  from a hidden themed root (the `CardTokenColours` pattern). Recommendation: (a), because markers render outside any panel.
- **Wall developer knobs (few, semantic):** display font, body font, accent colour, roundness (sharp / soft / round), default
  mode (light), motion level (full / reduced / off). NO free per-block token overrides (the old "Aa"): instead a closed list of
  per-block VARIANTS designed in the theme (emphasis: normal / featured / quiet; picture frame: rectangle / arch ...), which
  gives variety without breaking contrast.
- **Block `preview` display** (new, between `_3.2`'s one-line compact row and `inline`): capped at a FRACTION of the sheet's full
  height (~50-60 %, never a px value), cut with a fade, ending in an explicit affordance ("Read the whole story · 6 min ›") that
  opens the existing full view. Small kinds stay inline. Light interactions in place (swipe pictures, rotate the model, play
  audio, answer the quiz); deep ones in the full view. A gesture rule: horizontal drag belongs to the block, vertical to the card.
- **Previews that move:** default a slow Ken Burns on the first picture when the block enters view; auto-advance OFF by default
  (an Editor option, pauses on touch; WCAG 2.2.2); muted video preview only when >= 50 % visible, one at a time, an Editor
  option (AR already costs GPU and battery); audio never starts itself.
- **Domain separators:** a section header per family (icon + name), sticky in the scroll layout, more space before a section
  than between blocks.
- **Sheet over the camera:** blocks ALWAYS opaque; any text outside a block sits on its own plate. The sheet ground has a glass
  level: `solid` / `tinted` (translucent fill showing the raw camera, 6.3) / `frosted` (`backdrop-filter`, after the upgrade, or
  a blurred camera snapshot as fallback). The developer's idea (translucent sheet, raw camera visible, opaque blocks) is the
  `tinted` level; its risk is that a bright sunny wall behind a white block weakens the block's edge, so blocks carry a border
  + shadow whose contrast is measured against PHOTOS of sunny walls, not a grey test ground.
- **Contrast policy:** all text >= 7:1 in both modes (secondary and captions included); meaningful icons, input borders, focus
  >= 4.5:1; no ink made with alpha (today `--ts-ink-2/3` are alpha); no text on a picture without a solid plate; APCA Lc >= 75
  for body as a second check. Measured on the rendered pixel where something is translucent (LINEAR colour, see section 2).
- **Fonts (P4 decides by a bake-off render, recommendation):** display **Fraunces SemiBold** (heritage character, sturdier
  hairlines than Playfair), alternative Source Serif 4; body **Atkinson Hyperlegible Next** (designed for legibility, OFL),
  alternative Inter; no monospace. All OFL with Latin Extended (ã ç õ). Bake-off: three pairs on the real card, light mode, plus
  a simulated-glare render (contrast lowered, slight blur), the developer picks.

### R6. Motion catalogue (Architect proposal, 2026-10-22; the developer reviews it on recorded frames in P6)

The developer asked the Architect to propose the immersive / motion / micro-motion / parallax ideas and judge the result
later. Rules first: motion EXPLAINS (where a thing comes from, where it goes, what can be dragged), never moves text being read;
one moving thing at a time in view; only `translate` / `scale` / `rotate` / `opacity` (no layout properties) because the AR
camera runs at the same time; durations from the scale (fast ~120 ms, base ~220 ms, slow ~360 ms, emphasis ~500 ms); enter =
decelerate, exit = accelerate, a finger-driven thing = follows the finger then settles (spring). Three levels (wall knob +
visitor setting + the OS flag): `full` / `reduced` (no movement, cross-fades and state changes only) / `off`.

| # | Moment | Motion | Reduced |
|---|---|---|---|
| M1 | Card opens from a marker | the tapped marker pulses (existing effect), the sheet rises; the header, then the first two blocks, fade + rise 12 px, ~40 ms apart | sheet appears, no stagger |
| M2 | A block enters on scroll (first time per open) | fade + rise 16 px, slow; skipped when a navigation jump scrolls past it | none |
| M3 | Picture in a preview / the hero | parallax: the picture moves at ~0.85x the scroll inside its clipped frame (a window with depth); the hero scales 1.06 -> 1 and fades while the header collapses | static |
| M4 | Gallery preview in view | slow Ken Burns on the first picture (~12 s, scale 1 -> 1.06 + small pan), pauses off-screen | static |
| M5 | Preview -> full view and Back | container transform: the block's card grows from its own rect into the page, content cross-fades; Back shrinks it into the same slot (spatial continuity) | cross-fade |
| M6 | Press on anything tappable | scale 0.97 + surface tint (fast), springs back on release | tint only |
| M7 | Navigation follows the reader | the tab underline / marked chip SLIDES to the new section instead of jumping; the sticky section header swaps icon + words with an 8 px slide | instant swap |
| M8 | Affordance hints, once per session | the carousel nudges 24 px and back; the 3D model turns ~20 deg and back; the before / after handle sweeps a little | a static hint ("Swipe", "Drag") |
| M9 | Audio playing | bars / waveform move ONLY while playing; the mini-player slides in | static bars, state by icon |
| M10 | Quiz answer | right: the check draws + a small pop; wrong: a 6 px shake | colour + icon + words |
| M11 | The ONE "wow" focal point | an animated gradient contour (UI Shader Graph material) on the "See it here in AR" call to action, only while the visitor faces the wall | static gradient edge |
| M12 | Loading media | a soft shimmer on the picture's placeholder | static placeholder |

Not proposed: motion on body text, bouncing icons, autoplaying carousels by default, more than one glowing element per screen.

### R7. Liquid glass on 6.3, and the engine upgrade (2026-10-22)

- **Glass, closest to the real thing on 6.3** (P0 S5 decides by measurement): (1) **frosted by a low-resolution camera copy** --
  the AR camera image copied each frame (or every second frame) to a small RenderTexture (~1/8 size) and drawn under the sheet by
  a UI Shader Graph material in screen space: the low resolution IS the blur, plus the theme's tint on top; live, cheap, URP;
  (2) **tinted**: a translucent fill with the raw camera behind, no blur; (3) a blurred SNAPSHOT taken when the card opens (static,
  cheapest). Order of preference 1 > 2 > 3; in every case blocks stay opaque.
- **The camera is LIVE behind the sheet in every option** (the AR camera draws under the UI every frame): a translucent sheet
  already shows the wall moving as the visitor points the phone; only the BLUR needs the copy, and option (1) copies every frame
  (or every second frame), so it is live too. A copy every ~0.5 s was considered and rejected: the blurred image would step
  behind the live movement and read as lag. (3) is the only still image.
- **Developer idea (2026-10-22), to evaluate in P0 S5 as option (4):** tinted at ~50 % with a UI Shader Graph mask of irregular
  areas of more / less transparency (soft noise or a vertical gradient: clearer near the top where the sheet meets the camera
  view, more solid behind the reading area). Rules if chosen: static or very slow (one moving thing in view, R6), section headers

### R10. P3 -- Card architecture: displays, previews, sections, gestures (Architect proposal 2026-10-23; developer gate below)

The built card (`_3.2`) already has: five layouts (scroll, accordion, tabs, pages, bento), the one-line compact row
(`expandable`), `takeover` for video / model_3d / panorama_360, and the full view (a block's own page, breadcrumb, sibling swipe,
Back). What is missing is the middle step the developer described: a block shown COMPACTLY but RICHLY on the main page.

**R10.1 The display ladder** (per block instance, `display`; the Editor's existing Display row gains one value):
`inline` (the whole block: small kinds) -> **`preview` (NEW, the default for long kinds)** -> `expandable` (one-line row) -> `takeover`.
The full view is where every `preview` opens. Accordion stays a LAYOUT choice, never the default.

**R10.2 The preview cap.** A preview is at most `--ts-preview-max` of the sheet's FULL height (proposal 0.55, about 440 pt of the
796 pt Full stop at 390 x 844). A fraction, never px. A USS percentage does not resolve inside the ScrollView (`_3.2` step 12
found that), so the cap is computed in C# from the measured viewport, like `CardTrackFit`. A block whose natural height fits
shows whole, with no affordance, unless its kind declares that the full view holds more (a gallery's other pictures).

**R10.3 How a kind previews.** By default the block is CLIPPED at the cap with a fade into the block surface and the affordance
row under it. Kinds where a clip reads badly get their own preview content (`IPreviewBlockView`, designed per kind in P5): gallery
= a swipeable strip + "12 photos"; timeline = the first 3 events + "3 more events"; sources = the first 2 rows + "8 sources";
knowledge_check = the first question, live, + "3 questions"; rich_text = lede + first paragraph faded; story_chapters = chapter 1 +
the chapter bar.

**R10.4 The affordance row** (D3): verb + object + metadata, in CardStrings EN / PT: "Read the whole story · 6 min ›", "See all
12 photos ›", "Open the timeline · 6 events ›", "Play the guide · 3:11". Targets that open the full view: the affordance row and
the block header. A NON-interactive preview body (text) also opens on tap. An interactive one (carousel, quiz, model) keeps its
own gestures.

**R10.5 Interactions allowed IN the preview** (light ones; the deep ones live in the full view):

| Kind | In the preview | Only in the full view |
|---|---|---|
| gallery | swipe pictures | full-screen viewer, captions, zoom |
| before_after | drag the handle | labels, full size |
| model_3d / panorama_360 | drag to turn (horizontal) | zoom, AR place, settings |
| hotspot_image | tap a spot -> short popover | every spot's detail, loupes |
| zoom_image | none (a pinch inside a scrolling page fights the scroll) | pinch zoom |
| audio_guide | play / pause | chapters, speed, captions |
| video | poster + play; optional muted preview (R10.6) | the player, captions, chapters |
| knowledge_check / poll | answer the first question / vote | the other questions, results |
| timeline, rich_text, sources, story_chapters | none (reading) | everything |

**Gesture rule:** after an 8 pt slop, a drag that is more horizontal than vertical (|dx| > 1.2 |dy|) inside an interactive area
belongs to the block; any other drag scrolls the card. A preview never captures a vertical drag. Reuse the swipe tracks'
existing arbitration if `_3.2` already holds one; else it is one small pure rule.

**R10.6 Moving previews** (D6; wall-level Editor options, P8 finalises the rows): gallery motion = `ken_burns` (default, slow,
first picture, stops off-screen) | `auto_advance` (opt-in, pauses on touch) | `none`; video preview = `poster` (default) |
`muted_in_view` (>= 50 % visible, one at a time); audio never starts itself. With reduce motion, all of them are static.

**R10.7 Sections (domain separation).** In the scroll layout, a **section opener** where the family changes: the family icon + the
family's name in the display face + one line ("4 blocks · 9 min"). The space before an opener is twice the block gap. The

**Interleaved families** (P1b: "Listen" stayed marked to the end of the Lamp): under a block order that is not grouped by family,

### R11. Prototype v2 -- the developer's review of v1 and what changed (2026-10-23)

Developer's verdict on v1: "everything right, but flat: no wow, no life". (v1's motion was mostly invisible because the
canvas had saved the Reduce Motion tweak ON, and what ran was too subtle.) Decisions:
- **Glass = `tinted`** (clear glass in light, SMOKED glass in dark), made alive: not uniform, with coloured light moving inside.
- **Fonts = Fraunces + Atkinson Hyperlegible Next. Preview cap = 0.5.**
- **A section is its own sheet of glass laid over the previous one**, tinted with its family's hue (About amber, Stories plum,
  Media blue, Listen green, Play red, Visit violet), with slow moving light blobs inside; its opener is a FILLED pill in the family
  colour + a full-width line in the same colour.
- **Blocks get a lit metal rim** (a light-to-dark gradient edge, not a grey border + shadow); the block being read catches a
  moving light that sweeps around its edge (one at a time).
- **The whole block is the tap target** (a block that opens -> its page; the audio guide -> play / pause); interactive parts
  (strips, handles, answers, spots) keep their own gestures.
- **Every preview shows what it can do, by itself, until the visitor touches it:** the gallery and timeline strips drift
  sideways; the before / after handle sweeps back and forth; a finger taps the painting's spots; the "Did you know?" card has a
  dog-eared corner that peels; the play button breathes. The first touch stops the demo and the block answers the visitor only.
- **Scroll:** blocks rise and scale in as they enter, their parts follow one by one; pictures move inside their frames
  (parallax); the hero full-bleeds under a title card that slides over it.
- **Timeline preview = a HORIZONTAL strip**, not an inner vertical scroll: a vertical scroll inside the vertical card is a
  scroll trap on a phone (which one moves depends on where the finger lands and where each one is in its range); a sideways strip
  keeps R10.5's gesture rule (horizontal = the block, vertical = the card).
- **A block's page has Previous AND Next** (siblings in card order).

### R12. P4 -- Foundations: where every value lives (Architect plan 2026-10-23; one developer question at the end)

**Ground (verified on disk).** One `PanelSettings` (`Runtime/UI/Shared/PanelSettings.asset`) serves every UI Toolkit panel; its
`themeUss` is `UnityDefaultRuntimeTheme.tss` (only `@import url("unity-theme://default")`). The card adds its sheets in code
(`CardStyleSheets.InOrder`: `CardTokens.uss` first) and its root carries `.ts-card.ts-theme-default`. C# reads tokens BY NAME
from the `.ts-card` element's own custom style in 8+ places (`CardTokenColours`, `PoiCardSheetView` top gap / collapsed header,
`CardTrackFit` peek, `CardBentoView`, `FabRadialNavView`, `FloatingSlot`). `SearchUI.uss` and `ZoomControlView.uss` keep their
own palettes; markers write colours in C# (`MarkerHaloEffect`, `MarkerRippleEffect`, `MarkerClusterView`) and fonts through
`FontKeyLibrary` (TMP). The prototype's values (R11 v4) are the visual target.

**Constraint found in P0 S1:** `customStyle` holds only an element's OWN declarations. If the tokens move up to an app root,
every C# read on `.ts-card` breaks silently (a broken var paints transparent with no warning). So C# must not read colours
from USS at all.

**R12.1 The single source = a Theme asset (ScriptableObject), the USS is GENERATED from it.**
- `ThemeAsset` (`Runtime/UI/Theme/`) holds T1 + T2 for both modes: palette ramps, the semantic roles per mode, family colours
  (fill, ink on fill, glass hue 1 / 2), metal (gradient stops, sweep colour + strength per mode), glass (tint, edge, highlight,
  shadow per mode), scrims, the type roles (font keys + sizes + weights + line heights), spacing / radius / duration scales,
  easings.
- An Editor generator writes `Runtime/UI/Theme/Generated/Theme.<name>.uss` (classes `.ts-app.ts-theme-<name>.ts-mode-light` /
  `-dark`, plus the knob classes of R12.4). A test fails when the committed USS differs from what the generator produces now
  (a stale theme can never ship). The generated file is committed (builds need it; diffs show what changed).
- **UI Toolkit** gets it app-wide through the TSS: `PanelSettings.themeUss` -> a `TileStoriesTheme.tss` that imports Unity's
  default AND the generated theme, so the card, search, zoom, onboarding, every panel reads the same tokens. A `ThemeController`
  puts `.ts-app` + theme + mode + knob classes on every UIDocument root (switching mode = swapping classes: no rebuild, the
  `_3.2` pattern).
- **C# and UGUI** read the SAME asset through a `ThemeResolver` (role + mode + knobs -> `Color` / `float` / font asset): markers'
  halo / ripple / cluster colours, the card's family colours (replaces `CardTokenColours`' USS read), the section-glass and metal
  MATERIALS' parameters (a Shader Graph material takes its colours from C#, never from USS). Layout numbers C# needs (top gap,
  peek, bento gap, radial sizes) stay COMPONENT tokens read from the component's own element, which declares them itself (R12.2,
  T3), so `customStyle` still finds them.

### R14. Composable blocks: a library of UI elements a developer composes (Architect analysis 2026-10-23; questions at the end)

**The developer's idea.** A block (first: The story) is a TABLE OF ELEMENTS in the Editor: title, carousel, heading, paragraph,
paragraph, highlight box, paragraph, picture with caption, video... The developer adds, removes, reorders rows, fills each, and
sets each row's style (tone, size, motion) from good defaults. The Block Library holds the wall's designed blocks; a POI that
uses one may change its structure. Elements are a component library ("our own HTML / CSS / JS") reused across blocks.

**Ground (verified on disk).** A block instance is `kind + variant + display + fields`; a field holds text per language, a number,
a flag, a choice, an asset, or `items` -- a repeater of rows, each with its own keyed sub-fields (`BlockItemData`, one level
only: JsonUtility allows no recursion). The Editor already draws Items as a table with add / delete / reorder, undo / redo, the
unsaved flag and live Play Mode sync; `rich_text`'s `sections` variant is already a small "heading + text" row list. The Block
Library today is per KIND (`BlockKindSetting`: enabled, default variant, Choice field defaults). Ready-made content is written
by Card Starters and navigation Presets: a preset WRITES values in one undo step; nothing stays linked.

**R14.1 Decision: elements are TYPED ROWS of a new field type, `Elements`** -- not a second data model.
- `BlockFieldType.Elements`: like `Items`, but every row names its element kind (`element` key) and holds the sub-fields THAT
  element defines. Storage stays `BlockItemData` rows (the same JSON, the same Editor table machinery, the same undo / live sync /
  validation paths), plus one small addition: a row may hold a list of media refs (`asset + caption + credit`, a separate class,
  so still no recursion) for elements such as a carousel or a picture pair.
- `ElementKindDefinition` + `ElementRegistry` (the BlockRegistry pattern, so an APP can register its own elements as it registers
  kinds): key, label, icon, category (Text / Media / Structure / Interactive), the sub-field schema, its STYLE options, how it
  previews, how much reading time it adds, how it feeds search, and the view that draws it.
- Any kind may declare an `Elements` field. The first is a new kind **`story`** ("Story", About family) whose body IS an Elements
  field. Later, other kinds may gain an optional Elements field ("more content") where open content helps -- one field type, one
  table, everywhere.
- Rejected: converting the 37 existing kinds into element compositions. The interactive kinds (audio, video, quiz, 3D, 360,
  AR) own services, gestures and one-at-a-time rules a free composition would break; they stay kinds. The SHARED building blocks
  (a picture with caption, a carousel, a callout...) become components that the existing kinds' views also reuse, so the look is
  one system.

**R14.2 The UI component library** (`Runtime/UI/Components/`, the developer's "UI_components" folder). Each component = one
`VisualElement` class with `Bind(row, context)` / `Unbind`, styled ONLY by theme tokens (P4) + its own T3 tokens in
`Components.uss`, with a designed default and the element's closed style options. First set (the story's):
| Category | Elements (v1) | Style options (closed lists, contrast-safe, R12.4 logic) |
|---|---|---|
| Text | title, eyebrow, heading, lede, paragraph, callout (highlight box), pull quote, list | tone (neutral / family / accent / inverse), size (s / m / l), alignment, drop cap (paragraph) |
| Media | picture (+ caption, credit), picture pair, carousel, video (poster -> the existing video takeover) | width (inset / full-bleed), frame (rectangle / arch), motion (none / parallax / slow zoom / pan) |
| Structure | divider (line / azulejo ornament), spacer | -- |
Later sets: 3D model and 360 (through their existing owners), audio snippet, map, key facts, timeline strip, person, quote with
portrait, AI / voice prompt. Every component gets the block frame's states (reveal on entry, demo where it has one, reduce motion).

**R14.3 Preview and page of a composed block.** The page shows every row. The preview (R10, cap 0.5) shows rows in order until
the cap, with a FIRST picture row promoted to the preview's picture slot; text rows beyond the cap fade. Each row may opt out of
the preview (`in_preview`, default on for the first rows the cap fits). Summary, reading time and search keywords come from the
rows (one pure `ElementRules`).

**R14.4 Library and POI: templates are PRESETS, copied (recommended).** The Block Library gains BLOCK TEMPLATES: named
compositions ("Story -- magazine", "Story -- short") of element rows with their styles and empty content; built-in ones ship as
code (like Card Starters), a wall may save its own (`card_settings.block_templates`). Adding a block to a POI from a template
COPIES its rows; the POI then owns its structure (add / remove / reorder freely). "Re-apply template" adds the template's
missing rows without touching content. Considered and rejected for now: LIVE-linked templates (a library change flows into every
POI): it needs per-row identity merges and an "overridden" state per row, and fails confusingly when a POI deleted a row the
template later changes; copy + re-apply is how Card Starters and Presets already behave (one pattern, `prefer-uniform`).

**R14.5 The Editor flow.** Detail Card > Block Library: the kinds table as today + a TEMPLATES table (create from a built-in,
edit its rows, name, delete). Specific POI > Card Content: a story block shows its ELEMENT TABLE: each row = element icon + name +
the first words / a thumbnail; row actions: move up / down (and drag), duplicate, delete; "+ Add element" opens a menu grouped by
category with icons; a row opens its content fields inline and a "Style" button opens its style options in the shared
`EditorPopup`. Every edit through `DrawConfigMutationScope` (undo, unsaved, live Play Mode). Card Starters gain the templates.

**R14.6 What changes in `_3.1` / `_3.2`.** Additive, no rewrite: one field type, one registry, one kind, one component folder,
one Editor table. `_3.1`: the registry and validation learn `Elements`; `BlockSummaryRule` / Reading Time / search keywords read
rows; the media scope serves element media (video through the existing owner). `_3.2`: nothing -- navigation targets stay
blocks; a story's headings could become in-page anchors later (LATER, not now). JSON: old configs load unchanged (no field = no

### R17. A block = two SURFACES (Preview, Page) built from parts; shared chrome components (Architect analysis 2026-10-23)

Replaces R14.8's "five domain tabs" with what the developer asked for: the Editor organised by the THINGS a visitor sees.

**R17.1 Every block has two surfaces, and the Editor shows them as two sections.**
```
The story (story · About)          display: Preview · emphasis: Normal · reading time: Auto (4 min) · ✓ / ✕ validated
├─ Preview  (what the card shows)     mode: Automatic ▾ | Custom
│    rows: [Picture ↗ from Page #1] [Title ↗ from Page #3] [Text ↗ from Page #4] [+ Add]   (Custom only)
│    Open Row ............ inherits the wall's Open Row ▾ (Override)
│    Tap ................. Open the page ▾
│    Idle demo ........... Slow zoom on the picture ▾
│    Motion .............. Block entry: Rise ▾ · its rows: (table)
└─ Page  (the block's own page)
     rows: Picture · Eyebrow · Title · Lede · Paragraph · ... · Callout · Video   [+ Add]
     Page chrome ......... breadcrumb + Previous / Next: inherit the wall's ▾ (Override)
     Opening ............. Grow from the preview ▾
     Motion .............. (table: one line per row)
```
- **Page = the content.** The developer writes the story ONCE, in the Page's rows (the element table of R14).
- **Preview = Automatic by default:** it is derived from the Page by R14.3's rule (the first picture + the title + the first
  text, cut at the cap). Most blocks never need more. **Custom** turns the preview into its own row list, where a row is EITHER a
  **linked row** ("↗ from Page #3: Title" -- same content, its own size / style, edited once on the Page) OR an **own row**
  (content only the preview shows, e.g. a teaser sentence). Actions on any Page row: "Use in the preview (linked)" / "Copy to
  the preview"; on a linked preview row: "Unlink (make a copy)". A linked row whose Page row was deleted turns into a warning row
  ("its Page row is gone") with Unlink / Remove, never a silent blank.
- Why this order of defaults: a developer fills ONE thing (the Page) and gets a good preview for free; full control is one
  switch away. Linking avoids writing the title twice and keeps EN / PT in step.

**R17.2 The same two sections for EVERY kind -- composed or not.** Each kind exposes named **parts** (its building blocks):
- a composed kind (`story`): its parts ARE its Page rows;
- a fixed kind exposes its own: gallery -> "the strip", "the count"; audio_guide -> "the player"; knowledge_check -> "the
  first question", "the score"; video -> "the poster"; timeline -> "the strip"; model_3d -> "the turntable"...
The Page of a fixed kind = its fields (as today) + an optional **"More content"** row list (elements, R14.1) before / after it --
this is how pictures, video, 3D reach "many blocks" (the developer, R13 answer). The Custom Preview of a fixed kind lists its
parts by reference ("↗ the first question") + own rows. So `Automatic / Custom`, linked rows, Open Row, Tap, Motion and Page
chrome look and work the same for all 37 kinds and every future one.

**R17.3 Motion: ONE value per row, shown in two places.**
- Data: each row carries its motion (`effect`: Auto / None / Reveal / Slide from left / Slide from right / Parallax / Slow zoom /
  Pan; `strength`: subtle / strong). **Auto** = the theme's default for that element (pictures: subtle parallax, text: reveal)
  -- so a developer only touches exceptions.
- Editor: (1) in the row's accordion ("Motion" line, next to Content and Style) while editing that row; (2) the surface's
  **Motion table**: one line per row of that surface (by reference, automatically -- nothing to "add"), its effect and
  strength editable inline, plus the surface's own line (Preview: block entry; Page: opening + rows stagger). The table is the
  choreography overview; both places edit the SAME field.
- **Reduce motion is not configured per row: it is a rule.** Every effect has a defined still fallback (movement -> none;

### R15. Where UI renders: screen, world, both (Architect analysis 2026-10-23)

**Ground (`Runtime/UI/`).** UGUI world-space: `World/Markers/` only (TMP labels, rings, effects on world canvases at the wall).
UI Toolkit screen-space: `Screen/Cards/` (the sheet and its navigation), `Screen/Search/`, `Screen/Zoom/`, `Screen/Filter/`,
`Screen/Minimap/`, `Screen/Results/`. UI Toolkit on any panel: `Blocks/` (every family's views + USS) and `Components/`. Both
systems: `Theme/`, `Shared/` (the one PanelSettings). Empty scaffolds: `Screen/{Onboarding,Scanning,Sharing,Gamification,Circuits}/`,
`World/GuideCharacter/`. No folder mixes the two systems, and the folder names say which is which.

**World-space UI Toolkit exists (Unity 6.2+, so 6.3 has it).** A `UIDocument` whose `PanelSettings` render mode is World Space
draws on a plane in the scene (placed by its transform); input comes from camera rays against colliders on chosen layers (Panel
Input Configuration / World Document Raycaster). Known limits: `backdrop-filter` does not work on world panels (irrelevant: our
glass is a Shader Graph material, R11), and the details for AR (the AR camera as event camera, legibility at 1-3 m, sorting
against the UGUI markers, cost of a second panel) are unproven here -> a spike before any world feature.

**So the developer's idea works:** tap the castle's marker and a compact card (a short description + a picture slider) appears
FIXED ON THE WALL under the marker, built from the SAME UI Toolkit components and block previews as the sheet. It needs one rule

## 3. Spike first: runtime overrides in UI Toolkit (step 0)

USS custom properties (`var(--x)`) are defined in style sheets; UI Toolkit's C# `IStyle` has no setter
for a custom property (the read side is `ICustomStyle`). So a value typed in the Editor and saved in
`config.json` cannot simply be written as a variable at runtime. Options, to confirm against the
Unity 6.3 API BEFORE step 7:

| Option | How | Cost |
|---|---|---|
| A. Presets only | overrides = choosing another preset class | no free colour picking |
| **B. Presets in USS + a `TokenApplier` for overrides (proposed)** | presets set the variables; a small applier writes the handful of overridden tokens as INLINE styles on elements carrying token-role classes (`.ts-role-accent-bg`, `.ts-role-ink`...) | one mapping table role -> properties; inline styles beat the cascade, so overrides always win |
| C. Generate a StyleSheet asset in the Editor on save | the Editor writes a per-wall `.uss` from `card_settings.style` | runtime stays pure USS, but a build step and an asset per wall |

Spike: prove B on one token (accent) end to end (config -> applier -> rendered pixel) and check the
current Unity docs for a newer custom-property API; if one exists, prefer it and rewrite this section.

## 4. Presets

Each preset = one USS file defining every token under a root class, e.g.
`.ts-theme-luxury.ts-mode-dark`, `.ts-theme-luxury.ts-mode-dark.ts-sunlight`. `PoiCardHost` sets the
classes on the card root; switching preset, mode or sunlight is swapping classes (no rebuild).

| Preset | Fonts | Standard dark (key tokens) | Sunlight dark | Sunlight light |
|---|---|---|---|---|
| Stone & Gold Luxury (main) | Fraunces + DM Sans | bg #1A1510, ink #F7EFDC, ink-2 80%, accent #F59E0B | bg #000, ink #FFF, accent #FFB224 fill + black | bg #FFF, ink #000, accent #8A3B00 fill + white |
| Candlelit Antiquarian | Playfair Display + Spectral | bg #12100E, ink #F8EBD0, gold #F59E0B, body upright | black, ink #FFF6E2, gold #FFC53D | paper #FFFDF6, black, navy #0B1A33 |
| Glassmorphic Aurora | Outfit | bg #050D1A, azure #38BDF8, cells 12% fill | black, cyan #5CD3FF, solid cells | white, ink #00111F, blue #005A8C |

Values above are the canvas values (already raised from the prototypes: light-theme buttons used white
on amber, which fails AA). The contrast tests of section 9 are the authority; if a value fails, the
test wins and the table is updated.

## 6. Sunlight expansion

- Visitor control: a sun button in the card header (always visible, 48 px) toggles `.ts-sunlight`;
  remembered on the device (`CardLocalState`).
- Wall policy (`card_settings.style.sunlight`): `visitor_toggle` (default), `always`, `never`,
  `auto_light_sensor` (Android only: Input System `LightSensor`; iOS has no public ambient-light API,
  so it falls back to the toggle -- verify on device before promising "auto").
- Glass blur: UI Toolkit has no backdrop blur; "glass" in standard presets is a translucent fill.
  Sunlight replaces it with the solid `--ts-surface`.
- Reduce motion and text size are visitor settings built in this step too, next to the sun button in
  the card's "Aa" menu (canvas "New blocks" 02-G).

## 7. Overrides

- **Wall level:** `card_settings.style` = `preset`, `mode` (dark / light / follow system),
  `sunlight` policy, `tokens` (list of `{token, value, sunlight_value}`; empty = preset value).
- **Block level:** `BlockInstanceData.style` = `inherit` (bool) + the same token list, applied to that
  block's root only. Sunlight value auto-derived when empty (lighten/darken until >= 7:1), shown as
  derived in the Editor.
- Order: preset < wall tokens < block tokens < sunlight rules for non-overridable properties
  (solid surfaces, borders, sizes -- a block cannot re-enable glass in sunlight).

## 8. Editor: Detail Card > Style & Contrast

As on the canvas "POI Editor - Card tab": Style Preset, Base Mode, Sunlight policy, Sunlight Variant,
"Show sunlight side by side" (demo card, dev-only); the token table (Token, Standard value, Sunlight
value, contrast of each against its surface via `UIAccessibility`, USS variable) with a red warning
under AA / AAA; buttons Reset to preset, Duplicate as new preset. Per block: the "Aa" button in
Specific Marker > Card Content opens a "Block Style" `EditorPopup` (the `LevelLabelStylePopup`
pattern): Inherit toggle + per-token overrides, drawn inside the owner's `DrawConfigMutationScope`.

## 9. Testing

- `CardTokenContractTests` (EditMode): every preset x mode x sunlight defines every token of section 2;
  no literal colours/px in card C# (scan); every view uses only role classes.
- `CardContrastTests` (EditMode): for every preset x mode, each text token vs each surface it sits on
  meets AA (standard) / AAA (sunlight); borders >= 3:1.
- `CardStyleGalleryTests` (PlayMode, Phase A): the gallery of `_3.1` rendered under every preset x mode x
  sunlight -> `Card_style_<preset>_<mode>_<hc>.png` for the Tier 1 vision pass.
- `CardStyleSceneTests` (PlayMode, Phase B): toggling sunlight on the real card swaps classes (no
  rebuild, same scroll position); a wall override and a block override both render (sampled pixel).
- Device check (Tier C, `40-testing.md` 4.6): the three sunlight presets read outdoors in direct sun,
  noted with photos.
