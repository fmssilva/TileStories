4. **`SearchTokenizer.cs`** created at `Assets/Framework/Runtime/POI/SearchTokenizer.cs`:
   - **Architecture**: Static utility class, pure C#, no dependencies beyond `System`, `System.Collections.Generic`, `System.Globalization`. Zero MonoBehaviour.
   - **Method `Tokenize(string input) -> List<string>`**:
     - Null/empty/whitespace input → returns empty list
     - NFKD normalization → strips diacritics (accent-folding)
     - Lowercase invariant culture
     - Split on `char.IsWhiteSpace` and `char.IsPunctuation`
     - Filter out empty/whitespace-only entries
     - Deduplicate (preserve first-occurrence order)
     - Single-character tokens preserved (someone might search "x")
     - Numeric tokens preserved ("1755" is a valid search term)
     - Punctuation-only input after stripping → returns empty list
   - **Method `IsTokenValid(string token) -> bool`**: returns `token != null && token.Length > 0 && token.Any(c => !char.IsWhiteSpace(c))` — used internally; also exposed as public for external consumers.
5. **`POISearchIndex.cs`** created at `Assets/Framework/Runtime/POI/POISearchIndex.cs`:
   - **Architecture**: Plain C# class, not a MonoBehaviour. Contains the inverted index and ranking logic. Instantiated with `new POISearchIndex()`.
   - **Internal state:**
     - `_tokenToPoiIds: Dictionary<string, List<int>>` — inverted index: token → list of POI indices
     - `_poiDatas: List<POIData>` — stored reference for name match and metadata retrieval
     - `_allIndexedTokens: HashSet<string>` — for prefix-based auto-complete (`GetMatchingKeywords`)
     - `_poiIds: HashSet<string>` — for fast O(1) duplicate-ID detection during Build
     - Static `SearchTokenizer` reference for all tokenization
   - **Method `Build(WallConfigData config)`**:
     - Clears all existing state (replaces, not additive)
     - Iterates over `config.pois`; skips any POI with null/empty `id`
     - For each POI, collects token sources:
       - **POI.name** → tokenize, index with rank group "name"
       - **POI.summary** → tokenize, index with rank group "summary"
       - **POI.category** → tokenize, index with rank group "taxonomy"
       - **POI.search_keywords** → tokenize (each keyword as a single unit first, then split multi-word), index with rank group "keyword"
       - **Hierarchy level label**: looks up `config.hierarchy_levels` by `poi.hierarchy_level_key`, reads that entry's `label`, tokenizes it, indexes with rank group "taxonomy"
       - **Taxonomy-level search_keywords**: for the POI's category, looks up matching `config.category_styles` entry, reads its `search_keywords`, tokenizes and indexes with rank group "taxonomy". Same for `badge_categories`, `outline_levels`.
     - Stores `_poiDatas` by index
   - **Method `Search(string query) -> List<SearchResult>`**:
     - Null/empty query → returns empty list
     - Tokenizes query via `SearchTokenizer.Tokenize(query)`
     - For each token, retrieves matching POI indices from `_tokenToPoiIds`
     - Scores each matching POI by the highest rank group matched:
       - `1.0f` — exact name match (any token equals POI.name, case-insensitive)
       - `0.9f` — name prefix (POI.name.StartsWith(token, OrdinalIgnoreCase))
       - `0.7f` — keyword match (token found in POI's search_keywords or taxonomy-level keywords)
       - `0.4f` — summary/substring (token found in POI.summary via Contains)
       - `0.3f` — taxonomy match (token matches POI.category string or hierarchy level label)
     - Multi-token queries: score for each POI is the **maximum** score across all query tokens (not additive — prevents a POI that matches three weak categories from outranking an exact name match)
     - Ties broken by POI index (lower = earlier in config = stable sort)
     - Returns `List<SearchResult>` sorted by score descending, then by POI index ascending
   - **Method `GetMatchingKeywords(string prefix) -> List<string>`**:
     - prefix is lowercased and NFKD-normalized
     - Returns all tokens from `_allIndexedTokens` that start with the prefix
     - Sorted alphabetically
     - Empty prefix → returns empty list (don't dump everything)
   - **Method `Clear()`**: drops all internal state (index, stored datas, token set)
   - **Method `ConfigureWithSynonyms`** — see deliverable 6 below
   - **`SearchResult` struct** (defined inside POISearchIndex.cs):

SearchTokenizer.cs — Design rules:

Use CultureInfo.InvariantCulture for all string operations (culture-independent — important for Portuguese accented characters which are the primary use case).
Accent folding: input.Normalize(NormalizationForm.FormD) then new string(c.Where(ch => CharUnicodeInfo.GetUnicodeCategory(ch) != UnicodeCategory.NonSpacingMark).ToArray()) then Normalize(NormalizationForm.FormC) — this is the standard C# approach for diacritic stripping.
The deduplication preserves first-occurrence order. This is important because the first token is often the most semantically significant.
Edge case: input like "São João" → after NFKD + diacritic stripping → "Sao Joao" → lowercase → "sao" + "joao". Verify this in a test with the exact accented characters.
Edge case: input like " hello world! " → after split → ["hello", "world"] (no empty strings).
POISearchIndex.cs — Design rules:

The inverted index is a Dictionary<string, List<int>>. Each token maps to the set of POI indices that contain it. Since we need stable ordering and deterministic results (for tests), use List<int> not HashSet<int> — deduplication happens at Build time by checking _poiIds before adding an index.
Build replaces the index — calling Build() a second time drops the old index and rebuilds from scratch. This is an explicit design choice (not additive) to match the lifecycle pattern where a wall session loads config once and builds the index once.
Ranking is computed at Search time, not stored in the index. The index stores only "which POIs match this token". At Search time, for each matching POI, the rank group is determined by re-checking the original POIData fields. This keeps the index simple and the ranking logic testable in isolation.
No LINQ in hot paths. Use foreach, for, manual List.Sort with Comparison<SearchResult> delegate. LINQ OrderBy allocates per call.
ConfigureWithSynonyms is stored as private List<SynonymGroup> _synonymGroups. It's applied during Build() — not during Search() — so there's zero per-query cost for synonym expansion.

Wrapped entirely in #if UNITY_EDITOR ... #endif (not just [CreateAssetMenu] conditional) so the type never exists in a build.

WHY: Architectural rationale
search_keywords on both taxonomy AND POIData: The taxonomy level lets a wall author tag "all religious POIs have keywords [worship, faith]" in one place. The POI level lets them add per-POI exceptions ("this church was also a fortress" → add "fortress"). This mirrors the exact same additive-exception pattern that category_styles already uses over the deterministic hash colour. No new architectural concept.
Build(WallConfigData) instead of Build(List<POIData>): The index must read taxonomy-level search_keywords and hierarchy level labels at build time. If it only received List<POIData>, the caller would need to flatten taxonomy data into each POI before calling Build — that's a leaky abstraction that couples the caller to internal taxonomy structure. Passing WallConfigData keeps the flattening logic inside the search index where it belongs.
SearchTokenizer in Runtime/POI/: Tokenization is a pure data-domain concern (transforming strings into normalized query tokens). It doesn't reference Unity, UI, or any framework concept. It sits alongside POISearchIndex because they're consumed together.
SearchSynonymGroups in Editor/: The synonym groups are authoring-time assets that are resolved into flat search_keywords at config save/bake time. The runtime never needs to know about synonym expansion — the baked search_keywords already contain the expanded terms. This follows the project's pattern of keeping authoring complexity out of the runtime assembly.
search_mode as a free string, not enum: A wall author in the future might want a value not in the current set ("voice_only", "image_based", etc.). An enum would require a code change and framework update. A free string lets any wall experiment without forking Framework.
Rank-by-max, not additive sum: If a POI matches query "palacio" with exact name score (1.0) and also matches "sintra" with keyword score (0.7), the final score should be 1.0 (the best match), not 1.7 (which could let an accidental multi-match outrank a genuine exact name match from another POI). This matches standard IR practice where per-document score is max over query terms, not sum.

#### 3. Zoom-on-select wiring
- **No new orchestrator needed if the selection event already flows to a central place** — but to keep layers clean, I'll add a tiny dedicated responder:
  - File: `Assets/Framework/Runtime/UI/Markers/ZoomOnSelectController.cs` (plain C#, no MonoBehaviour).
  - Dependencies:
    - `WallSession` (for `WallConfigData` → read `zoom_on_select_trigger`, `zoom_on_select_density_threshold`, `zoom_on_select_factor`).
    - `ARZoomController` (to call `SetZoomAnimated`).
    - Some way to get the selected unit's `neighborCount` — see WHERE.
  - On `SelectionEventBus.OnMarkerSelected`:
    - Read config; if `zoom_on_select_trigger` is `None` → return.
    - Determine if the selected unit is a marker or cluster:
      - The selection payload (`string poiId`) is ambiguous — it could be a marker **or** a cluster (clusters also need to expose an ID).
      - Solution: make the selection payload richer — either:
        - Option A: Change `SelectionEventBus.OnMarkerSelected` to `OnUnitSelected(string unitId, bool isCluster)`.
        - Option B: Keep `string unitId` and have the listener query a service: `"Is this ID a cluster ID?"`.
        - I'll choose **Option B** to avoid changing the event signature if other consumers only care about the ID. Add a service: `IUnitResolver` with `bool IsCluster(string unitId)` and optionally `int GetNeighborCount(string unitId)`.
    - If the unit type (marker/cluster) matches `zoom_on_select_trigger`:
      - Get `neighborCount = unitResolver.GetNeighborCount(unitId)`.
      - If `neighborCount >= wallConfig.zoom_on_select_density_threshold`:
        - `float target = Mathf.Clamp(ARZoomState.ZoomFactor * wallConfig.zoom_on_select_factor, wallConfig.zoom_min, wallConfig.zoom_max);`
        - `ARZoomController.SetZoomAnimated(target);`
- **Where to get neighborCount**:
  - The `neighborCount` is already computed by `_2.4`'s `LODController` during density evaluation (it lives in the `VisualUnit` struct internal to `LODController`).
  - To avoid breaking encapsulation, add a method to `LODController`: `public int? TryGetNeighborCount(string poiId)` → returns the neighbor count if the POI is active and in LOD controller's tracking, else null.
  - `ZoomOnSelectController` calls this; if null → skip zoom (treat as not meeting threshold).

### WHY: Architectural Rationale
Following the project's core principles (`10-structure.md` §1.1, `20-code-quality.md`):

- **Framework/apps boundary**: Zero wall-specific code — all new files live in `Framework/Runtime/` and depend only on abstractions (`WallConfigData`, `IWallTracker`-adjacent systems like `LODController`, `MarkerView`). No `Apps/*` references.
- **Editor/runtime boundary**: All new files are pure runtime — no `#if UNITY_EDITOR`, no UnityEditor dependencies. Editor tooling (Block 5) will live in `Assets/Framework/Editor/` and reference these Runtime types (allowed direction).
- **Domain-centered folders**: All new marker-related code lives in `UI/Markers/` — groups by what they do (marker interaction), not by technical type (`Scripts/`).
- **No Utils.cs**: Each new class has a single, clear responsibility:
  - `MarkerSelectable` → tap detection only.
  - `SelectionEventBus` → decoupled pub/sub only.
  - `SelectionHighlightController` → highlight/dim logic only.
  - `ZoomOnSelectController` → zoom-on-select logic only.
  - `IUnitResolver` → contract for unit-type/neighbor queries only.
- **Thin MonoBehaviours**: `MarkerSelectable` is the only new MonoBehaviour — it does only Unity lifecycle + event wiring; zero decision logic.
- **Configuration is data**: All tunables live in `WallConfigData` (selection_highlight_enabled, zoom_on_select_trigger, zoom_on_select_density_threshold, zoom_on_select_factor) — no hardcoded values in C#.
- **Prefer simple duplication**: The highlight/dim logic reuses the existing `MarkerView.SetVisible` fade method — no new animation system built. Zoom-on-select reuses `_2.4`'s `ARZoomState`/`ARZoomController` — no second zoom math.
- **Session/orchestrator classes stay thin**: The new controllers (`SelectionHighlightController`, `ZoomOnSelectController`) are plain C# classes with no Unity lifecycle — they are invoked by `WallSession` (the orchestrator) which calls them in sequence when a selection event arrives. No logic leaks into `WallSession` itself.
