### 2.2 Component map (one line each — read the file itself for behaviour)

| Component | Role |
|---|---|
| `MarkerView` | Root orchestrator. `Initialise(anchor, outlineMode, useBadge, shape, badgeShape, ...)` — the real entry point every spawn path must call. Resolves category/custom-symbol/status and wires every sub-component below. It also switches the effects (see `_2.2.4_Markers_Effects.md`). |
| `MarkerCircleGlyphView` | One reusable "coloured shape + centred icon" element — used at two sizes/positions for both Symbol and Badge. `SetBackgroundVisible(bool)` supports `MarkerShape.None`. |
| `MarkerRingView` | The status ring/contour. Colour from `StatusLevel` (gold ramp or same-hue-drained-to-black), dash pattern from `lineStyleLibrary` (falls back to the fixed 5-slot `RingSpriteSet` if unassigned). `SetRotating(bool)` for `rotate_contour`. |
| `MarkerCircleSpriteFactory` | Single shared source of runtime-generated circle/ring sprites (`GetRing`/`GetFilled`), used by the effect layers. Domain-reload-safe caching (explicit `== null` checks + `[RuntimeInitializeOnLoadMethod]` reset) — don't reimplement sprite generation anywhere else. |
| `SpriteKeyLibrary` | Generic `{key -> Sprite}` lookup, reused for icons, shapes, and ring line styles. Framework defaults referenced directly by the prefab; wall-local overrides loaded via `Resources.Load` at a config-supplied path — see `_5.1_Editor_Tab.md` §14 for the full asset-pipeline explanation. |
| `CategoryPalette` / `BadgeCategoryPalette` | Hash-based fallback colour + `Configure`/`ClearOverrides` for wall-authored `category_styles`/`badge_categories`. |
| `StatusRamp` | Resolves a status level (by `status_level_key` or nearest `pct`) to a colour + dash pattern; `ShadeTowardBlack` for `OutlineSameHue`; includes semantic unknown fallback level (`unknown` → dotted + neutral grey). |

## 2.5 Design principles (read once, apply throughout)

1. **`category` and `status` stay free-form wall data, forever.** Confirmed by the
   real `LivingRoom/config.json`: its categories (`furniture`, `art`, `test`,
   `electronics`) share nothing with the Panorama-wall taxonomy
   (`religious`/`military`/…) used in the design prototype. Never hardcode a
   category switch statement anywhere in this stage — this is why `CategoryPalette`'s
   fallback is a deterministic hash, not a fixed lookup table.
1b. **A wall can still hand-pick specific category colours/icons.** The hash
   fallback guarantees *every* category renders distinctly with zero authoring, but a
   dev may reasonably want "religious" to be a specific violet, not whatever the hash
   lands on. `WallConfigData.category_styles` (§7 Step 2) is an *optional*, *additive*
   list — any category not listed still falls through to the hash/`KnownIcons` path
   untouched. This is the resolution to "let the dev put whatever colours they want,
   but give a good default" raised early in the design discussion for this stage:
   automatic default + optional explicit override, not one or the other.
2. **`marker_style` and `marker_shape` ARE fixed enums.** They are a *rendering*
   choice the framework itself offers (3 styles, 5 shapes), not wall content — the
   opposite case from principle 1. Stored as plain strings in `config.json` (not
   native C# enum fields) because Unity's `JsonUtility` enum serialization has been
   inconsistent across versions; a string parsed with a safe fallback avoids that
   risk entirely. This is the same reasoning already applied to
   `captured_position_source` elsewhere in `WallConfigData`.
3. **A ring that fades to invisible is a bug.** It becomes indistinguishable from a
   POI that has no status axis at all (a real case — a mural has no "destroyed"
   axis). Every status level renders fully opaque; gradation is dash rhythm + colour
   warmth only. "No status axis" is a *structurally separate* case (no ring/badge
   element at all), gated by `has_status`, never by a faded value. There is a third,
   equally distinct case — `status_unknown` (§7 Step 2): this wall *does* track
   status, and this specific POI's fate is a genuine historical unknown, not merely
   undocumented in this dataset. Rendered as its own universal grey "?" badge (§7
   Step 7), never blended with either the "no axis" case or any known percentage.
4. **Symbol and Badge are the same component.** Both are "a coloured shape with a
   centred icon" — `MarkerCircleGlyphView` is used for both, just different
   size/position/content. Likewise `SpriteKeyLibrary` (a plain key→Sprite lookup) is
   used as both the icon library and the shape library — same data shape, one class.
5. **Sprite-swap over shader/particle, by default.** Dashed rings and shapes are
   pre-made PNGs recoloured via `Image.color`, not a procedural shader — the same
   low-tech, easy-to-debug pattern already used elsewhere in this project (see
   `_2.2.4_Markers_Effects.md` section 3 for the one deliberate exception: the runtime-generated effect layers).
6. **MonoBehaviours stay thin.** `MarkerView` wires things together; it does not
   decide colours, shapes, or ramps. `CategoryPalette`, `StatusRamp`, and
   `MarkerLayout` are plain static C# classes with no Unity lifecycle — easy to unit
   test, easy to read end to end.
7. **Any icon a dev wants reduces to one workflow.** Hand-drawn line art, an
   emoji-style PNG, a downloaded icon pack, a photo — import as a Sprite (2D and UI),
   add one entry to `IconLibrary.asset`. No second rendering path is needed to
   "support emoji" — a dev who wants that look just imports an emoji-style PNG. TMP's
   built-in emoji sprite asset (`EmojiOne.asset`, already in this project) is
   available for zero-import placeholder testing, but is not wired into this system;
   it isn't needed since Sprite import already covers that case.

## 2.6 Where visual constants live — architecture decision

This project already draws a hard line between two UI systems (see
`_0_work_plan.md`, the `UI/` folder comment): **uGUI** for `Markers/` and
`NextStopArrow.cs` (world-space, physically placed), and **UI Toolkit** for
everything else (screen-overlay chrome — toasts, panels, guide dialogue), themed
through a central `DesignTokens.uss` (`--ts-color-primary`, `--ts-font-body`, etc.).

That existing split already answers the "where do marker colours live" question:
**`DesignTokens.uss` is explicitly scoped to UI Toolkit chrome.** It is a USS file —
not readable from uGUI C# code without a custom bridge — and its stated contents
(corner radius, spacing scale, motion curve) are generic UI-chrome concerns, not
POI-domain semantics. Routing marker colours through it would require inventing that
bridge for no benefit, and would falsely couple two things that mean different
things: "the app's brand accent colour" and "what religious-building-60%-destroyed
looks like."

### The general principle (why, not just what)

A single global "AppColors" file that holds *every* colour used anywhere is a false
economy once one domain (here: markers) needs colours that are **generated from
runtime data**, not authored design decisions — `CategoryPalette.ResolveColor` hashes
an arbitrary wall-defined string; there is no finite palette to centrally enumerate.
Forcing it into a shared namespace also creates accidental coupling: a future
developer changing "the app's warning colour" could unknowingly shift what
"destroyed" looks like on markers, or vice versa. This is the same reasoning
Domain-Driven Design calls a **bounded context** (Evans, 2003) — each subsystem owns
the vocabulary meaningful to *it*; sharing happens at an explicit boundary, not by
default.

The opposite extreme — zero shared foundation, every component invents its own
colours *and* fonts — loses product cohesion: nothing stops two UI domains drifting
to different typefaces or accent colours over time.

The resolution used throughout mature design systems (Curtis, 2020; the Design
Tokens W3C Community Group; Material Design's colour-role system) is a **tiered
token model**:

- **Global tokens** — raw values, no meaning yet (a hex code, a font file).
- **Semantic/alias tokens** — a *cross-cutting* meaning applied at the app level
  (`--ts-font-body`, `--ts-color-primary`) — this is what `DesignTokens.uss` already
  is, correctly scoped to UI Toolkit chrome.
- **Domain/component tokens** — a meaning that only makes sense *inside* one
  subsystem (`CategoryPalette`, `StatusRamp`) — owned by that subsystem, not the app
  shell.

### Concrete decisions for this project

| Concern | Where it lives | Why |
|---|---|---|
| Marker category colour | `POI/CategoryPalette.cs` (already built, this stage) | Generated from wall data, meaningless outside the marker domain |
| Marker status colour/ring/dash | `POI/StatusRamp.cs` (already built, this stage) | Same — a domain-specific ordinal scale, not a brand colour |
| UI Toolkit chrome colours/radius/spacing | `DesignTokens.uss` (already planned, unrelated to this stage) | Cross-cutting brand identity for screen-overlay UI |
| **Font family, app-wide** | **TextMeshPro's own default asset mechanism** (`Project Settings → TextMeshPro → Settings`, the *Default Font Asset* field) | Unity/TMP already solves "one font everywhere" natively — every `TextMeshProUGUI` component that doesn't explicitly override its Font Asset field inherits this one. No custom C# class needed; this is the simplest-robust-approach principle applied directly. **Action for this stage: leave `labelText`'s Font Asset field on the `POI_Marker` prefab unset/inherited — do not assign a font per-prefab.** |
| Marker layout proportions (badge offset, ring size ratio, label gap) | `UI/Markers/MarkerLayout.cs` (this stage, §7 Step 5) | Domain-specific composition rule, not a brand token |

Do not create an `AppTheme`/`DesignTokens.cs` C# asset in this stage. If a second
uGUI UI domain is ever built that genuinely needs to share 1–2 brand colours with
markers (unlikely — markers are the only planned uGUI content), *that* is the moment
to extract a minimal shared asset — not before (YAGNI).

Note on typography across the two rendering systems: UI Toolkit (USS `font-family`)
and uGUI/TMP (`TMP_FontAsset`) use different technical font resource formats, so "one
font app-wide" is a *process* discipline (both reference the same underlying
typeface file) rather than something one shared C# token class can enforce across
both systems mechanically. Worth a one-line note in the project's design doc, not a
code abstraction.

## 4. Bibliography / references

Used to ground the architecture decisions in §5 and §7 (design-token tiering,
bounded contexts, uGUI layout mechanics):

- Evans, E. (2003). *Domain-Driven Design: Tackling Complexity in the Heart of
  Software*. Addison-Wesley. — bounded context concept, used to justify marker
  colours as domain-owned rather than centralized in a global palette.
- Curtis, N. (2020). "Naming Tokens in Design Systems." *EightShapes*.
  https://medium.com/eightshapes-llc/naming-tokens-in-design-systems-9e86c7444676
  — the global/alias/component three-tier token model referenced in §5.
- Design Tokens Community Group, W3C. *Design Tokens Format Module* (draft
  specification). https://design-tokens.github.io/community-group/format/ — formal
  reference for the tiered-token concept in general use across the industry.
- Frost, B. (2016). *Atomic Design*. https://atomicdesign.bradfrost.com/ — general
  reference for hierarchical composition of design decisions (informs the
  global→semantic→component framing, though not quoted directly).
- Material Design (Google). "The Color System." https://m2.material.io/design/color/
  — example of a large production design system's colour-role architecture,
  referenced as a real-world comparison point for the tiered model.

  Practices*. Prentice Hall. — Single Responsibility Principle, underlying the

- Unity Technologies. *RectTransform* and *Transform* class documentation, Unity
