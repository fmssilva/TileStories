# Labels, Text & Fonts (2.0)

Everything about text typography across the app: today, a marker's persistent text label (gap
from the Symbol, font size, font choice), wall-default-with-per-level-override; tomorrow, UI
Toolkit screen-space typography (the POI detail card and beyond) once that need is concrete.
Numbered `_2.0` (ahead of `_2.1_Marker_Orientation.md`) because it is meant to become the one
place every text/font decision in the app lives, not a sub-topic of the marker domain. Renamed
from `_2.3.1_Labels_Design.md` on 2026-09-22, the same day the underlying editor UI was
substantially reorganized (own top-level Global Scene section, per-level overrides made visible
and fixed, the confusing "Label" field renamed) -- this file is the single source of truth for
that work and should be read instead of any prior session's summary. **Scope today: uGUI marker
labels only** (`Runtime/UI/Markers/`). Sibling docs: `_2.2.1_Marker_Design.md` (the marker
Symbol/background this label sits under), `_2.3_Marker_Hierarchy.md` (the Hierarchy Levels
table this domain's per-level override lives in), `_5.1_Editor_Tab.md` (the POI Editor window).

**Audience:** an agent or developer with full Unity Editor + project access and no chat history.
Everything here was re-derived from the code on disk and real test runs, most recently 2026-09-24.

## 2. Concepts

### 2.1 Ratio, not absolute distance/point size

`label_gap_ratio` (Symbol-bottom to label-top distance) and `label_font_size_ratio` (the
label's TMP font size) are both expressed as a multiple of the Symbol's own diameter -- the
same proportional-sizing convention `ring_size_ratio`/`badge_size_ratio` already use. One
number reads correctly at every hierarchy level's own size automatically: a 30cm "Hub" marker
and a 5cm "detail" marker both get a proportionally correct gap and font size from the same
wall setting, with no per-level tuning needed for the common case. This was a real,
pre-existing bug before 2026-09-22: `labelGap` used to live only as a hardcoded, never-wall-
configurable field on `POI_Marker.prefab`, at a fixed absolute distance regardless of a
level's actual size, and font size was similarly fixed.

### 2.2 Per-level override: why it exists alongside the wall-default ratio

The ratio design already solves "does this look right at every size" for the common case. The
per-level override exists for the case the ratio genuinely can't cover: a *deliberate*
exception, most often accessibility (keeping one level's text large and legible even though
its marker is visually small), or a stylistic choice (one hero level using a distinct,
heavier font while the rest of the wall reads consistently). This reasoning survived a real
second look: an earlier pass the same day considered and rejected a per-level override,
reasoning the ratio already solves the common case and a per-level override "would risk
inconsistent typography across tiers." That reasoning is still correct for the *default* case
-- it is why the override is opt-in (inherits the wall default until a level explicitly sets
one), not a second independent per-level default a developer has to fill in for every row. What
changed is recognizing a real, named use case (accessibility) the ratio-only design has no
answer for at all: no wall-level ratio can simultaneously be "correctly proportioned for every
level" AND "always large enough to read, even on the smallest marker" -- those only diverge for
outlier levels, which is exactly what an opt-in override is for.

### 2.3 The font-type system

`FontKeyLibrary` (`Runtime/UI/Markers/FontKeyLibrary.cs`) is a `{key -> TMP_FontAsset}`
ScriptableObject lookup, structurally identical to `SpriteKeyLibrary`
(`_2.2.1_Marker_Design.md`) but kept as its own class: a font asset is a genuinely different
resource type, and Unity's generic-ScriptableObject serialization would cost more machinery
than this small duplication does (`20-code-quality.md`'s "prefer simple duplication" rule).

The framework default, `Runtime/UI/Markers/FontLibrary.asset`, ships three keys:
- `liberation_sans` -- the framework's original default (`LiberationSans SDF.asset`,
  `Assets/TextMesh Pro/Resources/Fonts & Materials/`), a clean, neutral body sans.
- `roboto_bold` -- a bolder, more legible sans at small marker sizes.
- `oswald_bold` -- a condensed bold face, useful for longer labels on smaller markers where
  horizontal space is tight.

All three are Google Fonts, OFL-licensed, sourced from Unity's own bundled TMP package
(`com.unity.ugui`'s "TMP Examples & Extras", already pre-built as TMP SDF font assets with
correct atlas/shader references -- no manual SDF atlas generation was needed). Their `.ttf`
sources and OFL license text ship alongside them in `Runtime/UI/Markers/Fonts/` for
provenance.

**Recipe for adding a wall's own font (UI-driven).** A font first has to become a TMP SDF asset
(Unity's own `.ttf` -> TMP Font Asset step, which this window cannot shortcut); after that it is
one drop:
1. In the Project window, select the `.ttf` and run `Window > TextMeshPro > Font Asset Creator`
   (standard Unity workflow).
2. In the POI Editor, drop that TMP Font Asset on **"Add font"** -- under the Font popup in
   "Labels, Text & Fonts" or in a level's Marker Label Style window, the same control in both.
   The first time, this creates the wall's `FontKeyLibrary` next to its other marker assets,
   seeded with the framework's 3 fonts, and sets `label_font_library_resources_path`. The font is
   registered under a key from its asset name (`"Oswald Bold SDF"` -> `oswald_bold_sdf`, `_2`/`_3`
   on a clash; the same font twice reuses its entry) and selected in the popup it was dropped under.
3. Every Font popup now offers that key alongside the framework's 3.

Once a wall has its own library it REPLACES the framework default entirely at runtime (same rule
`WallIconLibrary`/`marker_icon_library_resources_path` already follows), which is why the new
asset is seeded with the framework's 3 entries. "Select Font List" (shown once a library exists)
opens it in the Inspector for renames/removals; "Stop Using Wall Fonts" clears
`label_font_library_resources_path` back to the framework default only, without deleting the
asset (the next "Add font" finds it again).

### 2.4 The "Label" field rename: level_name (2026-09-22)

`HierarchyLevelEntry.label` (JSON key `"label"`) is renamed to `level_name` (JSON key
`"level_name"`), everywhere: the C# field, `config.json`'s 5 hierarchy-level entries, and
every call site (`GlobalScene.cs`, `EffectsPreviewSpawner.cs`, `OutlinePreviewSpawner.cs`'s
sibling `OutlineLevelEntry.label` field is UNRELATED and untouched, `LivePlayModeMarkerApplier`,
`POISearchIndex`, `SpecificMarker.cs`, and every test that constructs a `HierarchyLevelEntry`).
No `[FormerlySerializedAs]` shim: `WallConfigData` uses `JsonUtility`, not Unity's binary
serializer, and the safest way to carry the existing 5 values across the rename was a direct
text edit of `config.json` in lockstep with the C# rename (verified by loading afterward), not
relying on an attribute whose `JsonUtility` support was uncertain enough not to risk silent
data loss on.

**Why this needed fixing, not just cosmetic renaming in the UI.** This field is a
developer-facing name for the LEVEL ITSELF -- shown in the per-POI "which hierarchy level"
dropdown -- and has never had anything to do with what text appears under any actual marker on
the wall (that is always the POI's own name, resolved completely separately, in
`MarkerView.ApplyLabelState`). The old field/column name ("Label") invited exactly the confusion
a developer hit: mistaking "the level's own identifying name" for "the text a marker shows."
(The demo grid made the same mistake until 2026-09-24 by showing the level name under its level
cells; it now shows the Base marker's own name, exactly as a real POI at that level would --
`_2.3_Marker_Hierarchy.md` section 6.) Leaving the C# field still called
`label` while the UI called it something clearer would have just relocated the same confusion
into the source, so both were renamed together, following this project's own precedent (the
`labelGap` -> `labelGapRatio` rename).

**Why level_name, not priority, as the identifying name.** Priority alone cannot serve as a
level's human-facing identity: two levels are explicitly allowed to share the same priority (a
tie is legal, per `_2.3_Marker_Hierarchy.md` section 3), so it cannot disambiguate them in a
dropdown or a log message the way a name can.

### 3.2 Resolution order (`MarkerView.ApplyVisuals`)

1. `ResolveHierarchyStyle(poi)` -- gets this marker's `HierarchyStyle` (a demo grid cell passes
   its level's `StyleOf` result as a style override instead).
2. If `OverridesLabelStyle`: gap, font-size ratio and font key all come from the level; else all
   three come from `_settings` (the wall default). One switch, one `if`.
3. Font size is applied as `labelText.fontSize = (SizeCm / 100f) * ratio`.
4. The font key is looked up
   in `_settings.FontLibrary ?? fontLibrary` (wall override, else the prefab's own framework
   default); a missing key leaves the TMP component's current font untouched (null-safe,
   matches the icon-fallback convention -- never crashes on a bad key).

`layout.labelGapRatio` is set here, in `ApplyVisuals`, not in `UseSettings` (which runs
before the per-POI hierarchy level is even resolved) -- moved specifically to make the
per-level override possible; safe because `ApplyLayout()`, the method that actually reads
`labelGapRatio`, runs at the end of the same `ApplyVisuals()` call.

## 4. Editor

**Wall defaults** -- its own top-level Global Scene section, **"Labels, Text & Fonts"**,
placed first (ahead of Marker). Its content sits inside a collapsible **"Marker Label"**
sub-foldout (opens by default, since it is this section's one real content group): Gap slider
(0-1.0), Font size slider (0.08-1.5), Font popup (the 3 framework keys plus any extra key the
wall's own `FontKeyLibrary` defines, `GetAvailableFontKeyOptions` --
`AssetPaths/POIEditorToolWindow.AssetPaths.cs`), then **"Add font"** (the shared
`DrawLabelFontRows`, section 2.3), and -- once the wall has its own font list -- a "Select Font
List" / "Stop Using Wall Fonts" row. Same shared field-drawer helpers every other section uses,
own Test sub-foldout (Scene/Playmode/Device guides) carrying an **"Add Labels demo grid"** switch
-- the same `effect_defaults.preview` flag Effects and Hierarchy Levels also surface.

**Per-level: the "Marker Label Style" window** -- Hierarchy Levels table, "Marker Label" group,
the "Aa" button (bold while that level overrides). A real draggable utility `EditorWindow`, one
instance (opening another level's "Aa" retargets it), titled only "Marker Label Style" in its
title bar, with no inner title and no Close button (the title bar's X closes it). Content:
- a small grey context line, "Hierarchy level: <name>", so it is clear which level it edits;
- one bold checkbox, **"Override global label config"**, with its (i) help;
- Gap and Font size sliders (the shared limits) and the shared Font + "Add font" rows.
Unticked, the rows are read-only and SHOW the current wall default, so they visibly follow any
change made in "Labels, Text & Fonts"; ticked, they edit this level only and never write the wall
default. Ticking seeds the level from the wall default, so its markers do not jump; unticking
keeps the level's values (ignored until it is ticked again, which re-seeds).

**How it edits (the one data path).** `LevelLabelStylePopup` is only popup content (shown in the
POI Editor's one shared floating popup window, `EditorPopup`: drag it anywhere, X or Esc closes it): its `Draw`
calls the owning POI Editor's `DrawLevelLabelStyleEditor(levelKey)`, which runs the fields inside
that window's own `DrawConfigMutationScope`. So an edit here gets exactly what a field in the
main window gets: undo/redo (Ctrl+Z works while this window has focus -- it calls the owner's
`HandleUndoShortcuts`), the unsaved flag, the Scene-view rig refresh (the override is visible in
Edit Mode too) and the live Play Mode push. The level is looked up BY KEY on every repaint: Undo
replaces the whole config object, so a cached reference would keep editing a stale copy. When the
level no longer exists (deleted or undone away) the window closes itself. Deliberately its own
component, not `EntryDetailsPopup` reused: that holds a free-text note, this holds functional
config (`20-code-quality.md`).

**Design history (kept for the thesis).**
- 2026-09-22: the fields started as a `PopupWindowContent`. Two real bugs: its `OnGUI` runs outside
  the main window's `DrawConfigMutationScope`, so edits never reached a running wall; and
  `PopupWindow.Show` is a transient, non-draggable dropdown. Replaced by a real `EditorWindow` that
  pushed live edits itself.
- 2026-09-24: that self-push still bypassed undo/redo, the unsaved flag and the Scene rig refresh,
  held a direct reference that went stale after an Undo, and showed three separate "override"
  checkboxes over a sentinel data model (`<= 0` / `""` = inherit) plus a duplicated inner title and
  a redundant Close button. Replaced by the current design: one `override_label_style` switch with
  plain values (one `if` in `MarkerView` instead of three sentinel checks), the window as a thin
  shell over the owner's mutation scope, and one shared font drawer. At the same time the demo
  grid, which built its own `HierarchyStyle` and silently dropped every label override, was moved
  onto `MarkerHierarchyResolver.StyleOf`.
- 2026-09-26: the window's good behaviour (draggable, X to close, non-blocking, edits through the
  owner's mutation scope, held by key) became the ONE popup kind of the whole POI Editor
  (`EditorPopup`, `_5.1_Editor_Tab.md` "Popups: the two kinds and when to use which"); this window
  became its `LevelLabelStylePopup` content, next to help, notes, the symbol picker and notices.

*(Considered and rejected: an inline expandable row instead of a floating window at all --
avoids the popup problem entirely, but reflows every row below it for something used rarely
per level, worse for "easy to find fast" than a small window you can park to the side.)*

## 5. Camera persistence in the demo grids (2026-09-22)

Not this domain's own field, but fixed the same day and worth recording here since it directly
affects testing this domain live: **a developer editing anything in the Marker/Hierarchy
domain while Play Mode ran saw the effects/outline demo grid's camera reset to its auto-fit
framing on every single edit**, making it impossible to stay zoomed in on one marker while
tuning its label.

**Root cause:** `WallSession.ApplyMarkerSettings`/`ApplyEffectSettings` destroy and respawn the
whole demo-grid `GameObject` on nearly every live edit (`EffectsPreviewSpawner`/
`OutlinePreviewSpawner.TrySpawn`). The new root gets a brand-new `EffectsPreviewFocus`/
`OutlinePreviewFocus` component, whose `DevPreviewCameraDolly` is a fresh instance field --
so pan/zoom always restarted at zero. Not a dolly bug: nothing carried the old dolly's offset
across the rebuild gap.

**Fix:** `DevPreviewCameraDolly.SetOffsets(pan, zoom)` (new, absolute-set, unlike the existing
delta-based `ApplyPan`/`ApplyZoomDelta`). `WallSession.RebuildEffectsPreview`/
`RebuildOutlinePreview` (new, replacing the old inline `Destroy` + `Spawn...Preview()` call
sites) read the outgoing Focus's dolly offset immediately before `Destroy` (safe: `Destroy`
only schedules destruction for end-of-frame, the component is still valid when read), then
apply it to the new Focus's dolly right after respawn. `ClampedPan` already re-clamps against
the new grid's own extent every frame, so a drastically different layout can't leave the
camera looking at nothing -- no extra safety code needed. The offset lives on the GameObject's
own component chain, not a new `WallSession` field, so it naturally resets when Play Mode
stops.
