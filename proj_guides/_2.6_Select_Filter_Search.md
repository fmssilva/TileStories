# Select, Filter & Search (2.6)

Tap-to-select markers/clusters (with optional local zoom-in for precision
on small/dense targets), facet filtering (category/badge/outline/
hierarchy level), keyword search (typed and voice), and three ways to
view results (list, minimap, camera highlight). Plus a deliberately
minimal `DetailCard` — enough to prove selection works end-to-end, not
the future full content card. All net-new except one wide-reaching
extension: `search_keywords` added as a column on four *existing* tables
(§6), not a new isolated system.

## 1. Scope

**In scope:** tap-to-select (marker + cluster), optional zoom-on-select,
facet filtering, keyword search (typed + voice), structured per-POI
keyword fields, synonym authoring (3 tiers), minimap, results list, view
toggle, no-results/recent/suggested search UX, a minimal proof-of-life
`DetailCard`.

**Explicitly out of scope:**
- The full `DetailCard` (6-block content system, scroll view, spring-up
  animation) — future domain; this one builds the empty shell it will
  extend, nothing more.
- Local-magnifier zoom as a *standalone* feature independent of
  selection — only the selection-triggered version (§11) is in scope
  here; a general-purpose magnifier-on-demand is a different feature.
- True ML/embedding-based semantic search — deliberately not built;
  §6's synonym system is the chosen alternative, with reasoning.

## 2. Framework philosophy, restated for this domain

Every option below is a real, developer-selectable choice, not a
hardcoded decision — same discipline as `_2.3`-`_2.5`.

**Libraries used, with exact integration paths, not just names:**
- **Voice search**: `yasirkula/UnitySpeechToText`
  (`https://github.com/yasirkula/UnitySpeechToText`) — wraps Android's
  native `SpeechRecognizer` and iOS's `Speech` framework behind one C#
  API. Add via Package Manager → "Install package from git URL" using
  the repo URL above, or import the `.unitypackage` from its Releases
  page. Do not write native Obj-C/Java plugin code from scratch — this
  is a maintained wrapper for exactly this need.
- **WordNet-assisted synonyms (§6, optional tier)**: no existing C#
  package is good enough to depend on (the two found —`WordNetSharp`,
  `WordNet.Net` — are old, poorly documented, licensing-ambiguous per
  their own communities). Instead: bundle a **trimmed** extract of
  Princeton WordNet's raw data files (noun/adjective synsets only,
  filtered to vocabulary plausibly relevant to buildings/architecture —
  a few MB, not the ~25-35MB a full conversion runs) as an Editor-only
  asset, with a small custom parser (the raw WordNet index/data file
  format is simple and documented — this is a real but modest build, not
  importing a package). **Editor-only — never ships in the built app.**
- **Everything else** (tokenizer, search index, ranking, minimap, list,
  filter tray, selection) — hand-rolled. No good existing fit for any of
  these at this project's scale and shape; importing something here would
  add a dependency to save writing code that's small and specific to this
  exact schema. Same "write it, don't import it" call as `_2.5`.

## 5. Search index & matching — `POISearchIndex.cs`

New file, `Runtime/POI/`, sibling to the other resolvers, but shaped
differently — it's a **built index**, not a stateless lookup, since
search needs to scan every POI's full keyword set per query:

```csharp
public static class POISearchIndex
{
    // Built once when wall config loads (mirrors StatusRamp.Configure's
    // timing), rebuilt if config changes at runtime (Editor live-edit).
    public static void Build(WallConfigData config, IEnumerable<POIData> pois);

    // Tokenizes + normalizes the query, matches against every POI's
    // full keyword set, returns ranked results. Empty query -> empty list,
    // not "everything" (that's what clearing search/filters does).
    // candidatePoiIds: the set to search within — pass every POI's id for
    // an unfiltered search, or the already-facet-narrowed id set from
    // §7's FilterTrayView for a combined search+filter query. Facets
    // narrow first, search ranks within whatever they leave — the same
    // composition order the "tray" pattern (§7, §22) itself describes:
    // facets and search are two inputs to one result set, not two
    // independent, separately-displayed outputs.
    public static List<(POIData poi, float score)> Search(string query, IEnumerable<string> candidatePoiIds);
}
```

**`search_mode` (§3) — the actual operational difference, not just a
label:** `"dynamic"` (default) calls `Search()` on every keystroke (or a
short debounce, e.g. 150ms, to avoid searching on every single character
of a fast typist — an implementation detail, not a config field);
`"explicit"` only calls `Search()` when the visitor submits (return key /
a search button), useful for a developer expecting a very large wall
where re-running search per keystroke would feel laggy or wasteful — not
a concern at this project's actual POI-count scale, but the config exists
for the developer building an unusually large wall who wants the
control.

**Per-POI searchable set, precomputed once per `Build()` call into a
small internal struct — not methods hung on `POIData` itself.** `POIData`
stays pure data (matches how it's treated everywhere else in this
project); resolving categories/hierarchy/badge/outline into searchable
text needs `WallConfigData` context `POIData` doesn't have, so the
resolved set belongs in the index, not the data class:
```csharp
private readonly struct PoiSearchEntry
{
    public readonly string PoiId;
    public readonly HashSet<string> NameTokens;
    public readonly HashSet<string> CustomFieldTokens;
    public readonly HashSet<string> DerivedLabelTokens; // category/hierarchy/badge/outline + their search_keywords
    public readonly HashSet<string> OthersTokens;
}
```
Built as the union of:
1. POI name (`weight_name`).
2. Every `POISearchKeywordField.keywords` entry (`weight_custom_field`,
   except the reserved `"others"` field key, which uses `weight_others`).
3. The POI's *resolved* category/hierarchy-level/badge/outline labels,
   **plus each of those entries' own `search_keywords`** (§6) —
   `weight_derived_label`. Resolved live from the POI's current
   assignments, not duplicated into POI data — if a POI's category
   changes, this updates automatically on the next `Build()`, nothing to
   manually re-sync.

**Ranking formula** — sum of field weights for every distinct query
token that matched anywhere in that entry's token sets, sorted
descending:
```csharp
float score = 0f;
foreach (var token in queryTokens)
    if (entry.NameTokens.Contains(token)) score += settings.weight_name;
    else if (entry.CustomFieldTokens.Contains(token)) score += settings.weight_custom_field;
    else if (entry.DerivedLabelTokens.Contains(token)) score += settings.weight_derived_label;
    else if (entry.OthersTokens.Contains(token)) score += settings.weight_others;
// one token can only score once per POI, at its highest-weight match location
```
No secondary scoring for *how* a token matched (exact vs. substring) —
deliberately kept to this one dimension; every successful match counts
equally regardless of match type, per the reasoning already settled: a
second scoring axis would add real complexity for negligible benefit at
this content scale.

**`SearchTokenizer.cs`** — small, pure, testable static utility, same
folder:
```csharp
public static class SearchTokenizer
{
    // lowercase -> Unicode NFD normalize -> strip combining-mark
    // characters (accent-fold, e.g. "Álvaro" -> "alvaro") -> split on
    // whitespace/punctuation. No stemming, no library — confirmed
    // sufficient at this project's content scale; see chat discussion
    // for why (multi-word queries need this; full NLP tokenization
    // doesn't add value here).
    public static List<string> Tokenize(string input);
}
```
Genuinely necessary (a multi-word query like "old church" cannot match a
keyword list of individual words without splitting the query first) but
genuinely trivial — a handful of lines using .NET's built-in
`string.Normalize(NormalizationForm.FormD)`, no dependency.

## 6. Synonyms — three tiers, and where they actually live

**`search_keywords: List<string>` added directly to `CategoryStyleEntry`,
`BadgeCategoryEntry`, `OutlineLevelEntry`, and `_2.3`'s
`HierarchyLevelEntry`** — not a separate synonym-groups table. This
avoids a real sync-drift risk a separate table would have (a category
renamed/deleted in its own table could silently orphan a same-keyed entry
in a second table with no structural link back). The category/badge/
outline/hierarchy row *is* the group; one field, not a second system.

**Three ways to fill this field in, all writing to the same field, none
required over another:**
1. **Manual** (default) — developer types keywords directly in the new
   table column.
2. **WordNet-assisted** (optional, offline, free) — a "Suggest synonyms"
   button per row, opens a small popup with WordNet-derived candidates
   the developer accepts/edits/rejects individually. Uses the trimmed
   data extract + custom parser from §2. Zero network, zero API key.
3. **AI-assisted** (optional, advanced) — an "Ask AI" button per row,
   calls an LLM API using a key the developer supplies in a new Editor
   Preferences-style settings field (`AISynonymSettings` — API endpoint,
   API key, stored via `EditorPrefs`, never in `config.json`). For cases
   WordNet can't help with — project-specific or culturally-specific
   vocabulary (e.g. "azulejo" relating to Portuguese tilework) a generic
   lexical database wouldn't know. Editor-time only, real per-call cost
   (developer's own API usage), off the runtime app entirely.

**This touches real, already-shipped code** (`CategoryStyleEntry` etc.
are pre-existing, not new to this domain) — the same table-editing UI
(`DrawSymbolTable`) gets one new column added in four places
(Category/Badge/Outline tables via the shared drawer, Hierarchy table
directly), not four separate new UI builds.

## 7. Filter — facets, the "tray" pattern, no-results state

Four independent, combinable facets: category, badge category,
outline/status level, hierarchy level — each a multi-select chip/toggle
group, all visible simultaneously alongside results (NN/G's
"faceted-search-with-a-tray" pattern — no separate screen, no "apply"
step; toggling a facet updates the visible result set immediately).

**`FilterTrayView.cs`** — UI Toolkit, lives in the same
`PanelSettings`-backed `UIDocument` as everything else in this domain.
Facet options are populated from whatever categories/badges/outline
levels/hierarchy levels the wall's config actually defines — never a
hardcoded list. Produces the narrowed POI-id set §5's `Search()` takes as
its `candidatePoiIds` argument — this is the concrete mechanism behind
§5's composition note; the filter tray doesn't display its own separate
result set that search then re-filters, it feeds directly into the one
search call.

**No-results state** — `no_results_message` (§3) with a `{query}`
placeholder, plus a computed **"relax filters" suggestion**: when zero
results and more than one facet is active, compute which single facet
removal would yield the most results, offer it as a one-tap action
rather than making the visitor guess which filter is blocking them.

**Filtered/searched results reveal via `_2.3`'s existing
`CanvasGroup`-based fade** (`MarkerRevealEffect`'s mechanism, same
`reveal_delay_s`/`reveal_duration_s` fields already on each hierarchy
level) — not a second animation system built for this domain.

## 8. Minimap — a UI element, not a second camera

**Deliberately not** the standard Unity minimap pattern (a second
orthographic camera rendering to a `RenderTexture`) — that exists to
*create* a 2D top-down view for 3D game worlds that don't otherwise have
one. This project already has one: `POIData.x_norm`/`y_norm` (confirmed
pre-existing, §0). A flat wall's minimap is a scatter-plot of coordinates
already in the schema.

**`MinimapView.cs`** — a `VisualElement` sized to represent the wall's
aspect ratio, with a child element per visible POI absolutely-positioned
at `(x_norm * width, y_norm * height)`. No camera, no `RenderTexture`, no
extra render pass. `minimap_icon_style` (§3) controls whether each dot is
plain, category-colored, or a scaled-down copy of the actual marker icon.
Tap a dot → same selection path as tapping the real marker (§11) — one
selection system, two possible input surfaces feeding it, not two.

Built to double as the future home for search/filter result highlighting
even though filtering into it is this domain's own job already — no
retrofit needed for the reason it doubles: the same POI-list-in,
dot-positions-out shape already is what a filtered result set needs.

## 11. Selection — tap detection, zoom-on-select, highlight

**`MarkerSelectable.cs`** — new small component on `POI_Marker.prefab`,
implements `IPointerClickHandler`, reuses the already-confirmed
`GraphicRaycaster` on the prefab's Canvas (§0) — no custom raycasting.
On tap: resolve `PoiId`, raise a selection event.

**Zoom-on-select** — reuses `_2.4`'s `ARZoomState`/`ARZoomController`
directly, does not add a second zoom mechanism. `zoom_on_select_trigger`
(§3) controls whether this fires for individual markers, clusters, both,
or neither; `zoom_on_select_density_threshold` gates it further — only
auto-zoom if the selected unit's `VisualUnit.neighborCount` (already
computed by `_2.4`'s density evaluation) meets or exceeds this, so an
isolated, easy-to-tap Level-1 marker doesn't get an unnecessary zoom, only
ones that actually need the precision help. This is the concrete
implementation of Hoang & Thomas's Augmented Viewport technique (§22) —
zoom specifically to improve tap accuracy on small/distant/dense targets,
not a general "make everything bigger" behavior.

**Selection highlight** — `selection_highlight_enabled` (§3): dims
non-selected markers via `MarkerView.SetVisible(true, fadeDuration)` at
partial alpha (reusing the existing fade-capable method, not a new one),
selected marker stays at full visibility. Clearing selection restores
everyone via the same call.

Selecting anything opens the minimal `DetailCard` (§14).

## 12. Voice search

**`VoiceSearchController.cs`** wraps `yasirkula/UnitySpeechToText` (§2).
On a successful transcription, the result string feeds through the exact
same `SearchTokenizer.Tokenize()` → `POISearchIndex.Search()` pipeline
typed search already uses — **not a separate voice-specific search
system**, one preprocessing step (speech → text) ahead of the same
pipeline.

`voice_search_match_mode` (§3): `"all"` (default) requires every
remaining token to match — "churches Alfama" means churches *in* Alfama,
not an OR across both; `"any"` is available for developers who prefer
broader recall over precision.

**Off by default** (`voice_search_enabled = false`) — real, stated
caveats, not hypothetical: iOS requires two separate permission prompts
(microphone + speech recognition), the on-device model needs an initial
download from Apple on first use (not instant), and `SFSpeechRecognizer`
has documented real-world reports of falling back to a server call even
when on-device recognition is explicitly requested. A developer should
opt in knowingly, not discover this friction in production.

## 13. Recent & suggested searches

**Recent** — last `recent_search_count` (§3) queries, stored device-local
(`PlayerPrefs` or a small local JSON file — not synced anywhere, this is
device UX polish, not data worth a backend).

**Suggested** — `show_suggested_categories` (§3): computed live from the
wall's *actual* category distribution (e.g. a wall that's 80% religious
buildings surfaces "religious" as a suggestion), not manually curated by
the developer — one less thing to maintain, and it can't go stale as POIs
are added or removed.

## 15a. Accessibility — a real requirement, not a config toggle

Unlike everything else in this doc, accessibility isn't a developer
choice to expose in the Editor — it should just work. Unity's first-party
Accessibility module (added 2023.2 Tech Stream, actively extended through
current 6.x releases) supports both uGUI and UI Toolkit as entry points
into the same screen-reader system (TalkBack/VoiceOver), but **support
existing doesn't mean it's automatic** — every `VisualElement` this
domain adds (filter tray chips, search field, results list rows, minimap
dots, the DetailCard's label and close button) needs its
`AccessibilityRole` and a readable label set explicitly. Build this in
from the start for each new element, not as a pass at the end — retrofitting
accessibility roles across a dozen already-built elements is real,
avoidable extra work.

**Verify with Unity's own Accessibility Hierarchy Viewer** (a built-in
Editor tool, `Window > Accessibility > Hierarchy Viewer` or current
equivalent menu path — confirm exact path against the project's actual
Unity version, menu locations have moved between releases) during Phase A
— this is the concrete Tier 0.5 check (§17) for this requirement, not an
open-ended "make sure it's accessible."

## 17. Phase A — isolated verification

Per `40-testing.md` §4.4. Extend `_2.4`'s shared spatial harness
(`Assets/Dev/LODGallery/`) rather than building a new scene — it already
has spatially-distributed fabricated markers with real distance/density
variation, exactly what filter/search/selection testing also needs.

- **Tier 0**: fabricate a small POI set with known names/categories/
  custom keywords, assert `POISearchIndex.Search()` returns the exact
  expected ranked order for several queries (including a query that
  should rank a name-match above a category-label-match, confirming the
  weight formula, not just that *some* match happened).
- **Tier 0**: `SearchTokenizer` — assert accent-folding works (`"alvaro"`
  matches a keyword list containing `"Álvaro"`), assert multi-word
  splitting, assert lowercase normalization.
- **Tier 0**: facet filtering — assert combining two facets narrows
  correctly (AND across facets), assert the "relax filters" suggestion
  picks the facet whose removal yields the most results.
- **Tier 0**: zoom-on-select threshold — fabricate a dense and a sparse
  region, assert zoom fires only for the dense one when a density
  threshold is configured.
- **Tier 0.5**: minimap dot positions — assert each dot's rendered
  position matches `x_norm`/`y_norm` within tolerance (RectTransform/
  layout assertions, no vision needed). Tap-target size on minimap dots
  and filter-tray chips (44×44px minimum, same check as every prior
  domain).
- **Tier 0.5**: WCAG contrast on the filter tray and results list text
  against their backgrounds.
- **Tier 0.5**: accessibility roles (§15a) — open Unity's Accessibility
  Hierarchy Viewer against the built filter tray, search field, results
  list, minimap, and DetailCard; confirm every interactive element
  appears in the hierarchy with a non-empty role and label. This is the
  concrete check §15a promises, not a vision judgment call — either the
  viewer shows a populated, sensible hierarchy or it doesn't.
- **Tier 1 (vision, itemized checklist, not open-ended)**: one screenshot
  each of the three result views (list/minimap/camera-highlight) for the
  same filtered set.
  > List view: are all and only the expected POIs shown? [yes/no]
  > Minimap: do dot positions visually match where those POIs actually
  > are on the wall (roughly left/right/up/down as expected)? [yes/no]
  > Camera-highlight: are non-matching markers visibly dimmed relative to
  > matching ones? [yes/no]
  > DetailCard: does tapping a marker show its name and close correctly
  > on "X"? [yes/no]

Do not proceed to live wiring/Phase B until every item above is green.
