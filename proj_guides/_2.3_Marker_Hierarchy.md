# Marker Hierarchy (2.3)

Wall-configurable, developer-defined levels (as many as wanted, labelled
freely) that drive one POI marker's **size, label visibility, effect
combination, outline rotation, and reveal delay** — replacing the old binary
`is_hero` concept entirely. Distance/screen-space size compensation and
LOD/marker-count management are **explicitly out of scope** — deferred to
future domain docs; see §1.

## 1. Scope boundary

**In scope:** hierarchy level definition, per-level size/label/effects/
rotate-contour/reveal-delay, per-POI level assignment, custom-symbol
override (renamed from hero).

**Explicitly out of scope, do not implement:**
- Distance/screen-space size compensation (root `Transform.localScale`
  continuous adjustment). `size_cm` below is the marker's fixed real-world
  size, full stop — it is **not** adjusted for viewing distance in this
  pass. That's a separate future domain doc.
- LOD / marker-count management (show/hide by distance, clustering). All
  markers render, always, regardless of distance, in this pass.
- Renaming `RingPulse` (naming confusion noted, not fixing now).
- Level-1-as-wayfinding-anchor tap behaviour, printable field-guide export.

If implementing this plan surfaces a reason either deferred item needs to
be touched, stop and flag it rather than expanding scope silently.

## 2. Data model — `WallConfigData.cs`

New class, sibling to `OutlineLevelEntry`, same explicit-per-row shape (not
formula-driven — Option A, decided over ratio/hybrid alternatives):

```csharp
[System.Serializable]
public class HierarchyLevelEntry
{
    public string key;             // stable id, e.g. "level_1"
    public string label;           // developer-facing, e.g. "1" or "Landmark"
    public string details;         // free text, developer's own notes (§6)
    public int priority;           // explicit, developer-set — lower number = higher
                                    // priority, matching "Level 1" being most important.
                                    // NOT derived from row position (see note below).
    public float size_cm;          // Symbol diameter, real-world cm
    public bool show_label;
    public string sun_effect;      // "none" | "sun_contours" | "sun_circles"
    public string accent_effect;   // "none" | "ring_pulse" | "simple_sun" | "beacon"
    public bool pulse;
    public bool rotate_contour;    // meaningful only when wall outline mode != none
    public float reveal_delay_s;    // seconds after spawn before fade/scale-in begins
    public float reveal_duration_s; // seconds the fade/scale-in animation itself takes
}
```

**Why `priority` is its own explicit field, not derived from list position
(correction from an earlier draft of this doc, which used row index):**
using row order as an implicit priority signal is fragile and invisible —
a developer reordering rows for display/organization purposes (nothing
stops that; this is a normal list UI) would silently change priority as a
side effect, with no indication anything meaningful just happened. An
explicit `priority` column is visible, directly editable, and decoupled
from display order — the developer can see and set exactly what "more
important" means without it being an implicit consequence of row
position. Duplicate priority values across levels are allowed (not
validated against) — ties are meaningful and already handled by
`_2.5_Displacement.md`'s tiebreak logic, not an error state.

Wall-level: `public List<HierarchyLevelEntry> hierarchy_levels = new();`

**Why `reveal_duration_s` is per-level, not a wall-level scalar (correction
from an earlier draft of this doc):** every other visual property in this
table — size, effects, even the reveal *delay* right next to it — is
already per-level, because different levels legitimately want different
treatment (a Level 1 hero marker might warrant a slower, more dramatic
reveal; a Level 5 marker should probably just snap in quickly). Making
duration the one wall-level exception was an inconsistency, not a
deliberate simplification — there was no actual reason for it beyond not
having thought it through. Corrected: it's a column in the table like
everything else, and the wall-level `HierarchySettings` wrapper this
earlier draft introduced just to hold this one field is removed entirely
— an empty-after-this-fix wrapper object is exactly the kind of
speculative structure `20-code-quality.md` warns against; if a genuine
wall-wide hierarchy setting is needed later, add the wrapper back then,
not preemptively now.

`POIData` changes:
- **Add**: `public string hierarchy_level_key;`
- **Add** (hero replacement, isolated to just this one job):
  `public bool has_custom_symbol;` / `public string custom_symbol_key;`
- **Remove** (§12, last step, not yet): `is_hero`, `hero_icon_key`,
  `effect_mode`, `rotate_contour`.

**Why `size_cm` not `size_m`:** Unity/Immersal both use metres as their
internal unit, but that's an engine convention, not a reason to expose it
to a human typing numbers. cm avoids the decimal-place transcription error
class (0.02 vs 0.2) that metres invites for marker-scale objects. One `/100`
conversion, at one call site (§9), is the entire cost.

**Why explicit-per-row, not base+ratio:** matches every sibling taxonomy
(`category_styles`, `badge_categories`, `outline_levels`) — no new mental
model, no formula for a developer to reverse-engineer when hand-editing
`config.json`, full control per level.

## 3. Runtime resolver — `MarkerHierarchyResolver.cs`

New file, `Assets/Framework/Runtime/POI/`, sibling to `StatusRamp.cs`,
same shape:

```csharp
public readonly struct HierarchyStyle
{
    public readonly float SizeCm;
    public readonly bool ShowLabel;
    public readonly MarkerEffectFlags EffectFlags;
    public readonly bool RotateContour;
    public readonly float RevealDelaySeconds;
    public readonly float RevealDurationSeconds;
    // ctor assigns all six
}

public static class MarkerHierarchyResolver
{
    // Deliberate exception to "authored-only, suppress if missing" (Editor
    // Tab §8): a 0cm marker is invisible, not gracefully degraded, so the
    // fallback size matches today's prefab default (12cm) rather than 0.
    // RevealDurationSeconds similarly needs a non-zero fallback (0.35s,
    // matching the earlier hardcoded default this doc's fix replaced) —
    // a 0-duration reveal is an instant, jarring pop-in, not a graceful
    // degrade. Every other field defaults to the visually-inert value.
    public static readonly HierarchyStyle Fallback =
        new HierarchyStyle(12f, false, MarkerEffectFlags.None, false, 0f, 0.35f);

    public static void Configure(IEnumerable<HierarchyLevelEntry> entries);
    public static void ResetToDefaults(); // clears to empty -> Fallback always
    public static bool TryResolveByKey(string key, out HierarchyStyle style);

    // Added for _2.5_Displacement.md's tiebreak logic, not this doc's own
    // original scope — noted here since it's this resolver's rightful
    // responsibility, discovered while grounding that later domain. Solves
    // a real gap this doc and _2.4_LOD.md both had: "lower level number =
    // higher priority" was assumed but never defined for a free-form
    // string key. Reads the explicit HierarchyLevelEntry.priority field
    // (not list index — see the note above §2's schema block for why an
    // earlier draft's list-index approach was corrected), backed by the
    // same data Configure() already captured — no new dependency, just a
    // second lookup alongside the existing one.
    public static bool TryResolvePriority(string key, out int priority);
}
```

**Confirmed convention as actually implemented** (a genuine refinement
beyond what this doc originally specified, worth preserving): priority
is a pure 1-based sort key. An explicit author value `>= 1` is used
as-is. A value `<= 0` (including the default for any config predating
this field) means "unset," and falls back to the level's 1-based
position within the `hierarchy_levels` list — this is **not** the
list-index approach this doc explicitly rejected earlier (§2's own note
above) reintroduced by the back door; it's a deliberate, narrower
fallback that only activates when a developer hasn't set an explicit
priority at all, keeping old configs (predating this field) working
without requiring every level to be manually re-authored. Unknown/blank/
null keys resolve to `int.MaxValue` — always lowest priority, always
loses every tie, which is exactly what `_2.4`'s count-cap truncation
needs (drop unknowns first). A `GetLevelPriority(string key)` convenience
wrapper also exists, returning `int.MaxValue` directly on failure rather
than requiring the `out`-parameter pattern — used by `LODController`.

`Configure` parses `sun_effect`/`accent_effect` strings into
`MarkerEffectFlags` bits (`"sun_contours"` → `SunContours`, etc.; unknown/
`"none"` → no bit) and ORs in `Pulse` when `entry.pulse` is true. Keep this
parsing local to this file — it's the only consumer.

## 4. Wiring — three call sites, not one

**This is the single most important fix in this revision.** An earlier
draft of this doc only wired `MarkerHierarchyResolver.Configure()` into
`WallSession.cs`, missing that `POIAuthoringToolWindow.RigLifecycle.cs`
has its **own, independent** `Configure()` calls for `CategoryPalette`/
`BadgeCategoryPalette`/`StatusRamp` — confirmed in code at two locations
(`PopulateRig` and `RefreshRigVisuals`), completely separate from
`WallSession`. `WallSession` is a Play-Mode runtime path; the Editor's
authoring rig never runs it. **Without adding the same line to all three
places, Edit-Mode preview (§15) cannot work as designed** — the
resolver's static dictionary stays empty in Edit Mode, and every marker
silently renders at `Fallback` regardless of what the Hierarchy table
actually contains, no error, no warning, just visibly wrong sizes that
would be easy to misread as "the table isn't wired to the prefab" when
the real cause is "the resolver was never told the table exists."

Add the identical line to all three, matching each site's own existing
guard-or-unguarded style (no new guard needed, §4's original point about
`Configure` on an empty list already falling through to `Fallback` still
holds):

```csharp
MarkerHierarchyResolver.Configure(_config.hierarchy_levels);
```

- `WallSession.cs`, alongside its existing three `*.Configure(...)` calls.
- `POIAuthoringToolWindow.RigLifecycle.cs`, `PopulateRig` — alongside its
  `CategoryPalette`/`BadgeCategoryPalette`/`StatusRamp` calls.
- `POIAuthoringToolWindow.RigLifecycle.cs`, `RefreshRigVisuals` — same,
  second location. **These two RigLifecycle sites are the ones §10
  already flags for `effectFlags` resolution — this Configure() call is a
  second, separate thing both of those same two sites also need. Don't
  fix one and assume the other is covered by fixing effectFlags; they're
  independent requirements that happen to live in the same two methods.**

## 5. Reveal effect — `MarkerRevealEffect.cs`

New component on `POI_Marker.prefab`'s root, alongside `MarkerBillboard`.
Requires adding a `CanvasGroup` to the prefab root (currently absent —
confirmed by search).

- `public void Play(float delaySeconds, float durationSeconds)`: coroutine
  — `yield return new WaitForSeconds(delaySeconds)`, then lerp
  `CanvasGroup.alpha` 0→1 and root `localScale` 0→1 over
  `durationSeconds`, smoothstep eased. Both parameters come from the
  resolved per-level `HierarchyStyle` (§3), not a wall-level setting or a
  hardcoded constant — corrected from an earlier draft that made duration
  the one wall-level exception among an otherwise fully per-level table.
- Called once, at the end of `MarkerView.Initialise(...)`, with
  `hstyle.RevealDelaySeconds` and `hstyle.RevealDurationSeconds` (both
  resolved in §9, from the same cached `_resolvedHierarchyStyle`).
- **Edit-Mode guard, mandatory:** the "start hidden" (alpha=0, scale=0)
  state must only apply when `Application.isPlaying`. In Edit Mode
  (authoring tool populate/refresh), always show at full alpha/scale
  immediately — coroutines don't tick in Edit Mode anyway, so without this
  guard, markers would render invisible while a developer is placing them.
  This is the exact §4.4.1 hazard class — flagging explicitly here so it
  isn't rediscovered as a "bug" later.
- **Cross-domain handoff contract with `_2.4_LOD.md`, now concrete rather
  than a vague heads-up** — `_2.4_LOD.md` §6 exists now and specifies
  exactly what it needs: its `shrink_and_fade`/`hybrid` density response
  multiplies the *same* `CanvasGroup.alpha` and applies its own size
  multiplier on top of this domain's hierarchy-level size, continuously,
  every evaluation cycle. For that to compose correctly rather than fight
  this effect: **`MarkerRevealEffect`'s coroutine must settle at exactly
  `alpha = 1` / `localScale = Vector3.one` and then stop touching either
  value** — it must not keep writing to them every frame after the reveal
  animation completes. This leaves both channels at a clean, known
  baseline for `_2.4`'s `LODController` to multiply against once it
  starts evaluating. A reveal effect that kept nudging alpha/scale
  indefinitely (e.g. a subtle idle breathing effect bolted onto the same
  mechanism later) would silently corrupt whatever density factor `_2.4`
  computes, since the two would be multiplying against a constantly
  shifting baseline instead of a settled one. If a persistent idle effect
  on these same channels is ever wanted, it belongs in `_2.4` or a later
  domain that already owns continuous evaluation, not here.
- **Still separately deferred (§1, §17), not `_2.4`'s concern either:**
  distance/screen-space size compensation. When that future domain is
  built, it will need the same settled-baseline contract described above
  — read/write the same `localScale` channel only after this effect's
  coroutine has finished, or use a distinct transform/multiplier entirely
  rather than fighting this one.

## 6. Global Scene → Hierarchy table

New foldout in `POIAuthoringToolWindow.GlobalScene.cs`, positioned after
Outline. Row-per-level, no cap on row count (matches every other table).

**Columns, in order:**

1. **Label** — text field.
2. **Priority** — int field, writes `priority`. `(i)` button (§7):
   "Lower number = higher priority. Used when levels compete for a
   limited slot (LOD count caps) or conflict (Displacement's tiebreak) —
   not tied to this row's position in the table, and not auto-filled from
   it. Duplicate values across levels are allowed and meaningful (a tie),
   not an error." Positioned right after Label since it's the other
   field that identifies what this row *means*, before Details (which
   only explains it) and Size (which is a visual property, not an
   ordering one).
3. **Details (`...`)** — reuses `EntryDetailsPopup` exactly as-is (same
   component, not reimplemented). Developer's own free-text explanation of
   what the level means — this is *data*, saved into `config.json`
   (`details` field, §2), intended for a future in-app legend. Positioned
   3rd — the Outline table's own Details column sits 2nd, this table's
   differs by one because Priority claims that slot instead (Category/
   Badge table's own `DrawSymbolTable` puts Details later still — a
   pre-existing minor inconsistency across tables, noted, not fixed in
   this pass).
4. **Size (cm)** — float field, writes `size_cm`. `(i)` button (§7):
   "Real-world printed size of the marker Symbol. This is not yet adjusted
   for viewing distance — that's a separate future feature." **Soft
   sanity check, not a hard clamp** (a genuinely oversized wall mural might
   legitimately want a large level-1 marker, so don't block it) — if a
   typed value falls outside roughly 0.5-100cm, show a non-blocking
   Editor warning icon next to the field (e.g. "unusually large/small —
   confirm this is intentional") rather than silently accepting a likely
   decimal-place typo (0.5 vs 5 vs 50 is an easy mistake when typing cm
   values, the same class of error §2 chose cm specifically to reduce, not
   eliminate).
5. **Show Label** — dropdown, "Show Label" / "NOT show Label" (explicit
   wording per earlier decision, clearer than a bare checkbox specifically
   here).
6. **Sun Effect** — dropdown: None / Contours / Circles. Mutually exclusive
   by construction (single `MarkerSunEffect` component, one style at a
   time — confirmed in code).
7. **Accent Effect** — dropdown: None / Ring Pulse / Simple Sun / Beacon.
   Mutually exclusive by construction (single `MarkerAccentEffect`
   component; code has an explicit priority order `RingPulse > SimpleSun >
   Beacon` if ever misconfigured, but the dropdown makes that unreachable).
8. **Pulse** — checkbox (not dropdown — plain boolean, no third state;
   dropdown-for-a-boolean adds a click with no clarity gain here, unlike
   Show Label which needed worded clarity). Independent of both effect
   families — `Pulse` is its own standalone component.
9. **Rotate Contour** — checkbox, **shown only when the wall's Outline
   toggle (§4.3 of Editor Tab doc) is on** — same conditional-visibility
   pattern already used elsewhere in that table. **Correction to earlier
   assumption:** despite its name, `RingPulse` (Accent Effect column,
   above) is *not* tied to the outline — it renders on the Symbol's own
   RectTransform, independent of whether the outline/ring is enabled.
   Only this column is outline-gated.
10. **Reveal Delay (s)** — float field, `reveal_delay_s`. No enforced
    ordering, no auto-generation from level number — developer sets any
    value per row, including non-monotonic or repeated values.
11. **Reveal Duration (s)** — float field, `reveal_duration_s`. How long
    the fade/scale-in animation itself takes, independent of the delay
    column next to it (delay = *when* it starts, duration = *how long* it
    runs) — per-level, not a wall-wide setting, for the same reason every
    other visual property here is per-level: a Level 1 marker might
    warrant a slower, more dramatic reveal than a Level 5 one. `(i)`
    button clarifying the delay/duration distinction, since the two
    columns sitting next to each other with similar names is an easy
    place for a developer to mix them up.
12. **Remove** button.

No starter-row seeding for this table (unlike Category/Badge) — hierarchy
levels are wall-specific in a way category/badge/outline aren't; an empty
table falling through to `Fallback` (§3) is a safe, correct empty state.

## 9. `MarkerView.cs` refactor

Only after §8 is fully verified. Two methods change; `Initialise(...)`'s
signatures **do not change** (preserves the gallery's ability to pass raw
`MarkerEffectFlags` directly for combinations no real hierarchy level
uses — see the fallback rule below).

**`ApplyVisuals()`** — near the top, after resolving category. **Cache the
resolved style in a field** rather than leaving it to be re-resolved
elsewhere — this is a deliberate decision, not left open for whoever
implements it. Cache the success flag too, as a separate field — the
`effectFlags` fallback rule below needs to distinguish "resolution
succeeded" from "resolution failed, substituted `Fallback`," which
`_resolvedHierarchyStyle` alone can't express (`Fallback.EffectFlags` is
`None`, a real value, not a marker meaning "ignore me"):
```csharp
private HierarchyStyle _resolvedHierarchyStyle; // new field, class-level
private bool _hasHierarchy;                     // new field, class-level

// inside ApplyVisuals():
_hasHierarchy = MarkerHierarchyResolver.TryResolveByKey(poi.hierarchy_level_key, out var hstyle);
_resolvedHierarchyStyle = _hasHierarchy ? hstyle : MarkerHierarchyResolver.Fallback;
symbol?.RectTransform.sizeDelta = Vector2.one * (_resolvedHierarchyStyle.SizeCm / 100f);
```
(`ApplyLayout()` at the method's existing last line already re-derives
everything else — no other change needed for size.)

Replace the icon-override condition:
```csharp
// was: poi.is_hero && !string.IsNullOrWhiteSpace(poi.hero_icon_key) ? poi.hero_icon_key : iconKey
string resolvedIconKey = (poi.has_custom_symbol && !string.IsNullOrWhiteSpace(poi.custom_symbol_key))
    ? poi.custom_symbol_key : iconKey;
```

Replace the rotate line:
```csharp
// was: ring?.SetRotating(showRing && poi.rotate_contour);
ring?.SetRotating(showRing && _resolvedHierarchyStyle.RotateContour);
```

**Effective `effectFlags` — fallback rule, this is the one subtle part:**
if `_hasHierarchy` is true, use `_resolvedHierarchyStyle.EffectFlags`
(real per-POI production path). If false (no `hierarchy_level_key` set —
e.g. the gallery/tests calling `Initialise` directly with hand-built flags
and no hierarchy config loaded), keep using the `effects` field already
set by the `Initialise(...)` parameter, exactly as today. This is what
lets the gallery keep testing arbitrary effect combinations (including
ones no real hierarchy level uses) without every test needing a matching
`HierarchyLevelEntry` to exist.

**`ApplyHeroState()`** — rename to `ApplyLabelState()` (the concept it
names no longer exists; keep the method's job — label show/hide, sizing —
identical, just re-source the boolean). **Reads the field cached by
`ApplyVisuals()` above, does not re-resolve** — `Initialise()` calls both
methods synchronously in the same call, so there's no reason for a second
lookup, and a cached read guarantees both methods agree even if that
ever changes:
```csharp
// was: bool isHero = _anchor.Data.is_hero;
bool showLabel = _resolvedHierarchyStyle.ShowLabel;
```
No fallback path for this one — `is_hero` is fully retired, not dual-path.

Update the call site: `Initialise(...)` calls `ApplyVisuals();
ApplyHeroState();` → `ApplyVisuals(); ApplyLabelState();`. **Order
matters** — `ApplyVisuals()` must run first since it populates the two
cached fields `ApplyLabelState()` depends on.

**This is a separate requirement from §4's `Configure()` wiring, not the

silently falling back to whatever raw `effects` was passed here anyway —
which could look like it's working by coincidence during testing and then
break the moment Fallback's actual values differ from what a test happened
to pass in. Verify both independently, don't let one's apparent success
stand in for the other's.

### 11b. Validation — no check for this existed in an earlier draft

Two failure modes silently degrade to `MarkerHierarchyResolver.Fallback`
(§3) rather than erroring: a POI whose `hierarchy_level_key` was never
set, and one that references a level since deleted from the table. Both
are indistinguishable from each other at resolve time, and both currently
have **no warning anywhere** — a developer could add a POI, forget to
assign a level, and get a plausible-looking-enough 12cm marker with no
signal anything's wrong. Add a non-blocking Editor-side validation pass
(natural home: alongside whatever existing config-validation the
authoring tool already runs, e.g. near `POIAuthoringRigSafetyCheck.cs`,
or a simple pass at `Load Config` time) that lists any POI whose
`hierarchy_level_key` doesn't match a key currently in `hierarchy_levels`
— a warning, not a hard error, since `Fallback` genuinely does produce a
safe, visible marker rather than a broken one, but a developer should see
this rather than discover it by noticing a marker looks generic.
