# Marker Hierarchy (2.3)

Wall-configurable, developer-defined levels (as many as wanted, labelled freely) that drive
one POI marker's **size, label visibility, effect combination, outline rotation, reveal
delay/duration, and Facing Options override** -- replacing the old binary `is_hero` concept
entirely. Distance/screen-space size compensation and LOD/marker-count management are
explicitly out of scope; see "Deliberately deferred". This file is the single source of
truth for this domain: read it instead of any prior session's summary, and verify its claims
against the code cited, not the other way around.

Sibling doc: `_2.0_Labels_And_Fonts_Design.md` owns everything about the text label itself (gap,
font size, font type, and a level's own "Marker Label Style" override of all three) -- this file
only owns where that override lives in the table (the "Aa" button, section 6) and its live-config
ownership (section 8).

Verified against disk on 2026-09-24 (full domain review, section 11): `WallConfigData.cs`,
`MarkerHierarchyResolver.cs`, `MarkerView.cs`, `EffectsPreviewSpawner.cs`, `WallSession.cs`,
`GlobalScene.cs`'s `DrawGlobalHierarchySection`, `HierarchyHelp.cs`, `LabelsAndFonts.cs`,
`LevelLabelStylePopup.cs` (was `LevelLabelOverrideWindow.cs`), `RowLayout.cs`'s `TableRowScope`, the four Live Play Mode appliers,
`SpecificMarker.cs`'s `DrawHierarchyLevelDropdown`/`CreateDefaultPoi`, both LivingRoom
`config.json` copies, and the full EditMode (934) + PlayMode (133) suites.

## 1. Scope boundary

**In scope:** hierarchy level definition; per-level size/label/effects/rotate-contour/
reveal-delay/reveal-duration/Facing-override/search-keywords; per-POI level assignment;
custom-symbol override (the old "hero" concept, isolated to just this one job).

**Explicitly out of scope:**
- Distance/screen-space size compensation (continuous `Transform.localScale` adjustment by
  viewing distance). `size_cm` is the marker's fixed real-world size, full stop.
- LOD / marker-count management (show/hide by distance, clustering) -- see `_2.4_LOD.md`.
  `MarkerHierarchyResolver.TryResolvePriority`/`GetLevelPriority` exist for LOD's count-cap
  truncation to consume, but this domain does not evaluate distance or counts itself.
- Renaming `RingPulse` naming confusion (noted, not fixed).
- Level-1-as-wayfinding-anchor tap behaviour, printable field-guide export.

## 2. Data model -- `WallConfigData.cs`

```csharp
[Serializable]
public class HierarchyLevelEntry
{
    public string key;               // stable id, e.g. "level_1"
    public string level_name;        // developer-facing NAME OF THE LEVEL, e.g. "1" or "Hub" --
                                      // NOT a marker's own on-wall text (renamed from `label`
                                      // 2026-09-22, see _2.0_Labels_And_Fonts_Design.md section 2.4)
    public int priority;             // explicit, 1-based sort key (lower = higher priority)
    public string details;           // free text, developer's own notes
    public List<string> search_keywords = new(); // extra terms every POI at this level is indexed with
    public float size_cm;            // Symbol diameter, real-world centimetres
    public bool show_label;
    public bool override_label_style;  // Marker Label Style (_2.0): false = follow the wall default
    public float label_gap_ratio;      // used only while override_label_style is true
    public float label_font_size_ratio;
    public string label_font_key = "";
    public string ripple_effect;     // "none" | "ripple_rings" | "ripple_discs"
    public string halo_effect;       // "none" | "halo_ring" | "halo_disc" | "beacon"
    public bool pulse;               // independent of ripple/halo -- standalone component
    public bool rotate_contour;      // meaningful only when wall outline mode != none
    public float reveal_delay_s;     // seconds after spawn before fade/scale-in begins
    public float reveal_duration_s;  // seconds the fade/scale-in animation itself takes
    public string facing_mode_override = ""; // "" = inherit the wall's facing_mode
}
```

Wall-level: `public List<HierarchyLevelEntry> hierarchy_levels = new();`

`POIData` fields this domain owns: `hierarchy_level_key` (string, resolves against the table
above), `has_custom_symbol` (bool), `custom_symbol_key` (string, icon key from `IconLibrary`
when `has_custom_symbol` is true). The old `is_hero`, `hero_icon_key`, `effect_mode`, and a
POI-level `rotate_contour` are fully retired -- no back-compat shim, correct for a
single-wall thesis codebase with no shipped installs to preserve.

**Design rationale worth keeping (for the thesis writeup):**
- **`priority` is its own explicit field, not derived from row position.** Row order is a
  display convenience a developer can reorder freely for organisation; using it as an
  implicit priority signal would make that reordering silently change priority too, with no
  visible sign anything meaningful happened. Duplicate priorities are legal -- ties are
  meaningful, resolved by whichever consumer reads them (LOD count-cap, Displacement's
  tiebreak), not an authoring error.
- **`reveal_duration_s` is per-level, not a wall-level scalar.** Every other visual property
  in the table is already per-level because different levels legitimately want different
  treatment; making duration the lone wall-level exception was an oversight, not a deliberate
  simplification, and was corrected before shipping.
- **`size_cm`, not `size_m`.** Unity/Immersal use metres internally, but that is an engine
  convention, not a reason to expose it to a human typing numbers -- cm avoids the
  decimal-place transcription error (0.02 vs 0.2) that metres invite at marker scale.
- **Explicit-per-row, not base+ratio.** Matches every sibling taxonomy (`category_styles`,
  `badge_categories`, `outline_levels`): no formula to reverse-engineer, full control per row.
- **Convention basis:** Bertin (1967/1983) treats size as an ordinal, not continuous, visual
  variable -- the basis for choosing discrete author-set levels over a continuous size formula.
  See "Bibliography".

## 3. Runtime resolver -- `MarkerHierarchyResolver.cs`

`Assets/Framework/Runtime/POI/MarkerHierarchyResolver.cs`, same shape as `StatusRamp.cs`.

```csharp
public readonly struct HierarchyStyle
{
    public readonly float SizeCm;
    public readonly bool ShowLabel;
    public readonly MarkerEffectFlags EffectFlags;
    public readonly bool RotateContour;
    public readonly float RevealDelaySeconds;
    public readonly float RevealDurationSeconds;
    public readonly bool OverridesLabelStyle;   // Marker Label Style (_2.0); false = wall default
    public readonly float LabelGapRatio;        // clamped to MarkerVisualSettings' shared limits
    public readonly float LabelFontSizeRatio;
    public readonly string LabelFontKey;
}

public static class MarkerHierarchyResolver
{
    // 0cm/0s-reveal would be invisible/jarring, not a graceful degrade -- Fallback uses the
    // pre-hierarchy prefab default (12cm) and the original hardcoded reveal (0.35s) instead.
    public static readonly HierarchyStyle Fallback = new(12f, false, MarkerEffectFlags.None, false, 0f, 0.35f);

    public static MarkerEffectFlags EffectFlagsOf(HierarchyLevelEntry entry, bool logWarnings = true);
    public static HierarchyStyle StyleOf(HierarchyLevelEntry entry, bool logWarnings = true); // the ONE row -> style conversion
    public static void Configure(IEnumerable<HierarchyLevelEntry> entries);
    public static void ResetToDefaults();
    public static string ResolveFacingModeOverride(string key);     // "" on any failure -- inherit the wall's mode
    public static bool TryResolveByKey(string key, out HierarchyStyle style);
    public static bool TryResolvePriority(string key, out int priority);
    public static int GetLevelPriority(string key);                 // convenience wrapper, int.MaxValue on failure
}
```

`Configure` stores `StyleOf(entry)` per key. `StyleOf` parses `ripple_effect`/`halo_effect` into
`MarkerEffectFlags` bits (ORing in `Pulse` when `entry.pulse` is true; unknown non-empty values log
a warning and are ignored) and clamps the level's label values. It is also what the demo grid
builds its level cells from, so a column can never reach real markers and miss the grid (the grid
once built its own 6-field style and silently dropped every label override).

**Priority resolution convention:** an explicit author value `>= 1` is used as-is. A value
`<= 0` (including a config predating this field) means "unset" and falls back to the level's
1-based position in the table -- this is a narrower fallback than the list-index approach an
earlier draft used (rejected because reordering rows for display would have silently changed
priority), activating only when nothing was explicitly authored, so old configs keep working.
Unknown/blank keys resolve to `int.MaxValue` -- always lowest priority, always loses ties,
which is exactly what `_2.4_LOD.md`'s count-cap truncation needs (drop unknowns first).

## 4. Wiring -- three call sites, not one

`MarkerHierarchyResolver.Configure(_config.hierarchy_levels)` is called at all three places
that maintain the resolver's static state, matching every other palette
(`CategoryPalette`/`BadgeCategoryPalette`/`StatusRamp`) exactly:

- `WallSession.cs` -- the real Play-Mode spawn path.
- `POIEditorToolWindow.RigLifecycle.cs`, `PopulateRig` -- Edit-Mode rig creation.
- `POIEditorToolWindow.RigLifecycle.cs`, `RefreshRigVisuals` -- Edit-Mode rig refresh on every
  config mutation.

Missing either `RigLifecycle` site would leave the resolver's dictionary empty in Edit Mode,
so every marker would silently render at `Fallback` with no error -- easy to misdiagnose as
"the table isn't wired to the prefab" when the real cause is "the resolver was never told the
table exists." Confirmed on disk at all three sites.

## 5. Reveal effect -- `MarkerRevealEffect.cs`

Component on `POI_Marker.prefab`'s root (alongside `MarkerBillboard`), with a `CanvasGroup`
on the same root.

- `Play(delaySeconds, durationSeconds)`: coroutine -- waits `delaySeconds`, then lerps
  `CanvasGroup.alpha` 0->1 and root `localScale` 0->1 over `durationSeconds`, smoothstep
  eased. Both parameters come from the resolved per-level `HierarchyStyle`, never a
  wall-level setting or hardcoded constant.
- Called once at the end of `MarkerView.Initialise(...)`.
- **Edit-Mode guard:** the "start hidden" state only applies when `Application.isPlaying`.
  Coroutines do not tick in Edit Mode, so without this guard markers would render invisible
  while a developer is placing them in the authoring tool.
- **Settled-baseline contract with `_2.4_LOD.md`:** the coroutine must settle at exactly
  `alpha = 1` / `localScale = Vector3.one` and then stop writing to either value.
  `_2.4`'s density response (`shrink_and_fade`/`hybrid`) multiplies the same two channels
  continuously every evaluation cycle; a reveal effect that kept nudging them after settling
  would corrupt whatever density factor `_2.4` computes against a non-fixed baseline. The
  same contract applies to any future distance/size-compensation effect that reads/writes
  `localScale` on this object.

## 6. Editor UI -- Global Scene > Hierarchy Levels

`GlobalScene/POIEditorToolWindow.GlobalScene.cs`'s `DrawGlobalHierarchySection`, a custom
inline renderer, one `TableRowScope` per row (`Shared/POIEditorToolWindow.RowLayout.cs`) --
**not** `DrawSymbolTable<T>` (like Outline, this table's column set is too domain-specific for
the generic symbol-table renderer). `TableRowScope` pays the section's indent once as a leading
space and zeroes `EditorGUI.indentLevel` for the cells: every cell is an `EditorGUI` Rect control
(`Toggle`, `TextField`, `IntField`, `FloatField`, `Popup`), and those run their rect through
`EditorGUI.IndentedRect`, which inside the section's indent scope moved each cell 15 px right and
shrank it as much -- the three checkbox columns' hit boxes slid off their glyphs (clicks did
nothing) and adjacent fields (Delay/Duration, Name/Priority) showed a gap (section 11, corrections). A
`miniBoldLabel` header row, with every group's `(i)` help button right-aligned at the group's
own right edge and its title text left-aligned at the group's own left edge, matches the
Marker/Outline tables' convention exactly (`_5.1_Editor_Tab.md`, "Tables"); self-labelled row
controls (the Ripple/Halo/Facing popups) draw `GUIContent.none` so the header title is not
repeated on every row.

**Column groups, in order** (`TableGapBetweenGroups` between groups, `TableGapWithinGroup`
between siblings inside one). Reorganized 2026-09-22 into 3 clearer groups where "Level
identity" used to mix an identifying name with marker-facing label config:
- **Hierarchy Level Name + Priority + Details** -- Hierarchy Level Name (text, renamed from
  "Label"/`label` to `level_name`, 2026-09-22 -- full rationale in
  `_2.0_Labels_And_Fonts_Design.md` section 2.4: it identifies the LEVEL for humans, and was
  never a marker's own on-wall text, which is always the POI's own name) + Priority (int) + Details
  (`...` popup, `EntryDetailsPopup`, persisted per-row notes). Details' own header cell IS the
  group's one shared `(i)` help button -- no separate blank spacer column, still "right-aligned
  at the group's own right edge" per the established convention, just without the redundant
  middle step.
- **Marker Size (cm)** -- its own group (float, soft 0.5-100cm sanity warning icon), renamed
  from "Size (cm)" to disambiguate from the Marker Label group next to it.
- **Marker Label** -- **Show Marker Label?** (checkbox) + **"Aa"** (opens the "Marker Label
  Style" window for this level; the button text is bold while the level overrides the wall
  default). The window: one bold "Override global label config" checkbox, then Gap / Font size /
  Font / Add font -- read-only and showing the wall default while unticked, editing only this
  level while ticked (seeded from the wall default when ticked). It edits through the POI
  Editor's own `DrawConfigMutationScope` (undo/redo, unsaved flag, Scene rig refresh, live push)
  and holds the level by key -- full design in `_2.0_Labels_And_Fonts_Design.md` section 4. One
  shared `(i)` help button. Not a reuse of `EntryDetailsPopup`: that is a free-text note; this is
  functional config (`20-code-quality.md`).
- **Effects** -- Ripple + Halo (popups, filtered to effects ticked in the Effects section) +
  Pulse (checkbox, greyed out when the Pulse effect is off wall-wide).
- **Spin Ring** -- Rotate Contour (checkbox); the entire group, header included, is hidden
  while the wall's Outline is disabled (meaningless otherwise).
- **Reveal** -- Delay + Duration (float pair), one shared help button explaining the
  distinction.
- **Facing Override** -- popup, `""` = inherit the wall's Facing Options mode.
- **Search Keywords** -- `DrawKeywordListField`, the same shared cell every other taxonomy
  table's Search Keywords column uses.
- **Remove** -- trash button, no header text or help.

No starter-row seeding (unlike Category/Badge/Outline) -- hierarchy levels are wall-specific
in a way those taxonomies aren't; an empty table falling through to `Fallback` is a safe,
correct empty state. `+ Add hierarchy level` seeds `priority = hierarchy_levels.Count + 1`,
12 cm, no label, no effects, 0.35 s reveal, and a key from `NextFreeHierarchyLevelKey`: the
smallest free `level_N` with N >= Count + 1 (the old `"level_" + (Count + 1)` handed out a
duplicate key after a middle row had been deleted -- rows `level_1`, `level_3` -> a second
`level_3`). The key is never shown; the delete tooltip and its confirmation dialog name the
level by its Hierarchy Level Name.

**On per-level Facing Override -- why keep it:** the alternative (dropping it) was weighed and
rejected. It is not speculative: it is fully wired end to end (`MarkerHierarchyResolver.
ResolveFacingModeOverride`, `WallSession`, `MarkerBillboard.ReapplySettings`, `LODController.
ReapplyClusterOrientation`), live in Play Mode via its own `LivePlayModeOrientationApplier`,
and covered by real tests (`OrientationWallSessionIntegrationTests.
SpawnPOIs_HierarchyLevelOverride_BeatsWallDefault`, `OrientationLiveUpdateTests`). Its concrete
benefit: it lets a wall's most important tier stay legible (Always Facing Camera) while lower
tiers sit flat on the wall (Wall Fixed) to reduce visual noise and per-frame rotation cost --
exactly the kind of per-tier behavioural difference this whole domain exists to express.
Removing it would mean unwinding tested Orientation-domain machinery for a feature that already
works, not simplifying dead code.

**Test sub-foldout** (`_5.1_Editor_Tab.md`, "Domain Manual Tests"): at the end of the
section, open by default, guide text in `HierarchyHelp.cs`. No Scene-Mode Preview toggle of
its own -- size and label are already live in the Scene view via the existing Edit-Mode rig
refresh path (section 9 below), so there is nothing separate to toggle. Instead it carries an **"Add
Hierarchy demo grid"** toggle: the SAME `effect_defaults.preview` switch Effects > Test calls
"Add effects demo grid" (one underlying switch, two discoverable entry points -- not a second
spawner, see section 8). Three collapsed guides (Scene/Playmode/Device), same shape as Marker/Badge/
Outline/Effects/Orientation. The guide text describes framework behaviour generically (no real
wall's POI ids or category names -- `_5.1_Editor_Tab.md`, "Domain Manual Tests" > "Guide
content must stay app-agnostic") and names Editor Tab controls only (no doc, code file or class
name). Covered by `HierarchyDesignAuthoringTests`' guide-contract tests (ASCII-only, names every
column group, states plainly what cannot be checked in Scene test, the Device guide says to
untick the demo grid, and a forbidden-terms scan over every hierarchy and labels text: doc and
code names, "LivingRoom", stale column names).

**The demo grid's level cells show the MARKER's name, never the level name (2026-09-24).** A
hierarchy level name is an authoring id (it may be shared-priority, and could later serve as a
search keyword); it is never text under a marker. Each level cell is labelled with the Base
marker's own name ("The Lamp" when a POI named so is chosen, "Plain grey circle" for the
default base -- the same words the Base marker dropdown uses) and honours that level's Show
Marker Label? and Marker Label Style exactly like a real POI at that level. The cell's
GameObject is still named `Preview_Level: <level name>` so it can be found in the Hierarchy
window. The quick/combo rows keep their effect names: those cells are the Effects legend.

**Only one demo grid at a time (2026-09-22):** this grid and Outline's own "Add outline demo
grid" (`_2.2.3`) each build a dedicated camera drawn at "main camera depth + 100" over the
full viewport; with both switches on simultaneously the two cameras tie on depth and one
silently paints over the other, so the losing grid still spawns (cost, POIs, everything) but
is never visible with no signal why. Fixed as mutual exclusion, not a picker dialog: ticking
one automatically unticks the others (`POIEditorToolWindow.DemoGridExclusivity.cs`,
`MakeThisTheOnlyActiveDemoView`, which since 2026-09-25 also covers LOD > Test > "Add LOD demo
field": a grid camera would hide that field), stated inline in the help texts. A blocking
`EditorUtility.DisplayDialog` was deliberately avoided -- it can freeze an Editor session that
is being driven programmatically. `DemoGridExclusivityTests` covers every view against the others.

**Demo grid camera controls (2026-09-22):** scroll wheel zooms, WASD/RMB-drag/Alt+LMB-drag/
arrows pan, driven by the shared `DevCameraInput` (`Runtime/DevTools/DevCameraInput.cs`) --
the same reader `MockLocalizationProvider` uses for the real wall camera, gated on the mouse
actually being over the Game view (fixes an earlier version's scroll also scrolling the POI
Editor's own GUI, since `Mouse.current` is OS-level state, not window-scoped). Deliberately
**pan, never independent rotation**: every cell's `MarkerBillboard` always faces `Camera.main`
(hardcoded), never this grid's own dedicated camera, so an independently-rotated grid camera
would desync from what the cells are actually facing. `DevPreviewCameraDolly`
(`Runtime/DevTools/`) holds the manual zoom/pan offset on top of the grid's own auto-fit
framing, clamped so panning/zooming can push the view off-centre but never lose the grid
entirely. Shared by both demo grids (`EffectsPreviewFocus`/`OutlinePreviewFocus`) by
construction -- one dolly class, one input reader, not two copies.

**Camera position survives a live edit (2026-09-22, follow-up fix):** a developer reported the
camera snapping back to the auto-fit framing on every single editor edit made while Play Mode
ran, since a rebuild used to hand the new grid's Focus component a fresh, zero-offset dolly
(`WallSession.ApplyMarkerSettings`/`ApplyEffectSettings` destroy and respawn the whole grid on
most marker/hierarchy edits). Fixed via `DevPreviewCameraDolly.SetOffsets` plus
`WallSession.RebuildEffectsPreview`/`RebuildOutlinePreview`, which read the outgoing dolly's
offset immediately before `Destroy` (safe: `Destroy` only schedules destruction for end of
frame) and apply it to the new dolly right after respawn -- full rationale and tests in
`_2.0_Labels_And_Fonts_Design.md` section 5, since it was found and fixed alongside that
domain's own work.

**Per-POI (Specific Marker > Marker Style):** `DrawHierarchyLevelDropdown` populates from
`_config.hierarchy_levels`' own `level_name` values, "(none)" clears the key so the marker falls through to
`Fallback`. A read-only note under it (`EffectUsageSummary.DescribeLevelEffects`) shows what
the assigned level actually applies, so a developer never has to jump back to the table just
to check. `+` (add-near) on an existing POI copies `hierarchy_level_key`, `has_custom_symbol`,
`custom_symbol_key`, category, badge, status, search keywords and the three Facing angles from
the source POI (`CreateDefaultPoi(sourcePoi)`) -- only position is left unset, since a new marker
still needs manual placement. "+ Add first POI" (no source) leaves the level at "(none)" on
purpose: Config Validation then flags it, nudging the developer to choose a level instead of the
framework guessing one.

## 8. Live Play Mode config

Every field this table owns is live in Play Mode, split across three appliers by ownership
(`_5.1_Editor_Tab.md`, "PlayMode Live Config") -- each fingerprints only its own columns so an
edit in one domain never re-triggers a sibling's re-apply:

- `LivePlayModeMarkerApplier` -- Hierarchy Level Name, Priority, Details, Marker Size, Show
  Marker Label?, Spin Ring, Reveal Delay/Duration, Search Keywords, and each level's Marker Label
  Style (`override_label_style` + gap/font-size/font key). `WallSession.ApplyMarkerSettings`
  calls `ReplaceHierarchyLevels(...)` + `marker.ReapplyVisuals(...)` on every real marker and
  rebuilds the "Add Hierarchy demo grid" preview (section 6), whose level cells use `StyleOf` -- so a
  Marker Label Style edit reaches the grid too.
- `LivePlayModeEffectsApplier` -- Ripple, Halo, Pulse.
- `LivePlayModeOrientationApplier` -- Facing Override.
- `LivePlayModePoiLevelApplier` (2026-09-24) -- a POI's OWN `hierarchy_level_key` (Specific
  Marker > Marker Style > Hierarchy Level). Its own applier because that one field drives size,
  label, label style, effects and facing at once; folding it into any one domain's fingerprint
  would make that domain re-apply the others. Fingerprint = each POI's `id=hierarchy_level_key`;
  `Apply` calls `WallSession.ApplyPoiHierarchyLevels(pois)`, which updates each spawned marker's
  anchor key, re-applies its visuals (size/label/style/effects, no reveal restart) and re-points
  its billboard at the new level's facing override. It re-applies every matched marker, not only
  changed ones, so the result never depends on which applier ran first in the same push.

Every hierarchy field is now live; nothing in this domain needs Save + Copy + restart to be seen.
(Search Keywords reach the running wall's config live, but the search index itself is built
once at load -- that is the Search domain's own live-update scope, `_2.6`.)

## 12. Marker size/scale bug -- design history (fixed, kept for the thesis writeup)

An earlier stage's marker-prefab rework introduced a real, since-fixed bug worth recording:
`POI_Marker.prefab`'s root `localScale` was changed from `(0.15,0.15,0.15)` to
`(0.3,0.3,0.3)` while the Label's TextMeshPro Font Size was left at its old value (`24`)
after the Label's own compensating child scale had been flattened to `(1,1,1)`. Since
TextMeshPro's Font Size is a local-space unit subject to the same parent-scale
multiplication as any other `RectTransform` value, the effective glyph height became
`fontSize * Label.localScale.y * Root.localScale.y = 24 * 1 * 0.3 = 7.2` -- a single
character roughly 7 metres tall, rendered at the marker's correct, unmoved real-world
position (confirmed via `WallSession`'s existing `dist=` log line matching the pre-bug
baseline, ruling out a position regression). The Symbol was affected the same way,
shrinking to an all-but-invisible 3.6cm behind the oversized letter.

**Root cause, structurally:** two independent scale multipliers (root scale and per-child
scale) doing overlapping jobs is inherently error-prone. **Fix applied:** the root's own
`localScale` was set to a clean `(1,1,1)`, made the *only* multiplier in the whole marker, so
every `sizeDelta`/`anchoredPosition` in the prefab directly means metres with no second
hidden multiplier to account for; Label Font Size was corrected to `0.05` (yielding a ~5cm
glyph height) and Symbol's existing `sizeDelta` (already correct once root scale was fixed)
produces a 12cm circle unchanged. `CanvasScaler` was confirmed NOT to be the cause (per
Unity's own docs, `Reference Pixels Per Unit`/`UI Scale Mode` only affect pixel density for a
World Space canvas, never geometric size) and was left untouched. This is the arithmetic
`size_cm`'s single `/100` conversion (section 2) now protects against recurring: one authored value,
one conversion, one call site.
