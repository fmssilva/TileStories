# Marker & Label Displacement (2.5)

Resolves individual marker/label overlaps that survive `_2.4`'s LOD and
density/clustering pipeline — nudging apart whatever's left crowded on
screen, without hiding or merging anything (that's `_2.4`'s job).
Continuous, re-evaluated every `LODController` cycle, not a one-shot
spawn-time fix. Builds on `MarkerOverlapResolver.cs`, which already exists
and already does part of this job — evolved, not replaced.

## 1. Scope

**In scope:** detecting and resolving individual marker/label overlaps
among whatever `_2.4` already decided is visible, continuously, every
evaluation cycle. Three interchangeable displacement algorithms. Leader
lines. Tiebreak for equal-priority conflicts.

**Explicitly out of scope:**
- Deciding *which* markers are visible or how many — that's `_2.4`.
- Marker/tap-selection UI, local-magnifier zoom — separate future domain.
- Search & filtering — separate future domain.

**Naming note:** earlier discussion used "occlusion" and "displacement"
loosely interchangeably. This domain is named Displacement deliberately —
for a genuinely *flat* wall, markers are coplanar, so there's no true
depth occlusion (one marker literally hidden behind another) the way a
3D scene would have. What looks like overlap at a shallow viewing angle
is screen-space crowding from foreshortening (`_2.4` §5 makes the same
distinction for density evaluation) — this domain resolves that, not
depth occlusion. If this project ever extends to a non-flat/sculptural
wall, true occlusion handling would be a different, currently out-of-
scope problem.

## 2. Framework philosophy, restated for this domain

Every algorithm and parameter below ships as a real, working option — the
developer picks per wall in the Editor, none is hardcoded as "the"
answer. Where research literature suggests one approach is generally
better (below), that becomes the *default*, not the *only* option.

**On using established tooling instead of hand-rolling:** this domain's
actual math (union-find grouping, candidate-position search, force
relaxation) is small enough, and specific enough to this project's exact
`VisualUnit`/screen-space setup, that no external package meaningfully
fits — Unity has no first-party point-label-displacement system, and the
general-purpose ones (GIS label-placement libraries) target a different
problem shape (static printed maps, not a live per-frame AR view). This
is genuinely a "write it, don't import it" case, unlike `_2.4`'s zoom
work — worth stating explicitly rather than silently skipping the
research question.

## 3. Priority ordering — the gap spanning `_2.3` and `_2.4`, resolved here

Both prior docs assumed "lower level number = higher priority" without
ever defining how that's computed from `hierarchy_level_key`, a free-form
string a developer can name anything (`"level_1"`, `"hero"`,
`"background"`). **Resolved as an explicit, developer-set field, not a
derived one** — an earlier draft of this section used the level's index
within the `hierarchy_levels` list, which is fragile: a developer
reordering rows for display purposes would silently change priority as a
side effect, invisibly. Instead, `_2.3_Marker_Hierarchy.md`'s
`HierarchyLevelEntry` gets a new `priority` int field (lower number =
higher priority, matching "Level 1" being most important) — visible,
directly editable in the Hierarchy table, and fully decoupled from row
order.

`MarkerHierarchyResolver.cs` (same file, same pattern as its existing
`Configure`/`TryResolveByKey`):
```csharp
public static bool TryResolvePriority(string key, out int priority)
```
Backed by the same list already captured in `Configure()` — no new data
dependency, just a second lookup (key → `priority` field) alongside the
existing key → `HierarchyStyle` one. Duplicate priority values across
levels are allowed and meaningful (a deliberate tie, resolved by this
domain's own tiebreak logic, §7) — not validated against as an error.
**`_2.3_Marker_Hierarchy.md`'s Implementation Status is patched to add
both the field and this method** — it's that resolver's responsibility,
discovered while grounding this domain, not invented fresh here.

## 4. The screen-space/wall-space mismatch — fix, and why `label_only` sidesteps it

Confirmed by tracing the prefab (Implementation Status, above):
`ApplyOverlapOffset`'s fixed Y-offset is in wall-space, while overlap is
detected in screen-space. Two different fixes for the two `displace
_target` modes:

- **`label_only` (default) needs no fix — it's correct by construction.**
  `labelText.transform` is a *child* of the billboarded root
  (`MarkerBillboard` rotates the whole `POI_Marker` root every
  `LateUpdate` to face the camera). Moving the label via its own local
  `anchoredPosition` is therefore already expressed in camera-relative
  space — local X/Y on a billboarded object *is* screen-right/screen-up,
  automatically, every frame, with no conversion math needed. This is
  the concrete reason `label_only` is the safer default, not just a
  cartographic-convention preference — it's also the mechanically
  simpler, less bug-prone path.
- **`marker`/`both` need a real fix.** `_anchor.transform.localPosition`
  is relative to the *parent* (the wall's fixed anchor), not to the
  billboarded rotation — a fixed axis offset here does not reliably
  resolve screen-space overlap at a shallow viewing angle. Fix: compute
  the desired 2D screen-space offset, then convert to a world-space
  delta using the **camera's current right/up vectors, recomputed every
  evaluation cycle** (`cam.transform.right`, `cam.transform.up`), not a
  fixed world axis:
  ```csharp
  Vector3 worldOffset = cam.transform.right * screenOffset.x * worldPerPixel
                       + cam.transform.up    * screenOffset.y * worldPerPixel;
  ```
  (`worldPerPixel` derived the same way `_2.3`'s deferred distance-
  compensation work would — from the marker's current distance and the
  camera's FOV; a small, self-contained helper, not a dependency on that
  still-unbuilt feature.)

**Step order should build `label_only` first, exactly because it needs
none of this conversion math** — isolates the straightforward path from
the one with real geometry to get right. Full step order is §11a.

## 5. Displacement algorithms — three options, one default, with real citations

Point-feature label placement is a formally studied, NP-hard
combinatorial optimization problem — Christensen, Marks & Shieber's
landmark empirical study (1995, *ACM Transactions on Graphics*, 14(3),
203–232) tested every major approach and found simulated annealing
performs best for static printed maps with unlimited compute budget. That
is not this project's situation — a live AR view at this project's POI
scale (~150 ceiling, tens per visible region after `_2.4`'s thinning)
needs something cheap enough to re-run every evaluation cycle. Three
practical options, all real, developer-selectable via
`displacement_algorithm`:

- **`fixed_axis`** — the existing behaviour, kept as the cheapest option:
  vertical stacking by deterministic index within an overlap group.
  Simplest, but can look mechanical (everything stacks the same
  direction regardless of the group's actual shape).
- **`candidate_position`** — Christensen/Marks/Shieber's own simpler
  model, not their optimal one: try a small fixed set of candidate
  offsets around the true position (8 compass directions at a fixed
  radius), pick whichever has the least remaining overlap with the
  group's other members. Deterministic, no iteration/convergence
  concerns, meaningfully better-looking than fixed-axis for groups of 3+
  without the cost of simulation.
- **`force_directed` (default, per explicit direction)** — treat
  overlapping members as mutually repelling particles; a few relaxation
  steps per evaluation cycle (3-5 is a reasonable starting point, itself
  a config value, see §10):
  ```csharp
  foreach (member in group)
      foreach (other in group, other != member)
      {
          Vector2 delta = member.screenPos - other.screenPos;
          float dist = Mathf.Max(delta.magnitude, 1f); // avoid div-by-zero
          Vector2 repulsion = delta.normalized * (overlap_threshold_px - dist) / dist;
          member.accumulatedOffset += repulsion * relaxation_step_weight;
      }
  // clamp each member's accumulated offset to max_displacement_px after all steps
  ```
  Best-looking result (groups spread naturally to their own shape rather
  than a fixed axis or discrete ring), at real but small extra cost —
  fine at this project's scale, per §2.

## 6. Leader lines

- `leader_lines_enabled` toggle.
- `leader_line_style`: `straight` / `dashed` / `elbow` (right-angle,
  common in infographic callouts) — all three real options.
- `leader_line_min_distance_px` — only draw once displacement exceeds
  this; a small nudge doesn't need one.
- **Color: not a config field.** Reads the marker's own resolved
  category color from `CategoryPalette` at draw time — the same source
  `MarkerView` already uses for the Symbol's background shape. This was
  a deliberate simplification agreed on directly: one less field to
  configure, and the leader line visually "belongs" to its own marker by
  construction rather than needing to stay manually in sync with a
  separately-configured wall-wide color.
- Rendering: a simple `UILineRenderer`-equivalent (a thin `Image` with
  `Image.type = Sliced` stretched between two points, or Unity's
  built-in `LineRenderer` if the leader line should render in the same
  World Space canvas as the marker — either is fine; pick whichever
  integrates more simply with the existing `POI_Marker` canvas setup,
  this is an implementation detail, not a design decision requiring a
  config option).

## 7. Tiebreak, and interaction with `_2.4`'s clusters

`displacement_tiebreak` (`symmetric` / `lower_priority_only`) — **moves
here from `_2.4`'s `LodSettings`, where it was only ever a reserved
placeholder field for a domain that didn't exist yet.** Now that this
domain exists and actually implements the logic, the field belongs in
`DisplacementSettings` (§10), not `LodSettings` — `_2.4_LOD.md` is
patched (alongside this doc) to remove its now-redundant reserved copy
and point here instead. Don't implement both; there is exactly one
`displacement_tiebreak` field, and it lives in this domain's schema.
- `symmetric` — level-agnostic by definition, no tiebreak logic needed;
  every group member's displacement is computed identically regardless
  of priority.
- `lower_priority_only` — the higher-priority member (lower `priority`
  value, §3) stays anchored at its true position; only the lower-priority
  member(s) displace. **Same-priority ties fall back to `symmetric`** for
  that specific pair — no arbitrary asymmetry between equals. An optional
  deterministic secondary tiebreak (farther-from-camera moves, nearer
  stays anchored, using `effectiveDistance` already on `VisualUnit`) is
  available for developers wanting full determinism even among equal
  levels — not a separate config field, just the documented fallback
  order: `priority` value, then distance, then `PoiId` string comparison
  (matching `MarkerOverlapResolver`'s own existing deterministic-ordering
  convention) if genuinely everything else ties.

**Cluster interaction:** operate on `VisualUnit`s, not raw `MarkerView`s
— a `_2.4` cluster representative (once Phase 4 populates
`VisualUnit.clusterMembers`) is one visual unit for this domain's
purposes, exactly as it is for `_2.4`'s own count-cap. A cluster badge
can still crowd a nearby lone high-priority marker even though the
cluster resolved its own internal overlap by existing as one unit — this
domain's grouping pass must include cluster units alongside individual
markers, not skip them.

## 8. Wiring — `LODController` step 8, and a precise fix to its enabled-flag logic

**Displacement becomes `LODController.Evaluate()`'s step 8**, called on
whatever `VisualUnit`s survive step 7 (`ApplyVisibility`) — not a second
independent timer. Reasoning, not just a preference: `LODController`
already ticks the pipeline this domain's continuous re-evaluation needs;
a second timer risks the two loops observing inconsistent in-between
states of each other's output, the same class of bug `_2.4`'s own
pipeline-ordering fix addressed within a single pipeline. This also keeps
the algorithm itself in its own class (`MarkerOverlapResolver`, evolved,
not merged into `LODController`) — matches `20-code-quality.md`'s
preference for small, single-purpose classes over one accumulating
responsibilities; `LODController` orchestrates, it doesn't implement.

**A precise fix to `Update()`'s early-return, required for a real design
goal (confirmed in prior discussion): Displacement must still run on
walls where LOD is disabled** (a small wall with few POIs may never need
distance culling but still wants close markers nudged apart). Current
code: `if (!_settings.enabled) return;` skips everything, including any
future step 8. Fix: only skip the *whole* `Evaluate()` if **both**
`lod_settings.enabled` and `displacement_settings.enabled` are false;
otherwise run, and internally skip only the LOD-specific stages (1-7)
when `lod_settings.enabled` is false, still reaching step 8.

**`MarkerOverlapResolver.cs` evolves**, keeping its existing grouping
logic (union-find, `overlap_threshold_px` — now a config field, no
longer a hardcoded `const`) but adding:
```csharp
public static void ApplyDisplacement(
    List<VisualUnit> visibleUnits,
    Camera cam,
    DisplacementSettings settings,
    Dictionary<string, int> stabilityCounters) // §9 hysteresis
```
**`WallSession.SpawnPOIs()`'s existing one-shot call to
`ApplyOverlapOffsets` is removed** — superseded by the continuous
per-cycle call from `LODController`, which runs within one evaluation
interval of spawn anyway. Keeping both would mean a redundant, stale
initial computation immediately overwritten by the first real cycle —
delete it, don't leave it as dead-but-harmless code.

## 9. Hysteresis — mirrors `_bandCache` exactly, same reasoning as `_2.4`'s own fix

Same class of problem `_2.4` solved for density/cluster membership: a
marker hovering right at the overlap-detection threshold could flicker
in and out of a displaced group as a visitor's stance drifts slightly.
**Same fix, same shape, for consistency** — not a new pattern to learn:
a marker's overlap-group membership only commits after **two consecutive
`Evaluate()` cycles** agree, tracked in a new `Dictionary<string, int>`
(consecutive-agreement counter, keyed by `PoiId`), directly alongside
`LODController`'s existing `_bandCache` and `_prevEffectiveDistance`
fields — same cadence (`evaluation_interval_s`), no new interval to
configure.

## 11a. Step order — isolating the risky geometry fix from the rest

Consolidated here (referenced from §4); build in this order, each step
verified via Phase A (§12) before the next:

1. §10 schema additions (`DisplacementSettings`) + §3 (`priority` field
   on `HierarchyLevelEntry` and `TryResolvePriority` on
   `MarkerHierarchyResolver`) — purely
   additive, nothing existing changes behaviour yet.
2. `label_only` displace-target path, `fixed_axis` algorithm — the
   simplest combination, and per §4, needs **no** camera-relative
   conversion math since it's correct by construction. Get the union-find
   grouping + label-offset mechanics right here first, in isolation, with
   the least geometry that can go wrong.
3. `candidate_position`, then `force_directed`, still under
   `label_only` — layer in algorithm complexity before touching the
   riskier displace-target modes.
4. **Only now**, `marker`/`both` displace-target modes — this is where
   §4's camera-relative conversion fix actually gets exercised. Isolated
   to this late a step deliberately, since it's the one part of this
   domain with real geometry to get wrong, per the shallow-angle
   regression test (§12) that must be written before this step is
   considered done, not after.
5. §6 leader lines — independent of the above, can be built any time
   after step 1, but sequenced late here since it's cosmetic and
   shouldn't block the geometry work.
6. §8 wiring into `LODController.Evaluate()` as step 8, plus the

8. §11's Editor UI.
9. Phase B (§14) — only once everything above is green.
