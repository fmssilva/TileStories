# Marker Positioning — Final implementation state

This document is the single, authoritative reference for the positioning domain in TileStories.

## 2. Final model: one real position, one editor-only QA flag

The final model is intentionally minimal and explicit:

- `POIData.position` is the canonical runtime position.
- `POIData.position_verified` is an editor-only QA flag.
- The runtime resolver never consults `position_verified`.
- A POI with `position == null` resolves to origin.
- A POI with a valid `position` resolves directly from that position.
- The verified flag is used only by the editor to prevent accidental scene moves after a position has been intentionally accepted.

This is the design decision that closes the old draft/precise drift: the app does not need a second historical position state. The project only needs one usable position and one separate lock/verification signal.

## 3. Runtime logic

`POIPositionResolver.TryResolvePosition(...)` is the runtime authority.

The rule is simple:
1. If `poi` is null, fail with a log message.
2. If `poi.position != null`, validate it and use it.
3. If `poi.position == null`, return the origin vector.
4. `position_verified` is ignored by runtime.

That decision matters because it keeps runtime behavior deterministic and independent from editor QA state. The authoring tool can lock a scene object for protection, but the real app should still keep resolving a valid `position` as the true source of placement.

## 4. Editor behavior and lock semantics

The authoring workflow lives in the POI Editor window. The key semantic is:

- the editor may block a user from dragging a verified marker in the scene,
- but it must snap back to the last accepted verified position,
- not to stale JSON or an old capture value that may no longer match the in-memory scene state.

The solution in the current implementation is:

- keep the most recent verified in-memory position in `_lastVerifiedPositions` per POI,
- when a verified marker is moved, compare the current local scene position against that last verified anchor,
- if the difference exceeds tolerance, revert the scene object and show a notification,
- keep the verified/lock state as a guardrail, not as a second source of truth for runtime positioning.

This is the correct behavior for the final design because it prevents accidental edits while still preserving the single canonical `position` field.

## 5. UI contract and final presentation

The current UI is intentionally simple and explicit:

- Rotation is drawn first.
- X, Y, Z are displayed in explicit order.
- The verification state is a separate toggle/button.
- Verified positions are visually distinct and the status text communicates whether the marker is locked or editable.

The current ordering is not accidental. It reflects the practical authoring workflow:
1. adjust rotation,
2. check XYZ values,
3. decide if the POI is verified and therefore locked in the scene.

This is also where the final decision around labels matters: the fields are intentionally labeled as `X`, `Y`, `Z` without extra ambiguity, which removes the old confusion caused by legacy naming drift.

## 6. Save, sync, rig lifecycle, and POI deletion

The authoring loop is straightforward:

- Load config
- Populate rig from JSON
- Move marker in scene
- Save all to JSON
- Auto-sync rig positions into config before writing
- Clear rig only with explicit safety checks when the rig is out of sync
- Delete POIs only through the editor row action with a confirmation dialog before removing the POI from config and the scene rig

The critical rule is that the editor writes the authoring state directly back to config and not to a secondary hidden position channel.

The delete interaction is intentionally explicit and dangerous-looking for a reason: POI removal is a destructive action that affects the config list and the scene rig. The editor therefore uses a visibly red, high-contrast delete button and a confirmation dialog that says: “Delete POI?” with the actual POI name and an explicit warning that the POI will be removed from both the config and the scene rig. The destructive affordance sits alongside the row’s edit/move controls so the action is obvious, and the darker red treatment is intentionally stronger than normal utility buttons to make the danger cue clear before the developer confirms the action.

Key implementation points:
- `CapturePositions(...)` is the write-back step that pushes scene positions into the config model.
- `IsRigInSyncWithConfig(...)` compares live rig positions against config data via a small tolerance.
- `Clear Rig` is intentionally destructive only after the tool has checked whether the rig contains unsaved or out-of-sync data.
- Build/play safety checks guard against shipping a rig that is still present in the scene.

## 7. Why this model was chosen

The final design decision is a product of the project's constraints and the need for maintainability:

- keep runtime resolution simple and testable,
- keep editor safety checks explicit,
- avoid multiple competing position systems,
- avoid persistent hidden state that can drift from scene and JSON representations.

This is why the older model was removed:
- no `x_norm` / `y_norm` runtime path,
- no dual draft/precise mode,
- no calibration-anchor interpolation as a primary runtime mechanism,
- no separate historical capture state treated as a second truth.

The result is a clean separation of responsibilities:
- `position` = actual placement data
- `position_verified` = QA/editor lock status
- `POIEditorToolWindow` = authoring safety layer
- `POIPositionResolver` = runtime placement rule

## 8. Known practical realities and guardrails

The final implementation is intentionally conservative and minimal.

Important decisions already in place:
- verified status is a convenience and safety mechanism, not a runtime truth source,
- scene drag locking must respect last verified in-memory data,
- the project keeps the config-save path as the canonical persistence method,
- current tools avoid overengineering the positioning model beyond the real needs of the wall authoring flow.

This is the correct final state for a stable authoring workflow: explicit, testable, and easy to reason about.
