the documented convention) and narrowed `ColorPickerWidth` 60f -> 32f (still above the

rect-based verification the first time. Fixed by zeroing `EditorGUI.indentLevel` around

`DrawCoordinateRow` and `DrawColorSwatchAndHex` already use for the identical symptom --
`extraIndentPixels`' own nudge (a raw pixel add to the spacer's width) is untouched

## Lessons Learned (read before touching row layout or verifying UI visually)

A single per-POI coordinate row (`DrawCoordinateRow` in `PositionTabs.cs`) went through
seven rounds of fixes in one session chasing an invisible-label / misaligned-row bug.
Each lesson below is durable and will recur on future IMGUI row work in this window if
not read first.

1. **`GUILayoutUtility.GetLastRect()` proves reserved space, not that anything painted.**
   A label wrapped in `EditorGUI.DisabledScope(true)` got a real, correctly-sized rect
   and still rendered invisibly. Never treat a rect's existence as proof of visible text;
   verify with an actual screen capture instead (lesson 6).
2. **A size constant "measured via a live experiment" is valid only for the EXACT
   rendering mechanism it was measured under.** `16f` label width was correctly found
   "too narrow to render" under one bug (indent applied twice, see lesson 4); once that
   bug was fixed and the code switched to manual Rect splitting, the same
   investigation's old `40f` conclusion was stale and caused a NEW "dead space" bug.
   Re-derive size constants from `GUIStyle.CalcSize(new GUIContent(text))`, never from a
   number that "already passed a test once" under different code.
3. **`EditorGUILayout`'s automatic inter-control spacing (~3px) does not respond to
   `GUIStyle.margin` overrides.** Verified directly: zeroing both controls' margins left
   the gap unchanged. For a label+value pair needing a guaranteed ZERO gap, reserve ONE
   combined rect via `GUILayoutUtility.GetRect(...)`, split it manually in C#
   (`valueRect.x = labelRect.x + labelRect.width`), and draw both with `EditorGUI`
   (immediate mode, explicit rects) -- not `EditorGUILayout`.
4. **Indent is applied twice when more than one control follows a row's indent spacer.**
   `DrawEditorRow`'s spacer already pays the runtime indent once; each subsequent
   `EditorGUILayout` control independently re-applies `EditorGUI.indentLevel` again on
   top of it. Invisible on a single-control row, it compounds visibly across several
   controls sharing one row. Fix: zero `indentLevel` for the row's own controls after the
   spacer has drawn. **Variant of this same trap, hit again in `DrawFramedFoldout`'s
   `rightAlignTrailing` branch**: adding a manual `GUILayout.Space(indent)` in front of
   an `EditorGUI.Foldout(rect, ...)` double-shifted it, because that Foldout overload
   already lands correctly aligned with a sibling plain `EditorGUILayout.Foldout` row
   with NO manual spacer at all -- there is no one universal rule for "does this control
   need a manual indent spacer," it depends on whether the specific control already
   absorbs indent on its own; verify against a real sibling row's alignment, don't
   assume every row needs the `DrawEditorRow` spacer pattern.
5. **Never add a second right-margin subtraction on top of `DrawEditorRow`'s `rowWidth`.**
   It already has `AddButtonRowRightMargin` baked in once. Every multi-element row splits
   that ONE budget locally (`(rowWidth - gaps) / n`); a private extra margin just makes
   that one row inconsistent with its siblings.
6. **For LEFT-INDENT / absolute-position comparisons BETWEEN two different rows, a real
   screen-pixel capture beats `Debug.Log(GetLastRect())`.** Rect logging reported two
   different rows starting at the identical x on three separate occasions; a direct
   pixel-luminance scan of an actual screenshot proved a real 28px gap existed. Rect
   logging IS reliable for geometry WITHIN one row's own draw call (lesson 3's zero-gap
   check); it was repeatedly misleading for cross-row absolute position. When in doubt
   for this comparison class, screenshot + pixel-scan first -- don't iterate on rect
   logs. (Technique: capture with `InternalEditorUtility.ReadScreenPixel`, save as PNG,
   then read it back with `Texture2D.LoadImage` and scan pixel luminance across x at the
   target y-row to find where a glyph actually starts.)
7. **Screen-pixel capture safety:** `ReadScreenPixel` reads raw ABSOLUTE DESKTOP pixels.
   Setting `.position` on a DOCKED window silently fails to move it; reading pixels at
   the position you assumed it moved to can capture a COMPLETELY UNRELATED application
   window (this happened once -- captured a browser tab, not Unity). Only capture at a
   window's freshly-queried real `.position`, and only on a window opened via
   `GetWindow<T>(utility: true, title, focus: true)` for this purpose -- never a person's
   own working window.
8. **`PopulateRig()` can trigger a blocking confirmation dialog** ("Clear and
   repopulate?") if the rig already has children, freezing the Editor's main thread.
   UI-only verification never needs the rig populated -- `LoadConfig()` alone gets real
   POI data into `_config`.
9. **Delete leftover diagnostic/scratch test files immediately after use.** A forgotten
   `Assert.Fail`-based diagnostic probe (meant to print measured rects, never assert
   correctness) was the one failing test in a 704-test suite, unrelated to production
   code.
10. **`ReadScreenPixel` reads in raw DEVICE pixels; `window.position` is in POINTS.** On
    a display with `EditorGUIUtility.pixelsPerPoint != 1` (e.g. 1.25 at Windows 125%
    scaling), capturing at `(int)pos.x, (int)pos.y, (int)pos.width, (int)pos.height`
    directly reads only a `1/pixelsPerPoint` FRACTION of the window (a cropped, not
    scaled-down, view) -- it looks like the right/bottom content is genuinely clipped
    when it isn't. Always multiply `x/y/width/height` by `EditorGUIUtility.pixelsPerPoint`
    before calling `ReadScreenPixel`, and build the output `Texture2D` at that scaled
    pixel size. This cost one full round of false-positive "the name is still clipped
    even after widening the window" debugging before the real (much smaller) bug was
    found in lesson 11.
11. **`GUIStyle.CalcSize` can under-measure a label's real rendered width for a bold
    custom header style.** Confirmed directly (not assumed) via a corrected, DPI-scaled
    screenshot: a `+4f` pad clipped the last glyph, `+10f` still clipped it on longer
    names ("Residential" -> "Residentia"), `+18f` was reliably enough. When sizing a
    flexible-width label against a computed available-space cap (`min(natural,
    available)`), pad the natural-width side generously -- it only matters when natural
    is the smaller of the two, so a generous pad never steals space unnecessarily.
12. **A downloaded icon PNG's "transparent" background can be real checkerboard PIXELS,
    not alpha.** Some icon-site exports flatten the preview-tool's checkerboard
    transparency indicator into the actual opaque image (`alpha=255` everywhere,
    including the "background"). Rendered with `GUIStyle.none` in IMGUI (no background
    of its own), this shows as a literal grey/white checker square around the glyph
    instead of a transparent one -- looks like a GUIStyle or blending bug but isn't one.
    Diagnose by sampling actual pixel alpha (a short PowerShell `System.Drawing.Bitmap`
    script reading `.A` on a few background pixels settles it in seconds); an image
    viewer or this tool's own Read preview cannot be trusted to distinguish "real alpha"
    from "an image that happens to render a checker pattern," since a real-alpha PNG and
    a fake-checker PNG can look IDENTICAL in a preview that composites transparency onto
    its own checker background. Fix by keying the grayscale/light background pixels to
    `alpha=0` in place and reimporting -- same category of bug as the delete-icon
    watermark noted in the changelog above (a stock icon asset with a baked-in
    placeholder artifact), just a different symptom.
13. **`GUILayout.FlexibleSpace()` only caps at an intended boundary if its ENCLOSING
    horizontal group is itself width-constrained.** `GUILayout.Width(w)` on the
    individual controls around it is not enough -- that's the pattern `DrawEditorRow`'s
    callers use for FIXED-width controls, and it works because there's no flexible
    element trying to expand. A `FlexibleSpace()` inside a plain, unconstrained
    `EditorGUILayout.HorizontalScope()` expands to fill the REAL container width (which
    can be far wider than any intended row cap), not the width implied by the controls
    around it. To cap a row that mixes a flexible gap with right-aligned trailing
    content, wrap the whole group in `new EditorGUILayout.HorizontalScope(GUILayout.
    Width(indent + rowWidth))` (or the equivalent `BeginHorizontal` overload) using the
    same `indent`/`rowWidth` this file's other rows compute via
    `EditorRowWidthForIndent` -- only then does `FlexibleSpace()` stop at the intended
    edge instead of the window's.
14. **Passing the "same" size constant to two call sites does not guarantee the same
    rendered SHAPE if the underlying rect-construction differs.** `DrawIconButtonLayout`
    used to build a SQUARE rect from one `size` value; the POI header row's real
    buttons were never square (`width`-wide, only `singleLineHeight`-tall, since they
    share a single text line's height). Both call sites passed `size: IconButtonSize`
    and were still visibly different sizes -- the shared constant matched, the shape
    it got built into didn't. This is a variant of lesson 2 ("a size constant is valid
    only for the exact rendering mechanism it was measured under") applied to a whole
    reusable HELPER rather than a hand-measured literal: extracting a shared constant
    is not enough by itself if the function using it still makes an undocumented shape
    assumption (here, "square"). When unifying several near-identical implementations
    into one helper, verify the new helper reproduces the ORIGINAL reference control's
    actual geometry (width AND height), not just that both sides now reference the same
    named constant.

## Row Indentation & Spacing (the global convention -- read before adding a
## conditional/dependent field row anywhere in this window)

**There is one indentation system for the whole window, already built --
never invent a second one.** `DrawEditorRow` (see the command above) reads
`EditorGUI.indentLevel` at call time via `EditorGUI.IndentedRect`, sizes its
transparent spacer to match, and narrows `rowWidth` by the same amount
(`EditorRowWidthForIndent`). Every row in every section already goes through
this, so nesting one more `EditorGUI.IndentLevelScope` around a group of rows
is the ONLY correct way to make them sit one step deeper than their siblings
-- the spacer, the field width, and every other row's own indent all stay
consistent automatically.

**Left indent (a "second level" section's own fields vs. a "third level"
conditional row):** a section or sub-foldout's own base fields (e.g.
"Marker", "Label", "Badge", "Clusters" under Vertical Alignment; "Category",
"Hierarchy Level" under Specific Marker's Marker Style) draw at the SAME
ambient indent level the section/sub-foldout TITLE itself was drawn at --
**do not add an extra `IndentLevelScope` around a section's own base
fields.** The foldout's own arrow glyph already reads as "one step in" with
no additional level needed (confirmed the hard way -- see the correction
entry above: Orientation's four sub-sections used to wrap their base fields
in an unconditional `IndentLevelScope(1)`, one real level deeper than every
sibling section and than Specific Marker's equivalent fields, which is what
actually produced the "2-3cm too far right" bug -- not just the conditional
rows below, which were a real but smaller part of the same symptom). A field
that only shows conditionally on another field's value (e.g. "Up Reference"
only when something is set to World Up; "Relaxation Steps" only for the
force_directed algorithm) is the one case that DOES sit a bit deeper than
its section's base fields, via a raw pixel nudge, NOT an `IndentLevelScope`:

```csharp
if (someCondition)
    o.someField = DrawScalarField("Some Field", o.someField, SomeFieldHelp, SubFieldIndentPixels);
```

`SubFieldIndentPixels` (`POIEditorToolWindow.Constants.cs`, `= 8f`) is the ONE
named constant for this step, passed as the trailing `extraIndentPixels`
argument every shared field-drawer (`DrawScalarField`/`DrawIntField`/
`DrawToggleField`/`DrawPopupField`, and `DrawEditorRow` itself) now accepts.
It adds straight to the row's computed indent (the spacer width and the
`rowWidth` narrowing together) WITHOUT touching `EditorGUI.indentLevel` --
deliberately narrower than a whole `IndentLevelScope` step (~15px) and immune
to Lesson 4's double-indent trap, since the row's own control never sees a
changed ambient `indentLevel` to re-apply. A field conditional on TWO nested
conditions (e.g. "Custom Up X/Y/Z", which only shows when Up Reference is
ALSO set to Custom) passes `SubFieldIndentPixels * 2`, not a second nested
scope -- see `DrawOrientationVerticalAlignmentSubSection` in
`POIEditorToolWindow.Orientation.cs` for the shipped example.
`PositionTabs.cs`'s `DrawCoordinateRow` call (`IndentLevelScope(2)`) is a
different, non-conditional case that genuinely needs a whole extra level for
a different reason (matching a sibling row's rendered position -- Lesson 4)
and is unaffected by this convention.

**Value-column alignment for a nudged row (2026-09-18, developer screenshot
feedback):** `SubFieldIndentPixels` correctly nudges a conditional row's
LABEL start to the right, but on its own it also drags that row's VALUE box
(the dropdown/number field after the label) right by the same amount --
visibly, "Up Reference"'s dropdown sat right of "Marker"'s dropdown above it,
"Facing Basis"'s sat right of "Facing"'s. Root cause: `DrawEditorRow`'s spacer
widens by `extraIndentPixels` (correct -- that's the whole nudge), but the
row's own labelled control still reserves the SAME `EditorGUIUtility.labelWidth`
for its label column as an un-nudged sibling, so the value box -- which starts
at `control rect.x + labelWidth` -- ends up exactly `extraIndentPixels` right
of where it should be. Fixed at the one shared choke point every nudged row
already passes through: the four field-drawers wrap their control draw in
`using (new FieldLabelWidthCompensationScope(extraIndentPixels))`
(`Shared/POIEditorToolWindow.RowLayout.cs`), which shrinks
`EditorGUIUtility.labelWidth` by exactly `extraIndentPixels` for that one
control, then restores it. **This is deliberately LOCAL, not a second global
"indent level -> label width" lookup table:** `extraIndentPixels` already IS
the one piece of data that says how much wider this row's spacer got, so the
compensation just re-spends that same number on the label column instead of
introducing a parallel constant that could drift out of sync with it. A field
using `SubFieldIndentPixels * 2` (the doubly-conditional case) is compensated
automatically too, since the scope takes whatever `extraIndentPixels` value
the row already passed -- no second constant to maintain. If you add a new
kind of row that is NOT one of the four shared field-drawers but still uses
`extraIndentPixels`/a raw pixel nudge, wrap its own control draw in the same
`FieldLabelWidthCompensationScope` rather than inventing another fix.

**Never fake this with leading spaces inside a label string** (e.g.
`"  Up Reference"`, `"    Custom Up X"`). This was a real bug found and fixed
2026-09-18: it only shifts the label's own glyphs inside its already-fixed-width
label column -- it does NOT move the row, its spacer, or its field width the
way a real `IndentLevelScope` does, so the amount of visual shift depends on
the font's own space-character width and drifts out of alignment with every
other real indent step in the window (this is what produced the "Up
Reference" / "Facing Basis" rows sitting oddly far right of their siblings).
If you find a label starting with literal spaces anywhere in this codebase,
that is this exact bug -- replace it with an `IndentLevelScope`, never add
more.

**Right spacing (scrollbar clearance) is global for `DrawEditorRow` rows --
nothing to add per-row.** `AddButtonRowRightMargin` (20f, `Constants.cs`) is
baked into `EditorRowWidthForIndent` itself, so every row produced by
`DrawEditorRow` (and therefore every `DrawScalarField`/`DrawIntField`/
`DrawToggleField`/`DrawPopupField` call, since they all open a
`DrawEditorRow`) already keeps its right edge clear of the ScrollView's
vertical scrollbar. A row that builds its own layout instead of going through
`DrawEditorRow` does NOT get this for free and needs it restated by hand as a
trailing `GUILayout.Space(AddButtonRowRightMargin)` -- every Global Scene
taxonomy table (Marker/Badge's shared `DrawSymbolTable`, Outline, Hierarchy
Levels, LOD bands, Synonym Groups, Search Fields including its read-only
system rows) now does this (2026-09-18); if you add a new table-shaped row
that builds its own `HorizontalScope` instead of using `DrawEditorRow`, add
this same trailing space rather than assuming the global rule covers it.

### 1.2 Visual Tab Structure

The editor window uses two levels of visual containment for clear information hierarchy:

**Outer Containers (Tabs): `DrawTabContentContainer`**
- Wraps the entire content of each top-level tab (Global Scene, Specific Marker)
- Uses a light greenish/gray background (`new Color(0.9f, 1.0f, 0.9f)`)
- Contour color differs per tab: `GlobalSectionColor` (bluish) for Global Scene, greenish for Specific Marker
- The selected tab's content container sits directly beneath the tab buttons (no spacer), so the container's top contour touches the tab row

**Tab Buttons:**
- Custom styled buttons (not GUILayout.Toolbar) with `FontStyle.Bold` text
- Global Scene tab: blue background (`GlobalSceneTabColor`), white text (`TabTextColor`)
- Specific Marker tab: green background (`SpecificMarkerTabColor`), white text (`TabTextColor`)
- No selection-based color change — each tab always uses its own base color. Selection is indicated by which tab's content container appears beneath the button row
- Horizontal layout with `GUILayout.ExpandWidth(true)` for equal-width distribution

**Inner Section Containers:**
- Each foldout section inside a tab uses `DrawFramedFoldout` with a bold colored title and a distinct section color — **no outer `DrawTabContentContainer` wrapper** around individual sections (the per-POI wrapper was removed; only the 2 top-level tab containers remain)
- In the Specific Marker tab, the five per-POI sections are nested one indent level under each POI header foldout (EditorGUI.IndentLevelScope); their fields render one further level deep
- Global Scene sections: Marker (green), Badge (orange), Outline (purple), Effects (blue), Hierarchy Levels (yellow), LOD (teal), Zoom (magenta), Displacement (violet-pink), Search & Filter (brown). **CORRECTED** (audit, `_2.7_Corrections_TODO.md` #5.1-b fold-in, 2026-08-26): this list previously omitted Displacement because it predated that domain landing; the foldout and its color are confirmed on disk (`POIEditorToolWindow.Displacement.cs`, `DisplacementSectionColor`).
- Specific Marker sections: Position (soft green), Marker Style (soft orange), Badge Style (soft purple), Outline (soft blue), Search Keywords (soft yellow)
- Provides visual grouping so authors can instantly identify which section they're editing

Non-table rows (buttons, fields, sliders) that must sit "inside" their foldout and
NOT stretch across the whole window use the shared helpers in
`POIEditorToolWindow.RowLayout.cs`:

- `DrawEditorRow(out float rowWidth, out Rect spacerRect)` opens the row, draws a
  transparent indent button whose width is the indent Unity actually applies at that
  point (`EditorGUI.IndentedRect`, ~30px at foldout level 2), and computes the
  row's usable width.
- `EditorRowWidth(remaining)` = `max(MinRowWidth, min(remaining, MaxRowWidth))`
  where `remaining` = `EditorGUIUtility.currentViewWidth` (the VISIBLE panel; the
  scroll content can be ~928 while the panel is ~700 because the tables widen it)
  minus a right margin and the indent.
- Caller draws its controls with `GUILayout.Width(rowWidth)` +
  `GUILayout.ExpandWidth(false)`, then `EditorRowEnd()`.

`ExpandWidth(false)` is mandatory (the editor button style is stretchy, so
`GUILayout.Width` alone would be overridden). Width must be computed from
`currentViewWidth` + the indent ONLY -- both are stable across the Layout and
Repaint IMGUI passes; using a just-drawn control's `GetLastRect` makes the two
passes disagree (measured 299 vs 267 on a 300px panel). `DrawAddButtonRow` is a
thin wrapper in `SymbolTable.cs` over this shared row.

The four shared field helpers in `LodZoom.cs` (`DrawScalarField` / `DrawIntField` /
`DrawToggleField` / `DrawPopupField`) are themselves shared rows now: each opens
`DrawEditorRow`, caps the labelled field to `rowWidth - 36f` when a help button is
present (else the full `rowWidth`), and closes with `EditorRowEnd()`. They cover every
LOD / Zoom / Displacement / SearchFilter field. Direct rows (Global badge/marker/outline
toggles+popups, Effects sliders, SpecificMarker status toggles/sliders/dropdowns and the
Search Keywords text fields) use the same recipe inline. The indent spacer is measured at
call time (`EditorGUI.IndentedRect`), so rows already inside a nested `IndentLevelScope`
(POI -> Position/Marker Style, or SearchFilter Minimap/Voice/Zoom groups) keep their own
deeper indent -- never flattened to the outer foldout level. Taxonomy TABLE cells
(fixed per-column widths aligned to a header row) are deliberately NOT converted: capping
those to rowWidth would break column alignment.

`TableGapBetweenGroups` is the single spacer drawn between every logical column
group in the marker / badge / outline taxonomy tables (both header and rows),
i.e. between [key+details], [Symbol + interactive Preview], [Color], [SearchKeywords]
and [trash]. `TableGapWithinGroup` spaces sibling controls inside one group
(e.g. the ObjectField from the preview thumbnail). The Color group starts with the REAL
working `EditorGUILayout.ColorField`, forced wide via `ColorPickerWidth` so it
is easy to click (no flat draw-only swatch in front of it -- that read as a dead,
non-clickable cell), with the hex field ("color name") directly after it. The
picker/hex pair is deliberately FLUSH by design: GUILayout's own default
inter-control spacing (~3px) already separates them, and a measurement pass
confirmed that is all the gap there is -- an explicit spacer is not needed.
`SymbolColumnPad` is the header pad that keeps the info button flush with the
preview thumbnails' right edge, derived from the within-group gap so both move
in sync. All live in `POIEditorToolWindow.Constants.cs`; both renderers
(`DrawSymbolTable` + the outline table's inline rows) reference the same
constants, so tuning one value retunes every table. Layout widths used by the
headers/placeholders come from derived constants (`ColorGroupWidth`,
`SymbolColumnPad`) so header titles and row cells can never drift apart.

## 2. Source of Truth

Two config copies by design:

- **Authoring source (read/write):** `Assets/Apps/<Wall>/config.json`
- **Runtime copy (write-only):** `Assets/StreamingAssets/<Wall>/config.json`

Expected workflow: Load + Populate + edit source -> Save All to JSON -> Copy to StreamingAssets.

`Load & Populate Rig` (single button, calls LoadAndPopulateRig -> PopulateRig, which always reloads the source file first to avoid stale data).
`CopyToStreamingAssets` reads source, writes streaming, then `AssetDatabase.Refresh()`.

## 3. Data Flow

### 3.1 Config In (Load)

```
Load & Populate Rig button
  -> RigLifecycle.LoadAndPopulateRig()
     -> [Guard 1] uncaptured rig moves? DisplayDialogComplex
        ("Capture & Reload" / "Discard & Reload" / "Cancel")
     -> [Guard 2] _hasUnsavedChanges? DisplayDialogComplex
        ("Save & Reload" / "Discard & Reload" / "Cancel")
     -> RigLifecycle.PopulateRig()
        -> ConfigFileIO.LoadConfig()  [always reloads source first: read + parse
        + seed defaults + icon library + history snapshot + ValidateAndAlert]
     -> GetOrCreateRig + spawn markers (see 3.4)
```

### 3.2 Config Mutation (Undo-Aware)

Every field edit in Global or Specific sections is wrapped in `DrawConfigMutationScope`:

```
UI field changed
  -> DrawConfigMutationScope(drawContent, refreshRigOnChange: true)
     -> snapshot before = JsonUtility.ToJson(_config)
     -> drawContent()  [mutates _config fields directly]
     -> snapshot after = JsonUtility.ToJson(_config)
     -> if before == after: return (no change, no history record)
     -> RecordConfigChange(before, after)  [JSON snapshot diff, not Unity Undo]
     -> _hasUnsavedChanges = true
     -> if refreshRigOnChange: RefreshRigVisuals()
```

Key detail: undo/redo uses a JSON string list (`_configHistory`), not Unity's Undo system.
`UndoConfigChange` decrements index and calls `ApplyConfigSnapshot` (re-deserializes + Repaint).
`_isApplyingHistory` flag prevents snapshot recording during apply.

### 3.3 Config Out (Save)

```
Save All to JSON button
  -> SaveAllToJson()
     -> CapturePositions(silentWhenRigMissing: true)  [rig positions -> config]
     -> ValidateAndAlert("before save")
     -> SaveConfig()
        -> JsonUtility.ToJson(_config, prettyPrint: true) -> File.WriteAllText
        -> AssetDatabase.Refresh()
                 -> _hasUnsavedChanges = false
```

### 3.4 Rig Flow (Populate / Refresh / Capture)

```
Load & Populate Rig (single button)
  -> RigLifecycle.LoadAndPopulateRig()  [two blocking guards, then PopulateRig]
     -> ConfigFileIO.LoadConfig()  [always reloads source first]
  -> GetOrCreateRig()  [finds or creates POIEditorRig under PlacementCorrectionAnchor]
  -> if rig has children: prompt "Clear and repopulate?"
  -> load prefab from _prefabPath
  -> foreach poi:
     -> POIPositionResolver.TryResolvePosition(poi, out localPos)
        [null position resolves to origin; new single-parameter
         signature confirmed 2026-09-13 -- no anchors parameter]
     -> PrefabUtility.InstantiatePrefab(prefab, rig)
     -> instance.name = poi.id  [child name == poi.id is the binding key]
     -> instance.transform.localPosition = localPos
     -> anchor.Initialise(poi) + markerView.Initialise(...)
  -> SelectRigObjects()  [Selection.objects for editor focus]
```

```
RefreshRigVisuals (called on config mutation with refreshRigOnChange=true)
  -> GetExistingRig()  [no-op if no rig]
  -> configure palettes: CategoryPalette / BadgeCategoryPalette / StatusRamp /
     MarkerHierarchyResolver
  -> parse wall-level settings: shape, outline mode, badge mode (with legacy fallback)
  -> foreach poi:
     -> child = rig.Find(poi.id)  [name-based binding]
     -> anchor = child.GetComponentInChildren<POIAnchor>() ?? AddComponent<POIAnchor>()
     -> anchor.Initialise(poi)  [updates runtime data, NOT position]
     -> markerView.Initialise(...)  [updates visuals from current config]
```

RefreshRigVisuals does NOT move marker positions -- it only updates visuals. Position
changes require manual Transform editing in the rig, and the authored position is persisted by the main `Save All to JSON` action.

```
Save All to JSON syncs rig positions into config
  -> GetExistingRig()
  -> build Dictionary<string,Transform> of rig children by name
  -> foreach poi:
     -> if sceneObjects.TryGetValue(poi.id):  [only matched POIs]
        -> localPos = markerTransform.localPosition
           [rig sits at origin under the correction anchor, so
            localPosition == world position -- no inverse-transform
            conversion is performed; confirmed 2026-09-13]
        -> poi.position = new PositionData { x, y, z, }  (position_verified untouched)
     -> else: skipped++
```

```
Clear Rig
  -> GetExistingRig()
  -> if no children: "Nothing to clear" dialog
  -> IsRigInSyncWithConfig() check:
     if outOfSync: "N marker(s) differ. Clear anyway?" [save/clear or cancel]
  -> for each child: Undo.DestroyObjectImmediate(child)  [undoable]
```

angles (this slider's Y, plus X/Z via Unity's Rotate tool) reach the runtime marker
depends on the wall's global `facing_mode`: `wall_fixed` uses all three exactly as
authored; `yaw_only` uses X/Z and replaces Y with a live camera-facing yaw every frame;
`always_facing_camera` ignores all three (editor-preview-only in that mode). See
`_2.1_Marker_Orientation.md` section 4.2 for the full design.
Config is the source of truth -- PopulateRig and RefreshRigVisuals both re-apply it so
spawn/undo/redo/refresh stay in sync. New POIs seed 0.

**Full X/Y/Z rotation (editor-preview).** The dev can rotate a marker with Unity's own
Rotate tool: `POIData` now carries `editor_rotation_x_deg` and `editor_rotation_z_deg`
alongside the original `editor_rotation_deg` (kept as Y for backward compatibility with
existing configs). All three are applied through
`PoiRotationResolver.ToEulerQuaternion(x, y, z)`; `ToYawQuaternion(y)` remains as a
thin wrapper for yaw-only callers/tests.

The Y slider and the Scene rotate gizmo stay **in sync in both directions**:
- slider -> scene: `ApplyPoiEditorRotation` writes the child's localRotation from the
  three stored angles.
- scene -> config: `HandleSceneGui` (already registered on
  `SceneView.duringSceneGui`) reads the child's `localRotation.eulerAngles` back
  through `SyncPoiRotationFromScene` **unconditionally**, normalizing each axis into
  [0, 360). This runs inside OnSceneGUI, deliberately *outside* the window's
  `DrawConfigMutationScope`, so it cannot feed back through the scope's JSON diff and
  spam undo history on every Scene repaint.
- On Save, `CapturePositions` also reads `localRotation.eulerAngles` into all three
  fields, so scene-rotate edits persist.

Rotation is **never** locked by Verified -- only position is. The Verified lock covers
position alone: `HandleSceneGui` runs the rotation sync first (so it fires for every
POI, verified or not), then separately checks `position_verified` and, only if the
*position* moved off its last-verified value, reverts the position component (leaving
rotation untouched). This makes X/Z behave exactly like the Y slider already does --
freely and live-editable regardless of verified state -- and removes a prior edge case
where a combined move+rotate on a verified marker could wrongly discard an in-progress
rotation change along with the blocked position move.

**Rotate-tool position drift.** With the Scene view's Tool Handle Position set to
Center, Unity's Rotate gizmo can nudge `localPosition` slightly as a side effect of
spinning the marker around its visual bounds center rather than its own transform
origin -- incidental drift from rotating, not an intentional position edit. The revert
above still corrects it (so it never persists), but the "already verified" notification
banner is suppressed specifically while `Tools.current == Tool.Rotate`, so rotating a
Verified marker never shows a spurious lock message the way a genuine Move-tool drag
does.

Pure math (normalize + quaternion map) lives in PoiRotationResolver; the write-back
rule lives in `POIEditorToolWindow.SyncPoiRotationFromScene` (both Tier-0 tested).

## 5. Data Types Reference

### 5.1 WallConfigData (Runtime)

Top-level config. Key fields:
- `wall_id` / `wall_name` / `immersal_map_id`
- `marker_shape` (string, parsed by MarkerVisualsParser)
- `marker_style` (LEGACY string: gold/same_hue/badge -- kept for backward compat)
- `marker_outline_mode` (string: gold/same_hue/free_colors/none)
- `marker_use_badge` (bool)
- `marker_icon_library_resources_path` (string, for runtime Resources.Load)
- `badge_shape` (string)
- `category_styles`: List<CategoryStyleEntry> -- {category, icon_key, color_hex, details}
- `badge_categories`: List<BadgeCategoryEntry> -- {key, label, icon_key, color_hex, details}
- `outline_levels`: List<OutlineLevelEntry> -- {key, label, pct, line_style, color_hex}
- `hierarchy_levels`: List<HierarchyLevelEntry> -- {key, label, size_cm, show_label,
  sun_effect, accent_effect, pulse, rotate_contour, reveal_delay_s, reveal_duration_s,
  facing_mode_override}
- `effect_defaults`: EffectDefaults -- {pulse, sun, accent} with amplitude/period/alpha/tint
- `displacement_settings`: DisplacementSettings
- `orientation_settings`: OrientationSettings (`_2.1_Marker_Orientation.md` section 7)
- `pois`: List<POIData>

### 5.2 POIData (Runtime)

- `id` / `name`
- `category` (string -> CategoryPalette)
- `badge_category` (string -> BadgeCategoryPalette)
- `position` (PositionData class: x, y, z -- a reference type; null means no position)
- `position_verified` (bool -- editor-only QA flag; runtime never reads it)
- `has_status` / `status_pct` / `status_unknown` / `status_level_key`
- `hierarchy_level_key`
- `has_custom_symbol` / `custom_symbol_key`

### 5.3 PositionData

A `[Serializable]` class with `float x, y, z` and a `ToVector3()` helper. Being a
reference type makes the `poi.position != null` check in `POIPositionResolver`
meaningful. When JsonUtility synthesizes a zero-initialized object for an absent
position, that is functionally equivalent to a cleared position (both resolve to
origin at runtime) -- so no extra guard flag is needed.

## 7. Gotchas

1. **Rig child naming is the binding key.** Each rig child is named `poi.id`.
   `RefreshRigVisuals` does `rig.Find(poi.id)`. Rename a POI's id -> repopulate rig.

2. **Undo uses two separate systems.** Rig objects use Unity `Undo`
   (InstantiatePrefab auto-registers, `Undo.DestroyObjectImmediate`). Config field edits
   use JSON snapshot list (`_configHistory`). Ctrl+Z / Ctrl+Y for config;
   `Edit > Undo` for rig objects. Do not mix them.

3. **`free_colors` is editor-only.** Not a runtime `MarkerOutlineMode` enum value.
   Editor normalizes it; runtime reads per-level `color_hex` via `StatusRamp.Configure()`.
   Do not add to `MarkerOutlineMode` enum.

4. **`marker_style` is legacy.** Modern fields: `marker_shape` + `marker_outline_mode`
   + `marker_use_badge`. `RefreshRigVisuals` has a fallback calling
   `MarkerVisualsParser.TryParseStyle` to derive outline+badge from legacy enum.

5. **Position needs no presence flag.** `POIPositionResolver` uses `poi.position != null`
   as its only gate; a JsonUtility-synthesized `(0,0,0)` object resolves to origin just like
   null would, so no extra `has_*` flag is required. `position_verified` is editor-only QA.

6. **Icon library must be in `Resources/`.** `AssetPathToResourcesPath` finds `/Resources/`.
   If wall library isn't under `Resources/`, `marker_icon_library_resources_path` is null
   and runtime falls back to defaults. Window shows HelpBox warning but does not block.

7. **Wrap field edits in `DrawConfigMutationScope`.** Without it, undo (Ctrl+Z) won't
   capture the change, `_hasUnsavedChanges` won't be set, and the rig won't refresh.

8. **OnSceneGUI draws handles but doesn't edit.** Scene view shows cyan handles for
   anchor + POI positions. Edit via normal Transform tools + Capture Positions.

9. **Defaults seeded on first load only.** LoadConfig seeds empty lists from editor-only
   helpers. Do not seed non-empty lists -- overwrites developer choices.

10. **`POIPositionResolver.TryResolvePosition` can fail.** If a POI without captured
    position can't resolve, PopulateRig logs a warning and skips it. Check logs if
    markers are missing from the rig.

---

11. **`SyncPoiRotationFromScene` used to read rig rotation back UNCONDITIONALLY - fixed
    2026-09-18 (`_2.1_Marker_Orientation.md` section 9).** The orientation preview writes a
    rig child's `localRotation` for *display* purposes every `SceneView.duringSceneGui`
    repaint; without a guard that would have been captured into `editor_rotation_x/y/z_deg`
    as if the developer had authored it, silently corrupting the config. Both write-back
    points (`HandleSceneGui`'s call to `SyncPoiRotationFromScene`, and the rotation half of
    `CapturePositions`) now early-return while `_config.orientation_settings.
    edit_mode_preview_enabled` is true, and `RestoreRigRotationsFromConfig()` restores the
    authored angles when preview is turned back off. Any FUTURE Editor feature that writes
    a rig child's `localRotation` for display purposes needs the same kind of guard -
    this is not a generic mechanism, just this one flag being checked in the two places
    that matter.
