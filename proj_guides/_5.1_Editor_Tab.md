# POI Editor Tab (5.1)

The POI Editor window (`TileStories / POI Editor`, shortcut `Shift+P`) is the wall-editing control
center. It loads and edits one wall's `config.json`, spawns a temporary Edit-Mode scene rig for
visual marker placement, provides global and per-POI editing UI, captures scene positions back to
JSON, and copies the validated config to `StreamingAssets/`. This file is the GUIDE for building and
changing it: how to do things, what not to do, how to debug. It is not a changelog and not a domain
design doc (each domain has its own `_2.x` doc; this file only holds what is specific to the window).

## 0. Guidelines

### Rows: width, margins and the shared row

Covers every single-line control row that is NOT a taxonomy table cell: buttons, labelled fields, sliders, toggles, popups, headers with a trailing control.

**Rules**
- Every row goes through `DrawEditorRow(out float rowWidth, out Rect spacerRect)` and closes with `EditorRowEnd()` (`Shared/POIEditorToolWindow.RowLayout.cs`). It draws a transparent indent spacer sized to the indent Unity actually applies at call time (`EditorGUI.IndentedRect`) and returns `rowWidth = max(MinRowWidth, min(currentViewWidth - AddButtonRowRightMargin - indent, MaxRowWidth))`.
- The right margin is subtracted ONCE, inside `rowWidth`. A row must not subtract another margin on top; multi-element rows split that one budget locally.
- Each element is capped to a share of `rowWidth` and always gets `GUILayout.ExpandWidth(false)` (the editor button style is stretchy; `GUILayout.Width` alone is overridden):
  - single button / labelled field with no trailing control: `Width(rowWidth)`
  - field + browse/help button: field `Width(rowWidth - 36f)`, button fixed `Width(30f)` (help buttons: `IconButtonSize`)
  - n equal buttons with gap g (default 4f): each `(rowWidth - g*(n-1)) / n`
  - fixed + flexible mix: flexible elements share `(rowWidth - fixedTotal - gaps) / count`
- `rowWidth` must depend on `currentViewWidth` and the indent ONLY. Both are identical in the Layout and Repaint IMGUI passes; using a just-drawn control's `GetLastRect` makes the passes disagree (measured 299 vs 267 on a 300 px panel).
- A label + value pair that needs a TRUE zero gap: `EditorGUILayout` adds ~3 px between controls and ignores `GUIStyle.margin`, so reserve one combined rect (`GUILayoutUtility.GetRect(pairWidth, lineHeight, GUILayout.Width(pairWidth), GUILayout.ExpandWidth(false))`), split it in C# (`valueRect.x = labelRect.x + labelRect.width`) and draw both with `EditorGUI` (immediate mode). Size the label from `GUIStyle.CalcSize(new GUIContent(text))`, never from a number that "passed once" under different code.
- A flexible gap (`GUILayout.FlexibleSpace()`) only stops at the intended edge if its enclosing horizontal group is itself width-constrained: wrap the group in `new EditorGUILayout.HorizontalScope(GUILayout.Width(indent + rowWidth))`. `Width` on the controls around it is not enough.
- Taxonomy TABLE cells are deliberately not converted to `DrawEditorRow` (capping to `rowWidth` would break column alignment); see "Tables".

**How to** add a row: use a shared helper from "Shared row helpers and buttons" if one fits. Only when none fits, open `DrawEditorRow` yourself (it already runs your controls at indent 0, see "Indentation"), draw, `EditorRowEnd()`. Never draw a labelled control without a row.

**Do not**
- Do not invent a second width or margin formula, or hard-code widths that duplicate a constant.
- Do not use `GUILayout.Space` for the indent (use the spacer button `DrawEditorRow` draws; a zero-alpha real `GUILayout.Button` with `whiteTexture`, never `background = null`).
- Do not put a private extra right margin on one row.

**Constants** (`POIEditorToolWindow.Constants.cs`): `MinRowWidth`, `MaxRowWidth`, `AddButtonRowRightMargin`.

### Indentation

Covers the left edge of every element and the alignment of value columns. One vocabulary, decided by the element's PLACE IN THE TREE, not by taste.

**The tree and the named levels** (constants in `POIEditorToolWindow.Constants.cs`; a child sits one level right of its parent container):

| Level | Where the element is | Examples |
|---|---|---|
| `IndentLevel0` | direct child of a section (`DrawFramedFoldout` content, or a per-POI inner section) | Marker's "Background shape", Effects' "Enable effects", Specific Marker's "Category" / "Facing X" / "Has status", plain labels and HelpBoxes of that section |
| `IndentLevel1` | child of a sub-foldout inside a section | Orientation's Vertical Alignment rows, the rows inside an Effects effect foldout, the guide foldouts of a Test |
| `IndentLevel2` | child of a sub-foldout of a sub-foldout, or the text block of an open guide | guide text under "How to Scene Test" |
| `IndentLevel3` | one level deeper still | (none today) |
| `ConditionalAdvance` | added to any level for a row shown only when another field has a value | "Up Reference" = `IndentLevel1 + ConditionalAdvance`; doubly conditional adds it twice |

Pass the level as the trailing `extraIndentPixels` argument of a shared field drawer or of `DrawEditorRow`. Tokens are raw pixels, so they never touch `EditorGUI.indentLevel`.

**Element types and where each one starts**
- **Field / button rows** (`DrawEditorRow` and everything built on it): the spacer pays the indent, and `DrawEditorRow` itself runs the row's controls at `indentLevel` 0 until `EditorRowEnd` (a control after the spacer would otherwise re-apply the indent to its own label: the double-indent trap). Callers do not zero it by hand any more; new rows must always open with `DrawEditorRow` and close with `EditorRowEnd`.
- **Plain labels, `HelpBox`, `EditorGUILayout.LabelField`** outside a row: EditorGUILayout indents them once by the ambient level, so they land at the same x as the rows of that container. A help button or any second control on the same line must be inside a `DrawEditorRow` (a help button drawn outside a row lands on its own line at the far left).
- **Foldouts** (`DrawFramedFoldout`, `EditorGUILayout.Foldout`): the title sits at the container's own level; the children start one step right (under the title text). Foldout, `SelectableLabel` and other controls that re-apply ambient indent inside a row are fine now that the row zeroes it; outside a row (a foldout drawn directly) do not add a manual `Space(indent)`.
- **Tables** (taxonomy tables): start at the container's ambient indent like plain labels and build their own fixed columns (see "Tables"). They do not use the tokens.

**Rules**
- Containers: `DrawFramedFoldout` adds one `IndentLevelScope` to its content, and that is the only container-level scope. Do not wrap a section's rows in another `IndentLevelScope`, and do not use one to "collapse" indentation (`IndentLevelScope(-1)` was a workaround for the double-indent bug and is gone). The Specific Marker inner sections (Position, Marker Style, Badge Style, Outline, Search Keywords) follow the same rule as the Global Scene sections.
- Sub-foldouts inside a section (`EditorGUILayout.Foldout`): their rows pass `IndentLevel1`; guide text passes `IndentLevel2`.
- Conditional rows: add `ConditionalAdvance` to the level; never `IndentLevelScope`, never leading spaces in a label (it shifts only the glyphs inside the label column and drifts with the font).
- **Value-column alignment:** a nudged row would drag its value box right by the nudge because the control still reserves the full `labelWidth`. Every shared drawer wraps its control in `using (new FieldLabelWidthCompensationScope(extraIndentPixels))`; a hand-built row that uses `extraIndentPixels` must do the same. `extraIndentPixels` is the single source of truth; no parallel "level -> label width" table.
- A whole extra `IndentLevelScope` is right only for a non-conditional row that must match a sibling's rendered position, and then only with evidence (a capture); when in doubt use a token.

**Status of the sections:** Marker, Badge, Outline, Effects, Orientation and the Specific Marker containers follow this vocabulary. LOD, Zoom, Displacement and Search & Filter use the same tokens (`ConditionalAdvance` for conditional rows) but their structure has not been cleaned yet; do that audit before treating them as reference.

**Debug:** when two structurally equivalent rows look differently indented, recompute the FULL indent stack from the top of the call chain for both (foldout level, `DrawFramedFoldout`'s scope, any other scope, `extraIndentPixels`) and diff it; fixing only the deepest visible symptom leaves a partial fix. Compare with a capture (see "Verifying and debugging layout"): the label start of a row should equal its container's arrow plus one step, the same for every section in both tabs.

### Shared row helpers and buttons

Covers the drawers every section builds on, and every icon-shaped control.

**Field drawers** (`GlobalScene/POIEditorToolWindow.LodZoom.cs`): `DrawScalarField`, `DrawIntField`, `DrawToggleField`, `DrawPopupField`, `DrawSliderField`, `DrawColorField`. Each opens `DrawEditorRow`, caps the labelled control to `rowWidth - 36f` when a help button is present, applies the `FieldLabelWidthCompensationScope` fix, and closes the row. They accept `extraIndentPixels` and an optional help text.
- Use them for every labelled row. Raw `EditorGUILayout.Popup/Toggle/Slider/FloatField/IntField/TextField/EnumPopup` calls belong only inside taxonomy table rows. A hand-built labelled row (an `EnumPopup`, a text field) must copy the recipe: `DrawEditorRow`, `FieldLabelWidthCompensationScope` when it uses `extraIndentPixels`, `EditorRowEnd`.
- Colour rows: `DrawColorField(label, ref hex, ...)`. Never call `DrawColorSwatchAndHex` bare: without a row wrapper the picker and hex stack vertically at the raw left margin with no label.
- When two hand-built rows look identical, migrate both to the helper instead of matching numbers by eye.

**Help (i) buttons.** There is exactly ONE renderer: `HelpInfoButton.Draw(title, body, size = IconButtonSize)` (`Shared/HelpInfoPopup.cs`), built on `DrawIconButtonLayout`. Pass an explicit `size` only to line up with a neighbouring column (a table's Details column uses 26f above it, the Symbol column lines up with the 36 px preview). Do not add a compact variant, a literal "?" or "(i)" text button, or a direct `new HelpInfoPopup(...)` call. A framework-authored read-only help text and a developer-editable per-row note are different things: `EntryDetailsPopup` is persisted data, never share it with help ("Messages, dialogs and popups").

**Icon buttons** (`Shared/POIEditorToolWindow.IconButton.cs`): `DrawIconButton` (Rect) and `DrawIconButtonLayout` (GUILayout) draw a real `EditorStyles.miniButton` background (identical hover and press feedback everywhere) with the glyph drawn separately by `GUI.DrawTexture(..., ScaleMode.ScaleToFit)` inside `iconInset`. All icon-only buttons in the window use them, including the POI header cluster.
- Geometry: width is `IconButtonSize`; height defaults to `EditorGUIUtility.singleLineHeight`. The button is NOT square. A helper that unifies several call sites must reproduce the reference control's real width AND height; sharing a size constant is not enough if the helper builds a different shape.
- `GUI.DrawTexture` ignores `GUI.enabled`; `DrawIconButton` halves the glyph alpha itself when disabled. A new icon-drawing helper must do the same.
- Delete buttons: `DeleteButton.Draw` / `DrawLayout` (`Shared/POIEditorToolWindow.DeleteButton.cs`), default icon `TrashIcon`, default size `IconButtonSize`. Every delete affordance in the window (table rows, header row) uses it; a destructive action also needs a confirmation (`IdentityDeleteGuard`, section 9) and, in tables, the wider `TableGapBeforeDelete` gap.

**Icon assets (PNG).** A stock icon can carry defects that look like layout bugs:
- Baked watermark or footer rows (a black bar at the bottom shows as a stray line once scaled down): crop the file and reimport.
- A checkerboard "transparency" flattened into opaque pixels (`alpha = 255` everywhere) renders as a grey/white square under `GUIStyle.none`. An image preview cannot tell real alpha from a fake checker; read pixel alpha (a short PowerShell `System.Drawing.Bitmap` script reading `.A` on corner pixels) and key the near-grey light pixels to `alpha = 0`, then reimport.
- When an unexplained artifact appears at small size, inspect the source PNG before blaming the GUIStyle. After editing a PNG or `.meta`, force a refresh (`.clinerules/40-testing.md` 4.3).

**Tests:** `POIEditorTableLayoutTests` (which rows use the shared row and helpers), `POIEditorAddButtonRowRenderTests`, `POIEditorCoordinateRowRenderTests`.

### Tables

Covers the taxonomy tables: Marker/Badge (`DrawSymbolTable`, shared), Outline (inline renderer in `GlobalScene/POIEditorToolWindow.MarkerDesign.cs`, `DrawGlobalOutlineSection`), Hierarchy Levels, LOD bands, Synonym Groups, Search Fields.

**Rules**
- Tables build their own fixed-column layout (`HorizontalScope` per row) so header cells and row cells align; they do not go through `DrawEditorRow`.
- Both renderers (`DrawSymbolTable` and the Outline inline rows) reference the SAME constants, so tuning one value retunes every table. Header widths come from derived constants (`ColorGroupWidth`, `SymbolColumnPad`), so a header and its cells cannot drift.
- Spacing constants: `TableGapBetweenGroups` between logical column groups (key+details, Symbol+preview, Color, keywords, trash), `TableGapWithinGroup` between siblings inside a group, `TableGapBeforeColor` before the colour group, `TableGapBeforeDelete` before the trash (bigger, so the destructive action reads as set apart). GUILayout adds its own ~3 px between controls on top of an explicit gap, so a measured gap is `constant + 3`; assert that in render tests instead of loosening tolerance.
- Colour group: a REAL `EditorGUILayout.ColorField` (no draw-only swatch in front of it, it reads as a dead cell) forced to `ColorPickerWidth`, the hex field directly after, flush (the ~3 px auto spacing is all the gap wanted). Both controls need `GUILayout.ExpandWidth(false)` or they stretch into a wide bar. Zero `indentLevel` for just the picker+hex pair (see "Indentation").
- Right-edge scrollbar clearance is NOT automatic for table rows: add a trailing `GUILayout.Space(AddButtonRowRightMargin)` after the last column of the header and EVERY data row, including read-only system rows. It also works when a row ends in `FlexibleSpace()` (the fixed margin is subtracted from what the flexible space can claim).
- A header help button above a per-row Details ("...") column passes `26f`, matching the Details column.
- The Symbol column's header pad (`SymbolColumnPad`) is derived from `TableGapWithinGroup` so header and cells move together.

**Do not** convert table cells to the row helpers, add a second gap constant per table, or hard-code a column width that a derived constant already provides.

**Debug / verify:** measure real geometry with the render harness: `POIEditorColorGroupRenderTests` runs the production `DrawSymbolTable<CategoryStyleEntry>` (via reflection, it is a private generic) inside a genuine `OnGUI` pass and reads the rects through the `captureFirstRowRects` callback (null by default, zero cost). Copy that seam pattern, as `DrawCoordinateRow` does with its out-Rect parameters. A gap or width that "looks wrong" may be an optical illusion caused by a neighbouring oversized element; measure before changing constants.

### Foldouts and header rows

**Rules**
- Default state: every `_showGlobal*` foldout field is `false` (Global Scene opens fully collapsed); `_showTopConfig` (Scene Configuration, above the tabs) stays open; per-POI foldouts and their five inner sections are collapsed, a newly added POI is opened explicitly by `SpawnAndFocusNewPoi`. A Test sub-foldout is the one exception that starts open (see "Domain Manual Tests").
- Section containers: each Global Scene / Specific Marker section is a `DrawFramedFoldout` with its own section colour; no extra `DrawTabContentContainer` around individual sections (only the two tab containers exist).
- A header row with right-aligned trailing content (`DrawFramedFoldout(..., rightAlignTrailing: true)`, the POI header cluster) is capped like every other row: compute `indent` and `rowWidth` with `EditorRowWidthForIndent`, wrap the group in `HorizontalScope(GUILayout.Width(indent + rowWidth))` so the flexible gap stops at the row edge, and compute icon rects right-to-left from `rowRight` with the name as the flexible element (`min(natural width, space left)`). Pad a bold header label's natural width generously (`CalcSize` under-measures a bold custom style; 18 px was reliably enough), it only matters when natural width is the smaller side.
- All icon buttons in a header cluster share one width (`IconButtonSize`) and go through the shared icon-button helpers.
- Details of the POI header row and Position foldout behaviour: section 4.4.

**Do not** add a manual `GUILayout.Space(indent)` before a `Foldout` rect (see "Indentation"), or rely on an unconstrained `HorizontalScope` plus `FlexibleSpace()` (it runs to the far window edge).

### Verifying and debugging layout

**What tests can and cannot prove.** Structural tests and real IMGUI geometry harnesses prove geometry WITHIN one row's own draw call (widths, gaps, which helper a row uses). They do NOT reliably prove cross-row alignment, and never the padding a control adds before its own label glyph. After any layout change, say plainly that it is not eyeballed and ask the developer to look at the real window once.

**Rules for chasing a layout bug**
1. `GUILayoutUtility.GetLastRect()` proves reserved space, not that anything painted (a label inside `EditorGUI.DisabledScope(true)` had a correct rect and rendered invisibly). Never treat a rect's existence as visible text.
2. Rect logs were repeatedly misleading for absolute-position comparison BETWEEN two rows (three rows "started at the same x" while a pixel scan showed a 28 px gap). For cross-row comparison capture the screen and scan pixels; use rect logs only within one row.
3. A size constant measured under one rendering mechanism is valid only for that mechanism; re-derive from `GUIStyle.CalcSize`, and re-derive again when the mechanism changes.
4. Recompute the indent-level stack (see "Indentation" Debug) before touching any constant.

**Screen capture procedure** (Tier 1 evidence, `.clinerules/40-testing.md` 4.5):
- Open the window with `GetWindow<T>(utility: true, title, focus: true)` for the capture. Never capture a person's own working window. Setting `.position` on a DOCKED window silently fails, and reading pixels where you assumed it moved can capture an unrelated application (once captured a browser tab); read the freshly queried real `.position`.
- `InternalEditorUtility.ReadScreenPixel` reads raw DEVICE pixels while `window.position` is in POINTS: multiply x, y, width and height by `EditorGUIUtility.pixelsPerPoint` and build the output `Texture2D` at that pixel size, or you capture a cropped fraction and chase false "clipped content" bugs.
- Save as PNG, read it back with `Texture2D.LoadImage`, scan luminance across x at the target y to find where a glyph actually starts.
- A capture is only valid if the PNG really shows the window. `ReadScreenPixel` reads whatever is on the desktop at those coordinates: when the Editor is not the visible foreground application, or the utility window is not where it was moved, the file contains OTHER applications (it once captured a chat window with private text). Always open the PNG and look at it before using it, and delete any capture that shows anything other than the window. If the window cannot be brought on screen reliably, do not capture; use the pending-verification list below.
- A side-by-side screenshot "at a glance" is not proof; compare footprints (width AND height) in a zoomed capture.

**When the Editor is not visible (another window in front).** A capture needs Unity on top. If it is covered: do NOT stop the whole task. Finish everything that does not need pixels (code, tests, docs), then, before the final report, ask the developer ONCE to leave Unity in front and retry; if they cannot, list the unverified items under "Pending visual verification" and say so in the report. Ask early (in the plan) when the whole task is visual. Never claim a layout is verified without a capture you looked at or the developer's confirmation.

Every agent that changes layout adds one line (what to look at, where); an agent must never claim a layout is verified without the developer's confirmation or a valid capture.

### Config, rig and undo (data-model traps)

One-line traps of the config, rig and undo flow. Read before touching load/save, the rig, undo or rotation write-back.

1. **Rig child naming is the binding key.** Each rig child is named `poi.id`.
   `RefreshRigVisuals` does `rig.Find(poi.id)`. Rename a POI's id -> repopulate rig.

2. **Undo uses two separate systems.** Rig objects use Unity `Undo`
   (InstantiatePrefab auto-registers, `Undo.DestroyObjectImmediate`). Config field edits
   use JSON snapshot list (`_configHistory`). Ctrl+Z / Ctrl+Y for config;
   `Edit > Undo` for rig objects. Do not mix them.

3. **Outline colour mode is one of three, resolved at the `StatusRamp` level, not per-row
   text.** `marker_outline_mode` is `uniform` / `same_hue` / `per_type` / `none`
   (`MarkerOutlineMode` enum). `StatusRamp.Configure(entries, mode, uniformColor)` is mode-
   aware: Uniform ignores every row's `color_hex` and paints the one shared colour; Per
   outline type honours each row's own; Same hue never reads `StatusRamp` at all (`_2.2.3`
   §2.2). The editor's level table only shows the Color column in Per outline type mode.
   There is no editor-only mode string that the runtime enum doesn't also have (the old
   `free_colors` editor-only value was removed with this fix -- see `_2.2.3_Outline_Design.md`
   §1).

4. **`MarkerStyle` and `marker_style` no longer exist.** Removed entirely, no
   backward-compatibility shim (`_2.2.1_Marker_Design.md` §1): the enum, the config field,
   `MarkerVisualsParser.ParseStyle`/`TryParseStyle`/`DeriveOutlineAndBadgeFromLegacyStyle`,
   and the three legacy `MarkerView.Initialise` overloads are all gone. The modern fields are
   `marker_shape` + `marker_outline_mode` + `marker_use_badge`, resolved once by
   `MarkerVisualSettings.Resolve` (`_2.2.1` §3.1), with no legacy-enum fallback anywhere.

5. **Position needs no presence flag.** `POIPositionResolver` uses `poi.position != null`
   as its only gate; a JsonUtility-synthesized `(0,0,0)` object resolves to origin just like
   null would, so no extra `has_*` flag is required. `position_verified` is editor-only QA.

6. **Icon library must be in `Resources/`.** `AssetPathToResourcesPath` finds `/Resources/`.
   If wall library isn't under `Resources/`, `marker_icon_library_resources_path` is null
   and runtime falls back to defaults. Window shows HelpBox warning but does not block.

7. **Wrap field edits in `DrawConfigMutationScope`.** Without it, undo (Ctrl+Z) won't
   capture the change, `_hasUnsavedChanges` won't be set, and the rig won't refresh.

8. **OnSceneGUI draws handles but doesn't edit.** Scene view shows cyan handles for
   anchor + POI positions. Edit via normal Transform tools + Capture Positions.

9. **Defaults seeded on first load only.** LoadConfig seeds empty lists from editor-only
   helpers. Do not seed non-empty lists -- overwrites developer choices.

10. **`POIPositionResolver.TryResolvePosition` can fail.** If a POI without captured
    position can't resolve, PopulateRig logs a warning and skips it. Check logs if
    markers are missing from the rig.

---

11. **Never read the rig's rotation back into config while the Scene-Mode orientation preview is on.**
    The preview writes a rig child's `localRotation` for display every `SceneView.duringSceneGui`
    repaint; capturing it would store it as `editor_rotation_x/y/z_deg` as if authored and silently
    corrupt the config (`_2.1_Marker_Orientation.md` section 9). Both write-back points
    (`ProcessMarkerTransformEdit`'s call to `SyncPoiRotationFromScene`, and the rotation half of
    `CapturePositions`) skip while `_config.orientation_settings.edit_mode_preview_enabled` is true
    (`ProcessMarkerTransformEdit` still syncs the gizmo in `wall_fixed`, where the preview shows the
    authored angles untouched), and `RestoreRigRotationsFromConfig()` restores the authored angles
    when the preview is switched off. Any future Editor feature that writes a rig child's
    `localRotation` for display needs the same kind of guard.

### Messages, dialogs and popups

Covers every short message, decision and popup shown to the developer: which component to use, timing, and what never to do.

**ALERT: modal dialogs block everything.** `EditorUtility.DisplayDialog`, `DisplayDialogComplex` and the native notice dialogs freeze the Editor's main thread until someone clicks. While one is open, Unity MCP calls (`refresh_unity`, `run_tests`, `execute_code`) stall or time out with no useful error, and a test run never progresses. Therefore:
- Never write or run a test that opens a modal dialog (see "Tests, dead code and docs hygiene").
- If a run or a tool call stalls (test progress not moving, `editor_state` never ready), assume a dialog is open BEFORE retrying: tell the developer "a dialog may be open in Unity; please click it" (a screen capture can confirm), then continue. Do not start several new runs on top of a blocked Editor.
- If a task cannot avoid triggering one (for example a real build with a guard dialog), say so first and tell the developer which button to click.

| Need | Use | Why |
|------|-----|-----|
| Short informational message: a refused edit, "this change is invisible", result of the developer's own click, a validation report | `EditorNotice.Queue(title, message, quietSeconds, dontShowAgainKey)` | The ONE path. Native centred OK dialog, shown by an editor-update pump (works even if the POI Editor tab is hidden), testable through the queue |
| Yes/No/Cancel decision that must return a choice | `EditorUtility.DisplayDialog` / `DisplayDialogComplex` called directly | A queue cannot return the answer. Same native look as the notices |
| Read-on-demand explanation next to a control | `HelpInfoButton.Draw(title, body)` -> `HelpInfoPopup` | Anchored, non-blocking, framework-authored static text |
| Developer-editable note stored in config | `EntryDetailsPopup` | Persisted data; never reuse the read-only help popup for it (rule 20) |
| Pick a sprite from wall/framework icons | `ExistingSymbolPickerPopup` | Curated picker |
| Static hint that is ALWAYS true of the current state ("No POIs yet", "Enable badge to edit...") | `EditorGUILayout.HelpBox` in the layout | Persistent state, not an event |

Do NOT: use `SceneView.ShowNotification` (text size cannot be set; it rendered tiny), draw a
`HelpBox` from an event handler or button callback (it is drawn mid-layout for one frame and
nobody sees it -- this bug existed in `SpawnAndFocusNewPoi`), or add a new popup class for a
message a dialog already covers. Before adding any popup/dialog helper, grep `Shared/`.

Timing: a message fired repeatedly by a drag (Scene gizmo, slider) passes
`EditorNotice.GestureQuietSeconds` so it appears only when the developer stops -- a modal opened
mid-drag breaks the drag. A message answering a click passes 0.

`DisplayDialog` has no icon parameter (the triangle is fixed by Unity/OS), so there is no
severity flag. `DisplayDialogComplex` always has THREE buttons (an empty label still renders one),
so never use it just to get a second button.

"Don't show again": only for repeatable ADVISORY notices, via the notice's key (Unity's own
`DialogOptOutDecisionType` checkbox, stored per machine). Never for a message that explains why an
edit was refused (the verified lock) or reports the result of the developer's own click: hiding
those makes the editor look broken. Every hideable key must be listed in `NoticeKeys.All`, or the
`TileStories > Reset Hidden Notices` menu cannot bring it back (a test enforces the list).

### Dialog results, handlers, events and menu items

Covers Enter/Esc behaviour, event subscriptions and menu paths.

- `DisplayDialog`: Enter = the first (ok) button; Esc / X = false. Both are safe for OK-only
  notices. For a confirm whose ok button is destructive ("Delete", "Clear anyway") Enter confirms
  it -- keep the label an explicit verb naming the action, and prefer an undoable action.
- `DisplayDialogComplex`: returns 0 = ok, 1 = cancel, 2 = alt, and **closing the dialog or pressing
  Esc ALWAYS returns 1**. So slot 1 must be the safe Cancel and any destructive choice ("Discard &
  Reload", "Continue Without Clearing") must sit in slot 2. Three dialogs had this backwards
  (Esc discarded unsaved work / started Play with duplicate markers) and had to be fixed.
  Put the mapping in a pure `Resolve*` method that treats anything unexpected as Cancel, and test
  it (`ReloadGuardChoiceTests`).
- Text fields: Enter/Esc commit/cancel is resolved BEFORE the field draws (`PoiRenameKeys`).
- `PopupWindow.Show` ends by throwing `ExitGUIException` to unwind the current OnGUI. That is normal;
  call it first thing in a handler, and never rely on code after it.
- Every `SceneView.duringSceneGui` / static event subscribed in `OnEnable` must be unsubscribed in
  `OnDisable`. A missed one keeps a destroyed window's handler alive with its STALE config
  snapshot (it reverted rotations and raised the verified warning for a POI the live window showed
  as unverified). `PoiFacingModesAndLifecycleTests.ClosedWindow_LeavesNoSceneGuiHandlerBehind`
  guards it.
- Rig safety prompt: no opt-out. A `TileStories > Rig Safety Prompt on Play/Build`
  toggle used to exist. It was mis-pathed (Unity read the `/` as a submenu, showing "Rig Safety Prompt on
  Play > Build") and, worse, switching it off made `PromptBeforePlayOrBuild` return true even for
  builds, so a build could ship the editor rig's stand-in markers. It and its `EditorPrefs` key are
  removed; the prompt only appears while the rig actually holds markers. A test
  (`ReloadGuardChoiceTests.RigSafety_HasNoOptOut_...`) fails if a menu item or setting like it returns.
  Menu-item paths: a `/` always creates a submenu level, so never put a slash inside a label.


### Facing and rotation editing

Covers editing a POI's facing angles and anything that writes a rig child's rotation.

- Compare rotations as orientations (`PoiRotationResolver.IsSameOrientation`), never raw euler
  triples.
- The mode that applies to a POI is its hierarchy-level `facing_mode_override`, else the wall's
  `facing_mode`; anything that is neither `wall_fixed` nor `yaw_only` behaves as
  `always_facing_camera` (`FacingEditAdvice.EffectiveFacingMode`). Never test the global mode alone.
- The Verified lock reverts on edit (Unity's Rotate tool cannot be disabled). New editable POI
  state that should lock with Verified needs: a disabled control, a revert in
  `ProcessMarkerTransformEdit`, a skip in `CapturePositions`, and a notice.
- Any code that writes a rig child's `localRotation` for display needs the Edit-Mode-preview guard
  ("Config, rig and undo", item 11).
- Warnings about "no visible change" must be checked against the real pipeline in a test
  (`Advice_AgreesWithTheRealPipeline_...`) so they never claim an axis is inert when it is not.

### Tests, dead code and docs hygiene

Covers rules for tests of window code and for keeping the repo clean.

- Modal dialogs cannot be clicked by a test and hang the run (see the ALERT in "Messages, dialogs and popups": ask the developer to click, or avoid the test). Never call a method that opens one
  from a test. Informational messages go through `EditorNotice`, whose dialogs `TestDialogGuard`
  switches off; test the queue and the pure mapping instead. A test that would change a developer
  preference (opt-out checkboxes) must save and restore it.
- After removing or replacing a component, grep for leftovers (a whole class, its tests, "kept so old
  tests compile" aliases, comments naming it). No backward-compat shims (rule 00): update the callers.
- `EditorNotice` keeps `HasPending`/`PendingTitle`/`PendingMessage`/`PendingDontShowAgainKey`
  only as test observation points; do not add production readers unless they are needed.
- Any task that adds/removes/renames a file under `Assets/` updates `.clinerules/10-structure.md`;
  a quick check is to diff the file names on disk against the names in that file (both directions).

### Dev-only features and build safety

Covers anything meant for the developer only (preview grids, debug views, test switches) that must never reach the real app: how to build it, gate it, and guard the build.

**Why it matters (the real danger).** A config switch is just data in `config.json`, and the config that ships is the StreamingAssets copy. If a developer-only switch is ON in that copy, the runtime code that reads it decides what the visitor sees. Example: `effect_defaults.preview.enabled` ("Add effects demo grid") ON in the shipped config makes a DEVELOPMENT build replace the whole app with the labelled demo grid (its own camera, real markers hidden). A RELEASE build ignores it and shows the normal app, so the artifact only bites device tests and demos built with "Development Build".

**Rules for every developer-only feature**
1. **Default OFF** in code (the schema default) and in the shipped config.
2. **Gate it in the runtime** with an explicit allow rule, and keep that rule in one small pure method that a test can call (`EffectsPreviewSpawner.IsAllowed(isEditor, isDebugBuild)`). Prefer Editor-only (`includePlatforms: Editor`) when the feature has no reason to exist on a device; allow development builds only when device testing needs it, and never release builds.
3. **Register its config switch** in `DevFeatureBuildGuard.Registry` (`Editor/DevFeatureBuildGuard.cs`): name, how to turn it off (window path plus Save + Copy), whether it also works in release builds, and the predicate. `DevFeatureBuildCheck` (`IPreprocessBuildWithReport`) reads every wall's StreamingAssets config before a build and, if a registered switch is ON and would take effect in that kind of build, asks "Build anyway / Cancel build" (Esc or closing = cancel; batch mode only logs a warning). It changes no file.
4. **Say it in the UI:** the switch's label or help text states it is developer-only and where it applies (Editor, development builds), and the domain's Device guide says to untick it for a normal build.
5. **Test it:** an EditMode test for the guard (ON in a development build is reported with the how-to text; ON in a release build is not reported because the runtime ignores it; OFF reports nothing; the registry entry's release flag equals what the runtime really does). See `DevFeatureBuildGuardTests`.

**Do not** add a developer-only switch that silently changes the shipped app, a scene or gallery that is in Build Settings (`Assets/Dev/` scenes stay excluded), or code in the runtime assembly that only makes sense with the window open (put it in the Editor assembly, see "PlayMode Live Config").

**Domains still to check:** any future preview, gallery toggle or debug overlay follows these rules; when adding one, add its `DevSwitch` entry in the same change. The Orientation "Scene-Mode Preview" flag needs no entry: no runtime code reads it.

### Domain Manual Tests

Every domain whose behaviour a developer must judge by eye gets a **Test** sub-foldout at the end of its Global Scene section. Orientation is the reference implementation: `GlobalScene/POIEditorToolWindow.Orientation.cs` (`DrawOrientationTestSubSection`, `DrawTestGuideFoldout`), guide text in `POIEditorToolWindow.Constants.cs`, preview code in `RigLifecycle/POIEditorToolWindow.RigLifecycle.cs`, tests in `OrientationEditModePreviewTests` and `OrientationEditorRoundTripTests`. Skip the whole thing for domains with nothing visual to check. Copy the shape, not the orientation-specific content. **Second implementation: Effects** (`GlobalScene/POIEditorToolWindow.EffectsTest.cs`, guide text in `POIEditorToolWindow.EffectsHelp.cs`, tests in `EffectsAuthoringTests`): nothing it controls is visible without `Update`, so it has no Scene-Mode Preview toggle and its Scene guide says "Not possible in Scene test" for every animated part; instead its Test foldout carries a **"Add effects demo grid" switch** (a labelled grid of real markers on its own far-away camera, spawned by `WallSession`, Editor and development builds only, off by default) so the Playmode and Device guides start with one tick. It reuses `DrawTestGuideFoldout` from `Orientation.cs`. A domain that cannot show its result in the Scene view can still follow the handout: drop the toggle, keep the three guides and the guide-contract test, and add a Play-Mode preview only if the domain has combinatorial variants worth a grid (`40-testing.md` 4.4).

**Layout.** The Test foldout is the domain's last sub-foldout and is OPEN by default (a `bool _show<Domain>Test` field initialised to `true`), so the preview toggle is always visible. Inside it, in this order: (1) a **Scene-Mode Preview** toggle, only if part of the domain can really be seen in the Scene view; (2) three collapsible guides, "How to Scene Test", "How to Playmode Test", "How to Device Test", each COLLAPSED by default (three more `bool` fields, all `false`); only these guides start collapsed. Do not merge them into one text block and do not use a popup: the developer follows the steps while looking at the Scene or Game view, and a popup closes when focus moves there. Indentation follows the "Indentation" subject: the toggle and the guide foldouts are children of Test (`IndentLevel1`), the open guide text sits one step deeper (`IndentLevel1 * 2`). Both go through `DrawEditorRow`, with `EditorGUI.indentLevel` zeroed around `Foldout` and `SelectableLabel`, otherwise the indent is applied twice.

**Scene-Mode Preview.** The label is "Scene-Mode Preview", never "Edit-Mode", because it only affects the Scene view: no runtime code may read the flag, so Play Mode and devices always run the real behaviour (grep to keep it that way). It defaults to ON (the schema field is initialised to `true`, Orientation included), since it is free to look at and never touches saved data; a config without the block also gets ON. Edit Mode does not tick `Update`, `LateUpdate` or coroutines, so the preview is a static result at the current Scene camera, driven from `SceneView.duringSceneGui`. Rules that keep it honest: call the SAME pure resolver the runtime component uses, never a parallel implementation; call the real per-child entry point where one exists, but not a `Configure` that snapshots the current transform as "authored" (the preview rewrites it; Orientation ticks `MarkerChildOrientation` directly for this reason); make the preview non-destructive by skipping every write-back that reads the rig into config while it is active (save capture, scene-to-slider sync) and by restoring the rig from config when it switches off; unsubscribe the handler in `OnDisable`. Tell the developer in the guide what the preview cannot show (time, animation, anything needing camera roll or runtime-only objects such as LOD clusters), and write "Not possible in Scene test" for those parts instead of leaving them out.

**Guide content.** One block per sub-section of the domain, in the order they appear in the editor, not one bullet per field: the fields inside a sub-section are tested together. Each guide starts with a SETUP block and then one block per sub-section, and states plainly when that area cannot test it ("Not possible in Scene test, use Play Mode"). Write slide-style bullets, short and imperative, ASCII only. Name the exact UI labels and real POI ids (check the wall config first: which POIs actually carry the values the test needs, for example only `lamp` and `lamp_military` have authored facing angles in LivingRoom). Content per area:
- *Scene:* toggle the preview, "Load & Populate Rig", orbit with RMB or Alt+LMB, then per sub-section what to change and what must move or stay still. Mention that Q/W/E/R are Unity's own tool hotkeys in the Scene view.
- *Playmode:* save with "Save All to JSON" and "Copy to StreamingAssets" (Play reads the StreamingAssets copy), open the wall scene, press Play, and give the Editor mock-camera controls (project code in `MockLocalizationProvider`, Editor only: WASD move, Q/E down/up, RMB / Alt+LMB / arrows look, Z/C roll). Say what the developer SEES, not what the code does: on a PC the Game window never rotates, the world appears to rotate around the viewer (the camera is what rolls). Add the Phase A gallery scene under `Assets/Dev/` for side-by-side checks if the domain has one, and the Test Runner reminder (EditMode + PlayMode, zero failures). If the domain needs an input the mock cannot produce (roll was the orientation case), extend the mock first, per `40-testing.md` 4.1.
- *Device:* USB or Wi-Fi setup (`adb pair <ip>:<port>` + code, `adb connect`, or `npx adb-qr-connect`), save + copy config, Build And Run, no mock camera on device, logs with `adb logcat -c` then `adb logcat -s Unity > __logcat.txt` read from the file (no piping, per `50-terminal_and_tools.md`), and the physical actions to perform (`40-testing.md` 4.6). Only list what a device uniquely reveals: real rotation and display matrix, real tracking, performance and heat.

**Tests to write with it** (real code, no mocks, per `40-testing.md`): (1) preview correctness on a real prefab instance loaded with `PrefabUtility.InstantiatePrefab`, using a precondition assert so the test cannot pass vacuously, plus "switching off restores the rig" and "config values unchanged"; (2) a guide-contract test that reads the guide constants and option-label arrays by reflection, asserts ASCII only, one block per sub-section, every popup option label named, "Not possible in Scene test" where claimed, and the three guide foldout bools default to `false` (the Test foldout itself defaults to `true`). That second test is what stops the guides drifting when an option is added or renamed.

**Docs to update in the same session:** the domain doc's testing section (point to the guides instead of duplicating steps, add a table of which area covers which field), the domain's editor section, and `10-structure.md` for any new file. Keep the JSON key stable if a label is renamed; renaming saved keys breaks existing configs for no gain.

**Verify:** force compile, then check that `Library/ScriptAssemblies/TileStories.Editor*.dll` timestamps moved (a compile error leaves Unity on the last good build), run EditMode and PlayMode, and confirm the new test names appear in the results. Layout changes cannot be proven by tests here: ask the developer to eyeball the indentation once.

### PlayMode Live Config (handout for agents: make a domain's window edits show up in a RUNNING Play Mode)

**What it is.** While Play Mode runs, every change the developer makes in this window (or undo/redo) is pushed to the running wall, so a domain can be tuned live instead of "edit, Save, Copy to StreamingAssets, stop, Play again". Wired today: **Effects** (`_2.2.4` section 3.7), **Orientation** (`_2.1` section 13.5), and **Marker/Badge/Outline** (`_2.2.1` section 3.3). A new domain plugs in with one class and one line (recipe below).

**Build safety.** The whole mechanism (dispatcher, appliers, push, the hook lines in the window) is in the Editor assembly (`includePlatforms: Editor`), so none of it is compiled into a player build; a build without the window's code cannot contain it. The runtime re-apply methods it calls (`MarkerView.ReapplyEffects`, `WallSession.ApplyEffectSettings`, `WallSession.ApplyOrientationSettings`, `MarkerBillboard.ReapplySettings`, `LODController.ReapplyClusterOrientation`) are ordinary runtime code that ships but is never called in a build (nothing in a player pushes config). Separate from live updates: the effects "Add effects demo grid" preview creates its own camera and is allowed in the Editor AND in development builds (`EffectsPreviewSpawner.IsAllowed`), whenever the shipped `config.json` has `effect_defaults.preview.enabled` true; release builds ignore it. Untick it before copying the config for a device build you want to see normally.

**What it is NOT.** It never saves. The window keeps its edits after Play stops (its config and unsaved flag are serialized; Enter Play Mode options here have domain reload off). The developer still presses Save All to JSON, then Copy to StreamingAssets, to keep them; the next Play reads that copy. Nothing about it is compiled into a build.

**Architecture (three rules, all from `.clinerules` 10 section 1.2 and 20).**
1. **All logic lives in the Editor assembly**, `Editor/POIEditor/LivePlayModeConfig/`. Runtime never learns that a window exists. Runtime only exposes ordinary re-apply methods a domain would want anyway (`MarkerView.ReapplyEffects`, `WallSession.ApplyEffectSettings`, `MarkerBillboard.ReapplySettings`, `WallSession.ApplyOrientationSettings`, `LODController.ReapplyClusterOrientation`). No `#if`, no editor reference, nothing live-specific compiled into builds.
2. **The shared part only does plumbing**; each domain owns "how do I re-apply my settings" next to its own domain.
3. **The running wall gets a private COPY** of the config, never the window's object (the window's config is authoring data; sharing it lets the game mutate it).

**Files** (all `Editor/POIEditor/LivePlayModeConfig/`):

| File | Job |
|---|---|
| `ILivePlayModeApplier.cs` | The contract: `Name`, `Fingerprint(config)`, `Apply(session, configCopy)` |
| `LivePlayModeConfigDispatcher.cs` | Plain C#. Remembers each applier's last fingerprint per running wall; calls only appliers whose fingerprint changed; the FIRST push to a new wall applies all; makes one JSON copy per push |
| `LivePlayModeConfigPush.cs` | The one entry point the window calls. Holds the applier list (the one registration place). Does nothing unless `Application.isPlaying` |
| `LivePlayMode<Domain>Applier.cs` | One per domain (`...EffectsApplier`, `...OrientationApplier`) |

**Flow.** `DrawConfigMutationScope` (POIEditorToolWindow.ConfigHistory.cs) detects a change -> `LivePlayModeConfigPush.PushToRunningWall(_config)`; `UndoConfigChange` / `RedoConfigChange` call it too. -> finds the `WallSession` -> dispatcher compares fingerprints -> `applier.Apply(session, copy)` -> runtime re-apply methods.

**Recipe: add a domain (do these in order).**
1. **Find how the runtime consumes the domain's config.** Read the spawn path in `WallSession.SpawnPOIs` and whoever else caches the settings (LODController caches orientation for clusters; static resolvers such as `MarkerHierarchyResolver` are process-wide). List every consumer; a stale one is the usual bug.
2. **Add a runtime re-apply method per consumer, not a new mechanism.** Reuse the spawn-time entry point only if it is idempotent. Check: does it reset state that must survive (e.g. `MarkerBillboard.Configure` overwrites the authored rotation, so a separate `ReapplySettings` exists)? Does the new value take effect on the next frame even when a throttle would delay it (`_forceNextResolve`)? Extract shared pieces out of the spawn path instead of copying them.
3. **Write `LivePlayMode<Domain>Applier`.** `Fingerprint` must change for EVERY field the domain owns and for nothing else: too narrow = edits silently ignored, too wide = needless re-applies (a test caught the effects fingerprint hashing whole levels, so a facing edit also re-pushed effects). If the domain also owns level columns, include only those columns (`key=column` strings), not whole level entries. `Apply` calls the runtime methods with the private copy, plus any scene singleton (`Object.FindFirstObjectByType`, null-safe).
4. **Register it** in `LivePlayModeConfigPush.Dispatcher` (one line).
5. **Tests (real ones, `40-testing.md` 4.2.1):**
   - EditMode, `Tests/Editor/LivePlayModeConfigTests.cs`: fingerprint changes for every field (walk the settings class by reflection so a new field cannot be forgotten) and NOT for other domains' fields; the applier through the dispatcher on a real `WallSession` + real `POI_Marker` prefabs (built with reflection like `OrientationWallSessionIntegrationTests`); a first push reaches all appliers, an unrelated edit reaches none.
   - PlayMode, `Tests/Runtime/<Domain>LiveUpdateTests.cs`: measure the real behaviour after real frames (rotation, alpha, activeness), before -> apply -> after -> apply back. PlayMode tests cannot reference the Editor assembly, so they call the runtime seam directly; the EditMode test covers the applier.
   - Prove a throttle/guard fix is load-bearing: temporarily disable it and see the test go red, then restore.
   - Reset shared static state in fixtures; keep the effects preview grid off in fixtures that load the shipped config.
6. **Real run (Tier A):** Play the LivingRoom scene, drive `DrawConfigMutationScope` through the real window by reflection (or edit the UI by hand), read the running marker state before / after.
7. **Docs:** a "Live updates in Play Mode" section in the domain guide (what is live, what is not), the Playmode test guide text in the window (LIVE line), and `10-structure.md`.

**Traps found while building it.**
- `WallSession` is created inactive in tests, so `Awake`/config load never run: inject `_config` by reflection and guard runtime methods on `_config`, not on `_configLoaded`.
- Destroying the effects preview grid needs `Destroy`, which is PlayMode-only: EditMode tests keep the grid off; grid rebuild is proven in PlayMode.
- The window's config can be null after the window was closed and reopened; a push with a null config is ignored.
- Editing a domain that is not wired yet (level size/label, LOD, Zoom, Displacement, Search) still needs Save + Copy + restart; say so in the domain guide instead of implying it is live. Marker/Badge/Outline wall-level fields and a POI's own marker/badge/status fields are live (`_2.2.1` section 3.3); a POI's `hierarchy_level_key` (which level it uses) is not part of that applier and still needs Save + Copy + restart.
- One log line per applied domain (`[LivePlayModeConfig] applied: ...`) is intentional; a dragged slider produces many.

### 1.2 Visual Tab Structure

The editor window uses two levels of visual containment for clear information hierarchy:

**Outer Containers (Tabs): `DrawTabContentContainer`**
- Wraps the entire content of each top-level tab (Global Scene, Specific Marker)
- Uses a light greenish/gray background (`new Color(0.9f, 1.0f, 0.9f)`)
- Contour color differs per tab: `GlobalSectionColor` (bluish) for Global Scene, greenish for Specific Marker
- The selected tab's content container sits directly beneath the tab buttons (no spacer), so the container's top contour touches the tab row

**Tab Buttons:**
- Custom styled buttons (not GUILayout.Toolbar) with `FontStyle.Bold` text
- Global Scene tab: blue background (`GlobalSceneTabColor`), white text (`TabTextColor`)
- Specific Marker tab: green background (`SpecificMarkerTabColor`), white text (`TabTextColor`)
- No selection-based color change  --  each tab always uses its own base color. Selection is indicated by which tab's content container appears beneath the button row
- Horizontal layout with `GUILayout.ExpandWidth(true)` for equal-width distribution

**Inner Section Containers:**
- Each foldout section inside a tab uses `DrawFramedFoldout` with a bold colored title and a distinct section color  --  **no outer `DrawTabContentContainer` wrapper** around individual sections (the per-POI wrapper was removed; only the 2 top-level tab containers remain)

- Global Scene sections: Marker (green), Orientation (indigo), Badge (orange), Outline (purple), Effects (blue), Hierarchy Levels (yellow), LOD (teal), Zoom (magenta), Displacement (violet-pink), Search & Filter (brown).
- Specific Marker sections: Position (soft green), Marker Style (soft orange), Badge Style (soft purple), Outline (soft blue), Search Keywords (soft yellow)
- Provides visual grouping so authors can instantly identify which section they're editing

## 2. Source of Truth

Two config copies by design:

- **Authoring source (read/write):** `Assets/Apps/<Wall>/config.json`
- **Runtime copy (write-only):** `Assets/StreamingAssets/<Wall>/config.json`

Expected workflow: Load + Populate + edit source -> Save All to JSON -> Copy to StreamingAssets.

`Load & Populate Rig` (single button, calls LoadAndPopulateRig -> PopulateRig, which always reloads the source file first to avoid stale data).
`CopyToStreamingAssets` reads source, writes streaming, then `AssetDatabase.Refresh()`.

## 3. Data Flow

### 3.1 Config In (Load)

```
Load & Populate Rig button
  -> RigLifecycle.LoadAndPopulateRig()
     -> [Guard 1] uncaptured rig moves? DisplayDialogComplex
        ("Capture & Reload" / "Discard & Reload" / "Cancel")
     -> [Guard 2] _hasUnsavedChanges? DisplayDialogComplex
        ("Save & Reload" / "Discard & Reload" / "Cancel")
     -> RigLifecycle.PopulateRig()
        -> ConfigFileIO.LoadConfig()  [always reloads source first: read + parse
        + seed defaults + icon library + history snapshot + ValidateAndAlert]
     -> GetOrCreateRig + spawn markers (see 3.4)
```

### 3.2 Config Mutation (Undo-Aware)

Every field edit in Global or Specific sections is wrapped in `DrawConfigMutationScope`:

```
UI field changed
  -> DrawConfigMutationScope(drawContent, refreshRigOnChange: true)
     -> snapshot before = JsonUtility.ToJson(_config)
     -> drawContent()  [mutates _config fields directly]
     -> snapshot after = JsonUtility.ToJson(_config)
     -> if before == after: return (no change, no history record)
     -> RecordConfigChange(before, after)  [JSON snapshot diff, not Unity Undo]
     -> _hasUnsavedChanges = true
     -> if refreshRigOnChange: RefreshRigVisuals()
```

Key detail: undo/redo uses a JSON string list (`_configHistory`), not Unity's Undo system.
`UndoConfigChange` decrements index and calls `ApplyConfigSnapshot` (re-deserializes + Repaint).
`_isApplyingHistory` flag prevents snapshot recording during apply.

### 3.3 Config Out (Save)

```
Save All to JSON button
  -> SaveAllToJson()
     -> CapturePositions(silentWhenRigMissing: true)  [rig positions -> config]
     -> ValidateAndAlert("before save")
     -> SaveConfig()
        -> JsonUtility.ToJson(_config, prettyPrint: true) -> File.WriteAllText
        -> AssetDatabase.Refresh()
                 -> _hasUnsavedChanges = false
```

### 3.4 Rig Flow (Populate / Refresh / Capture)

```
Load & Populate Rig (single button)
  -> RigLifecycle.LoadAndPopulateRig()  [two blocking guards, then PopulateRig]
     -> ConfigFileIO.LoadConfig()  [always reloads source first]
  -> GetOrCreateRig()  [finds or creates POIEditorRig under PlacementCorrectionAnchor]
  -> if rig has children: prompt "Clear and repopulate?"
  -> load prefab from _prefabPath
  -> foreach poi:
     -> POIPositionResolver.TryResolvePosition(poi, out localPos)
        [null position resolves to origin; new single-parameter
         signature, no anchors parameter]
     -> PrefabUtility.InstantiatePrefab(prefab, rig)
     -> instance.name = poi.id  [child name == poi.id is the binding key]
     -> instance.transform.localPosition = localPos
     -> anchor.Initialise(poi) + markerView.Initialise(...)
  -> SelectRigObjects()  [Selection.objects for editor focus]
```

```
RefreshRigVisuals (called on config mutation with refreshRigOnChange=true)
  -> GetExistingRig()  [no-op if no rig]
  -> configure palettes: CategoryPalette / BadgeCategoryPalette / StatusRamp /
     MarkerHierarchyResolver
  -> parse wall-level settings: shape, outline mode, badge mode (with legacy fallback)
  -> foreach poi:
     -> child = rig.Find(poi.id)  [name-based binding]
     -> anchor = child.GetComponentInChildren<POIAnchor>() ?? AddComponent<POIAnchor>()
     -> anchor.Initialise(poi)  [updates runtime data, NOT position]
     -> markerView.Initialise(...)  [updates visuals from current config]
```

RefreshRigVisuals does NOT move marker positions -- it only updates visuals. Position
changes require manual Transform editing in the rig, and the authored position is persisted by the main `Save All to JSON` action.

```
Save All to JSON syncs rig positions into config
  -> GetExistingRig()
  -> build Dictionary<string,Transform> of rig children by name
  -> foreach poi:
     -> if sceneObjects.TryGetValue(poi.id):  [only matched POIs]
        -> localPos = markerTransform.localPosition
           [rig sits at origin under the correction anchor, so
            localPosition == world position -- no inverse-transform
            conversion is performed]
        -> poi.position = new PositionData { x, y, z, }  (position_verified untouched)
     -> else: skipped++
```

```
Clear Rig
  -> GetExistingRig()
  -> if no children: "Nothing to clear" dialog
  -> IsRigInSyncWithConfig() check:
     if outOfSync: "N marker(s) differ. Clear anyway?" [save/clear or cancel]
  -> for each child: Undo.DestroyObjectImmediate(child)  [undoable]
```

### 3.5 Icon Library Flow

- `_defaultIconLibrary` auto-loaded from `DefaultIconLibraryPath` on OnEnable and LoadConfig
- `_wallIconLibrary` auto-created (copies from defaults) if not found via
  `CreateOrAssignWallIconLibrary`
  - Lives in wall's `Resources/` folder so runtime can load it
  - Path auto-populated to `_config.marker_icon_library_resources_path`
  - Never shown as ObjectField -- managed internally
- `ResolveSpriteForKey(key)`: wall library first, then default library
- `AssignSpriteToLibraryAndGetKey(sprite, name)`: registers sprite to wall library,
    returns key

```
OnGUI()
```

### 4.1 Top Config and Actions

```
Scene Configuration (foldout)
  - Config path     [______] [Browse...]
  - Streaming path  [______] [Browse...]
  - Marker prefab   [______] [Browse...]
  - Correction anchor  [ObjectField]  <- must be PlacementCorrectionAnchor
  - Wall mesh (ref)  [ObjectField]

[Load & Populate Rig]  [Clear Rig]
[Save All to JSON]     [Copy to StreamingAssets]  [Undo]  [Redo]
```

All these rows are shared editor rows (transparent indent spacer + width capped to
max(MinRowWidth, min(visible panel, MaxRowWidth))):
- The path rows via `DrawPathRow` (labelled TextField capped to `rowWidth - 36f`),
- The wall-mesh ObjectField row via `DrawEditorRow` directly (the whole labelled
  ObjectField takes `rowWidth`, `ExpandWidth(false)`),
- The two action-button rows via `DrawEditorRow`: [Load & Populate Rig] + [Clear Rig]
  each take `(rowWidth - 4) / 2`; Undo/Redo stay fixed 85px and Save/Copy share the
  rest: `(rowWidth - 182f) / 2`.
Repository rule: a multi-element row splits the shared `rowWidth` locally, per row --
no generic multi-button abstraction (only two such rows exist; simple duplication wins).

Button coloring:
- Clear Rig turns orange when rig has children
- Save All to JSON turns yellow when `_hasUnsavedChanges`
- Undo / Redo are disabled via `EditorGUI.DisabledScope` when no history available


Identity renames are COMMIT-STYLE (the cell IS the POI identity): keystrokes edit a
SessionState draft, the row's identity stays pristine until Enter / click-outside
commits it once and `IdentityRenameResolver.TryCommit` rewrites every POI holding the
old string via the concrete delegate for that identity (`CategoryRewrite` -> POI.category,
`BadgeKeyRewrite` -> POI.badge_category, `StatusLevelKeyRewrite` -> POI.status_level_key,
`HierarchyLevelKeyRewrite` -> POI.hierarchy_level_key; the nested search-field key uses
`SearchFieldReferenceResolver.RenameFieldKey` -> each `search_keyword_fields[].field_key`).
ESC discards the draft (no change). Blank or colliding target names are rejected with a
dialog and the original identity is kept. Each table owns one `IdentityRenameEditState`
instance (built lazily in `DrawMarkerGlobalSection` / `DrawGlobalBadgeSection` /
`DrawSearchFieldsTable`); the state reads rows/POIs through PROVIDERS so it keeps
pointing at the live `_config` even after Undo swaps it wholesale
(`ApplyConfigSnapshot`). Enter/ESC resolve BEFORE the shared TextField draws
(the `PoiRenameKeys` "press Enter twice" trap); no shared SymbolTable change was needed.
DrawPathRow (Scene Configuration) is a shared editor row: transparent indent
spacer + a LABELLED TextField capped to `rowWidth - 36f` (36 = browse-button
allowance + spacing) + a fixed 30px "..." button + `EditorRowEnd()`. The same
DrawEditorRow recipe used for buttons applies to non-button rows: the STRETCHY
element (here the TextField, there the button) is the one that gets
`GUILayout.Width(...)` + `GUILayout.ExpandWidth(false)`. Opens OpenFilePanel,
converts to Assets-relative path via `AbsoluteToAssetPath`, rejects paths outside project.

### 4.3 Global Scene Options

Ten foldout sections (Marker, Orientation, Badge, Outline, Effects, Hierarchy Levels, LOD, Zoom,
Displacement, Search & Filter), each wrapped in DrawConfigMutationScope:

**Marker**: Background shape popup (Circle/Rounded Square/Hexagon/Diamond/Star/None),
icon library selector + category symbol table.

**Orientation** (`_2.1_Marker_Orientation.md`): sits
between Marker and Badge. Four sub-foldouts -- Vertical Alignment, Facing Options,
Update Cost, Test -- choose how markers, labels, badges and cluster aggregates are
rotated at runtime and how to verify a choice. Progressive disclosure: `up_reference`
(+ custom vector) shows only when something is actually set to World Up; `facing_basis`
only for Always Facing Camera; a Wall Fixed/Y Rotation Only HelpBox explains which
authored per-POI angles that facing mode reads; `update_interval_s` / `camera_delta_deg`
only for their own update modes. Section color `OrientationSectionColor` (indigo).
Conditional sub-fields use `ConditionalAdvance` (section 0, "Indentation").

**Badge**: Enable toggle, badge background shape popup, badge corner popup, badge size
slider, badge category symbol table, then a Test sub-foldout. The rest of the section only
draws when `marker_use_badge` is true (`_2.2.2_Badge_Design.md` §4).

**Outline**: Enable toggle, a three-option Outline Color popup (Uniform color / Same hue as
marker / Per outline type), a conditional colour swatch+hex row (Uniform mode only), Ring
size and Contour spin sliders, the outline level table (its Color column shown only in Per
outline type mode -- Uniform and Same hue both resolve colour above the table instead), then
a Test sub-foldout carrying the "Add outline demo grid" switch (`_2.2.3_Outline_Design.md`
§4). Remove uses trash icon.

**Effects** (`GlobalScene/POIEditorToolWindow.Effects.cs`): this page DEFINES how each effect looks; the Hierarchy Levels table CHOOSES per level (Ripple / Halo / Pulse columns); every POI takes its level's effects. Layout: "Enable effects" master toggle (off hides everything below and keeps the values), then one foldout per effect (Pulse, Ripple Rings, Ripple Discs, Halo Ring, Halo Disc, Beacon) with its own enabled checkbox, a "used by" line, an (i) on the title and on every non-obvious parameter, and its own parameter rows; then the Test sub-foldout. Unticked effects disappear from the level dropdowns (a level still using one shows "(disabled)"). All rows use the shared field helpers. Periods below 0.1 s are raised at runtime, not in the field (a live clamp would fight typing).

**Hierarchy Levels**: Table with columns for key/label/size_cm/show_label/
ripple_effect/halo_effect/pulse/rotate_contour/reveal_delay_s/reveal_duration_s (Ripple / Halo dropdowns list only effects ticked in Effects; an (i) after Pulse explains the effect columns).
No cap on rows. **Built**: an explicit `priority` int column, column 2
(right after Label)  --  a 1-based sort key, see `_2.3_Marker_Hierarchy.md`
section 3 and section 6. Confirmed directly in code: `+ Add` seeds new rows with
`priority = hierarchy_levels.Count + 1` (`GlobalScene.cs`), matching the
outline table's same "seed from current row count" convention.
A `search_keywords` column (`_2.6_Select_Filter_Search.md` section 6) is part of the table, built on
`DrawSymbolTable<T>` like the other taxonomy tables.

#### Outline colour modes

`marker_outline_mode` is `uniform` / `same_hue` / `per_type` / `none`, every one a real
`MarkerOutlineMode` enum value -- there is no editor-only mode string any more (the old
`free_colors` value, never recognised by the runtime parser and so silently rendering no
outline at all, was removed; see `_2.2.3_Outline_Design.md` §1/§2.2). `StatusRamp.Configure`
takes the mode and the uniform colour explicitly and is mode-aware: Uniform ignores every
row's `color_hex`; Per outline type honours each row's own; Same hue never reads
`StatusRamp` at all. The editor normalizes an unknown/legacy saved string to `uniform` via
`MarkerVisualsParser.TryParseOutlineMode`.

#### Outline pct auto-spacing

RecomputeLevelPercentSpacing distributes `pct = (100 / (count-1)) * i` across levels.
Called on add, remove, and load. No cap on number of levels.

#### Defaults seeding

LoadConfig seeds empty sub-lists from editor-only helpers:
- DefaultCategoryStyles.Create() -> 6 heritage categories
- DefaultBadgeCategories.Create() -> 4 damage levels
- DefaultOutlineLevels.Create() -> 4 destruction levels
Seeded only when genuinely empty (not on every load).

### 4.4 Specific Marker Options

Per-POI list with foldout per POI (titled "N. Name"), **collapsed by default** (see
`GetPoiFoldout`). Each POI **title row** carries, left to right: the foldout arrow, the
name (click to toggle), a **focus crosshair icon**, the pencil (rename), the up/down
reorder buttons, a per-row **"+"** add-near button, and the trash button. The crosshair
selects the rig child named `poi.id`, pings it, and frames a context box sized to
~1.5 marker-widths across (min 0.2m) via `SceneView.Frame(bounds)` -- FrameSelected
alone uses the uGUI renderer's near-zero bounds, so the view stays zoomed far out.
Disabled when the rig has no such child yet (same `CanFocusPoiInScene` guard as
before). It lives on the header row specifically so a **collapsed** POI can still be
focused in one click. Pure steps (name check + width math) live in PoiFocusResolver
(Tier-0 tested).

Adding a POI: the per-row "+" (`AddNewPoiAfter(index)`) uses that POI as the template and inserts the
new one immediately below it; the empty-list "+ Add first POI" calls `AddFirstPoi()`. There is no
"insert before the first POI": add after it and reorder up. The header icons are explained in one place
by the row's "(i)" (`PoiHeaderIconsHelpBody`). The Focus action lives only on the title row (not inside
the POI body); its explanation is on the Position foldout's own "(i)".

The **Position** foldout's header row carries,
right-aligned after the flexible-width "Position" title, the **Verified/Unverified**
toggle itself followed by a small `(i)` help button -- both sized to match the POI
title row's own 22px icon buttons (`HelpInfoButton.Draw(..., 22f)`), not the
wider default help-button footprint. `DrawFramedFoldout` has a `rightAlignTrailing`
bool parameter (default `false`, so every other caller's fixed-40px-after-title layout
is unchanged) that swaps the fixed gap for `GUILayout.FlexibleSpace()` for this one
call site. The trailing content is drawn by a new `DrawPositionHeaderTrailing(poi)`
method in `PositionTabs.cs`, which now owns the Verified button instead of a standalone
row at the bottom of the foldout's content -- moving it next to the title reads as
"commit this position" sitting right where the developer is already looking.
`PositionSetupHelpBody` (the `(i)` popup body) was rewritten into an explicit numbered
workflow: (1) select via the crosshair (a new POI is auto-focused already), (2) move
with Unity's normal Move tool, (3) click Verified to lock -- plus an explicit note that
facing is locked too (Verified covers position AND facing, see the Facing paragraphs below).

Below it sit three **Facing** rows -- Facing X, Facing Y, Facing Z (named to match the
global Orientation section's Facing Options domain; the first row's `(i)` button carries
the detailed explanation). Each is a 0..360 slider wired to `POIData.editor_rotation_x_deg`
/ `editor_rotation_deg` (Y) / `editor_rotation_z_deg`, drawn by `DrawFacingSliderRow`,
wrapped in ONE config mutation scope (undo + unsaved-guard aware, no rig rebuild) and applied
live to the rig child via `ApplyPoiEditorRotation`. The sliders carry **no per-mode logic**:
the developer decides which axes matter. Which angles reach the runtime marker depends on the
effective `facing_mode` (the POI's hierarchy-level override, else the wall's): `wall_fixed`
uses all three exactly as authored; `yaw_only` uses X/Z and replaces Y with a live
camera-facing yaw every frame; `always_facing_camera` ignores all three. See
`_2.1_Marker_Orientation.md` sections 4.2 and 8.1. Config is the source of truth --
PopulateRig and RefreshRigVisuals re-apply it, so spawn/undo/redo/refresh stay in sync.
The first POI starts at (0,0,0); the row "+" copies all three angles from its source POI
(`CreateDefaultPoi(sourcePoi)`).

**Two-way sync with Unity's own rotation.** slider -> scene: `ApplyPoiEditorRotation`.
scene -> config: `HandleSelectedMarkerEdit` (fed by `HandleSceneGui` on Scene mouse
events and by `OnInspectorUpdate` at ~10 Hz for Inspector Transform edits) calls
`ProcessMarkerTransformEdit`, which writes the marker's rotation back through
`SyncPoiRotationFromScene`. That runs outside `DrawConfigMutationScope`, so it never feeds
the scope's JSON diff and spams undo history. Sync compares ORIENTATIONS
(`PoiRotationResolver.IsSameOrientation`), not euler triples: `eulerAngles` reads X=100 back
as (80,180,180), which would make a slider jump. On Save, `CapturePositions` also reads the
rotation (skipped for Verified POIs and while Edit-Mode preview is on).

**Verified locks facing AND position.** While a POI is Verified the
Facing sliders are disabled (`AreFacingSlidersEditable`) and any Scene/Inspector rotation is
reverted to the stored angles (`ShouldBlockVerifiedRotationChange`), any move to the last
verified position (`ShouldBlockVerifiedPositionMove`), each with a notice. Verifying captures
the rig's current rotation as the verified facing, like position. The Rotate-tool position
drift described below is still corrected silently.

**Edit-Mode preview and the gizmo.** With preview ON the rig shows what the runtime would show,
so some edits are invisible: `FacingEditAdvice` warns (every axis in always_facing_camera,
only Y in yaw_only, none in wall_fixed) for slider edits and for Rotate-gizmo drags. Under
preview the gizmo is a real edit only in `wall_fixed` (there the preview shows the authored
angles untouched); in the other modes its output is overwritten by the preview and is not
captured.

**Auto-reveal.** The first Scene-view edit gesture on a marker (pose change, or a Move/Rotate
handle drag -- `MarkerEditDetector`) opens the Specific Marker tab, expands that POI and its
Position foldout and scrolls to it (`RevealPoiInSpecificMarkerTab`; the scroll is applied
during Repaint when the POI's header rect is real, `_pendingScrollPoiId`). It reveals once per
selected marker, also when the edit was blocked by the lock, and never from the Inspector
poll or from a slider drag.

**Rotate-tool position drift.** With the Scene view's Tool Handle Position set to
Center, Unity's Rotate gizmo can nudge `localPosition` slightly as a side effect of
spinning the marker around its visual bounds center rather than its own transform
origin -- incidental drift, not an intentional position edit. The revert still corrects it
(so it never persists), but the "already verified" notice is suppressed specifically while
`Tools.current == Tool.Rotate`, so rotating a Verified marker never shows a spurious
position-lock message the way a genuine Move-tool drag does.

Pure math lives in `PoiRotationResolver`, `FacingEditAdvice` and `MarkerEditDetector`; the write-back
rule lives in `POIEditorToolWindow.SyncPoiRotationFromScene` (both Tier-0 tested).

**Position** (foldout, `PositionTabs.cs`):

**Marker Style** (foldout): Name text field, Category dropdown (from category_styles),
Hierarchy Level dropdown (from hierarchy_levels + "(none)"), "Use Custom Symbol" toggle.
Custom symbol shows Sprite ObjectField + preview -- overrides just the icon, not color/ring/badge.

**Badge Style** (foldout, only if marker_use_badge): Badge category dropdown.

**Outline** (foldout, only if marker_outline_mode != "none"): "Has status" toggle.
If checked: Status level popup (from outline_levels, showing label + pct) or Status % slider
(if no outline levels defined). "Status unknown" toggle triggers ApplyUnknownStatusDefaults.

#### Unknown status

ApplyUnknownStatusDefaults searches `_config.outline_levels` for key="unknown" and assigns
its key+pct. Also searches `badge_categories` for key="unknown_damage" and assigns it.
This is an editor convenience -- runtime rendering is driven by status_level_key + badge_category strings.

#### Dropdown patterns

Category/BadgeCategory/HierarchyLevel dropdowns: collect available keys from config tables,
build a string array, find current index, Popup, write back the key. Empty selection means
"fall through to framework default" (not an error).

### 4.5 Symbol Table Renderer

DrawSymbolTable<T> is generic over entry type, driven by delegates:
- getPrimaryLabel / setPrimaryLabel (category or key)
- getIconKey / setIconKey
- getColorHex / setColorHex

- showColorPicker (bool gate for color column)

Columns: primary | Details(...) | Symbol(Sprite ObjectField + interactive

### 4.6 OnSceneGUI

Draws cyan handles in the Scene view for:
- Each calibration anchor's position
- Each POI's resolved (pre-capture) position from POIPositionResolver

Does NOT edit positions itself -- scene objects are moved via normal Transform tools, then
Capture Positions writes them back. Separately, `HandleSceneGui` (Scene mouse events) and
`OnInspectorUpdate` run `HandleSelectedMarkerEdit` for the selected rig marker (facing sync,
Verified lock, auto-reveal -- see 4.4). Both handlers are subscribed in `OnEnable` and MUST be
unsubscribed in `OnDisable` ("Dialog results, handlers, events and menu items").

## 5. Data Types Reference

### 5.1 WallConfigData (Runtime)

Top-level config. Key fields:
- `wall_id` / `wall_name` / `immersal_map_id`
- `marker_shape` (string, parsed by MarkerVisualsParser)
- `marker_outline_mode` (string: uniform/same_hue/per_type/none -- see `_2.2.3_Outline_Design.md`
  §2.2; there is no legacy `marker_style` field any more, removed with no compatibility shim,
  `_2.2.1_Marker_Design.md` §1)
- `outline_uniform_color_hex` (string hex; the Uniform mode's one shared, developer-adjustable
  colour, default `#E3BD72`)
- `ring_size_ratio` / `contour_spin_deg_per_s` (wall-level ring size and spin speed)
- `outline_preview`: OutlinePreviewSettings -- {enabled, base_poi_id}. Dev-only "Add outline
  demo grid" (`_2.2.3` §4, same shape as `effect_defaults.preview` below)
- `marker_use_badge` (bool)
- `badge_corner` / `badge_size_ratio` (string / float; badge placement and size, `_2.2.2` §1)
- `marker_icon_library_resources_path` (string, for runtime Resources.Load)
- `badge_shape` (string)
- `category_styles`: List<CategoryStyleEntry> -- {category, icon_key, color_hex, details}
- `badge_categories`: List<BadgeCategoryEntry> -- {key, label, icon_key, color_hex, details}
- `outline_levels`: List<OutlineLevelEntry> -- {key, label, pct, line_style, color_hex}
- `hierarchy_levels`: List<HierarchyLevelEntry> -- {key, label, size_cm, show_label,
  ripple_effect, halo_effect, pulse, rotate_contour, reveal_delay_s, reveal_duration_s,
  facing_mode_override}
- `effect_defaults`: EffectDefaults -- {effects_enabled, one block per effect (pulse, ripple_rings, ripple_discs, halo_ring, halo_disc, beacon, each with its own enabled), preview}
- `displacement_settings`: DisplacementSettings
- `orientation_settings`: OrientationSettings (`_2.1_Marker_Orientation.md` section 7)
- `pois`: List<POIData>

### 5.2 POIData (Runtime)

- `id` / `name`
- `category` (string -> CategoryPalette)
- `badge_category` (string -> BadgeCategoryPalette)
- `position` (PositionData class: x, y, z -- a reference type; null means no position)
- `position_verified` (bool -- editor-only QA flag; runtime never reads it)
- `has_status` / `status_pct` / `status_unknown` / `status_level_key`
- `hierarchy_level_key`
- `has_custom_symbol` / `custom_symbol_key`

### 5.3 PositionData

A `[Serializable]` class with `float x, y, z` and a `ToVector3()` helper. Being a
reference type makes the `poi.position != null` check in `POIPositionResolver`
meaningful. When JsonUtility synthesizes a zero-initialized object for an absent
position, that is functionally equivalent to a cleared position (both resolve to
origin at runtime) -- so no extra guard flag is needed.

## 6. Testing

Location: `Assets/Framework/Tests/Editor/POIEditorToolWriteBackTests.cs`

Most tests in this file are pure data tests (construct `WallConfigData` in code, verify field
read/write) with no scene. The position write-back tests instantiate a real rig hierarchy
(`PlacementCorrectionAnchor`, a rig root, child POI objects) and a real
`EditorWindow.GetWindow<POIEditorToolWindow>()`, because they verify that `CapturePositions`
writes real `Transform.localPosition` values into config. Both are Tier 0 (EditMode, no rendering).

| Test | Verifies |
|------|----------|
| `CapturePositions_OnlyUpdatesMatchedPOIs` | 3 POIs in config, 2 scene objects placed. Only 2 matched POIs get position; 3rd untouched |
| `CapturePositions_PartialCapture_DoesNotAffectOthers` | Capturing one POI leaves others' fields unchanged |
| `CapturePositions_OriginPosition_IsStored` | A POI at (0,0,0) is stored and resolves to origin (synthesized zero-object is equivalent to null) |

Test pattern: `CreateTestConfig()` factory builds minimal WallConfigData with 3 POIs.
Tests simulate CapturePositions logic inline.

**Boundary note:** Tests validate the data contract, not the EditorWindow UI.
UI rendering is verified via manual inspection; data logic via tests. This is the
correct split -- the window is a shell with no serializable business logic.

Facing / notice tests (all real code: real window instance, real `POI_Marker` prefab, real rig,
real `Selection`, real IMGUI harness windows; no mocks): `PoiFacingLockAndSyncTests` (sync,
lock, detector, reveal state, slider rows, LivingRoom config round trip),
`PoiFacingModesAndLifecycleTests` (per-mode/per-axis visibility on the real prefab, warnings
checked against the real pipeline, verify/unverify wiring, leaked scene-handler check, reveal),
`EditorNoticeTests`, `ReloadGuardChoiceTests` (every dialog-result mapping incl. Esc), and
`TestDialogGuard` (a `[SetUpFixture]` that switches real notice dialogs off for the run).

Run via Unity MCP: `run_tests` with mode=EditMode. Acceptance: **zero failed tests**.
