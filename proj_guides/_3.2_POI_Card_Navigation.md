# POI Detail Card -- Navigation (3.2)

How a visitor moves between the blocks of ONE open card: the ontology that groups blocks (families, kinds, formats), the
order the card shows them in, the card LAYOUT modes (scroll, tabs, pages, accordion, bento) and the NAVIGATION ELEMENTS a
developer composes into the card's slots (top, bottom, floating, menu overlay, edge, in-flow blocks). Every layout and every
element is a choice in POI Editor > Detail Card > Navigation. Builds on `_3.1_POI_Card_Blocks.md` (sheet, stack, takeover,
owners); every look follows `_3.3`.

Design source: `_3.0_POI_Card_Prototypes/` boards "Ontology", "Navigation" (24 elements) and "Layouts".
Re-planned 2026-10-03 with `skills/Domain_Planning.md` on the BUILT card (`_3.1` closed, 34 kinds / 69 looks); this replaces
the one-pass plan of 2026-09-26.

## 1. Scope

**In:** moving inside ONE open card: block order, families / kinds / formats, layouts, every navigation element of the canvas
except the four below, the generic teaser / full view every layout needs, the placed-model chip, system Back.

**Out:** anything that moves between POIs or walls -- the AR orbit ring (F1, the card opens on a family chosen around the
marker), the ask bar / intent chips (F2, needs the AI or voice domain), the guided tour mode (F3, circuits): Stage 3. Lenses
(era, profile) `_3.4`. Theme / sunlight looks of every element: `_3.3` (this domain uses only `--ts-*` tokens and role classes).
Screen-reader support: Stage 7 (this domain keeps every element focusable and labelled).

## 2. Ontology (what every element navigates)

### 2.1 Levels (canvas "Ontology")

- **L1 Family** -- the visitor's intent ("what do I want?"). **L2 Kind** -- the block kind. **L3 Instance** -- one block.
- Why intent, not file type: visitors scan by goal; strong labels give "information scent" (Pirolli & Card 1999). Format is a
  second axis the same elements can pivot to (`group_by = format`, section 2.4).
- **At most two taps** to any block: Nielsen (2006) -- more than two disclosure levels "typically have low usability". The
  collapse rules (2.5) keep the three levels to two taps.

### 2.2 Families are data (step 1)

`FamilyDefinition` (Runtime/Blocks/): `Key`, `Order` (int), `LabelKey` (a `CardStrings` key: visitor words, localized,
overridable in Card Texts), `IconKey` (`CardIcons`), `ColorToken` (`--ts-family-<key>`, `_3.3`), `InNav` (bool), `AtEnd`
(bool). Step 1 declared the five the card read then; `IconKey` and `ColorToken` landed at step 6 with the elements that draw them
(built-in icons: about `info`, media `picture`, guides `listen`, stories `book`, ar `show_on_wall`, play `play`, visit `location`,
community `people`, meta `sources` -- the four-part USS icons of `CardIcons`; tokens `--ts-family-<key>` in `CardTokens.uss`, read by
NAME through `CardTokenColours` from the `.ts-card` root's custom style, so the value stays in the stylesheet).
`FamilyIconAndWordsTests` holds every registered family (an app's too) to an icon the set draws and a token a stylesheet defines,
each family colour >= 3:1 on `--ts-surface`. Since step 6 a KIND also names its visitor words: `BlockKindDefinition.LabelKey`
(`kind_*` CardStrings rows, en + pt; an app kind a row of its own table) -- what a chip says, never the Editor's `DisplayName`. `BlockRegistry.RegisterFamily(def)`; registering a kind whose family is not registered throws (today a
typo makes a new family silently). The check lives in the INSTANCE `Register`, which knows the registered families; the static
`Validate(definition)` keeps its signature and its shape checks, so the tests that call it keep compiling. An app
registers its own family exactly like a kind (`_3.1` extension rule); its label key goes in its own string table
(`CardStringSources`).

### 2.3 Block order (step 1) -- replaces `container.sources_at_end`

`navigation.block_order` (Editor "Block Order"):

| Option | What the stack shows | Why offer it |
|---|---|---|
| `authored` | the POI's authored order | a wall that tells one story top to bottom |
| `end_families_last` (default) | authored order, then the blocks of every family with At End on (meta), in their authored order | = today's Sources At The End on; a card ends with its sources |
| `by_family` | stable sort by family Order, authored order inside a family | family tabs and spy read cleanly: each family is ONE contiguous section |

`BlockStackBuilder` applies it after the skip rules (the header stays first). `container.sources_at_end` and its Editor row are
REMOVED (no shim, `00-process`). The LivingRoom config never wrote the key (it ran on the default, on), so it needs no edit;
a wall that had it off sets Block Order = `authored`. The tests that click the old row (`DetailCardEditorTabTests`,
`PoiCardLiveUpdateTests`, `BlockStackBuilderTests`, `PoiCardSceneTests` comments) move to Block Order.
Why one option and not a family flag alone: order is a wall choice (a story wall wants `authored`), "what goes last" is a family
fact (meta) -- the option reads the flag.

### 2.4 Format facet (step 2)

`BlockKindDefinition.Format`, one of `CardOptions.Formats`: `read`, `look`, `watch`, `listen`, `model` (3D / 360 / AR),
`interact`. Fixed list (formats are universal; families are a wall's vocabulary). Every built-in kind declares it; the app's
size_comparison too; `Validate` refuses an unknown one. Format labels are `CardStrings` keys like the families'.

Decided at step 2 (the guide named only watch, listen and model) -- a format is HOW the visitor takes the block in:
- `read` -- header, quick_facts, rich_text, fun_fact, pull_quote, process_steps, timeline, person, story_chapters,
  practical_info, sources
- `look` -- the picture or drawing IS the content: status (the ring), swatches, size_comparison, gallery, before_after,
  zoom_image, hotspot_image, compare_points (two rings), wall_locator (a strip), today_map
- `watch` -- video. `listen` -- audio_guide
- `model` -- model_3d, panorama_360, place_in_ar, show_on_wall (both AR kinds: "see it in the room / on the wall")
- `interact` -- the visitor DOES something: actions, knowledge_check, poll, collect, feedback, dialogue, related (a tap goes
  to another point)

Labels (`format_*`, en / pt): Read / Ler, Look / Ver, Watch / Assistir, Listen / Ouvir, Immersive / Imersivo, Interact /
Interagir (`model` reads "Immersive": one word that covers 3D, 360 and AR).

### 2.5 Collapse rules (`NavOntologyRule`, pure, step 2)

Applied to the rendered stack, in this order:
1. Only **targets** count: blocks in the scroll (not the header, not a pinned-top or footer look, not a block waiting for
   ShowAfterViewed until revealed, not a `navigation` / InNav-off family).
2. A family with no target is hidden.
3. Fewer targets than **Show Navigation From** (`min_blocks`, default 8) -> the card shows NO navigation element (scroll only).
   NN/g: in-page navigation on short pages "adds unnecessary length" (Wang 2023).
4. A family with one target: its item jumps straight to the block (L2 skipped). A kind with one instance: L3 skipped.
5. A bar with more sections than **Bar Slots** (`max_slots`, 3..5, default 5): the last slot becomes **More** (lists the rest).
6. `segmented`: families merge into the wall's Groups (section 3, `groups`); a group with no target is hidden. **Built at step 6:**
   `NavGroupRule` (the wall's rows, else the four defaults; a family's group = its Families row's `group`, else its default, and only
   when the wall has that group; `"none"` = no group) and `CardNavModel.Groups` -- FAMILIES merged whatever Group By says.
7. An element that navigates BETWEEN sections is not drawn with fewer than two sections: one tab is not a choice (decided
   at the 5a review). Elements that list blocks instead (`nav_contents`, `find_block`) ignore this rule. **Built at step 5b:**
   `NavOntologyRule.OffersASectionChoice` (2 and up), read by `NavSlotRule.TopElement` for an element whose
   `NavElementDefinition` moves between sections (since step 6 its `Choice`: Sections, Groups -- counted on the model's Groups -- or Blocks, which rule 7 skips; an app element declares it); `ShowsNavigation` does not read it, so a
   one-family card still shows navigation to an element that lists blocks (`NavOntologyRuleTests`, `NavElementRegistryTests`).

## 4. Architecture

### 4.1 One model, one controller, many views (`_2.6` "one result set every surface shows")

```
BlockStackBuilder (order, step 1) -> stack entries
   -> CardNavModel.Build(entries, families, settings)        pure: sections (family/group/format) -> kinds -> targets
   -> NavController (one per sheet)                            scroll / page / raise, spy, CurrentChanged, nav_jump event
   -> INavElementView x N (one per used slot)                 views only: Bind(model, controller, context), Unbind
```

- `CardNavModel` (Runtime/Blocks/Navigation/, built at step 2): `Build(entries, registry, settings, isRevealed)` ->
  `GroupBy`, `Sections` (each: `Key`, `LabelKey`, `Count`, `Kinds` (key, targets, `DirectTarget`), `Targets`, `DirectTarget`),
  `TargetCount`, `ShowsNavigation`, `BarSections` / `MoreSections`. Icon and colour token join at step 6 with the icons and
  tokens. Sections come in the order the stack shows their FIRST target: with Block Order `by_family` that is the family order,
  and in any other order an element still follows what the visitor scrolls through (so the spy rule of 4.4 stays monotone).
  `isRevealed` is the reveal state of the ShowAfterViewed blocks (the host passes `CardLocalState.Seen` for the POI). Rebuilt
  on every `Sheet.Show` (a POI switch, a live edit, a language switch) and when a waiting block is revealed. Elements never
  compute structure. `NavOntologyRule` holds rules 1-5 of 2.5 as small pure predicates the model calls.
- `NavController` (Runtime/UI/Cards/Navigation/): `JumpTo(sectionIndex)`, `JumpToBlock(blockKey)`, `Current`,
  `CurrentChanged`. Owns no element; the sheet owns it next to the stack.
- `NavElementRegistry` (like `BlockRegistry`): key, slot, Editor label, (i) help, factory. Built-ins registered by
  `BuiltInNavElements`; an app may register its own element for a slot with zero Framework edits. Editor popups list the
  registry's keys per slot.
- `INavElementView`: `Root`, `Bind(CardNavModel, NavController, NavElementContext)`, `Unbind()`. Pooled per key like block views.

Why not Unity's `TabView` (Unity 6, `UIE-uxml-element-TabView`): it swaps content containers (one panel per tab) and has no
scroll-spy or scrolling header strip; the card is ONE stack that every element views. Tabs are plain `Button`s in a strip
that scrolls sideways, styled by `--ts-*` tokens.

**Built at step 5a** -- the strip is a clipped viewport and a row moved by `NavStripRule`'s offset (`style.translate`), NOT a
horizontal `ScrollView`: Unity 6000.3's ScrollView starts touch-scrolling once a finger moved 10 px with any x part (Horizontal
mode zeroes y first), so a mostly vertical drag would scroll the strip, and its opt-out flag (`isHandledByDraggable`) is internal.
`NavElementRegistry` has `BlockRegistry`'s shape; its slots are only the BUILT ones (`NavSlotKeys.Built` = top), so an element for a
slot the sheet does not draw yet is refused. An element is bound with the card's own `BlockBindContext` (words, settings, reduce
motion), no second context type.

### 4.2 Slots (step 5)

| Slot | Where in the sheet | Elements |
|---|---|---|
| `top` | a strip in `Root` between the header (with its PinnedTop) and the stack `ScrollView` -- outside the scroll, so a jump needs no offset | text_tabs, icon_tabs, icon_tabs_chips, kind_chips, segmented, progress_map |
| `bottom` | under the stack, BELOW the sticky CTA footer (thumb zone; the CTA stays nearest the content) | bottom_bar, dock, bar_sheet, next_up |
| `floating` | the card layer, above the sheet's top-right edge, visible at every stop | fab_dial, fab_radial, placed-model chip |
| `menu` | the card layer over the sheet, below `TakeoverView` | drawer_tree, grid_overlay, find_block, More lists |
| `edge` | absolute over the stack viewport's right edge | edge_scrubber |
| in-flow | ordinary block slots in the stack | nav_icon_grid, nav_contents, nav_rails, nav_bento |

The peek stop is still the header's PeekPart (`PoiCardSheetView.RecomputeStops`): the top strip sits after it and is hidden at
peek, so adding navigation never moves the stops (measured at 5a: 195.00 / 337.60 / 796.00 with and without the strip; at 7a the
same with the Bottom Bar set and unset, at Full, Half and Peek, `PoiCardBottomBarSceneTests.TheLampsStops_...`).

**Built at step 7a** -- the BOTTOM slot: `PoiCardSheetView.BottomArea` (`poi-card-bottom`) takes the footer's old place right under the
stack and holds the footer FIRST and the bottom navigation slot (`NavSlots.Bottom`) after it -- the CTA nearest the content, the bar in the
thumb zone. The area, not the footer, is what the chrome hides, so the pair slides as one (two siblings sliding by their own heights
would overlap mid-slide). `NavSlotKeys.Built` = top, bottom; `NavSlotRule.BottomElement` reads `navigation.bottom` with the top's rules.

**Built at step 5a** -- `SwipeGrab` (`Runtime/UI/Cards`) is the ONE way a swipeable part takes a finger (the pattern of every
swipeable element: the true / false card, the strip; rails, pager and scrubber later). It never captures at touch-down; a drag is
judged ONCE as it leaves the slop (`SwipeGrabRule.ClaimsPointer` sideways / `ClaimsVertical`), then captured, followed and released.
Three UI Toolkit facts it is built on, each found by a real-input test: (1) a `Button`'s Clickable stops the press from bubbling, so an
area hears events aimed inside it on the way DOWN (TrickleDown); (2) a captured pointer's events reach ONLY the capturing element, so
while a button holds the finger the grab follows it on that button (Unity's own ScrollView does the same); (3) an event aimed at the
area itself is not delivered to its TrickleDown callbacks, so it is heard at the target. On the top slot the SHEET's grab claims a
vertical drag (it moves the sheet like the header) and the strip's own grab a sideways one; a tap still clicks the tab under it.

### 4.3 `CardChromeRule` (pure, step 5): what chrome shows now

Inputs: stop, the last scroll delta, at-top / at-end, `show_at`, `hide_on_scroll`, the model's "has navigation". Outputs: top
strip shown, bottom area (CTA footer + bottom nav) shown. Rules: nothing at peek; `full_only` hides at half; `down` hides the
bottom area (and a `dock`) after the content moved down by more than `HideAfterTravel` (24 panel px: about a finger's travel, so
a tap's wobble never hides it), shows it again on any upward move over `ShowAfterTravel` (8 px) or at the top / end of the
stack. The top strip stays (it is the map; NN/g sticky headers: keep them compact and opaque, Laubheimer 2021); the
"partially persistent" pattern is used for the bottom, where it costs reading space on every screen. Applied as a class on
the slot with a `--ts-duration` transition; reduce motion jumps.

**Built at step 5b** (`CardChromeRule` decides, `CardChromeView` measures and applies, owned by the sheet beside `NavSlots`):
- **THE FLOOR (two floors, the strip first; built at step 6 on the developer's call at the 5b review).** The TOP STRIP is shown only
  where it leaves the stack's viewport at least `MinStackViewport` = **72 px** beside everything else shown (a block heading 22 + its gap 8
  + two body lines 2 x 20 = 70, measured on The Lamp at 390 x 844, on the 8 px grid); it gives way FIRST -- the strip is a map, one drag
  to Full away. The BOTTOM AREA then needs only `MinStackViewportUnderFooter` = **24 px** (one body line on the grid): the sticky CTA is
  the one irreversible action the card offers ("show me where it is" on the wall) and often why the card was opened. Show Navigation At
  only hides more. A stack shorter than a floor needs only its own height.
  What it gives The Lamp at Half: 106.6 px under the header (sheet 337.6 - grab zone 24 - border 1 - header 206 = header bottom 231),
  strip 49 + footer 81 cannot both fit; the strip goes, the footer stays over **25.6 px** of content (`Chrome_Lamp_half_default_390.png`).
  The 5b review's "~57 px with the button" was the strip's number (106.6 - 49): with the 81 px footer one floor of 72 would have dropped
  both, so the developer chose the one-line floor for the footer (asked at step 6). Full keeps both (room 565).
- **A jump at Half sets the chrome moving** (found at step 6): once the footer stays at Half, a jump scrolls the stack, the header
  collapses, the room grows and the strip comes back -- over the next frames. An instant jump used to end on its first still frame and its
  block landed 60 px low. `NavScrollRule.JumpDone`: every jump holds its landing at least one motion length (`--ts-duration`) before it can
  end (smooth jumps unchanged: their glide is that long).
- **The gap under the strip** (step 6): `CardChromeView` sets `poi-card--nav-top-shown` on the sheet while the strip shows, and `PoiCard.uss`
  pads the stack's content `--ts-space-3` (the first heading sat ~4 px under the hairline). The view reads the blocks' height WITHOUT that
  padding, so showing the strip can never flip its own decision.
- **The header is measured live**, not taken from its open size: once the reader scrolls at Half the header collapses to one line, the
  room grows and the strip (and with room the footer) comes back -- a Half with its map, as long as it can afford it.
- **The rule reads the stop's REST height** (`Stops.HeightOf(stop)`), not the animated one, so a rising sheet does not flip chrome on its way.
- **Hidden = out of the flow, not out of the layout:** `poi-card__nav-top--hidden` (absolute + `visibility: hidden`) and
  `poi-card__footer--hidden` (absolute + `translate: 0 100%` under the sheet's clipped edge, a `--ts-duration` slide;
  `poi-card--chrome-instant` under reduce motion). `display: none` would leave the hidden part with no height, and the rule needs it
  to decide whether the part may come back. `NavSlots` keeps `display` for "is there an element at all".
- **Measured at Full** (`PoiCardChromeSceneTests`): content share 54.6 % at rest; scrolled down 86.8 % with Hide While Scrolling =
  down vs 76.6 % with never -- exactly the footer's share (the header's collapse is in both).
- **The bottom area is a PAIR (step 7a):** the footer and the bottom bar. Inputs `HasFooter` / `FooterHeight` and `HasBottomNav` /
  `BottomNavHeight`; output `Chrome.BottomNav` (only ever inside a shown area). Hide While Scrolling slides both; the one-line floor
  (`MinStackViewportUnderFooter`) measures BOTH -- both go or neither, never a footer without its bar -- and the strip still needs its own
  floor beside the whole pair. Show Navigation At (`NavShownAt`, was `TopShownAt`) is about NAVIGATION: Full Only hides the bar at Half,
  the footer (no navigation) stays. **The Lamp at Half with a Bottom Bar** (the default Top Bar on): room 106.6 under the header, footer 81
  + bar 52 + one line do not fit, so footer, bar and strip all give way and the stack keeps the whole 106.6 px (`Nav_Lamp_bottom_bar_half_390.png`)
  -- the rule working; Full shows all three (`Nav_Lamp_bottom_bar_full_390.png`).
- **A jump is no reading (step 7a):** `CardChromeRule.ReaderDelta` -- while `NavController.IsJumping` the scroll does not count towards
  Hide While Scrolling, or a tap on a bar slot would slide the bar away under the finger that used it (found writing the Phase B tap
  test). The footer gains the same: a tab's jump no longer hides it.

### 4.4 Scroll-spy and jumps (`NavScrollRule`, pure, step 3)

- **Target offset** of a block = its slot's top in the content container (`slot.layout.y`), clamped to `[0, range]` where
  `range = content height - viewport height`. No chrome offset (4.2: chrome is outside the scroll).
- **Current section** = the last section whose first target's top `<= scrollOffset.y + SpyLine`, with
  `SpyLine = 1/3 of the viewport height` (a block counts as "being read" once it fills the upper third); at the end of the
  range (`scrollOffset.y >= range - 1 px`) the LAST section is current, so a short final family can be marked.
- **Jump**: `jump_raises_to = full` first sets the sheet to Full (half shows ~250 px: too little to land on), then scrolls --
  smooth = `scrollOffset` animated over `--ts-duration` by the panel scheduler; instant / reduce motion = set at once. While a
  jump animates the spy is frozen on the TARGET section (else the underline flickers through every family it passes), then
  released.
- **Event**: each jump raises `CardEvent` `nav_jump` (element key, section key) through `ICardEvents`: the evaluation
  (`_7.1`) can compare which elements visitors really use. Built at step 3 on the existing `CardEvent`: BlockKey = the block
  landed on, Variant = the element's key (or the asking block's kind, `IBlockHost.ScrollToBlock`), Value = the section key ("" for
  a block of no section, e.g. Sources).
- **Built at step 3** (`NavController`, `NavScrollRule`), three facts the plan did not have: (1) a jump holds its landing until
  the stack really sits on it -- the ScrollView clamps an offset to its CURRENT range, and at peek, before the raise has grown the
  sheet, that is 0 -- bounded by a settle window of one motion length; instant / reduce motion still set the offset in the same
  call. (2) A jump into the final screen reaches the end, which reveals the Show After Reading blocks: the card grows and the
  rebuilt model must not cancel the jump (a reveal re-binds the SAME context; every Show makes a new one, and cancels). (3) Unity
  has no time-typed custom style, so `--ts-duration` is read through the sheet's own resolved height transition (which IS that
  token). Before the first section's top reaches the spy line the first section is named; a stack that does not scroll is read
  from its top. The `follow_scroll`, `jump_raises_to` and `jump_motion` DATA landed here (their rows: steps 4-5).

Worked example (Lamp as authored in `Apps/LivingRoom/config.json`, Block Order `by_family`, `text_tabs`): 62 blocks -> 56
targets (minus the header, the audio `hero_chip` (pinned top), the `actions` `sticky_cta` (footer), the 2 `sources` (meta: In
Nav off) and the `true_false_swipe` knowledge check (Show After Viewed, until revealed)). Sections: About 18, Media 14, Listen 1,
Stories 7, In AR 3, Play 4, Visit 7, Community 2 = 56, so 8 tabs; Listen has one target, so its tab jumps straight to the player
(rule 2.5.4). The visitor taps "Play" at Half: the sheet goes to Full, then the offset = the first knowledge_check slot's
`layout.y` (clamped to the range) animates; the spy stays on Play during the move; at rest the spy line (offset + viewport/3) is
past Play's first target and before Visit's first -> Play is current. Once the reveal fires (the visitor reached the end), the
model is rebuilt and Play has 5 targets. Lamp Military: 4 targets (6 blocks minus the header and its audio `hero_chip`, pinned
top) < 8 -> no strip, and its Listen family is hidden (its only block is no target). Lamp Religious: none (the header alone).
(Corrected at step 2: this line said 5, forgetting the pinned hero chip; `CardNavModelTests` asserts the 4.)

### 4.5 System Back (`NavBackRule`, pure, step 4)

`back_button = step_down`: each Back press undoes the innermost thing, in this order: an open full view (`TakeoverView`) closes;
else an open menu overlay closes; else an expanded accordion row collapses (step 13); else the sheet goes one stop down (Full ->
Half -> Peek); at Peek it closes through the selection bus (`SelectionEventBus.Clear`, like the X). The host reads the Input
System's `Keyboard.escapeKey`, which is where Android's Back arrives in a Unity player (verify on the device list; the Editor tests
press Escape). iOS has no Back button: nothing changes there. Why: NN/g bottom sheets -- visitors expect Back to work and it
prevents disorientation (Laubheimer 2023). `none`: Back is left to the app.

**Built at step 4** (`NavBackRule` decides, `PoiCardSheetView.Back` applies -- close the full view, `SetStop` one lower, or
`CloseRequested`, the X's own path to `SelectionEventBus.Clear` --, `PoiCardHost.Update` only reads `Keyboard.current.escapeKey`). Two
facts the plan did not have: (1) in LivingRoomScene UI Toolkit takes its input from the EventSystem's `InputSystemUIInputModule`, so a
real Escape also reaches the focused UI element -- as ONE `NavigationCancelEvent` (the UI Cancel action), never a `KeyDownEvent`; the
search field ignores it (words, query, results and focus unchanged, kept as a test), so the card's Back collides with nothing today. A
later element that closes on Cancel (the menu overlay, step 8) must go through `NavBackRule` instead, or one press would do two things.
(2) Back reads the settings of the card bound NOW, so the option is live with no extra wiring (a live edit rebinds the card).

**BlockRef** (step 4, for every holder: an Open Block button today, a hotspot pin at step 10, a bento tile at step 15): the value is a
block key of the SAME POI; the pure `BlockRefRule` says where it can lead -- `JumpTargets` (the shown blocks of the scrolling stack: not
the header, a pinned-top or footer look, a block waiting for Show After Reading) and `Check` (why a pick leads nowhere). The sheet hands
`JumpTargets` to every block through `BlockBindContext`; a holder offers its jump only to one of them, so a visitor never gets a dead
button; the Editor names the reason under the row. A target waiting for Show After Reading is offered from the next Show after the
reveal (the views are not rebound by a reveal). Repeated actions count an Open Block per action AND target: two buttons to different
blocks are two shortcuts, not a repeat (decided at step 4; a warning there would be wrong).

## 5. Elements (canvas ids), step by step

Every element: icon + label + family colour (never colour alone), targets >= `--ts-touch-target`, no clipping at 390 px with the
Portuguese labels, swipeable parts follow `SwipeGrabRule`, every drag has a single-pointer alternative (WCAG 2.2 SC 2.5.7).

### 5.1 Top (steps 5-6)

| Key | Canvas | Level | Behaviour | Why / evidence |
|---|---|---|---|---|
| `text_tabs` | A1 | L1 | families as scrolling text tabs, underline follows the spy | NN/g tabs: short 1-2 word labels, above the panel (Sunwall 2024); spy = "where they are on the page" (Wang & Brown 2023) |
| `icon_tabs` | A2 (top row only) | L1 | icon + short label tabs | labels obey `labels` |
| `icon_tabs_chips` | A2 | L1 + L2 | icon tabs; under them chips of the current family's kinds that exist on this POI | the canvas default for rich POIs |
| `kind_chips` | A3 | L2 flat | every kind one chip, dotted with its family colour | small POIs; long lists hide chips off-screen (warning in (i)) |
| `segmented` | A4 | merged L1 | 3-4 Groups that always fit, no scroll | Groups are config (section 3) |
| `progress_map` | E2 | L1 map | a thin bar split into family segments sized by target count; tap a segment to jump | orientation with almost no space |

**Built at step 6** (`Runtime/UI/Cards/Navigation/`):
- Shared parts: `NavStrip` (the strip machinery lifted out of text_tabs: clipped viewport + `NavStripRule` + `SwipeGrab`), `NavItems`
  (`NavTab`, `NavChip` -- a pill inside a full touch-target button --, `NavCount`, `NavTint`), `TabsNavView` (text_tabs and icon_tabs are
  its two thin subclasses), `NavChipRow` (kind_chips and icon_tabs_chips' row).
- What an element chooses between is `NavElementDefinition.Choice` (`NavChoice` Sections / Groups / Blocks, replacing the 5b bool): rule
  2.5.7 counts sections for tabs and the progress map, GROUPS for segmented, nothing for kind_chips (it lists kinds, so a one-family card
  gets it). `ReadsLabels` / `ShowsCounts` tell the Editor which rows apply.
- The kind / group being read comes from `NavController.CurrentBlock`: the same spy line over every target's own top (frozen on a jump's
  block), mapped through `CardNavModel.KindOf` / `GroupOf`. icon_tabs_chips shows its chip row only for a section with two kinds or more
  (`NavOntologyRule.OffersAKindChoice`) and keeps the row's place (hidden, not removed) so the strip never changes height while reading.
- `ProgressMapRule.Widths`: shares by target count, never under each piece's minimum (the touch token, or a word's width with no icon);
  minimums wider than the strip keep their minimum and the bar scrolls. On The Lamp at 390 px eight 48 px minimums leave About 54 px and
  every other piece 48: the proportions show on shorter cards (the small gallery case: 190 / 125 / 62) and wider screens.
- Labels: a format section (no icon) always shows its words (`NavLabelRule`).

### 5.2 Bottom (step 7)

| Key | Canvas | Level | Behaviour | Why / evidence |
|---|---|---|---|---|
| `bottom_bar` | B1 | L1 | up to `max_slots`, last = More | thumb reach; Hoober (2013): 49% one-handed, 36% cradled -- reach matters but grips change |
| `dock` | B2 | L1 | icon pill, active item widens to icon + label; hides on scroll down | partially persistent (Laubheimer 2021) |
| `bar_sheet` | B3 | L1 -> L2 | first tap jumps to the family; a SECOND tap on the current family opens its kinds with counts (no long-press: undiscoverable and not single-pointer friendly) | two taps, no top chrome |
| `next_up` | B4 | linear | "Up next: <heading> - 5 of 13" with a Next button | a gentle guided path; NN/g scrolling: 57% of viewing time stays above the fold (Fessenden 2018) -- a cue pulls readers on |

**Built at step 7a** -- `bottom_bar` (`BottomBarNavView`): the model's `BarSections` as icon tabs (`NavTab`, family icon in its colour
above the word, Labels applies) sharing the bar equally, and when `MoreSections` is not empty a last **More** slot (`CardIcons.More`,
`CardStrings` `nav_more` More / Mais). More opens a small list of the overflow rows (icon beside word) ABOVE the bar, inside the bottom
area -- so it slides away with the area and pushes the CTA up instead of covering it; a pick jumps and closes it, More again closes it,
every rebind closes it. `OpenMore()` is the seam: a Menu (step 8) opens there instead. The mark is the section read: its slot, or More
(and its row) for a section of the list. Built from `NavTab` / `NavTint` / `ElementPool` -- no new shared part; the additions are a
`more` icon in the existing set, a `nav_more` row and the definition flag `ReadsBarSlots` (the Editor's Bar Slots row). The list does
NOT close on a scroll or a jump from another element: the overlay owner of step 8 brings close-on-scrim / Back / jump to every menu.

### 5.3 Menu overlay (step 8)

| Key | Canvas | Level | Behaviour | Why / evidence |
|---|---|---|---|---|
| `drawer_tree` | C3 | L1 + L2 | the whole ontology as an outline with counts, from a menu button in the header | least discoverable, most complete (NN/g hamburger study, `nngroup.com/articles/hamburger-menus/`); never a default |
| `grid_overlay` | C4 | L1 -> L2 in place | big family tiles with counts + a Purpose / Format switch | kiosk-like, big thumbs |
| More list | B1 / A* | L1 | the overflow sections; opens as `menu` when one is set, else a small list | -- |

Overlay owner: one at a time, a scrim, closes on Back, scrim tap or after a jump; never stacked over another sheet (NN/g bottom
sheets: no stacking, keep a visible close, support Back -- Laubheimer 2023).

| `fab_dial` | C1 | one button fans out labelled family shortcuts | zero chrome until needed |

| Kind | Canvas | Behaviour |
|---|---|---|

### 5.7 Takeover breadcrumb (step 16, F4)

Today the takeover crumb is "<card title> > <name>" with chips per PAGE of one block. F4 adds the family ("Castle > Media >
360") and a swipe / chips across the SIBLING blocks of the same family that support the full view, without returning to the
card. NN/g subnavigation: sequential levels disorient when Back is ambiguous (Budiu 2017) -> Back returns to the card, never to
the previous sibling.

### 5.8 In-card find (step 18, only if time)

C5 reduced: a text field + facet chips (format, Reading Time <= 2 / 5 min, needs: headphones / camera / network declared on the
kind) over the model's targets; results grouped by section; tap jumps.

## 6. Layouts and the generic teaser

### 6.1 Layout modes (steps 13-15)

| Layout | What changes | Needs | Evidence / caution |
|---|---|---|---|
| `scroll` (default) | today's card | any element | -- |
| `accordion` | every target a compact row that expands in place | step 12 | NN/g mobile accordions: no auto-scroll on expand, keep the open row's header reachable, Back collapses (Budiu 2015) |
| `tabs` | one section visible at a time; the others `display: none` | a top or bottom element (if both are `none`, `text_tabs` is used and the Editor warns) | NN/g: avoid tabs when visitors must compare across them (Sunwall 2024); said in (i) |
| `pages` | one section per horizontal page, vertical scroll inside; the next page peeks; `family_pager` header with chevrons | `SwipePageRule`, `SwipeGrabRule` | changing scroll direction disorients (Paul 2023, scrolljacking): offered, never default; device check |
| `bento` | sections as tiles sized by target count; tap opens the full view | step 12 full view | a visual overview; the full view must not stack sheets |

Layouts only move the SAME bound slots between containers; a kind's view never knows the layout (unchanged from the 2026-09-26
plan). `NavController.JumpTo` asks the layout (scroll -> offset, tabs -> show section, pages -> page index, accordion -> expand +
offset, bento -> open full view).

### 6.2 Generic teaser and full view (step 12)

- **Compact row** (one look for every kind): family icon, heading (else the block's first words -- the same one-line summary the
  Editor's Card Content rows show since `_3.1` 15.1; move its pure part to Runtime if it lives in the Editor), format + minutes.
- **`expandable`** (per instance `display`): the slot shows the compact row; the real view is bound only on expand and unbound
  (media released) on collapse -- lazy, so a 60-row accordion holds no media. Every kind lists `expandable` in `DisplayModes`.
- **Open in full view**: any kind can be drawn into `TakeoverView` by binding a SECOND pooled view of its kind into the page
  (through the takeover's media scope). Owners (audio, video, preview, AR) already serve one block at a time; the step proves
  a block bound twice (card + full view) hands its owner over and back.
