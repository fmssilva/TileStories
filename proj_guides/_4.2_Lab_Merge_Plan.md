# 4.2 · One Lab: the merge plan (version 0)

The plan for merging the two prototypes into one Lab, agreed by two independent analyses and the developer (2026-11-16).

Names used below:
- **W** = the World Editor Lab (`_4.1.2_Prototype/lab_src`, frozen at v20.1, https://claude.ai/artifact/AmWUgE6nA9VLY7YeoUB4ir).
- **B** = the Block Components Lab (until P0: `_3.3.1_Prototype`; after P0: `_4.2_TileStories_Lab`).

## 1 · The decision
- **One Lab.**
  - Today the app is prototyped twice: two phone frames, two walls, two marker systems, two audience models, two Settings, two onboardings.
  - 360, Then & now and 3D are each written twice, with no shared code.
  - About 12 global function names, 80 CSS classes and 17 CSS variables collide, so the two cannot simply be pasted together.
- **Which Lab is final: neither of the old two. It is `_4.2_TileStories_Lab`.**
  - Its code starts as B's, so the card, the guide and their tests never stop working.
  - W's app is ported into it: the wall, the AR view, the screens, On tap and the design system.
  - So the final Lab looks and works like W's app, with B's card and guide inside it, all on W's design system.
  - The two old pages stay frozen at their links as references.
- **B's code base is the home,** moved with `git mv` to `proj_guides/_4.2_TileStories_Lab/` (lab_src + voicebench), with a new artifact.
  - The guide and its ~60 test files keep running in every round; nothing is rewritten from scratch.
  - B's history is kept.
- **The Lab is shaped like the app:**
  - the App screens, the wall and the AR view are the frame;
  - the card opens from On tap (and from Explore without the camera);
  - the guide runs over everything.
- **B gives the code organisation:** modules by area, hooks (`on` / `emit` / `pipe` / `.answer`), the structure check, the test tiers, and the Editor's accordion with ▸ demo and ? help.
- **W gives the look:** tokens, looks, modes, profiles, the UI kit, undo, and the Unity lint.
- **Moving means porting.** A file is rebuilt on the shared layers in full when it is touched:
  - never pasted as it is;
  - never kept working through an alias layer (`00-process` "Academic Reference Quality": no shims, wrappers or adapters);
  - a ratchet that only counts what is not yet ported is fine.
- **The Lab specifies Unity.** Its tokens, folders and data shapes use Unity's names, so nothing is translated twice.

## 2 · The merged Lab: its layers, mapped to Unity
Each layer uses only the layers above it. **Each module names the Unity file or folder it specifies.**

| Layer | In the Lab | In Unity |
|---|---|---|

| Theme | **one token table using Unity's `--ts-*` names** (167 today), per look × mode × text × audience, written by one `applyTokens(root)`. A test checks its values against `Theme.default.uss`. New tokens (e.g. the app glass, `_4.1.7` §6) go on a list, **"additions for the ThemeAsset"**. Looks are differences over Premium | `Framework/Runtime/UI/Theme/` (ThemeAsset → `Theme.default.uss`) |
| Services | Voice, Language (string tables; no `lang==="pt"?`), Motion (reduce motion, durations, easings), Sound and haptics, Accessibility (text size, contrast), Profile | plain C# classes (`20-code-quality`), e.g. the voice resolver |
| Components | one registry: button, icon button, chip, segmented, switch, row and list, panel, sheet, dialog, toast, badge, eyebrow, bubble, nav bar, choice button, picture viewer, media frame, open row… They never name their host | `Runtime/UI/Components/` (rule: `UiRenderTargetGuardTests`) |

| Editor | one kit: B's accordion, ▸ demo and ? help, plus W's typed fields and undo. Editor code is kept out of the domain modules (a ratchet: it moves out as each module is touched). Lab-only switches that look like features are marked **developer-only** | POI Editor; `DevFeatureBuildGuard` |
| Tests | the Node runner with the tiers (feature tests every round, core every 4, full every 12); W's regress, sweep and lint become its files; critics on captures: phone and tablet, portrait and landscape, light and dark, Premium and Playful, text L | -- |

**The authored config `D` has the shape of Unity's data.** Each part names its home:
- the ThemeAsset (tokens);
- the wall's `config.json` (styles, levels, POIs, On tap);
- `CardStrings.asset` (words);
- a new guide-config asset (the voice and the guide's settings).

**Define, assign, place** (`00-process`):
- The wall defines named styles once; a POI may pick another named style.
- A POI places its own content: position, shapes, media, and which action buttons it has.
- Values are never overridden one by one per POI. W's per-POI field overrides of On tap (`30_tap.js:118-126`: distance, tag, action component, focus) become a pick of a named style.
- The bold + blue bar + ↺ marking stays only where Unity has the same idea: a look over Premium, like a Prefab Variant.

**Media: one component per concept, several hosts.**
- 3D, 360, Then & now, before / after and gallery each have one component.
- The card block (inline) and the AR screen's action view (full screen) are UI Toolkit hosts. For 3D, that means a RenderTexture.
- **3D on the wall is not the same UI component.** It is a 3D object anchored to the wall (`10-structure` 1.5).
- What all hosts share is the model asset, the orbit rules and the configuration.
- The Lab renders 3D with three.js, generalised from `mascot/azu3d.js`.

**Every round's method** (`skills/Feature_Prototyping.md` step 3, the one home of these rules):
1. **Port onto the shared parts.** Each ported or new piece uses the base components and the global `--ts-*` tokens wherever one fits. A missing one is added to the shared layer. That way each component and block can be judged in every profile option.
2. **Implement, build:** structure 0, the lint ratchet holding.
3. **Capture the profile matrix and improve the design until it is right:**
   - Premium / Playful × light / dark, plus text L;
   - phone and tablet, portrait and landscape.

   W's `section_shots.py` / `state_shots.py` are ported in P1a for this.
4. **Confirm the Editor:** every good option and config, with its row, default and demo.
5. **Automated tests:** the feature's "all" checks, and its "core" checks tagged.
   - Every round runs the feature's all.
   - Every 4-5 rounds the prototype's core runs.
   - Every 12-15 rounds the prototype's all runs.

   Core and all run on a `git worktree` branch while the next round is built, then merge.

**Roles** (`.clinerules/00-process.md`):
- The Architect verifies, commits, decides and writes each round's brief. It does not write the code.
- A builder builds each round, with the test tiers. This is the method that worked for rounds 1-22.

**MCPs:** none until P5, which uses three.js in the page. Blender is needed only if models must be made or fixed. Unity is needed only when the Lab's decisions are carried into it.

**After the merge (not part of it, not to be forgotten):**

## 4 · The voice: why "device voice" keeps appearing (fixed in P2)
Every line goes through `say()` → `sayFrom()` → `sayOrder()` (`guide/voice.js:6-16`). The causes:

1. **Only one voice set covers the script.** Counted on disk (`voicebench/out`) against the 513-line script:

   | Voice set | Recorded lines |
   |---|---|
   | Ryan / Duarte | 519 |
   | Sonia / Raquel | 58 |
   | ElevenLabs | 58 |
   | Edge | 58–59 |
   | Gemini | 8 |

   With any other set chosen, most lines fall to the live voice, then to the device. This is the main cause.
2. **Recordings match only the exact text.** Edited, composed or per-point lines never match.
3. **The visitor's Settings writes the author's setting.**
   - `S.guideCfg.voice="device"` (`world/guide-button.js:118`).
   - Forget does not undo it (`phone/settings.js:4`).
   - Captions do the same.
4. **Resume, speed changes, the watchdog and Back to the game call the device voice directly.**
   - `person.js` `speakFrom`.
   - `game-ask.js` keeps `G.sayArgs`, which only the device path sets.
5. **The fallback voices ignore the chosen voice.**
   - The device voice reads `voice_en` / `voice_pt`.
   - ElevenLabs reads the keys file.
   - Azure follows the set only if the set is Azure.
   - The published Lab has no keys, so every unrecorded line is the device voice there.
6. **Answers are never recorded,** and the agent's "voice of the answers" (`agentCfg.liveVoice`) is separate from the recorded set.

**The fix: one voice service.**
- One guide-config object `D.guide.voice = { set, live:{provider, ids}, device:{en, pt}, noRec, speed, answers }`, plus the visitor's layer in `P`.
- One resolver `guideVoiceFor(ctx)`, a plain C# class in Unity. It returns:
  - the order of sources;
  - the voice per source, derived from the chosen set;
  - the speed;
  - the one label.
- Resume and seek go through the service.
- The Editor shows each set's coverage ("58 of 513 lines; the rest: …").
- A voice is offered to visitors only when its set covers the script. Rendering the missing lines costs provider credits, so it is the developer's call per voice.

## 5 · Design calls settled by the developer
1. **Expert forces the Deep time** (2026-11-16): Expert content is denser and longer by nature. P1b's profile model ties them.
2. **Voices: Azure for everything (2026-11-16).**
   - **Recorded lines and live answers both use Azure Speech.** The F0 tier of the developer's Azure for Students resource gives 0.5 M neural characters a month free.
   - The full script is 513 lines, about 35,000 characters in EN + PT, so one full Azure set uses about 7 % of a month. P2 renders Sonia / Raquel in full (Ryan / Duarte is already complete).
   - **ElevenLabs stays a provider option** in the Guide tab, for when the Azure credits run out or for another voice. A set is offered to visitors only once it covers the script (check below), and it is rendered on demand on the Creator plan.
   - Gemini stays developer-only (10 TTS requests a day). Edge stays private (not publishable).
3. **An automatic voice-coverage check (P2).**
   - It compares every line the app can say with each voice set: the script, the tour from the card, tips, games, the guide's pages, and Tell me more.
   - **In the Editor (Guide tab › Voice):** each set's coverage ("Sonia / Raquel: 513 of 513"). When a set is below 100 %, an alert lists the missing lines, each with its owner and language, and offers **Render the missing lines** (`voicebench/render.py`, only those lines).
   - **In the tests:** a check fails when a voice offered to visitors is below 100 %.
   - **Composed lines** (names, counts, minutes) cannot be recorded whole. The check lists each one with how it speaks: as recorded parts, or live, never silently as the device voice. Its words are reshaped into recordable parts where that is natural.
4. **Configuring the AI Guide, in two places, one service.**
   - **Editor › Guide tab › Voice and guide:** the author's settings, stored in `D` (the guide-config asset):
     - provider and voice set, with coverage;
     - the live provider (the same by default);
     - speed;
     - a line with no recording;
     - captions, music, and the mascot on or off.
   - **Editor › App tab › Settings:** which guide choices the visitor may change. That covers the voice (only sets at 100 %), speed, captions, music and the mascot.
   - **The visitor's Settings › The guide** shows exactly those choices and writes `P`.
   - B's Settings › The guide becomes this group in P2. It joins W's 5-area Settings in P4.
5. **Live answers where no key may be.**
   - **Local Lab and the Unity Editor:** the key is on this machine (`keys.local.js`; EditorPrefs), so live answers speak with Azure.
   - **The published Lab and phone builds** (the user study) never hold a key. Unity's build check already fails a build whose assets hold one.
     - They need the token service: a small Cloudflare Worker, `__Services_And_Keys.md`, that trades the key for a 10-minute Azure token.
     - Until it exists, a live answer there falls back to the device voice, and the label says so.
     - The Worker is a step before the user study, not part of this merge.
