## 2. Track A — `config.json` is stale relative to its own schema

### 2.1 The finding

Diffed both `Assets/Apps/LivingRoom/config.json` (source) and
`Assets/StreamingAssets/LivingRoom/config.json` (runtime copy) field-by-field
against the actual `WallConfigData.cs` class. Both files are missing:

- **3 top-level fields**: `badge_shape`, `marker_icon_library_resources_path`,
  `badge_categories`.
- **5 per-POI fields** (checked on every POI, not just one): `status_unknown`,
  `hero_icon_key`, `rotate_contour`, `badge_category`, `status_level_key`.

The two copies **are** consistent with each other (no drift *between* them —
both are equally behind), so this isn't corrupted or diverged data, just
stale structure. `SaveConfig()` in `POIAuthoringToolWindow.cs` calls
`JsonUtility.ToJson(_config, prettyPrint: true)`, which always writes every
public field of the class, in declaration order, regardless of value —
`JsonUtility` doesn't omit defaults. The only way for these fields to be
absent from the file is if it was never re-saved through that method since
they were added to the class — almost certainly because an earlier session
edited the JSON text directly (e.g. to add the §19.12 satellite POIs) rather
than going through the tool.

### 2.2 Why the underlying architecture is actually fine

This is worth being precise about, because it changes what the fix is: the
*ontology* of the config file isn't badly designed — its field order and
grouping are dictated entirely by `WallConfigData.cs`'s own field
declaration order, which is already the single source of truth for both the
runtime and the file's shape. There's no separate "make the JSON
well-organized" design task. The problem is purely that the file on disk
hasn't been regenerated from that source of truth recently enough.

### 2.3 The fix — and why it must go through the tool, not a hand-edit

**Do not hand-edit the JSON to add the missing fields.** Doing so would
repeat the exact problem being fixed here: a manually-patched file that
looks right today and silently drifts from the canonical class-driven shape
again the next time a field is added. The fix is to force one real
round-trip through the actual Save path:

1. Open `POI Authoring Tool` (`Shift+P`).
2. `Load Config` (loads `Assets/Apps/LivingRoom/config.json`).
3. `Populate Rig from JSON`.
4. `Save All to JSON` — this regenerates the file via `JsonUtility.ToJson`
   in full class-declaration order, with every field present (new fields
   get their zero-value defaults: `badge_shape=""`,
   `marker_icon_library_resources_path=""`, `badge_categories=[]`, and per
   POI `status_unknown=false`/`hero_icon_key=""`/`rotate_contour=false`/
   `badge_category=""`/`status_level_key=""`).
5. `Copy to StreamingAssets`.
6. **Diff the file before/after.** Confirm only the expected new fields
   appeared and nothing else changed — no POI positions, no existing field
   values. This is a schema round-trip, not a data edit; treat any
   unexpected diff as a bug to chase down before proceeding.
7. Compile + test (per §0's standard). A config schema round-trip shouldn't
   change any runtime behaviour — `WallConfigData`'s consumers already
   handle empty-string/false/empty-list defaults correctly for these fields
   — but confirm rather than assume.

### 2.4 Minor doc-clarity nit, while this file is open anyway

`marker_style`'s own field comment in `WallConfigData.cs` doesn't mention
that it's a legacy fallback — that framing currently only exists in
`MarkerVisualsParser`'s and `WallSession`'s comments, not on the field
itself. A reader looking at just the schema (not the runtime code) wouldn't
know. Text-only change, zero behaviour risk:

```csharp
// LEGACY fallback only -- prefer marker_outline_mode + marker_use_badge
// below for new walls. Still read by
// MarkerVisualsParser.DeriveOutlineAndBadgeFromLegacyStyle when
// marker_outline_mode is absent, kept for walls authored before the split.
// "outline_gold" / "outline_same_hue" / "badge". Missing/unrecognised falls
// back to MarkerVisualsParser.DefaultStyle...
public string marker_style;
```

## 3. Track B — `POIAuthoringToolWindow.cs` -> partial-class folder split

### 3.1 Current state

1,750 lines, one file, ~55 methods plus one nested class
(`EntryDetailsPopup`). Not a correctness problem today, but it's the single
largest file in the project by a wide margin (the next largest,
`MarkerGalleryTests.cs`, is 645 lines) and every new editor feature so far
has landed as more methods in this same file.

### 3.2 Why a partial-class split, not smaller cooperating objects

Two genuinely different refactors were possible here, and it matters which
one gets picked:

- **Option considered and rejected: decompose into several independent
  classes** (e.g. a `SymbolTableController`, a `RigManager`, each owning its
  own state, composed by the window). This is the "more properly
  object-oriented" option, but it requires redesigning how shared mutable
  state (`_config`, `_wallIconLibrary`, `_configHistory`, the whole rig
  scene-reference set) gets passed between the new objects — real design
  work, real risk of subtly changing behaviour, and explicitly **not** what
  was asked for ("keep the actual editor tab UI as is... just clean and
  refactor and reorganize the code").
- **Option chosen: split into a `partial class`, one file per concern,
  same single class at compile time.** C# partial classes let multiple
  files contribute to one class body; every field and method stays exactly
  as visible to every other method as it is today, because it's still
  literally the same class. This makes the refactor a pure file-organization
  move — no constructor changes, no new interfaces, no state redesign — and
  makes "did this change behaviour" a much easier question to answer
  (correctly done, the answer is provably no, since the compiled class is
  identical either way).

Given the explicit ask was reorganization without behaviour change, the
partial-class split is the right amount of refactor — decomposing into
separate objects is a legitimate thing to consider later, but as its own,
separately-scoped, separately-tested piece of work, not bundled into this
pass.

### 3.4 Step-by-step — one extraction at a time, compile + test after each

**Do not batch multiple extractions before testing.** Each step below is
independently compilable and independently testable; that's the entire
point of doing it this way instead of one large cut-and-paste.

1. Create the folder structure above. Move (not copy) `POIAuthoringToolWindow.cs`
   into `Assets/Framework/Editor/POIAuthoring/` unchanged. Compile + test —
   confirms the move alone (new path, same content) didn't break anything,
   before any content is touched.
2. Change `public class POIAuthoringToolWindow` to
   `public partial class POIAuthoringToolWindow`. Compile + test — a
   `partial` keyword with only one contributing file is legal C#, this
   should be a pure no-op.
3. Extract **Constants**: cut `OutlineModeOptions`/`Labels`,
   `LineStyleOptions`/`Labels`, `ShapeOptions`/`Labels`, `GlobalSectionColor`,
   `InnerSectionColor`, `_trashIcon`/`TrashIcon` into
   `POIAuthoringToolWindow.Constants.cs` (same root folder,
   `partial class POIAuthoringToolWindow`). Compile + test.
4. Extract **config-data undo/history**: cut `DrawConfigMutationScope`
   through `HandleUndoShortcuts` into
   `ConfigData/POIAuthoringToolWindow.ConfigHistory.cs`. Compile + test.
5. Extract **config file I/O**: cut `SaveAllToJson`, `SaveConfig`,
   `LoadConfig`, `CopyToStreamingAssets` into
   `ConfigData/POIAuthoringToolWindow.ConfigFileIO.cs`. Compile + test.
6. Extract **asset/path utilities**: cut `DrawPathRow` through
   `TryResolveWallIconLibraryFromConfig` into
   `AssetPaths/POIAuthoringToolWindow.AssetPaths.cs`. Compile + test.
7. Extract **shared symbol-table/glyph helpers**: cut
   `DrawWallIconLibrarySelector` through `ToHexRgb` into
   `Shared/POIAuthoringToolWindow.SymbolTable.cs`. Separately, pull the
   nested `EntryDetailsPopup` class out to its own standalone
   `Shared/EntryDetailsPopup.cs` (not partial — it's already self-contained,
   taking only constructor parameters, no dependency on the window's
   instance state). Compile + test.
8. Extract **global scene options**: cut `DrawGlobalSceneOptions` through
   `RecomputeLevelPercentSpacing` into
   `GlobalScene/POIAuthoringToolWindow.GlobalScene.cs`. Compile + test.
9. Extract **per-POI options**: cut `DrawSpecificMarkerOptions` through
   `DrawStatusLevelDropdown` and `GetPoiFoldout` into
   `SpecificMarker/POIAuthoringToolWindow.SpecificMarker.cs`. Compile + test.
10. Extract **rig lifecycle**: cut `RefreshRigVisuals` through `OnSceneGUI`
    (including `IsRigInSyncWithConfig`, `ClearRig`,
    `TryResolveSceneReferences`, `PopulateRig`, `CapturePositions`,
    `SelectRigObjects`) into
    `RigLifecycle/POIAuthoringToolWindow.RigLifecycle.cs`. Compile + test.
11. What should remain in the root shell file: fields, `ShowWindow`,
    `OnEnable`/`OnDisable`, `OnGUI`, `DrawFramedFoldout`, `DrawToolbar`,
    `DrawTopConfigAndActions`, `DrawSyncAndWarnings` — roughly 200-250 lines,
    not 1,750. Final compile + test, and explicitly **compare test counts**
    (not just "still green") against the §1 baseline — this is the step
    where a silently-dropped method would show up.

### 3.5 What not to do in this pass

- **Don't rename any method or field.** A pure move is provable-by-inspection
  (the method body is byte-for-byte identical, just in a different file); a
  move-plus-rename is not, without much more careful review. Renaming is a
  legitimate future improvement, just not bundled into a pass whose whole
  value is "nothing changed, just where it lives."
- **Don't "improve" any logic while moving it**, even something that looks
  like an obviously-correct small fix spotted along the way. Leave a comment
  noting it and handle it as its own separately-tested change afterward —
  mixing a behaviour change into a reorganization pass defeats the purpose
  of making this step easy to verify.
- **Don't touch `POIAuthoringRigBuildCheck.cs`/`POIAuthoringRigSafetyCheck.cs`**
  — already small, already separate, out of scope here.
- **Don't decompose into separate non-partial classes** — see §3.2's
  reasoning for why that's a different, bigger, separately-scoped refactor.

## 5. Doc-hygiene pattern worth fixing at the process level

Found twice now, independently, in two different files:

- `_2_2_Marker_Design.md`'s top "Implementation Status" block went stale
  relative to section-level checklists further down in the same file — once
  before this session (flagged and fixed 2026-08-02), and again this
  session (flagged and fixed 2026-08-04): the top block said §20/§21 were
  open while a "Next session should" line two paragraphs below, and the
  section-level checklists further down, said they were done. Both were
  true at different times; nobody reconciled them.
- `_5.1_Editor_Tab.md`'s own §13.8 checklist claimed "`_2.2_Marker_Design.md`'s
  implementation status already reflects completion at top of file" — that
  claim was checked directly (not trusted) and found false, for the same
  reason above.

Both are now fixed, but the pattern is worth addressing structurally rather
than just fixing the symptom a third time: a hand-maintained prose summary
at the top of a file, duplicating information that section-level checklists
further down already track accurately, is exactly the kind of artifact that
drifts — there are now two places that can say different things about the
same fact, and nothing forces them to agree.

**Recommendation, not yet acted on — worth a decision, not a unilateral
change:** either (a) drop the top-of-file prose status block entirely in
favour of "scan every section's own checklist" as the single source of
truth, or (b) keep it but regenerate it mechanically each time by literally
scanning the section checklists for unchecked boxes, rather than
hand-writing a separate narrative summary. Option (a) is simpler and
removes the duplication that caused this twice; option (b) preserves the
convenience of a single at-a-glance block for a large file. Either is
reasonable — flagging the choice rather than picking one, since it's a
process-design call, not a code fix.
