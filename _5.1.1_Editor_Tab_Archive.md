# POI Authoring Editor Tab (5.1)

> Historical note (2026-08-06): this file contains earlier planning/build
> snapshots. Current behavior is defined in `_5.1_Editor_Tab.md` and code,
> including key-driven unknown-status rendering (`status_level_key`,
> `badge_category`) and general icon fallback to `unknown`.

This document explains the current POI Authoring editor workflow, data flow, and extension points.

## 1. Purpose

The POI Authoring window is the wall-authoring control center for:

- Loading and editing one wall JSON config.
- Spawning a temporary scene rig (`POIAuthoringRig`) from JSON.
- Editing global marker rules and per-POI options.
- Capturing scene placement back to JSON.
- Copying the validated config to StreamingAssets.

Window path:

- `TileStories/POI Authoring Tool` (shortcut: `Shift+P`)

Primary implementation file:

- `TileStories/Assets/Framework/Editor/POIAuthoringToolWindow.cs`

---

## 2. Source of Truth

There are two config copies by design:

- Authoring source: `Assets/Apps/<Wall>/config.json`
- Runtime copy: `Assets/StreamingAssets/<Wall>/config.json`

Expected workflow:

1. Load and edit source config.
2. Save all edits to source config.
3. Copy source to StreamingAssets.

`Populate Rig from JSON` always reloads the source file first to avoid stale in-memory data.

## 3. Top-Level UI Layout

The tab now has a fixed top action area and a scrollable content area.

### 3.1 Top Action Area (always visible)

Contains:

- Config path
- Streaming path
- Marker prefab path
- Correction anchor reference
- Wall mesh reference

Actions:

- `Load Config`
- `Populate Rig from JSON`
- `Clear Rig`
- `Save All to JSON`
- `Copy to StreamingAssets`
- `Undo` / `Redo` (for config data history)

Visual warnings:

- `Clear Rig` is highlighted when generated rig content exists.
- `Save All to JSON` is highlighted when there are unsaved config edits.

### 3.2 Scrollable Content Area

Two main foldouts:

- `Global Scene Options`
- `Specific Marker Options`

---

## 4. Global Scene Options

Global options are split into three components.

### 4.1 Marker Foldout

Contains:

- Marker shape selection.
- Category symbol taxonomy table.
- Wall icon library selection/creation.

Category symbol rows include:

- Category name.
- Sprite object field (drag-and-drop + picker search).
- Symbol name display.
- Sprite preview.
- Compact color swatch picker (writes hex automatically).
- Hex field (`#RRGGBB`) kept visible for explicit/manual values.

### 4.2 Badge Foldout

Contains:

- `Enable badge` toggle.
- Badge taxonomy table (visible only when enabled).

Badge rows include:

- Badge key.
- Badge label.
- Sprite object field (drag-and-drop + picker search).
- Symbol name display.
- Sprite preview.
- Compact color swatch picker (writes hex automatically).
- Hex field (`#RRGGBB`) kept visible for explicit/manual values.

### 4.3 Outline Foldout

Contains:

- `Enable outline` toggle.
- Outline mode dropdown (`gold` / `same_hue`) when enabled.
- Outline levels list.

Each outline level supports:

- Label
- Percent anchor
- Line style
- Remove level

Add-level is capped to a bounded maximum to prevent unbounded style expansion.

## 6. Undo/Redo Model

There are two undo systems, intentionally separate:

### 6.1 Scene Undo (Unity Undo)

Used for object-level operations:

- Creating rig/container
- Creating marker instances
- Deleting rig children

### 6.2 Config Undo (Editor-local history)

Used for JSON-backed data edits:

- Category/badge/outline list edits
- Per-POI property edits
- Global marker toggles/options

Supports:

- Buttons (`Undo`, `Redo`)
- Keyboard (`Ctrl+Z`, `Ctrl+Y`, `Ctrl+Shift+Z`)

Implementation stores serialized config snapshots and reapplies them to `_config`.

## 7. Symbol Asset Strategy

### 7.1 Why runtime does not read arbitrary PNG paths

Runtime builds should not depend on raw file path crawling under `Assets/...`. Instead, runtime consumes Unity-imported assets referenced by library assets.

### 7.2 Current model

- Symbol lookup is key-based via `SpriteKeyLibrary`.
- Marker prefab has default `iconLibrary` and `shapeLibrary` references.

### 7.3 Wall-local icon library workflow

The authoring tab supports a wall-local icon library asset.

- Create/assign in wall folder under:
	- `Assets/Apps/<Wall>/MarkerAssets/Resources/MarkerSymbols/...`
- Config stores:
	- `marker_icon_library_resources_path`

Runtime (`WallSession`) loads this library through `Resources.Load` and passes it into `MarkerView`. If missing/invalid, prefab default icon library is used.

Result:

- Defaults remain available.
- Walls can add custom symbols without modifying shared framework assets.
- Developers assign sprites by object selection/drag-drop, not by remembering keys.

Color behavior note:

- Category `color_hex` is the base category color signal.
- In `same_hue` outline mode, ring/fill severity shading is derived from that category color (darkening toward black by status), not from the gold ramp.
- Badge category `color_hex` is used directly as badge background color when badge taxonomy is active.

## 8. Save + Propagation Workflow

Recommended sequence:

1. `Load Config`
2. `Populate Rig from JSON`
3. Edit scene/global/per-POI values
4. `Save All to JSON`
	 - Captures current rig positions (if rig exists)
	 - Writes full config JSON
5. `Copy to StreamingAssets`
6. Run Play/runtime validation

---

## 9. Runtime Strictness (important)

Runtime behavior is strict-authored:

- Missing/invalid optional visual config does not silently choose design defaults.
- Optional visuals are suppressed when required authored data is missing.

Examples:

- No valid category definitions -> category symbol styling suppressed.
- No valid shape config -> no shape override applied.
- No outline levels -> status outline visuals suppressed.

Editor may provide seeding helpers, but runtime stays authored-only.

## 12. Extension Guidance

When extending the editor, keep these rules:

1. Keep JSON as explicit source of truth for wall data.
2. Keep runtime asset loading deterministic (library references), not filesystem scans.
3. Keep scene-object undo and config-data undo separate.
4. Add foldouts/components before adding more always-visible controls.
5. Reuse the same symbol-row UI component for both category and badge taxonomies.

This keeps the tab scalable as wall complexity grows.

### 13.1 Visual framing -- distinguishing the two top-level groups

Small helper, no new dependency:

```csharp
private static readonly Color GlobalSectionColor = new Color(0.35f, 0.55f, 0.95f);
private static readonly Color SpecificSectionColor = new Color(0.35f, 0.55f, 0.95f);

private static bool DrawFramedFoldout(bool expanded, string title, Color accentColor, Action drawContent)
{
    var headerStyle = new GUIStyle(EditorStyles.foldoutHeader) { normal = { textColor = accentColor }, onNormal = { textColor = accentColor } };
    expanded = EditorGUILayout.Foldout(expanded, title, true, headerStyle);

    if (expanded)
    {
        var rect = EditorGUILayout.BeginVertical(GUI.skin.box);
        EditorGUI.DrawRect(new Rect(rect.x, rect.y, 2f, rect.height), accentColor);
        using (new EditorGUI.IndentLevelScope())
            drawContent?.Invoke();
        EditorGUILayout.EndVertical();
    }

    return expanded;
}
```

Use it for the two top-level foldouts in `OnGUI` (`Global Scene Options`,
`Specific Marker Options`) and, at a lighter/neutral accent colour (e.g.
`Color.gray` at reduced alpha), for the inner Marker/Badge/Outline foldouts
inside `DrawGlobalSceneOptions` -- same helper, different colour, so the
nesting reads visually (outer = blue, inner = grey box) without writing a
second near-identical method.

### 13.2 Shared symbol table -- category and badge use the same code

This directly fulfils §12 point 5 above, which was already the stated goal
but not actually implemented -- `DrawMarkerGlobalSection` and
`DrawGlobalBadgeSection` currently duplicate near-identical row-drawing code.
One generic method, driven by delegates rather than an interface hierarchy
(simpler for editor-only GUI code, no serialization constraints to satisfy):

```csharp
private void DrawSymbolTable<T>(
    List<T> entries,
    Func<T> createNew,
    Func<T, string> getPrimaryLabel,
    Action<T, string> setPrimaryLabel,
    Func<T, string> getIconKey,
    Action<T, string> setIconKey,
    Func<T, string> getColorHex,
    Action<T, string> setColorHex,
    Func<T, string> getDetails,
    Action<T, string> setDetails,
    Func<T, bool> showColorPicker,
    string addButtonLabel,
    string primaryLabelHeader) where T : class
{
    using (new EditorGUILayout.HorizontalScope())
    {
        EditorGUILayout.LabelField(primaryLabelHeader, EditorStyles.miniBoldLabel, GUILayout.MinWidth(130f));
        EditorGUILayout.LabelField("Preview", EditorStyles.miniBoldLabel, GUILayout.Width(40f));
        EditorGUILayout.LabelField("Symbol", EditorStyles.miniBoldLabel, GUILayout.MinWidth(140f));
        EditorGUILayout.LabelField("Name", EditorStyles.miniBoldLabel, GUILayout.MinWidth(110f));
        EditorGUILayout.LabelField("Color", EditorStyles.miniBoldLabel, GUILayout.Width(120f));
        EditorGUILayout.LabelField("", GUILayout.Width(50f)); // Details + remove
    }

    for (int i = 0; i < entries.Count; i++)
    {
        var entry = entries[i];
        using (new EditorGUILayout.HorizontalScope())
        {
            setPrimaryLabel(entry, EditorGUILayout.TextField(getPrimaryLabel(entry), GUILayout.MinWidth(130f)));

            Sprite current = ResolveSpriteForKey(getIconKey(entry));
            DrawSpritePreview(current);

            Sprite chosen = (Sprite)EditorGUILayout.ObjectField(current, typeof(Sprite), false, GUILayout.MinWidth(140f));
            if (chosen != current)
                setIconKey(entry, AssignSpriteToLibraryAndGetKey(chosen, getPrimaryLabel(entry)));

            string symbolName = chosen != null ? chosen.name : (current != null ? current.name : "(none)");
            EditorGUILayout.LabelField(symbolName, GUILayout.MinWidth(110f));

            if (showColorPicker(entry))
            {
                string colorHex = getColorHex(entry);
                DrawColorHexCompact(ref colorHex);
                setColorHex(entry, colorHex);
            }
            else
            {
                GUILayout.Space(120f);
            }

            if (GUILayout.Button("...", GUILayout.Width(24f)))
                PopupWindow.Show(GUILayoutUtility.GetLastRect(), new EntryDetailsPopup(getPrimaryLabel(entry), () => getDetails(entry), v => setDetails(entry, v)));

            if (GUILayout.Button("-", GUILayout.Width(24f)))
            {
                entries.RemoveAt(i);
                i--;
                continue;
            }
        }
    }

    if (GUILayout.Button(addButtonLabel))
        entries.Add(createNew());
}
```

**Remove the `pct` slider from the row entirely.** It becomes an
internal-only value, auto-spaced whenever the list changes:

```csharp
private static void RecomputeLevelPercentSpacing(List<OutlineLevelEntry> levels)
{
    if (levels == null || levels.Count == 0) return;
    if (levels.Count == 1) { levels[0].pct = 0f; return; }

    for (int i = 0; i < levels.Count; i++)
        levels[i].pct = (100f / (levels.Count - 1)) * i;
}
```

Call it right after the add/remove blocks in `DrawGlobalOutlineSection`
(after `_config.outline_levels.RemoveAt(i)` and after
`_config.outline_levels.Add(...)`).

**Type column as a preview, not just a Popup**, once §20.3 in
`_2_2_Marker_Design.md` (extensible `lineStyleLibrary`) lands: same
`DrawSpritePreview` + `ObjectField` + auto-register-to-library pattern as

asked about, and it sits between full sharing (§13.2, genuinely identical

### 13.5 Details column + floating popup (all three tables)

New `details` string field on all three entry types
(`CategoryStyleEntry`, `BadgeCategoryEntry`, `OutlineLevelEntry` --
add in `_2_2_Marker_Design.md`'s `WallConfigData.cs`, not here, since it's
schema). Deliberately a single free-text field, not several structured
sub-fields -- this is a framework used across arbitrary wall content
(religious/military taxonomies, furniture/art/electronics, whatever a future
wall needs); a fixed sub-schema for "description/typical values/examples"
would fit some walls and not others. One well-labelled text area, developer
writes what's actually useful for that wall.

One shared popup, used by the `"..."` button in `DrawSymbolTable` (§13.2)
and by the outline table's own row renderer (§13.4):

```csharp
private class EntryDetailsPopup : PopupWindowContent
{
    private readonly string _title;
    private readonly Func<string> _get;
    private readonly Action<string> _set;
    private string _buffer;

    public EntryDetailsPopup(string title, Func<string> get, Action<string> set)
    {
        _title = title;
        _get = get;
        _set = set;
        _buffer = get() ?? string.Empty;
    }

    public override Vector2 GetWindowSize() => new Vector2(320f, 160f);

    public override void OnGUI(Rect rect)
    {
        EditorGUILayout.LabelField(_title, EditorStyles.boldLabel);
        EditorGUILayout.LabelField("What this represents, when to use it, example POIs.", EditorStyles.wordWrappedMiniLabel);
        EditorGUI.BeginChangeCheck();
        _buffer = EditorGUILayout.TextArea(_buffer, GUILayout.ExpandHeight(true));
        if (EditorGUI.EndChangeCheck())
            _set(_buffer);
    }
}
```

## 14. Sprite Asset Pipeline — where things live, how they flow, how to extend them (2026-08-05)

Answers every question from this session, grounded by reading the actual
project files directly (not assumed), plus real research for the parts that
are general Unity behaviour rather than project-specific. Citations for the
thesis are in §14.10.

### 14.0 Short answers first

- **Are the default PNGs okay in the Runtime folder? Yes — they're required
  to be there (or anywhere that isn't a folder literally named `Editor/`).**
  See §14.1 for why.
- **Where does the big grid of "many sprites" in the `+` picker come from?**
  Nowhere we built. It's Unity's own built-in Sprite object picker, and it
  always shows *every* `Sprite`-typed asset in the whole project, regardless
  of folder — including sprites bundled inside TextMeshPro's own
  `EmojiOne.asset`. See §14.2.
- **What does Save write to `config.json`?** Only string *keys* (e.g.
  `"icon_key": "temple"`) — never a file path. The actual PNG-to-Sprite
  mapping lives entirely in the `SpriteKeyLibrary` `.asset` files, resolved
  at runtime. See §14.3-§14.4.
- **Does Save copy PNGs anywhere, into one unified folder?** No, and it
  doesn't need to — Unity's own GUID-based asset reference system is what
  keeps this correct, not physical file location. See §14.4.
- **Must sprites be PNG?** No — Unity's texture importer accepts several
  raster formats, and Unity 6.3+ has a *built-in* SVG-to-sprite import path
  too. PNG remains the right default recommendation. See §14.5.
- **Can a developer import an existing third-party icon pack?** Yes, this is
  completely ordinary Unity usage — no special support needed on our side,
  though one small addition (an `AssetPostprocessor`) removes a manual step.
  See §14.6.

### 14.1 Where the default PNGs live, and why that's correct

`Assets/Framework/Runtime/UI/Markers/{Icons,Rings,Shapes}/*.png` — confirmed
directly, these are genuinely under a path containing `Runtime`, not
`Editor`. This is not just acceptable, it's **required**: Unity treats any
folder literally named `Editor` (anywhere in `Assets/`, at any depth)
as editor-only — scripts inside compile only for the Editor, and *any*
asset inside is stripped from player builds entirely.<br>
[Unity Manual — Special folder names](https://docs.unity3d.com/6000.3/Documentation/Manual/SpecialFolders.html):
*"All scripts that are placed in a folder called Editor... will be treated
as editor scripts... not available to the finished game at runtime."*

If these PNGs were ever moved into an `Editor/` folder, every marker would
render with no icon at all on a real device build, while still looking
completely fine inside the Editor (since Editor-only assets *are* available
while working inside the Editor itself) — a bug that would only surface on
device, precisely the kind of Editor/Play-Mode-vs-build divergence this
project's guidelines already warn about generally. **Leave the framework
default PNGs exactly where they are.**

They're referenced by the prefab as **direct serialized references**
(confirmed in `POI_Marker.prefab`: `shapeLibrary: {fileID: ..., guid:
d9cb1f...}`), the ordinary way any Unity asset is wired into a prefab —
Unity's build pipeline includes any asset reachable from something that
ships, regardless of which folder it physically sits in. No special
mechanism is needed for these; "Runtime" here is a naming convention
signalling intent to a human reader, not something Unity itself checks.

### 14.2 Where the wall-local `living_room_IconLibrary.asset` lives, and why it's different

Confirmed at `Assets/Apps/LivingRoom/MarkerAssets/Resources/MarkerSymbols/
living_room_IconLibrary.asset` — inside a folder literally named
`Resources`. That's a second special Unity folder name, with the opposite
effect of `Editor/`: anything under any `Resources/` folder is *always*
bundled into the build **and** becomes loadable at runtime by string path,
via `Resources.Load(...)`, without needing a serialized reference baked in
ahead of time.<br>
[Unity Manual — Introduction to the Resources system](https://docs.unity3d.com/6000.3/Documentation/Manual/LoadingResourcesatRuntime.html)

This is used for exactly one reason, and it's the right reason: `WallSession`
needs to pick a *different* icon library per wall, chosen dynamically by a
string the config file supplies (`marker_icon_library_resources_path`) — a
direct serialized reference can't do that (it's fixed at edit time), so
`Resources.Load` is the one piece of this system that genuinely needs it.
Confirmed in code: `MarkerView`'s `activeIconLibrary` resolution is exactly
this fallback — `_runtimeIconLibraryOverride != null ? _runtimeIconLibraryOverride
: iconLibrary` — direct reference by default, `Resources`-loaded override
when a wall supplies one.

**Worth knowing for later, not urgent now:** Unity's own docs are explicit
that `Resources/` doesn't scale well — *"For full production of new
projects, you should usually use the Addressables package for asset
organization"* ([Unity Manual — The Resources folder](https://docs.unity3d.com/2022.3/Documentation/Manual/UnderstandingPerformanceResourcesFolder.html)),
because every object referenced from *any* Resources folder gets baked into
one combined index at build time regardless of whether it's ever loaded,
which costs build time and memory proportional to the *total* Resources
content, not just what's actually used<br>
([Unity Manual — Introduction to the Resources system](https://docs.unity3d.com/6000.3/Documentation/Manual/LoadingResourcesatRuntime.html)).
With one small library asset per wall, this project is nowhere near that
threshold — it's a legitimate use of `Resources`, not a mistake. If this
project ever grows to many walls each with sizeable custom icon sets,
migrating this one dynamic-load point to Addressables (which supports the
same "load by string key at runtime" need without the all-or-nothing
Resources bundling) would be the documented, official upgrade path. Not a
task for now — flagged so it isn't rediscovered as a surprise later.

### 14.3 Where the "big grid of sprites" in the `+` picker comes from

Fully resolved, not speculation: `EditorGUILayout.ObjectField(..., typeof(Sprite),
false, ...)` — the exact control every symbol row's `+`/sprite field uses —
is Unity's own generic object picker. It has no concept of "this project's
symbols" versus "everything else"; it lists **every asset of the requested
type anywhere under `Assets/`**, full stop. That includes:

- Our own 15 framework PNGs, imported as Sprite.
- **Every individual sprite sliced out of `Assets/TextMesh Pro/Resources/
  Sprite Assets/EmojiOne.asset`** — TextMeshPro ships a bundled emoji/inline-icon
  sprite sheet for its own inline-icon feature, and each of its sub-sprites
  is, to Unity's asset database, just another `Sprite`-typed asset like any
  other. This is exactly the source of the lock/checkmark/clock/coconut/barrel
  icons seen in the picker screenshot from an earlier session — nothing to
  do with any sprite library the project imported, purely TextMeshPro's own
  bundled content surfacing because the picker doesn't distinguish origin.
- Anything else `Sprite`-typed anyone ever adds anywhere in the project.

There's no way to scope Unity's *default* `ObjectField` picker to a folder
or a curated set — that's a real, structural limitation of the built-in
control, not a misconfiguration on our side. §14.7 covers what to actually
do about it.

### 14.4 The full data flow, end to end

1. **Developer adds a PNG** anywhere under `Assets/` (ideally the wall's own
   folder — see §14.8 for the recommended convention), imported by Unity as
   Texture Type "Sprite (2D and UI)".
2. **Developer drags it into (or picks it via) a table row's Sprite field**
   in the editor tab.
3. `AssignSpriteToLibraryAndGetKey` calls `SpriteKeyLibrary.EnsureKeyForSprite`,
   which stores a `{key, Sprite reference}` pair **inside the wall's
   `SpriteKeyLibrary` `.asset` file** — confirmed directly in
   `SpriteKeyLibrary.cs`: `entries.Add(new Entry { key = candidate, sprite =
   sprite })`. The Sprite is referenced the ordinary Unity way (an internal
   GUID pointer stored in the `.asset` file's own serialized data) — **not**
   as a path string.
4. **The category/badge/outline row stores only that key** (e.g.
   `icon_key = "temple"`) in `_config`, an in-memory `WallConfigData`.
5. `Save All to JSON` writes `_config` to `config.json` via
   `JsonUtility.ToJson` — **the PNG file itself is never touched, moved, or
   copied by this step.** Only the JSON text file changes. The key is what
   gets written; the library `.asset` (already saved separately via
   `EditorUtility.SetDirty` + `AssetDatabase.SaveAssets` in step 3) is what
   actually holds the key-to-Sprite mapping.
6. **At runtime**, `WallSession` reads `marker_icon_library_resources_path`
   from `config.json`, `Resources.Load`s that specific library asset, and
   passes it into every spawned `MarkerView` as `_runtimeIconLibraryOverride`.
   Each marker's `ApplyVisuals` resolves its `icon_key` string against that
   library (falling back to the framework default `IconLibrary.asset` via a
   direct reference if the wall didn't supply an override, or if the key
   isn't found there) — confirmed in code, `activeIconLibrary?.Get(iconKey)`.

**So: nothing ever gets physically relocated by this whole pipeline.**
The PNG can live anywhere in the project; what makes it "the wall's icon
for `temple`" is purely the *registration* (an entry in that wall's library
asset), not its folder. This is by design and it's the right design — Unity's
GUID-based reference system is exactly what makes an asset's physical
location not matter for correctness (move a PNG in the Editor and every
reference to it, including the library's, updates automatically; a raw
filesystem path string would silently break on the same move). The one
place a real path-like string exists at all is
`marker_icon_library_resources_path`, and that's a `Resources`-relative
*load* path for the library asset itself, not a path to any individual PNG.

### 14.5 PNG, or something else?

**PNG remains the right default recommendation**, but it isn't the only
option Unity's texture importer accepts — also supported natively: JPG, TGA,
PSD, TIFF, GIF, BMP, and a few others. PNG is specifically preferable here
because it's lossless and supports an alpha channel natively — every marker
icon needs a transparent background to read as a floating glyph rather than
a filled square (the exact class of bug this project already hit once with
opaque icon PNGs, back in §17). **JPG cannot represent transparency at all**
and should be actively avoided for anything in this pipeline, worth stating
explicitly in the help text rather than leaving it to be rediscovered.

**A genuinely worth-knowing option: SVG.** Unity 6.3+ (this project's
version) ships a **built-in** Vector Graphics module capable of importing
SVG as `Texture2D` or for UI Toolkit natively, with the separate
`com.unity.vectorgraphics` package needed only for the two import types this
project would actually want — Sprite (for `SpriteRenderer`-style use) and
uGUI/`SVGImage` (for `Image`-style use, which is what `MarkerCircleGlyphView`
uses today).<br>
[Unity Manual — About Vector Graphics](https://docs.unity3d.com/Packages/com.unity.vectorgraphics@3.0/manual/index.html):
*"Unity 6.3 includes a built-in Vector Graphics module... Install this
package only if you require... Sprite Import... uGUI Import."*

Why this is worth more than a footnote here specifically: marker icons in
this project get scaled up and down continuously by the Pulse/Sun/Accent/Beacon
effects (§19) — a raster PNG icon will visibly soften or pixelate at the
larger end of a Beacon's grow range, where a vector-sourced sprite wouldn't.
This isn't a change to make now — it would mean re-authoring every existing
icon as SVG, a real content cost, not a code change — but it's a legitimate,
Unity-native, already-installed-in-6.3+ option if icon crispness under
heavy scaling becomes a real complaint later, not something requiring a
third-party asset or a redesign of the `SpriteKeyLibrary` pipeline (an SVG
importer just produces a `Sprite`, same as a PNG import does — everything
from §14.4 onward works completely unchanged either way).

### 14.6 Importing an existing third-party icon set

This is completely ordinary Unity usage, and nothing about this project's
pipeline needs to special-case it — the moment a sprite exists as a
`Sprite`-typed asset anywhere in the project, it's already eligible to be
registered via the `+` picker or drag-drop, regardless of where it came
from. Two normal ways a developer would bring one in:

- **A folder of loose image files** (the common case for "I already have a
  big PNG icon set from another project") — drag the folder straight into
  the Project window under the wall's own folder. Unity imports each file
  as a Texture; if Texture Type doesn't default to "Sprite (2D and UI)"
  automatically (it usually does for image files with alpha, but not
  always, depending on the source format/naming), the developer sets it
  manually per file, or — better — §14.9 adds an `AssetPostprocessor` that
  does this automatically for anything imported under a `MarkerAssets/`
  folder, removing the manual step entirely going forward.
- **An Asset Store icon pack**, which typically ships as a `.unitypackage`
  — `Assets → Import Package → Custom Package`, which unpacks at whatever
  path the package author chose (often its own top-level folder, not
  inside any wall's folder). **Recommendation: move the imported sprites
  into the wall's own folder afterward** (a normal in-Editor move, GUIDs
  and references update automatically) rather than leaving a third-party
  package's folder structure scattered through the project — not required
  for correctness, but keeps "where do this wall's symbols live" answerable
  by looking in one place, consistent with the wall-folder convention in
  §14.8.

Nothing about licensing/attribution is a code concern, but worth a line in
the tool's help text since it's a real practical question a developer will
have: whatever the source pack's license terms are, they apply the same way
they would in any other Unity project — this pipeline doesn't change that.

### 14.7 A curated picker instead of Unity's whole-project one

This is a real, addressable gap, not just something to explain away: there
are two different jobs currently forced through the same noisy control.

1. **"Assign a brand-new PNG that isn't registered in any library yet."**
   This genuinely needs to reach into the Project window somehow — the
   current `ObjectField`/drag-and-drop approach is reasonable for this one
   case (most developers would drag from the Project window rather than
   open a picker and search anyway).
2. **"Pick which *already-registered* symbol to reuse for another
   category/badge/POI."** This does *not* need Unity's whole-project picker
   at all — it only ever needs to choose among symbols already sitting in
   the active `SpriteKeyLibrary` plus the framework defaults, typically a
   handful to a few dozen entries. Forcing this through the same
   thousands-of-project-sprites picker is unnecessary noise for the more
   common of the two actions.

Two legitimate ways to fix (2), found via research, both real Unity
mechanisms rather than something to build from scratch:

- **Scope Unity's own Advanced Object Picker** via a `[SearchContext]`
  attribute and a custom `SearchProvider`, querying something like `t:Sprite`
  restricted to the wall's library folder, with `SearchViewFlags.GridView`
  for a visual grid rather than a text list.<br>
  [Unity Manual — Use the Advanced Object Picker](https://docs.unity3d.com/6000.0/Documentation/Manual/search-advanced-object-picker.html)
  — lighter-weight (less code), but depends on the "Advanced Object Picker"
  being enabled in that developer's own Editor preferences
  (`Preferences → Search → Search Engines`), which isn't guaranteed
  consistent machine-to-machine on a team.
- **A small self-built curated popup**, using `PopupWindowContent` +
  `PopupWindow.Show` — the exact same mechanism `EntryDetailsPopup` (§13.5)
  already uses, just showing a scrollable grid of preview thumbnails sourced
  from `_wallIconLibrary.Entries` plus the framework default library's
  entries, instead of a text area.<br>
  [Unity Scripting API — PopupWindow](https://docs.huihoo.com/unity/5.5/Documentation/ScriptReference/PopupWindow.html)

**Recommendation: the self-built popup.** It behaves identically regardless
of any individual developer's Editor preferences (consistent with this
project's general preference for behaviour that doesn't depend on
per-machine settings), and reuses a pattern (`PopupWindowContent`) already
established and working in this same file for §13.5 — no new mechanism to
learn, just a second use of one already in the codebase.

Sketch, added alongside `EntryDetailsPopup` in `Shared/`:

```csharp
private class ExistingSymbolPickerPopup : PopupWindowContent
{
    private readonly SpriteKeyLibrary _wallLibrary;
    private readonly SpriteKeyLibrary _defaultLibrary;
    private readonly Action<string> _onPicked;

    public ExistingSymbolPickerPopup(SpriteKeyLibrary wallLibrary, SpriteKeyLibrary defaultLibrary, Action<string> onPicked)
    {
        _wallLibrary = wallLibrary;
        _defaultLibrary = defaultLibrary;
        _onPicked = onPicked;
    }

    public override Vector2 GetWindowSize() => new Vector2(280f, 320f);

    public override void OnGUI(Rect rect)
    {
        EditorGUILayout.LabelField("Existing symbols", EditorStyles.boldLabel);
        DrawGrid(_wallLibrary, "This wall");
        DrawGrid(_defaultLibrary, "Framework defaults");
    }

    private void DrawGrid(SpriteKeyLibrary library, string groupLabel)
    {
        if (library == null || library.Entries.Count == 0) return;
        EditorGUILayout.LabelField(groupLabel, EditorStyles.miniBoldLabel);

        int columns = 5;
        for (int i = 0; i < library.Entries.Count; i += columns)
        {
            using (new EditorGUILayout.HorizontalScope())
            {
                for (int c = 0; c < columns && i + c < library.Entries.Count; c++)
                {
                    var entry = library.Entries[i + c];
                    if (GUILayout.Button(new GUIContent(AssetPreview.GetAssetPreview(entry.sprite), entry.key), GUILayout.Width(48f), GUILayout.Height(48f)))
                    {
                        _onPicked(entry.key);
                        editorWindow.Close();
                    }
                }
            }
        }
    }
}
```

Wire a small "Choose existing" button next to each row's `ObjectField` in
`DrawSymbolTable<T>` (§13.2) opening this popup; picking a tile calls
`setIconKey(entry, key)` directly, skipping `AssignSpriteToLibraryAndGetKey`
entirely since the symbol is already registered.

### 14.8 Recommended folder convention going forward

Not a code change, a documented policy — worth writing down since nothing
currently states it explicitly and every wall added from here on benefits
from a consistent answer:

- **Framework defaults** (ship with every wall, rarely change):
  `Assets/Framework/Runtime/UI/Markers/{Icons,Rings,Shapes}/` — unchanged,
  already correct.
- **Per-wall custom symbols**: `Assets/Apps/<Wall>/MarkerAssets/Symbols/`
  (new PNGs a developer adds for that specific wall) and
  `Assets/Apps/<Wall>/MarkerAssets/Resources/MarkerSymbols/` (the
  `SpriteKeyLibrary` `.asset` itself, which must stay under a `Resources/`
  folder per §14.2 — the PNGs it references don't need to be, only the
  library asset does).
- **Freshly-imported third-party packs**, before triage: a
  `Assets/Apps/<Wall>/MarkerAssets/RawImports/` staging subfolder, moved
  into `Symbols/` (or discarded) once reviewed — keeps "stuff I haven't
  sorted yet" visibly separate from "stuff actually in use," without
  needing any code to enforce the distinction.

### 14.9 `AssetPostprocessor` — auto-configure import settings

Removes the "do I need to manually set Texture Type to Sprite" step for
anything dropped under a wall's `MarkerAssets/` folder — a genuine, standard
Unity pattern for exactly this
([Unity Scripting API — AssetPostprocessor.OnPreprocessTexture](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/AssetPostprocessor.OnPreprocessTexture.html)),
must live in an `Editor/` folder (postprocessor scripts are editor-only by
definition — this is the one place in this whole section where `Editor/`
really is the correct folder, unlike the PNGs themselves):

```csharp
// Assets/Framework/Editor/POIAuthoring/MarkerSymbolTexturePostprocessor.cs
using UnityEditor;

namespace TileStories
{
    // Any texture imported under a MarkerAssets/ folder is assumed to be a
    // marker/badge/outline symbol -- force the correct import settings
    // automatically rather than relying on a developer remembering to set
    // Texture Type to "Sprite (2D and UI)" by hand every time.
    public class MarkerSymbolTexturePostprocessor : AssetPostprocessor
    {
        private void OnPreprocessTexture()
        {
            if (!assetPath.Contains("/MarkerAssets/"))
                return;

            var importer = (TextureImporter)assetImporter;
            importer.textureType = TextureImporterType.Sprite;
            importer.spriteImportMode = SpriteImportMode.Single;
            importer.alphaIsTransparency = true;
            importer.mipmapEnabled = false;
        }
    }
}
```
