# TileStories - Stage 2.1: Marker Camera-Facing Orientation (v2 - verified against source)

Status: not started. Read `_0_guidelines.md` and `_0_work_plan.md` in full first -
this document assumes both and does not repeat their general rules.

**v2 note:** this replaces the v1 draft. v1 assumed a prefab structure it hadn't
actually inspected and proposed adding a new intermediate "visual container"
GameObject. After reading the real `POI_Marker.prefab`, `MarkerView.cs`,
`POIAnchor.cs`, `MarkerOverlapResolver.cs`, and `WallSession.cs`, that extra
object turned out to be unnecessary - see §2 for why. This version also folds
in a real, confirmed sizing/layout cleanup that v1 didn't cover, because
building orientation on top of the current hardcoded-scale-chain would have
meant re-touching this same prefab again almost immediately after.

## 0) Scope

**In scope:**
1. Make the whole marker (symbol + label, as one rigid visual unit) always
   face the camera.
2. Replace the current 3D sphere with a flat circular symbol, so orientation
   is actually visible during testing (a sphere looks identical rotated or
   not - it cannot verify anything).
3. Fix the marker's internal sizing so it uses one clean scale lever instead
   of three uncoordinated hardcoded multipliers (see §2.2 for what's wrong
   today and why this is genuinely part of the same task, not scope creep).

  spawn logic, `POIAnchor.cs`'s data-holding role - read them (already done
  for you in §2, but re-confirm against the real files in your own workspace
  before editing anything) but do not change their behaviour.
- Any Layout Group / Content Size Fitter setup - deliberately not used here,

## 1) Verified current implementation (read this before touching anything)

Confirmed directly from `Assets/Framework/Runtime/UI/Markers/POI_Marker.prefab`,
`MarkerView.cs`, `POIAnchor.cs`, `MarkerOverlapResolver.cs`, and
`WallSession.cs` - do not re-derive this from scratch, but do re-confirm it
still matches your working copy before relying on it, in case it has drifted:

- **`POI_Marker` (prefab root)** has: `RectTransform`, `Canvas` (World Space),
  `CanvasScaler`, `GraphicRaycaster`, `POIAnchor` (data holder only - stores
  the `POIData` reference, nothing else), and `MarkerView` (label text +
  `ApplyOverlapOffset`). **`POIAnchor` and `MarkerView` live on the same
  GameObject as the Canvas itself** - there is no separate per-marker anchor
  object today.
- **`WallSession.SpawnPOIs()`** instantiates `POI_Marker` as a child of a
  single shared `correctionAnchor` (`PlacementCorrectionAnchor`, one per
  wall), then sets `go.transform.localPosition = localPos` and
  `go.transform.localRotation = Quaternion.identity` once, at spawn.
  `correctionAnchor` itself never rotates - it is the one genuinely
  non-rotating reference frame in this hierarchy, and it already exists;
  nothing new is needed at that level.
- **`MarkerView.ApplyOverlapOffset(int)`** reads/writes `_anchor.transform.localPosition`
  (i.e. the `POI_Marker` root's own `localPosition`, since `_anchor` and
  `MarkerView` are the same GameObject) - **position only, never rotation**,
  and it is called exactly once per marker, right after spawn, not
  continuously.
- **Root RectTransform**: `sizeDelta (0.3, 0.15)`, `localScale (0.15, 0.15, 0.15)`.
- **"Sphere" child**: `MeshFilter`/`MeshRenderer` (a real 3D mesh, not a UI
  `Image`), `RectTransform` with `anchoredPosition (0,0)`, `sizeDelta (200,200)`,
  `localScale (3,3,3)`.
- **"Label" child**: `TextMeshProUGUI`, `RectTransform` with
  `anchoredPosition (0,0)`, `sizeDelta (200,50)`, `localScale (0.1,0.1,0.1)`,
  font size 24.
- **Both children currently sit at the identical `anchoredPosition (0,0)`** -
  despite every planning document describing "label below the marker," that
  is not what is actually built today. Confirm this yourself before assuming
  it's already handled.

## 2) Design decisions, with the reasoning

### 2.1 No new "container" GameObject is needed - rotate the existing root

v1 of this plan assumed the label needed a separate non-rotating parent to
avoid "swinging" around the symbol as the camera moves. That assumption was
wrong, for two independent reasons now confirmed against the real code:

1. **Position and rotation are independent Transform properties.** Setting
   `transform.rotation` never changes `transform.localPosition`. Since
   `MarkerOverlapResolver` only ever touches `localPosition` and this new
   work only ever touches `rotation`, they cannot conflict, on the same
   object or not.
2. **A full/screen-aligned billboard (§2.3) is supposed to rotate the whole
   assembly as one rigid block.** If the label sits at a fixed local offset
   below the symbol and the *whole* `POI_Marker` root rotates to match the
   camera's orientation, the label's local "down" direction rotates into the
   camera's actual screen-down direction too - meaning it correctly stays
   directly below the symbol on screen, from any viewing angle. That is the
   desired behaviour, not a bug to design around.

**Decision: attach the new billboard component directly to the existing
`POI_Marker` root**, the same object `WallSession` already sets
`localPosition` on. No prefab restructuring into new empty parent objects.

### 2.2 Fix the sizing chain while this prefab is already open

Today's sizing is three independently hand-tuned numbers multiplying through
the hierarchy (root scale 0.15, Symbol scale 3, Label scale 0.1) with no
proportional relationship between them - if you scale the root to make hero
markers bigger later, the Symbol and Label won't scale together predictably,
because their own baked-in scale multipliers were tuned to compensate for the
*current* root scale specifically, not for scaling in general.

**Decision: set every child's `localScale` to `(1,1,1)`, express every
child's `sizeDelta`/`anchoredPosition` as a literal, fixed value in the same
unit system as the root, and leave exactly one scale lever - the root's own
`localScale`.** Because uGUI RectTransforms multiply size by every ancestor's
scale down the hierarchy, this makes the root's scale the single, predictable
way to resize the *entire* marker (symbol, label, and the gap between them,
proportionally, together) - which is also exactly the mechanism a future
hero/secondary-importance size variant will want, with zero extra code.

This is not scope creep grafted onto the orientation task - it is a
prerequisite for the orientation task to be built on a sane structure, and
it would need doing almost immediately after orientation regardless.
**Do not add a Layout Group or Content Size Fitter to achieve this** - the
marker's content is fixed and already bounded (label truncated at a known
character count), so there is nothing dynamic here that needs auto-layout
machinery, and that machinery has known order-of-operation fragility for
exactly this kind of case. Fixed, explicit positioning is simpler and more
robust for content that never changes shape.

Do not try to algebraically preserve the *exact* current on-screen size
through the old scale numbers - the relationship between font size, child
scale, and root scale is not simple enough to reverse-engineer reliably on
paper. Instead: pick reasonable starting values (§4), then tune them visually
in the Editor/device pass in §6, the same "confirm visually, adjust from
real testing" approach already used elsewhere in this project (e.g. the
overlap-offset step size was raised from 5cm to 15cm after on-device testing
showed the original value insufficient - the same discipline applies here).

### 2.3 Full screen-aligned billboard (unchanged from v1)

`transform.rotation = camera.transform.rotation` (with a possible constant
180-degree yaw correction, verified empirically, not assumed - see §5). This
keeps the marker's plane always exactly parallel to the camera's near plane,
so it renders as a flat, upright, undistorted circle+label on screen at any
viewing angle, including steep up/down angles at a tall wall. Considered and
rejected: a Y-axis-only ("cylindrical") billboard, which would look correct
only when the camera is roughly level and would foreshorten/skew when
looking steeply up or down at a marker - the wrong trade-off for a project
whose walls are up to 6m tall.

### 2.4 Decentralized - one component per marker

Each marker's root gets its own small `MarkerBillboard` component with its
own `LateUpdate`, rather than a central controller iterating every marker.
At this project's scale (tens to ~150 markers on the largest wall), this is
not a proven performance problem, and the guidelines are explicit about not
building shared/centralized machinery speculatively. Revisit only if a real
profiling pass on a large-POI-count wall shows a need.

## 4) Prefab changes, concretely

Open `POI_Marker.prefab` in the Prefab editor and make these changes:

1. **Rename "Sphere" to "Symbol."** Remove its `MeshFilter` and
   `MeshRenderer` components. Add a uGUI `Image` component instead. Assign
   any simple, solid-fill circular sprite - Unity's built-in UI sprites
   include a circular "Knob" sprite (used by default for Slider/Toggle
   handles) which is sufficient as a placeholder; a custom circle sprite
   works equally well if one is already available in the project. This is a
   placeholder shape only - do not spend time on final art here, that is a
   later, separate stage.
2. **Symbol RectTransform:** `anchorMin`/`anchorMax` = `(0.5, 0.5)`,
   `pivot = (0.5, 0.5)`, `anchoredPosition = (0, 0)` - exact center of the
   root, unchanged from today. `localScale = (1, 1, 1)` (was `3,3,3`).
   Starting `sizeDelta`: try `(0.12, 0.12)` (in the same units the root's
   `sizeDelta` already uses) - this is a starting point to visually tune in
   §6, not a mandated final value.
3. **Label RectTransform:** `anchorMin`/`anchorMax` = `(0.5, 0.5)`,
   `pivot = (0.5, 1)` (top-pivot, so the text grows downward from a fixed
   point rather than growing from its own center into the symbol).
   `localScale = (1, 1, 1)` (was `0.1,0.1,0.1`). `anchoredPosition`: set the
   Y value to a small negative number that places it visibly below the
   Symbol - try `(0, -0.07)` as a starting point (roughly: half the Symbol's
   height plus a small gap, in the same units). Adjust the TextMeshPro
   `Font Size` field on the same object as needed once `localScale` is 1, so
   the text reads at a sensible size on screen - do not assume the old font
   size (24) is still correct once the compensating child scale is removed;
   verify visually.
4. **Leave the root's own `sizeDelta`, `localScale`, `Canvas`, and
   `CanvasScaler` settings exactly as they are.** Only the two children
   change. If, after visual testing in §6, the whole marker reads as too
   small or too large, adjust the root's `localScale` uniformly - that is
   the one lever this redesign is specifically for - rather than going back
   to tuning each child independently.

## 5) `MarkerBillboard.cs` implementation

```
- Awake(): cache Camera.main once into a private field. If null, log a
  one-line warning ("[Marker] MarkerBillboard found no Main Camera -
  disabling") and set enabled = false.
- LateUpdate(): if the cached camera reference is null, return. Otherwise:
    transform.rotation = _camera.transform.rotation;
  (Add a constant Quaternion.Euler(0, 180, 0) multiplied in, only if the
  front-face check in §6 step 2 shows the marker is backwards - do not add
  this speculatively.)
```

No other logic belongs in this component - no distance checks, no
interaction with `MarkerOverlapResolver` or `POIPositionResolver`. It reads
the camera and writes its own rotation, nothing else. This is a MonoBehaviour
with no meaningful pure-logic to extract - the entire behaviour is one line
of Transform math, which is why no accompanying plain C# class is needed here
(guidelines §3's "thin MonoBehaviour" rule is about pulling out *decisions*;
there is no decision being made here).

Attach the finished component to the `POI_Marker` root itself (the same
object holding `POIAnchor`, `MarkerView`, and the `Canvas`) - not to Symbol,
not to Label. See §2.1 for why.

## 6) Wiring and verification steps, in order

1. Enter Play mode using the existing mock localization + WASD flythrough
   setup (already built - do not build new test harness for this). Confirm
   the app boots and all markers still appear, at roughly the sizes tuned
   in §4.
2. **Front-face check.** Walk directly in front of a single marker. If the
   symbol and label are both legible and correctly oriented (label not
   mirrored), the rotation in §5 is correct as-is. If the label reads
   backwards, or the marker is only visible/correct from behind, add the
   180-degree yaw offset from §5, save, and re-test.
3. **Orbit check.** Walk/strafe in a wide circle around one marker. Symbol
   and label must both stay facing you, moving together as one rigid block,
   with the label remaining directly below the symbol from your point of
   view at every angle - no drifting apart, no independent movement between
   the two.
4. **Vertical check.** Get close to a marker and look steeply up at it, then
   steeply down (reposition a test marker higher/lower than the camera if
   the WASD controller has no pitch control). The whole marker must stay
   flat-on-screen and legible - not skew or foreshorten.
5. **Overlap-offset regression check.** Re-test the existing clustered test
   POIs (`painting_1`..`painting_4` in LivingRoom's `config.json`). Confirm
   they still separate via `MarkerOverlapResolver`'s vertical offset exactly
   as before, and that their resting positions are unchanged - only their
   facing should differ from the pre-billboard behaviour. This is the
   concrete check that §2.1's "position and rotation don't conflict" claim
   actually holds in practice, not just in theory.
6. **Sizing check.** Confirm the new fixed-size Symbol and Label read at a
   reasonable, legible size and distance, roughly comparable to what was
   already confirmed working in the last on-device pass (§0.3 of the Stage
   1.2 document). Adjust the values from §4 as needed - this is expected to
   take a few iterations, not a one-shot guess.

## 7) Automated tests

Per guidelines §6.2, this does not meet the bar for an EditMode unit test -
there is no pure/deterministic logic to isolate.

Add **one PlayMode test**, alongside the project's existing three in
`MarkerOverlapResolverTests.cs` (or a new sibling file in the same assembly,
`Assets/Framework/Tests/Runtime/`):

- `MarkerBillboard_CameraMoved_MarkerRotationMatchesCamera` - instantiate a
  camera and a `POI_Marker`-equivalent object with `MarkerBillboard`
  attached at an arbitrary starting rotation, move/rotate the camera to a
  new pose, run one frame (`yield return null` so `LateUpdate` executes),
  then assert the marker's world rotation equals the camera's world rotation
  (composed with the 180-degree offset, if §6 step 2 determined one is
  needed) within a small tolerance - do not assert exact float equality on
  quaternions.

Back the null-camera path with `Debug.Assert(_camera != null, ...)` in
`Awake()`, per guidelines §4.
