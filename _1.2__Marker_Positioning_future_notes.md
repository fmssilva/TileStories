## Section A - Open tasks and deferred work

### A.1 User-facing guide: explaining x_norm/y_norm

Still needed: a short, non-technical explanation for whoever is authoring a
wall's `config.json` by hand (remotely, from a reference photo, per Workflow A
step 3 in the plan's §5) of what `x_norm`/`y_norm` actually mean and how to
estimate them without opening Unity. The rough idea, not yet written up
properly:

> Look at a photo of the wall like a picture with an invisible grid over it.
> `x_norm` is how far across the picture the point is, left to right, as a
> fraction from 0 (far left edge) to 1 (far right edge). `y_norm` is the same
> idea top to bottom, 0 at the top, 1 at the bottom. A point roughly in the
> center of the photo is `x_norm: 0.5, y_norm: 0.5`.

This needs an actual short guide (a paragraph or two, maybe one annotated
example photo with a grid overlay) somewhere a non-Unity content author would
actually find it - candidate location: alongside the config.json schema
documentation once that exists (Stage 4/5 territory), or a short standalone
`AUTHORING_GUIDE.md` if content authoring starts happening before Stage 4/5's
tooling exists. Not written yet - just the raw explanation above, captured so
it isn't lost.

### A.2 Overlap-threshold follow-ups (found during Stage 1.2, not fixed)

- The 40px screen-space overlap threshold in `MarkerOverlapResolver.cs` has
  only been checked against the Editor/synthetic-camera setup used in
  `MarkerOverlapResolverTests.cs` and one real on-device pass on one tablet.
  It hasn't been checked for sensitivity to different device resolutions or
  camera FOV. Worth a pass once a second device model is available to test
  on, or before Panorama/Chafariz (much higher POI density) are integrated.
- Label clipping was checked visually only, once, on-device (see
  `_1_2_POI_markers_plan.md` §0.3). The current threshold only considers
  distance between marker anchor points, not label width - two markers could
  be technically >40px apart at their anchors while their text labels still
  visually overlap, if a future wall's POI names are meaningfully longer than
  LivingRoom's test set. Not a known problem yet, just an untested edge.

## Section B - Developer/framework guide material (for Stage 4/5 packaging)

Raw notes captured during Stage 1.2's implementation that should inform
whatever developer-facing guide eventually ships with the packaged framework
template. Not organized as a polished guide yet - just preserved here so
none of it has to be rediscovered from scratch later.

### B.1 The authoring-rig pattern, and why it looks the way it does

A future developer using this framework for a new wall will hit the same
question that came up mid-Stage-1.2: "why don't the POI markers I place in
the Editor just stay in the Hierarchy permanently, like normal Unity
content?" Worth explaining explicitly in the developer guide, not just
leaving as tribal knowledge:

- The runtime-spawned POIs (`WallSession.SpawnPOIs()`, reading
  `config.json`) and the Editor authoring-rig markers (`POIAuthoringRig`,
  created by `Populate Rig from JSON`) are deliberately two different
  mechanisms, not the same objects reused. This was tried the other way once
  (leftover rig children treated as reusable by `SpawnPOIs()`) and produced a
  real duplication/offset bug - worth including as a concrete cautionary
  example in the guide, not just an abstract rule.
- `config.json` is the single source of truth. The rig is a disposable
  measuring tool: populate it, drag markers to the right spot while looking
  at the reference mesh, capture their positions back to JSON, then clear it.
  This is standard practice for any procedurally-spawned Unity content (enemy
  spawners, waypoint systems) - not a deviation from "normal Unity," even
  though it can feel like one the first time you notice the Hierarchy is
  "empty again" after a session.
- The `Clear Rig` button, the live sync-status indicator, and the build-time
  hard block all exist specifically to make this workflow hard to get wrong
  by accident - a new developer shouldn't need to remember "always delete the
  rig children before building," the build itself refuses to proceed if they
  forget.

### B.2 Mandatory steps that are easy to silently skip

Worth calling out explicitly in a guide, each because skipping it fails
silently rather than with an obvious error:

- **Reset Transform immediately after dragging a `.glb` mesh into the scene.**
  Skipping this silently offsets every `captured_position` placed against the
  mesh by whatever arbitrary transform Unity assigned on import - no error,
  just wrong positions discovered much later.
- **Tag the mesh reference `EditorOnly`.** Otherwise it ships inside the
  build - it's a large reference asset with no purpose to a visitor.
- **Point-cloud vs. mesh alignment spot-check.** Worth a quick visual
  cross-check (enable Immersal's point-cloud Render Mode briefly) that the
  downloaded mesh and the live map coincide, before trusting either for
  precise placement - not confirmed as a known bug for this SDK's export
  path specifically, but cheap enough to check regardless (see the original
  plan's §4.7 for the full reasoning and its sourcing caveat).
- **Any new Unity test assembly needs its `.asmdef` checked for
  `overrideReferences`/`precompiledReferences` conflicts with the built-in
  test framework.** This caused a real IL2CPP linker error while adding the
  project's first PlayMode test assembly (`TileStories.Tests.Runtime`) -
  fixed by removing `overrideReferences: true` and the explicit
  `precompiledReferences`, adding a plain `nunit` reference instead. Worth a
  one-line checklist item for "adding a new test assembly" in the guide, so
  the next person doesn't have to rediscover this by hitting the same
  linker error.
- **Label truncation length must be checked against real label text, not
  assumed safe by analogy.** A 15-character truncation limit worked fine for
  LivingRoom's original 3 POI names, then silently made 4 different overlap-
  test POIs all display as the identical `"The Painting (ov..."` once they
  shared a long common prefix. Any naming convention that puts the
  distinguishing part of a label at the end, after a shared prefix, needs the
  truncation length re-checked against that specific pattern - it's not a
  property of "how long is 15 characters" in the abstract, it's a property of
  where the distinguishing text sits within the string.

### B.3 The dev-wall test-content exception

LivingRoom is being used as a genuine development/test wall, not content
shown to real visitors - which is why it was fine, for Stage 1.2's overlap
testing, to add real, permanent, clearly-tagged (`category: "test"`) POI
entries directly into its actual `config.json` rather than keeping test data
strictly synthetic/in-memory. Worth stating explicitly in the developer guide
as a named, deliberate exception with a condition attached: this is safe
*specifically because* the wall carrying the test data is confirmed
development-only. A future developer reusing this framework for a wall that
*is* shown to visitors should not assume the same shortcut applies there -
production content and test fixtures should stay separated for any wall
where that separation actually matters to a real audience.

### B.4 Independent verification paths are a feature, not duplication

For anything spatial/visual (the overlap resolver being the concrete example
so far), it's worth keeping both an automated test (synthetic, in-memory,
deterministic, CI-safe) *and* a real on-device check using actual captured
content - as two genuinely separate paths, not one replacing the other. The
automated test proves the math; the on-device check proves the math survives
contact with a real camera, a real device screen, real hand-placed
coordinates, and real label rendering. If the two ever disagree, that
disagreement is itself useful information (points at either a threshold
that doesn't generalize past the test's assumptions, or content that isn't
as clustered as intended) - worth a line in the guide encouraging developers
to keep both checks for future spatial features, rather than treating the
automated test as sufficient on its own once it's green.
